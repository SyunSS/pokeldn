# ESP32 无线模块

通过 USB 串口连接的 ESP32 开发板充当无线模块。它运行 `firmware/esp32/` 并传输 LDN 的厂商动作帧和以太网帧；广播信息加密、LDN 身份验证、IP 和 Pia 仍由主机端处理。`pokeldn.ldn.esp32_wlan` 为 LDN 库提供一个由开发板实现的工厂，因此 `ldn.scan`, `ldn.connect` 和 `ldn.create_network` 无需修改即可运行，主机端也无需 Wi-Fi 驱动。

## 支持的开发板

| 芯片 | 主机端连接方式 | 合并镜像 |
| --- | --- | --- |
| 经典 ESP32（ESP32-D0WD、WROOM-32E） | 通过 USB 串口桥接芯片连接 UART0 | `pokeldn-radio.bin` |
| ESP32-S3 | 原生 USB Serial/JTAG | `pokeldn-radio-s3.bin` |
| ESP32-C3 | 原生 USB Serial/JTAG | `pokeldn-radio-c3.bin` |
| ESP32-C6 | 原生 USB Serial/JTAG | `pokeldn-radio-c6.bin` |
| 经典 ESP32、ESP32-C6 | 蓝牙 LE（iOS 应用），以及上述 USB 方式 | `pokeldn-radio-ble.bin`, `pokeldn-radio-ble-c6.bin` |

所有目标均使用 2.4 GHz。不支持 ESP32-S2。Seeed Studio XIAO ESP32C3 和 XIAO ESP32S3 没有板载天线，需要连接随附的外置天线；N8R2、N16R8 等较大的 S3 开发板带有板载天线。如果 S3、C3 或 C6 开发板具有独立的 UART 和原生 USB 插座，无线通信必须使用原生插座。USB Serial/JTAG 使用 GPIO19（D-）和 GPIO20（D+），详见 [Espressif USB 指南](https://docs.espressif.com/projects/esp-idf/en/v5.2/esp32s3/api-guides/usb-serial-jtag-console.html)。C3 的原生 USB 使用 GPIO18（D-）和 GPIO19（D+），详见 [Espressif C3 USB 指南](https://docs.espressif.com/projects/esp-idf/en/latest/esp32c3/api-guides/usb-serial-jtag-console.html)。USB 标识符 `303a:1001` 由多种芯片共用；刷写时会使用 esptool 检测芯片。通过 S3 的 UART 插座（DevKitC 上为 WCH CH343 桥接芯片）刷写可以成功，但刷写后固件不会在该插座上回应。当通过 USB 串口桥接芯片无法得到固件回应时，桌面应用会从 ROM 引导加载器读取芯片类型（esptool `detect_chip`，然后硬复位），并将通过该方式找到的 S3、C3 或 C6 标明为插错插座。

Seeed Studio XIAO ESP32C3 的 USB-C 插座用于原生 USB Serial/JTAG。使用无线功能前，请连接随附的外置天线。BOOT 为 GPIO9，板载 LED 是充电指示灯（[Seeed 开发板指南](https://wiki.seeedstudio.com/XIAO_ESP32C3_Getting_Started/)）。C3 构建运行于 160 MHz。线路和按键任务运行于核心 0；双核目标将这些任务放在核心 1。

在 macOS 上通过原生 USB 测试的 XIAO ESP32C3 修订版 0.4，能以 1429 条消息完成 2,000,000 字节的 BENCH 传输，无消息缺失或校验和错误；主机端波特率设为 115200 时为 880.1 KB/s，设为 1500000 时为 878.3 KB/s：主机端波特率设置不会改变 USB 速度。启动后空闲可用堆为 152656 字节。

Seeed Studio XIAO ESP32C6（ESP32-C6FH4，4 MB 内嵌闪存）通过其 USB-C 插座使用原生 USB Serial/JTAG。GPIO3 为低时，射频开关获得供电；GPIO14 选择陶瓷天线（低）或 U.FL 插座（高）（[Seeed 开发板指南](https://wiki.seeedstudio.com/xiao_esp32c6_getting_started/)）；C6 固件会在 Wi-Fi 启动前将两者均置低，因此开发板通过陶瓷天线发射。所有 C6 开发板使用相同镜像，无需外接天线。在 ESP32-C6-DevKitC-1 上，GPIO3 和 GPIO15 仅连接到排针，GPIO14 未引出，可寻址 RGB LED 位于 GPIO8（[Espressif 用户指南](https://docs.espressif.com/projects/esp-dev-kits/en/latest/esp32c6/esp32-c6-devkitc-1/user_guide.html)），因此 XIAO 的引脚设置不会影响该开发板的无线模块和其他器件。BOOT 为 GPIO9；GPIO15 上的黄色用户 LED（低电平点亮）用于显示 LED 灯效；红色 LED 为充电指示灯。该构建以 160 MHz 运行，与 C3 一样将线路和按键任务放在核心 0。

C6 是 Wi-Fi 6 芯片。其站点模式被限制为 11b/g/n，使关联请求不包含 HE 元素，与其他目标一致。其接收头（`esp_wifi_he_types.h`）没有 `sig_mode`, `mcs` 或 `cwb`；固件会推导 RX_SNIFF 和 RX_CENSUS 的 `sig_mode`，其依据为 `cur_bb_format`；HT MCS 字节则取自 HT-SIG，该 HT-SIG 位于 `he_siga1`。其速率字节是 OFDM 帧的 L-SIG 速率码，而不是 `wifi_phy_rate_t`。ESP-IDF v6.1 的 C6 Wi-Fi 库导出了固件使用的全部私有符号，且 `lmacConfMib` 偏移量与 C3 相同。

在 macOS 上通过原生 USB 测试的 XIAO ESP32C6 修订版 0.2，能以 1429 条消息完成 2,000,000 字节的 BENCH 传输，无消息缺失或校验和错误，速度为 824.6 KB/s，并成功接收 5000 条上行命令中的全部 5000 条，无丢失。启动后空闲可用堆为 255196 字节。在使用陶瓷天线的《火红》加入端会话中，主机端发送的 5155 条 ETH_TX 命令全部被开发板计数记录，无错误线路帧，也无 USB 重新同步。

Seeed Studio XIAO ESP32S3（ESP32-S3 修订版 0.2、8 MB 闪存、8 MB PSRAM）通过 USB-C 插座使用原生 USB Serial/JTAG，且需要连接随附的外置天线。BOOT 为 GPIO0；GPIO21 上的黄色用户 LED（低电平点亮）用于显示 LED 灯效。在 macOS 上通过原生 USB，它能以 1429 条消息完成 2,000,000 字节的 BENCH 传输，无消息缺失或校验和错误，速度为 883 KB/s，并成功接收全部 5000 条上行命令，无丢失。启动后空闲可用堆为 212416 字节。

除非另有注明，下文经典 ESP32 的测试均使用 ELEGOO ESP32-D0WD-V3 开发板。各开发板已完成的交换见 [各开发板的交换测试](#trades-by-board).

### 复位后的 USB 连接（C6、S3）

打开串口会通过 USB Serial/JTAG 复位 C6 或 S3（复位原因 11，即核心复位）。当使用 `CONFIG_ESP_SYSTEM_BBPLL_RECALIB=y`（两种芯片的 ESP-IDF 默认设置）时，应用启动过程会运行 `recalib_bbpll()` (`esp_system/port/soc/esp32c6/clk.c`，S3 上也相同）：在 CPU 复位以外的任何复位中，它会调用 `rtc_clk_cpu_freq_set_xtal()`，不检查 USB 是否正在使用 BBPLL 就将其停止，然后再重启。主机端与 USB Serial/JTAG 通信时，后者从该 PLL 获取 48 MHz 时钟。在 XIAO ESP32C6 上，此后连接有时会出现数据损坏，并持续到拔下开发板为止：固件仍在运行，该次启动后 SOF 帧编号始终不变，`USB_SERIAL_JTAG_INT_RAW` 保留 PID、CRC5 和位填充错误（`0000b5b2`，正常值则为 `0000b50a`），回复卡在 IN FIFO 中；时钟使能、引脚及 PCR 寄存器与正常开发板一致，通过 EP0 执行 GET_CONFIGURATION 失败，esptool 的 USB 复位也无回应。

| C6 镜像 | 端口打开次数（复位并启动） | 直到拔出前连接都不可用 |
| --- | --- | --- |
| 开启重新校准 | 113 | 1 次，发生于第 113 次打开 |
| 关闭重新校准 | 900 | 0 |

C6 和 S3 构建设置了 `CONFIG_ESP_SYSTEM_BBPLL_RECALIB=n`；其 Kconfig 帮助允许在使用 ESP-IDF v5.2 或更新版本构建的引导加载器时这样设置，而每个合并镜像均自带 v6.1 引导加载器。关闭重新校准的 XIAO ESP32S3 在 300 次打开中全部回应。C3 没有此选项，也未出现故障。关闭重新校准后，C6 的 600 次打开中有 4 次首次无回应，但 macOS 重新枚举设备（“设备未配置”）后的下一次打开连接正常。

C6 和 S3 构建包含 USB 监视功能（`usbwatch.c`）：每 5 毫秒采样一次 SOF 帧编号；一旦曾经计数到帧，或主机端发送过一个字节，若随后停滞 2 秒便重启芯片，并在下一次 HELLO 中以 LOG 行报告停滞前后的 USB 和时钟寄存器。这可检测 USB 帧时钟停止；驱动停滞时 SOF 仍可能递增，而重启芯片也不保证能恢复卡死的 USB 外设。重启会结束当前传输。如果构建时设置 `POKELDN_USB_BEACON=1`，并将其放入 `idf.py` 的环境中，两种镜像还会每秒一次，以厂商动作帧（类别 127，OUI 为 `02:55:53`）向组地址 `03:55:53:42:57:00` 发送这些寄存器、已观测的 SOF 变化次数以及已读取的主机端字节数；USB 连接失效期间，嗅探开发板可使用 `esp32_sniff.py --mac 03:55:53:42:57:00` 保留这些帧。4 字节厂商头之后的帧正文由小端序 u32 组成：运行时间（毫秒）、SOF 变化次数、主机端字节数、`wire_dropped`、停滞次数，然后是 `usbwatch.c` 中列出的十六个目标专属寄存器。S3 会快照其 USB 端点、SYSTEM 时钟与复位、GPIO19/20；C6 会快照其 USB 端点、PCR 时钟与复位、GPIO12/13。S3 支持自固件 1.6.2 起提供。

## 角色

| 角色 | 开发板的工作 |
| --- | --- |
| 空闲 | 在单个信道上以混杂模式接收；所有带 Nintendo LDN 前缀 `7f 00 22 aa` 的动作帧都发往主机端 |
| 站点 | 使用主机端推导的 CCMP 密钥，按 BSSID 加入主机的网络 |
| 接入点 | 在主机端的 BSSID 上创建隐藏 SSID 的 WPA2 网络，使用相同方式设置密钥 |

主机的网络没有四次握手：两端都根据广播信息中的服务器随机数推导 CCMP 密钥。固件替换 ESP-IDF 私有 `struct wpa_funcs` 表中的四个条目（`esp_wifi_driver.h`）。其布局采用 v6.1 二进制库的 ABI；固件拒绝针对其他发行版本构建。

## 接入点的帧

softAP 的信标、探测响应和关联响应在闭源的 `libnet80211.a` 中构建。以下信息从 v6.1 二进制库中读取（`ieee80211_output.o` 偏移量），并与 `vendor/LDN` 的接入点向 Switch 发送的内容对比：

| 字段 | Switch 形式 | ESP32 softAP | 是否可设置 |
| --- | --- | --- | --- |
| 隐藏 SSID 元素 | 32 个零字节 | 长度 0（`ieee80211_beacon_construct` 0xc4） | 否 |
| 支持速率 | `82 84 8B 96 0C 12 18 24` | `8B 96 82 84 0C 18 30 60` | 否；相同的十二种速率及基本速率位，9 和 18 位于扩展速率中 |
| 扩展速率 | `30 48 60 6C` | `6C 12 24 48` | 否 |
| 能力字段，信标 | `0x0511` | `0x0431`（短前导码常量，`ieee80211_getcapinfo` 0x7b） | 否 |
| HT 元素 | 无 | 11b/g/n 中存在 | 已移除：固件设置为 11b/g |
| RSN 能力 | `0x000c` | hostapd 自带值 | 已设置：`wpa_ap_get_wpa_ie` 返回 Switch 的元素 |
| WMM | 无 | 11g 中存在 | 只有纯 11b 模式会移除它 |

隐藏 softAP 仅回应定向探测，在探测响应中携带真实 SSID。不含配置 SSID 的关联请求会被丢弃（0x9c6）。`esp_wifi_80211_tx` 接受信标，但拒绝关联响应（`ieee80211_raw_frame_sanity_check` 0xf9）；二进制库自身的信标无法停止。

## 串口协议

帧由 `COBS(type | payload | crc32-le(type | payload))` 后接 `0x00` 组成；CRC 使用 CRC-32/ISO-HDLC（`zlib.crc32`）。经典 ESP32 以 115200 波特率启动；`BAUD` 会切换两端的速率，开发板保持该速率直到复位。在 S3 上，`BAUD` 会得到确认，但不会改变 USB 传输速率。任何位于 `0x00` 之前的内容，包括 ROM 启动文本，都会因校验和失败而被丢弃。

| 类型 | 方向 | 载荷 |
| --- | --- | --- |
| `0x01` HELLO | 主机端 | 无；先以 CREDIT 0 回应，再发送 INFO。主机端会预先发送一个 `0x00`，用于终止以错误速率发送的 HELLO 在开发板解码器中留下的未完整帧；固件会跳过空帧 |
| `0x02` BAUD | 主机端 | u32 波特率；先以旧速率发送 RESULT，然后切换，切换前最多等待 3 秒让 UART 发送完毕（115200 时，环形缓冲区可容纳超过一秒的 RX_MGMT）。1500000 下的首次 HELLO 有时会丢失（实测约每四次打开出现一次）；`open_serial` 会重试 |
| `0x03` CHANNEL | 主机端 | u8 信道；仅限空闲状态 |
| `0x04` STA_JOIN | 主机端 | u8 信道、6 字节 BSSID、32 字节 SSID（LDN SSID 的十六进制文本）、16 字节密钥、6 字节站点 MAC（全零表示随机）；可选：u8 固定数据速率（使用 AP_START 位 3..5 的表）、u8 最大发射功率，单位为 0.25 dBm（`esp_wifi_set_max_tx_power`，8 到 84，驱动上限为 61）、u8 标志：1 表示每帧前发送 RTS，2 表示重试前不发送 RTS（`esp_wifi_internal_set_rts`) |
| `0x05` STOP | 主机端 | 无；返回空闲状态并清除密钥 |
| `0x06` AP_START | 主机端 | u8 信道、6 字节 BSSID、32 字节 SSID、16 字节密钥、u8 最大站点数、u8 标志：1 表示原始关联与四次握手，2 表示站点不使用 QoS，4 表示不复制每个站点数据帧的前 40 字节，位 3..5 指定固定数据速率，`0x40` 表示每 1000 TU 发送一次信标，`0x80` 表示关闭混杂接收；可选第二标志字节：1 表示关闭驱动的底噪检查，2 表示其间隔为 250，4 表示在每份 40 字节副本的头部携带接收时间，8 表示重试上限为 7 和 4，`0x10` 表示除自身站点的正常数据帧外，对每个帧发送 RX_CENSUS；随后可选最大发射功率，单位为 0.25 dBm |
| `0x07` AP_KICK | 主机端 | 6 字节 MAC、u16 原因；取消认证 |
| `0x08` ETH_TX | 主机端 | 以太网帧，由驱动使用站点密钥或组密钥加密。驱动队列满时（`ESP_ERR_NO_MEM`）会每 1 毫秒重试，最多 100 毫秒；发往已离开站点的帧会立即失败并返回 `0x3015` (`ESP_ERR_WIFI_NOT_ASSOC`）。站点将以太网源地址用作其 802.11 发送地址：若源地址不是 LINK 中的 MAC，就始终得不到确认（49 次中全部如此） |
| `0x09` RAW_TX | 主机端 | 不含 FCS 的 802.11 帧（`esp_wifi_80211_tx`）；用于广播信息 |
| `0x0A` SNIFF | 主机端 | u8 信道、6 字节 MAC；发往或来自该 MAC 的每个管理帧和数据帧，以及该信道上的每个动作帧（LDN 广播信息提供主机切换到的网络所需密钥信息），都会完整作为 RX_SNIFF 发送；MAC ff:ff:ff:ff:ff:ff 则将信道上的每个帧作为 RX_CENSUS 发送 |
| `0x0B` STATUS | 主机端 | 无；以 STATUS 回应 |
| `0x0C` BENCH | 主机端 | u32 字节数、u16 消息大小（8 到 1600）；先发送 RESULT，再以 UART 所能承载的最高速率发送 BENCH 消息 |
| `0x0D` LED | 主机端 | u8 灯效、u8 峰值亮度、u16 周期毫秒数（0 表示该灯效的默认值）、u16 持续毫秒数（0 表示持续到下一条 LED 命令）；以 RESULT 回应。较旧固件返回 `0x106` |
| `0x0E` DISPLAY | 主机端 | 屏幕命令（[屏幕](#the-screen)）；RESULT 为 `0x105` (`ESP_ERR_NOT_FOUND`）表示没有屏幕，`0x106` 则是较旧固件的返回值 |
| `0x0F` ALIVE | 主机端 | 无，不回复；启用 [主机端看门狗](#the-host-watchdog)。1.4.0 之前的固件会返回 `0x106`，因此主机端仅向 1.4.0 及更新版本发送此命令 |
| `0x81` INFO | 开发板 | u8 协议版本（1）、6 字节站点 MAC、6 字节 AP MAC、u8 芯片修订版、文本 |
| `0x82` RESULT | 开发板 | u8 命令、i32 `esp_err_t` |
| `0x83` LOG | 开发板 | 文本 |
| `0x84` RX_MGMT | 开发板 | u8 信道、i8 RSSI、不含 FCS 的帧：LDN 动作帧；作为主机端时，还包括发往开发板 BSSID 的管理帧、发往该 BSSID 的数据帧前 40 字节，以及站点发送的完整无 DS 广播帧 |
| `0x85` RX_ETH | 开发板 | 驱动已解密的以太网帧 |
| `0x86` LINK | 开发板 | u8 连接状态、u16 原因、6 字节 MAC；原因 `0xFFFF` 表示 15 秒内未完成关联，`0xFFFE` 表示密钥被拒绝 |
| `0x87` STA_JOINED | 开发板 | 6 字节 MAC、u8 AID、i8 密钥安装结果、u8 端口打开状态 |
| `0x88` STA_LEFT | 开发板 | 6 字节 MAC、u16 原因 |
| `0x89` STATUS | 开发板 | 文本计数器（见下文）；作为主机端时每 2 秒主动发送一次，写入跟踪记录的主机端每 5 秒轮询一次 |
| `0x8A` BENCH | 开发板 | u32 序号及载荷字节；最后一条携带序号 `0xFFFFFFFF` 和开发板耗时的 u32 微秒数 |
| `0x8B` CREDIT | 开发板 | u32，自上次 HELLO 以来读取并处理的主机端字节数，从其分隔符后的字节开始计数；在 HELLO 时、每累计 1024 字节时、线路转为空闲时，以及空闲期间每 100 毫秒发送，优先于所有排队消息 |
| `0x8C` RX_SNIFF | 开发板 | u8 信道、i8 RSSI、u8 `sig_mode`（0 为传统模式，1 为 HT）、u8 传统速率码（`wifi_phy_rate_t`）、u8 HT MCS（位 7 表示 40 MHz）、不含 FCS 的帧；还包括该信道上的每个 10 字节 ACK |
| `0x8D` TX_DONE | 开发板 | 驱动针对站点或接入点单帧的发送完成结果：u32 开发板时间（微秒）、u32 距其所完成 ETH_TX 的微秒数（无匹配时全部位为 1）、u8 是否由对端无线模块确认、u8 接口、u16 长度、帧的前 24 字节（802.11 头） |
| `0x8E` BUTTON | 开发板 | 一次 BOOT 按压，经 30 毫秒消抖：u32 开发板时间（微秒）、u16 启动以来的按压次数；主机端会输出 `BOOT button, mark N`，跟踪记录会保留该事件 |
| `0x8F` RX_CENSUS | 开发板 | 接收到的每个帧，包括 FCS 错误帧及控制帧：u32 接收时间（微秒）、i8 RSSI、i8 底噪、u8 `rx_state`（0 表示正常）、u8 数据包类型（0 管理、1 控制、2 数据、3 其他）、u8 `sig_mode`、u8 速率码、u8 MCS（位 7 表示 40 MHz）、u16 `sig_len`（含 FCS）、帧的前 16 字节 |

`rx_state` 值 98 标记双流 HT（MCS 8 到 15），单流 ESP32 永远无法解码此类帧（一次普查中 79 帧全部如此）；65 标记其他任意调制方式下的损坏帧（5605 帧中的 1397 帧）。

| STATUS 计数器 | 计数内容 |
| --- | --- |
| `tx_acked`, `tx_unacked` | 驱动的发送完成结果 |
| `tx_eth`, `tx_eth_failed`, `tx_eth_retried` | ETH_TX 已发送数、失败数，以及发现驱动队列已满的调用次数 |
| `tx_queued_max_us`, `_total_us`, `_n`, `_pending` | 在匹配的 TX_DONE 中统计 ETH_TX 到发送完成的耗时 |
| `wire_dropped`, `wire_rx_bad` | 丢弃的开发板到主机端消息数；COBS 或 CRC 校验失败的主机端命令数 |
| `uart_fifo_ovf`, `uart_buffer_full`, `uart_overflow` | 128 字节硬件 FIFO 与 16 KB 环形缓冲区溢出次数，以及两者之和 |
| `uart_frame_err`, `uart_events_full` | 帧格式错误、奇偶校验错误和 break 事件；UART 事件队列已满时的节拍数（计数器可能漏计） |
| `read_max_us`, `write_max_us`, `handler_max_us`, `handler_max_type` | 最长的主机连接读取轮次（含 20 毫秒超时）、写入等待，以及命令耗时和类型 |
| `heap_min`, `queue_max`, `refused_heap`, `refused_queue` | 最低可用堆、最深的发送队列，以及因达到堆下限或队列满而拒绝的消息数 |
| `tx_eth_max_us`, `tx_eth_total_us`, `tx_eth_slow` | ETH_TX 在 `esp_wifi_internal_tx` 中的耗时，包含重试：最长值、总和、超过 5 毫秒的次数 |

EtherType 为 `0x88B7` 的帧用于 LDN 身份验证；`esp32_wlan` 会将其转换为 LDN 库的 `CustomFrameEvent`。其他所有以太网帧都会发往一个 L2 端口，由以下选项决定：`POKELDN_L2=tap|userspace`:

| 端口 | 适用位置 | 启动器的套接字 |
| --- | --- | --- |
| `userspace_ip` 协议栈 | 默认值，适用于所有平台 | `userspace_ip.udp_socket` 和 `packet_socket` |
| 以接口命名的内核 TAP | Linux，`POKELDN_L2=tap` 专用 | 内核套接字，`SO_BINDTODEVICE` 和 `AF_PACKET` 保持不变 |
| `MemoryPort` | 测试 | 无 |

创建 TAP 需要 `CAP_NET_ADMIN`。桌面应用以普通用户身份运行，因此在 Linux 上将 TAP 设为默认值，会在开发板加入任何网络之前就失败。

### 主机端看门狗

自固件 1.4.0 起，主机端每秒发送一次 ALIVE（`esp32.ALIVE_EVERY`），是否发送由 INFO 的 `version=` 文本决定。HELLO 之后的首个 ALIVE 会启用监视；HELLO 会禁用监视，因此从不发送 ALIVE 的主机端永远不会被监视。启用后，非空闲状态的开发板如果 5 秒未读到主机端命令（`HOST_SILENT_US`），便执行 STOP 的清理流程：接入点停止发送信标，站点连接断开；站点角色则主动断开连接。随后它会丢弃发往主机端的所有消息且不计数，直到主机端再次发送命令；否则，USB 开发板失去主机端后，每条排队或侦听到的消息都会造成一次 500 毫秒写入以及一个 `wire_dropped`，并让 LED 警示变成持续的 `flash3`.

在 XIAO ESP32C6 上，零售版《火红》停留于 `frlg_trade_host.py` 的交换房间时，用 SIGKILL 终止主机端，主机会显示 2318-0006，之后 JOIN 搜索不再列出该主机端，LED 恢复空闲灯效。不丢弃消息时，LED 则一直保持 `flash3`.

## 串口带宽上限

经典 ESP32 UART 在 921600 波特率、8N1 下，从开发板到主机端的线路带宽为 92.16 KB/s。一条消息的开销为载荷加一个类型字节、四字节 CRC、COBS 开销（每 254 字节增加一个字节，另加分隔符），RX_MGMT 还要增加信道和 RSSI 两字节。Pia 载荷是 AES-GCM 密文，无法压缩。

| 流量 | 线路开销 |
| --- | --- |
| 主机端模式下站点的数据帧 | 以 RX_ETH 发送该帧；除非设置 AP 标志 4，否则还需为 40 字节的 RX_MGMT 副本额外传输 48 字节（`POKELDN_ESP32_AP_FLAGS=4`) |
| 加入模式下站点的数据帧 | 仅以 RX_ETH 发送该帧；站点模式只会额外传递管理帧 |
| 附近的 LDN 广播信息 | 完整动作帧，每个网络约每秒十个 |

发送队列容纳 384 条消息，可用堆低于 64 KB 时会拒绝消息；128 项队列在《朱》主机端的启动突发流量中会溢出（测得丢弃 337 条消息）。主机以线路极限速率发送时，会将可用堆维持在该下限（`heap_min` 63976, `queue_max` 95, `refused_heap` 219）：堆不足会在队列填满之前就拒绝 RX_ETH。

### 波特率

`POKELDN_ESP32_BAUD` 设置 `open_serial` 将切换到的速率，默认 921600。ESP32 UART 最高可达 5 Mbaud；实际限制由 USB 桥接芯片决定。`tools/ldn/esp32_bench.py --port PORT --bauds 921600,1500000,2000000,3000000` 会以每种速率流式发送 BENCH。ELEGOO 开发板的桥接芯片（“CP2102 USB to UART Bridge Controller”，idProduct 60000，bcdDevice 0x100）在 macOS 上的结果：

| 921600 | 91.7 KB/s | 1429 条，每条 1400 字节 | 0 | 0 |
| 1000000 | 99.4 KB/s | 1429 条，每条 1400 字节 | 0 | 0 |
| 1500000 | 149.1 KB/s | 4286 条，每条 1400 字节 | 0 | 0 |

### 主机端到开发板的命令丢失与 CREDIT

主机大量发送数据时，主机端命令可能在到达处理函数前丢失：某个《朱》席位在 7.5 秒内向开发板交付 660 条 ETH_TX，但仅 92 条被计数（`tx_eth + tx_eth_failed`），其余命令没有消耗 CCMP 包编号，且 `tx_eth_retried` 为 0。以下逐项列出未采取对应措施时测得的原因，以及固件的处理方式：

| 原因 | 无对应措施时的实测结果 | 固件处理方式 |
| --- | --- | --- |
| UART 中断与 Wi-Fi 任务同在核心 0 | 上述席位的情况 | 由核心 1 上的读取任务安装驱动 |
| 读取任务中的 ETH_TX 等待已满的 Wi-Fi 队列；16 KB 环形缓冲区填满，FIFO 溢出 | `esp32_bench.py --uplink 5000`（向空网络发送 5000 条广播 ETH_TX）在 1500000 时丢失 369 到 429 条，`uart_fifo_ovf` 305, `wire_rx_bad` 为 169；921600 时无丢失 | CREDIT：两种速率下 5000 条均无丢失 |
| FIFO 在 120 字节时排空（`UART_FULL_THRESH_DEFAULT`），1500000 下距填满仅 53 微秒 | 启用 CREDIT 的《朱》席位：1901 条中约丢失 210 条，`uart_fifo_ovf` 235 | 阈值改为 32（`uart_set_rx_full_threshold`），余量为 640 微秒：1691 条中丢失 10 条，`uart_fifo_ovf` 0 |
| `uart_read_bytes`（IDF 6.1 的 `uart.c:1738`）对每个环形缓冲区条目都会重新等待完整超时时间，直到获取 `length` | 每 15 毫秒发送一条 21 字节命令，读取却延迟 461 毫秒（`--trickle 5`）；某个《朱》席位的 `read_max_us` 311644 | 先等待一个字节，再获取 `uart_get_buffered_data_len`：20.3 毫秒 |
| `uart_write_bytes` 在 TX 环形缓冲区已满时忙等（`uart.c:1662`）；写入任务（优先级 20）与读取任务（19）共享核心 1 | 《朱》的大量流量使 ETH_TX 阻塞最长 707 毫秒；`esp32_pair_bench.py AP STA --flood 0 --send 20 --bench`: `read_max_us` 为 7982767，74 次发送被拒绝 | 写入任务休眠，直到剩余空间足以容纳整个帧（`uart_get_tx_buffer_free_size`）：30382 微秒，无拒绝（[朱与紫](sv.md#the-retail-acknowledgement-and-a-flood-of-retransmits)) |
| 每 32 字节就向同时承载溢出事件的 64 项队列提交一个 `UART_DATA` 事件（`uart.c:1369`, `1543`），1500000 下 14 毫秒即可填满 | 执行长命令期间发生的溢出可能未被计数 | 一个优先级高于读取任务的任务每个节拍都会清空该队列；`uart_events_full` |

忽略窗口限制时（`--uplink 5000 --no-flow`），每次 `uart_fifo_ovf` 会丢失 136.5 字节，约为一个 FIFO，且 `uart_events_full` 仍为 0：环形缓冲区已满会停止 `UART_DATA` 事件。

CREDIT：开发板发送过一次 CREDIT 后，主机端的写入线程会将已写入但尚未报告处理的字节数保持在 8 KB 以下（`esp32.FLOW_WINDOW`），因此启动器的 trio 循环只负责入队；当排队帧数超过 512 时，ETH_TX 和 RAW_TX 会被丢弃（`Radio.tx_dropped`）。窗口关闭期间若 CREDIT 不再推进，且计数连续 0.3 秒重复不变，便表示线路上发生字节丢失，主机端会重新打开窗口（`Radio.flow_resyncs`）；若开发板完全不发送计数，则视为忙碌，给予 5 秒。切勿仅凭静默就重新同步：忙碌的读取任务可能阻塞 0.7 秒，此时重新同步会让 16 KB 在途数据涌向 16 KB 环形缓冲区。已核销的丢失字节会继续保持核销；当 CREDIT 超出按丢失量推算的范围时，会缩小核销量。CREDIT 会越过发送队列（队列中最多一条），但在《朱》席位 150 KB/s 的 RX_ETH 流量后方仍会延迟约 0.5 秒才到达。不支持 CREDIT 的开发板从不开启该窗口机制，主机端不节流写入。计数为 u32（`wire.c` `s_consumed`）；主机端会根据自身字节计数展开回绕值，因此超过 4 GiB 的数据流仍可维持窗口。开发板每读取 1024 字节就发送一次 CREDIT（`wire.c` `CREDIT_STEP`），因此 CREDIT 可能已经计入某条 1.5 KB ETH_TX 的部分内容，而该条写入尚未返回；主机端会将其与已写入字节加上线路中的当前帧一起核算。如果不接受这种计数，帧尾将不足以跨过下一个计数步长，窗口会关闭，直到约 20 毫秒后收到空闲 CREDIT：在 USB 连接的 ESP32-S3 上（固件 1.6.2，Windows），连续发送 3000 条 1514 字节 ETH_TX，不接受时耗时 15.9 秒，计入时为 8.5 秒（0.29 对 0.54 MB/s），向 Switch 的 TCP 传输则从 0.31 提升到 0.52 MB/s。开发板会记录超过 50 毫秒的命令（`slow command`）以及超过 100 毫秒的读取轮次（`reader held`).

加入空闲计数并让 CREDIT 优先于队列后，开发板记录到了主机端交付的每条 ETH_TX：228 个开发板会话中，520315 条全部被记录（经典 ESP32 固件截至 1.2.0，以及 C3、C6 的 1.0.0）；所有溢出和线路计数器均为 0，每次重复的空闲计数均等于已写入字节数。其中六个会话中，主机端每秒写入超过 500 条 ETH_TX，而开发板到主机端的线路速率为 148 到 152 KB/s。

引入空闲计数前的固件会丢失少量主机端命令，但没有记录到溢出：921600 且无 CREDIT 时，2333 条中丢失 6 条；1500000 且 CREDIT 位于队尾时，1691 条中丢失 10 条，两者均为 `wire_rx_bad` 为 1，而 `tx_eth_retried` 为 0。丢失发生在主机端第一次突发发送期间，此时开发板到主机端线路已达上限（921600 下，一秒传输 91.4 KB）。该固件的写入任务优先级高于读取任务，并在 TX 环形缓冲区满时忙等，而只有读取任务会清空 UART 事件队列，因此读取任务无法运行期间发生的溢出未被计数。多个命令丢失仅对应一次 `wire_rx_bad`，符合一段连续字节丢失的情况。尚未测定具体是哪个缓冲区丢弃了字节：这些跟踪记录不包含 CREDIT。

HELLO 会重置两端计数，因此主机端会等到没有在途数据才发送，并在此过程中保持窗口关闭，直到收到开发板的 CREDIT 0。某主机端在会话中途 HELLO 后不节流写入（扫描会发送一次，`EspFactory.create_monitor`），对一个阻塞 0.5 秒的模拟 16 KB 环形缓冲区造成了 76423 字节的超量；`tests/test_esp32.py::test_a_hello_mid_session_does_not_open_the_window` 为此提供固定回归检查。`tools/ldn/esp32_cmd_loss.py TRACE` 会核对跟踪记录：将已写入 ETH_TX 与 `tx_eth + tx_eth_failed` 比较，并将 HELLO 以来已写入字节与最后一次 CREDIT 比较。

### 发送时序

在一个流量平稳的《朱》席位中，ETH_TX 在驱动内平均耗时 0.12 毫秒，最长 1.57 毫秒；发送后 0.35 秒，主机已持有加入端全部 44 条记录。

TX_DONE 能区分开发板和对端的情况。在一个大量发送流量的《朱》席位中，从 ETH_TX 到发送完成的等待中位数为 1.0 毫秒，最长 6.8 毫秒，主机无线模块确认了全部 1267 帧。流量平稳时，TX_DONE 在其开发板时间后 15 毫秒到达主机端；最差的一秒中则为 446 毫秒（最长 590 毫秒）：大量流量会使开发板到主机端线路积压。根据开发板时间并扣除最小到达偏移，可推算消息在线路上的延迟。

双开发板基准测试（`tools/ldn/esp32_pair_bench.py`，200 字节站点帧）交付了所有站点帧：每秒 20 帧时，187 帧全部到达（ETH_TX 到发送完成平均 1.6 毫秒，最长 10.7 毫秒）；接入点每秒发送 100 个 1200 字节广播、占用约 96% 空口时，1227 帧全部到达（平均 26.8 毫秒，最长 218 毫秒）。

测量注意事项：嗅探开发板的线路和其他开发板一样会在突发期间积压，因此其报告的帧可能在空中出现一秒后才到达主机端；应将它设为 1500000，并以对端确认来计量交付时间。其自身线路饱和时，对其他开发板帧的计数会偏低。BENCH 仅填充一次载荷；若每次用随机数生成器填充，会使速度低于线路带宽。开发板作为接入点发送的大量流量会以 1 Mbit/s 广播，超过每秒约 90 帧就会占满空口。

## 阻塞与漏收

### 《火红》的阻塞

开发板作为接入点完成五次《火红》交换，每行对应一次；主机确认了每一帧。等待时间指 ETH_TX 到发送完成；重试占比指嗅探器观察到的数据帧中设置重试位的比例。

| 信道 | 帧数 | 等待中位数 | 等待 p99 | 最长等待 | 超过 100 毫秒的阻塞次数 | 重试占比：AP／主机 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 7489 | 1.24 毫秒 | 116 毫秒 | 261 毫秒 | 5 | 13.3% / 12.8% |
| 6 | 13670 | 0.85 毫秒 | 18 毫秒 | 108 毫秒 | 1 | 10.5% / 7.7% |
| 11 | 7069 | 0.86 毫秒 | 9 毫秒 | 46 毫秒 | 0 | 15.0% / 5.7% |
| 1 | 7332 | 1.03 毫秒 | 25 毫秒 | 88 毫秒 | 0 | 20.6% / 9.4% |
| 1，固定 24 Mbit/s | 6892 | 0.73 毫秒 | 69 毫秒 | 185 毫秒 | 5 | 2.8% / 14.3% |

主机端到开发板额外增加 0.12 到 0.47 毫秒的中位数延迟（套接字到 ETH_TX 写入），以及 3.1 到 3.4 毫秒（ETH_TX 到达开发板）。所有超过 100 毫秒的等待都是队头阻塞：一个尚未被主机确认的帧会阻塞 108 到 261 毫秒，后面的帧随后突发完成（5 毫秒内最多 10 帧），而接入点的动作帧仍持续发送。嗅探器可见队头帧的一到三个副本，速率为 54 或 48 Mbit/s，之间穿插着主机发送的帧，所有帧的电源管理位都清零：主机一直在该信道上保持唤醒。决定阻塞的是信道（见“信道”），而不是重试占比。

| 发送方 | 首次以 54 Mbit/s 发送的比例 | 重试 |
| --- | --- | --- |
| 开发板（接入点） | 91 到 100% | 77 到 92% 使用 54 Mbit/s，其次为 48，极少使用 6 或 36 |
| 主机 | 92 到 99% | 48、36、24、18，最低降至 1 Mbit/s |

### 开发板是漏听更多的一方

嗅探开发板将每个 ACK 保存为 10 字节 RX_SNIFF；ACK 仅标识其接收方，因此 `tools/ldn/esp32_hold_air.py` 会将它与紧接其前的数据副本匹配；一个已被确认却再次发送的副本，说明发送方漏收了 ACK。以下为信道 1 上一次《火红》交换（6744 帧）：

| 发送方 | 首次副本数 | 其后没有 ACK | 已确认但再次发送 |
| --- | --- | --- | --- |
| 开发板 | 6514 | 490 (7.5%) | 56 |
| 主机 | 4517 | 428 (9.5%) | 2 |

该次交换中，开发板漏收的 ACK 远多于主机（56 对 2）。阻塞期间，开发板既听不到主机的数据，也听不到其 ACK：被阻塞帧的各副本约每隔 40 毫秒发出一次，主机发给它的帧中有 42 到 66% 带重试位（整个会话为 11 到 14%），而嗅探器以 -19 到 -21 dBm 听到了双方。

主机的重试对应开发板的漏收。按序号与嗅探器匹配后（`tools/ldn/esp32_rx_copies.py HOST_TRACE SNIFF_TRACE --ap BSSID --sta MAC`），主机发送多次的帧中，1027 帧有 1008 帧在开发板 RX_MGMT 头副本中仅出现一次，且带重试位；如果这种副本之前没有同序号的副本，仅凭开发板跟踪即可判断为漏收。在 -20 dBm、54 和 48 Mbit/s 下，开发板漏收了主机首次副本的 4.5 到 12.1%。漏收首次副本前紧跟另一主机帧的比例为 37 到 52%，成功听到的则为 28 到 32%；RSSI、速率和长度没有差别。

### 双开发板的漏收

`tools/ldn/esp32_pair_bench.py AP STA --flood 0 --burst N --send R` 让站点开发板发送 200 字节帧，并根据接入点的头副本统计漏收首次副本的帧数。在其他空口流量为空闲、站点信号为 -43 到 -48 dBm 时，两块开发板中任意一块作为接入点都会漏收：每秒 20 到 100 帧时为 5.5 到 22.2%，相同的 30 秒运行结果可在 6.1 到 43.7% 之间波动。站点等待确认的最长时间，在信道 1 上为 89 到 100 毫秒，信道 11 上为 8 到 22 毫秒。将接收时间加入头副本后（第二个 AP_START 标志字节的位 2，`rx_ctrl.timestamp`，在 RSSI 后增加 u32 微秒数），按 102.4、51.2、25.6、1024 毫秒，以及 50 和 100 Hz 周期折叠后，漏收分布均平坦。

| 变量 | 首次副本漏收比例 |
| --- | --- |
| 站点速率（STA_JOIN 速率字节，`--sta-rate N`），信道 11 | 54 Mbit/s OFDM：2.3 到 4.0%；6 Mbit/s OFDM：1.9 到 5.4%；1 Mbit/s DSSS：0.04 到 0.2% |
| 站点功率（`--sta-power`，单位 0.25 dBm），54 Mbit/s | 78（默认，19.5 dBm）：1.5 到 3.1%；28：4.5 到 12.9%；12：15.3 到 20.8%；设置为 17 到 61 时，接入点读取的信号均为 -33 到 -35 dBm |

以下更改均无影响：每 1000 TU 发送一次信标（AP `0x40`）；关闭混杂接收（AP `0x80`）；关闭底噪检查（第二字节位 0，清除 `g_pm+21`，使 libpp 的 `pm_noise_check` 提前返回），或将其 `NoiseTimerInterval` (`pp.o` `.data`，u16 默认值 100）设为 250（位 1）；静态接收缓冲区从 16 个增加到 25 个（`CONFIG_ESP_WIFI_STATIC_RX_BUFFER_NUM`）；240 MHz；`CONFIG_ESP_WIFI_EXTRA_IRAM_OPT=y`；接入点功率设为 19.5、10 或 3.5 dBm；Switch 休眠且关闭蓝牙。漏收与调制方式和信道相关，而非信号余量：6 Mbit/s 与 54 Mbit/s 的漏收频率相近，DSSS 几乎从不漏收。两个驱动的 `libphy.a` 和 `hal_mac_rx.o` 逐字节完全相同，寄存器写入、接收中断、缓冲区回收和发送完成代码也相同；v6.1 在逐帧路径上增加了 `wifi_assert`，并向 `wpa_ap_join` 传入一个结构体，而 v5.5.5 传入九个参数。

信道 1 和 11 的忙碌比例为 8.7 到 13%，每秒有 44 到 107 个邻近帧；信道 3 到 9 为 0.3 到 1.7%，所有信道底噪均为 -96 dBm（`tools/ldn/esp32_census.py`）。接入点自身的普查（第二标志字节 `0x10`）发现，漏收前 3 毫秒内存在邻近帧的比例为 13.1%，成功接收副本前为 11.0%；漏收前 2 或 5 毫秒内存在探测请求的比例为 0.0 或 1.1%，对照为 0.0 或 0.1%。85 到 91% 的漏收在接入点完全没有留下痕迹，甚至没有 FCS 错误。

开发板最容易漏收的是紧接自身发送之后到来的帧。《火红》主机的每个数据帧都会先进行 RTS/CTS，即使开发板信标中的 ERP 字节为 0；数据在开发板的 6 Mbit/s CTS 后 60 微秒到来（44 微秒加 SIFS），一次交换中 4034 帧有 329 帧漏收。基准测试以 54 Mbit/s 连发 4 帧时，首次副本漏收比例依次为：第一帧 0.5 到 3.0%，第二帧 2.4 到 4.6%，第三帧 4.7 到 8.7%（通常最高），第四帧 2.6 到 7.6%。

ESP32 站点每次重试都会先在数据前 128 微秒发送 RTS（`lmacConfMib` +42，发送 RTS 前的重试次数为 0；+22 处的 RTS 阈值为 2346）；`esp_wifi_internal_get_rts` 和 `_set_rts` 均通过一个紧凑排列的 `{u16 threshold, u8 retries before RTS, u8 long, u8 short}` 访问这两个值。ACK 和 CTS 速率表位于 `0x3ff73400`..`0x3ff7341c`。90 秒内接入点听到的 8527 个 RTS 中，有 311 个（3.6%）已得到回应，但 CTS 后的数据漏收；上述统计未包含这些情况。驱动在软件中重试：`lmacRetryTxFrame`（libpp 的 `lmac.o`）通过 `lmacTxFrame` 重新发送，次数不超过 `lmacConfMib` 的限制（短重试位于 +21，长重试位于 +20，默认均为 32），由 `esp_wifi_internal_set_retry_counter(short, long)` 设置。接入点每秒发送 100 个单播帧时（`--flood 100 --unicast`），帧最长等待 24 毫秒；双开发板无法复现 100 毫秒阻塞。

站点开发板的慢发送（超过 3 毫秒，`--done-out`）会集中在 102.4 毫秒周期中的两个二十分之一时间段内（29 到 43%，对照为 2 到 12%），不受信标间隔影响（`tools/ldn/esp32_bench_fold.py FILE PERIOD_US`). `tools/ldn/esp32_bench_drift.py` 会对照主机端测量两块开发板的时钟（600 秒内相差 1.9 ppm），并扫描折叠周期。

## 开发板 LED 与按键

LED 灯效在经典 ESP32 开发板上驱动 GPIO2，在 S3 上驱动反相的 GPIO21（XIAO ESP32S3 的黄色用户 LED，即 arduino-esp32 的 XIAO_ESP32S3 变体中的 `LED_BUILTIN`），在 C6 上驱动反相的 GPIO15（XIAO ESP32C6 的黄色 LED）。C3 固件不操作 LED 引脚。BOOT 跟踪标记在经典 ESP32 和 S3 上使用 GPIO0，在 C3 和 C6 上使用 GPIO9。

ELEGOO ESP-32 Type-C 开发板（CP2102、ESP32-D0WD-V3）搭载一个无品牌模块，带 PCB 天线，未印有 Espressif 模块名称：

| 部件 | 连接位置 | 是否可控 |
| --- | --- | --- |
| 红色 LED | 3.3 V 电源轨 | 否，只要开发板通电就会亮起 |
| 蓝色 LED | GPIO2，高电平点亮 | 是 |
| EN 按钮 | 芯片复位 | 否 |
| BOOT 按钮 | GPIO0 | 是：每次按压都会发送 BUTTON（`0x8E`）、闪烁 LED 并唤醒屏幕 |

GPIO2 和 GPIO0 是启动配置引脚（进入下载模式时，复位瞬间应为低电平或悬空）；固件仅在启动后驱动 GPIO2。在 ROM 引导加载器中，可通过写入 GPIO2 的 IO_MUX（`0x3FF49040`, `MCU_SEL` 2）、其输出选择寄存器（`0x3FF44538` = `0x100`), `GPIO_ENABLE_W1TS` 以及 `GPIO_OUT_W1TS`（位 2）点亮 LED。

固件由核心 1 上优先级为 1 的任务，每 10 毫秒通过 LEDC PWM（13 位、5 kHz）驱动蓝色 LED。占空比为亮度级别的 2.2 次方；灯效切换采用 150 毫秒交叉渐变。

| --- | --- | --- | --- |
| 自动 | 0 |  | 对应模式的灯效，见下文 |
| 关闭、常亮 | 1, 2 |  |  |
| 呼吸 | 3 | 3000 毫秒 | 升余弦曲线 |

## 屏幕

可选配通过 I2C 连接的 SSD1306 128x64 单色 OLED。用户反馈 128x64 SSD1315 和 SSD1309 模块也可使用相同固件。启动时，固件先探测 0x3C，再探测 0x3D；如果都不回应，就释放引脚且不启动屏幕功能。存在屏幕时，最后一个核心上优先级为 1 的任务会每 50 毫秒绘制一帧，并以 400 kHz 发送（1031 字节，约 23 毫秒）。

| 目标 | SDA | SCL | 开发板引脚 |
| --- | --- | --- | --- |
| ESP32 | GPIO21 | GPIO22 | DevKit V1 D21、D22 |
| ESP32-S3 | GPIO8 | GPIO9 |  |
| ESP32-C3 | GPIO6 | GPIO7 | XIAO D4、D5 |
| ESP32-C3 | GPIO5 | GPIO6 | 0.42 英寸 OLED 开发板自带的 72x40 屏幕，第二顺位探测 |
| ESP32-C6 | GPIO22 | GPIO23 | XIAO D4、D5 |

VCC 接 3V3，GND 接 GND。常见的四针模块（GND、VCC、SCL、SDA）自带 3.3 V 稳压器，SCL 和 SDA 上各有 4.7 k 上拉电阻；地址电阻选择 0x3C（丝印为 0x78）或 0x3D（0x7A）。面板将 segment 127 映射到第 1 列，COM0 映射到第 63 行，因此固件设置段重映射（`A1`）、反向 COM 扫描（`C8`）及替代 COM 引脚配置（`DA 12`).

ESP32-C3 0.42 英寸 OLED 开发板（以 ABRobot 及其他名称销售）通过 GPIO5 和 GPIO6 连接一块 72x40 面板，并在 GPIO8 上配有 LED，固件不操作该 LED。使用 128x64 INIT 驱动时，面板显示帧的第 30..101 列和第 24..63 行，即反向扫描的最后 40 行。列偏移与厂商示例的 x 偏移 30 一致。行范围根据一张从第 12 行绘制的空闲场景照片读取：第一条可见行是“pokeldn”字形的最底行，对应帧第 23 行，并受场景上下漂移一像素影响。厂商示例的 y 偏移 12 是 u8g2 文本基线。在这些引脚上发现屏幕后，会在该窗口内绘制紧凑场景：图像上方最多一行 12 个字符，精灵图缩为一半，原始 2x2 像素块中有两个像素点亮时，缩小后的像素就点亮。`tools/ldn/screen_preview.py --panel 72x40` 可渲染这些场景。

没有主机端命令时，屏幕显示无线模块状态：空闲、正在加入或作为主机端（精灵球周围有圆环），以及已连接；已连接时，主机与精灵球之间的线缆会为无线模块在每个方向计数到的每帧传送一个数字，每 70 毫秒最多一个，下方显示总数。

OLED 像素会随点亮时间老化，因此屏幕限制静态图像的持续显示时间。无线模块正在加入、已加入、作为主机端或嗅探时，播放交换完成或礼物送达动画时，以及这些状态结束、DISPLAY 命令、HELLO 或 BOOT 按压后的 60 秒内，屏幕保持全亮。随后将对比度降为 1，并使用 2+2 时钟的预充电（`81 01 D9 22`），600 秒后关闭（`AE`）；面板保留 RAM。再次发生上述事件时，会在下一帧点亮，且该帧会先于 `AF` 发送。空闲场景每 60 秒沿 2x2 方形移动 2 个像素。`scene_draw` 返回亮度；`tests/test_esp32_screen.py` 固定检查这些时间参数。

## 构建与刷写

固件发行版使用 `major.minor.patch` 中的 `firmware/esp32/version.txt`，由 ESP32、S3、C3 和 C6 共用。构建发行版前，修复递增补丁版本，兼容功能递增次版本，不兼容更改递增主版本。ESP-IDF 会将版本嵌入应用描述符；INFO 以 `version=...` 报告版本，“开发板”页面在检查返回后显示它。未标记版本的构建显示 `version unknown`，只要串口协议匹配仍可使用。串口协议版本与桌面应用版本相互独立；线路协议契约变化时，应递增协议编号。

ESP-IDF v6.1（标签 `v6.1`，提交 `fff9895c82d744c7237be8847347bdd1b07c6643`）可构建全部四个目标。请使用 `install.sh esp32,esp32s3,esp32c3,esp32c6` 安装工具，然后激活 IDF 环境。

```
cd firmware/esp32
idf.py set-target esp32   # esp32s3, esp32c3 or esp32c6 for those chips
idf.py build
idf.py -p <port> flash
```

控制台输出已关闭（`CONFIG_ESP_CONSOLE_NONE`, `CONFIG_ESP_CONSOLE_SECONDARY_NONE`）。在经典 ESP32 上，UART0 是主机端连接，因此固件自行分配 GPIO1 和 GPIO3（`uart_set_pin`）。在 S3 上，固件在核心 1 安装 USB Serial/JTAG 驱动；C3 和 C6 则在核心 0 安装。

桌面应用会在与刷写相同的连接上使用 esptool 检测芯片。写入前，它会检查合并镜像在对应芯片闪存偏移处的引导加载器（ESP32：`0x1000`；S3、C3 和 C6：`0x0`），自定义镜像也会检查。esptool 5.4.0 的 `write_flash` 在合并镜像以填充字节开头时，可能跳过芯片检查。切勿根据 USB 桥接芯片 ID 选择固件。[桌面版构建](gui.md) 介绍了如何将全部四种镜像打包。

### 蓝牙

使用 `POKELDN_BLE=1` 的构建还可通过蓝牙 LE 承载主机端连接，适用于没有 USB 串口的主机端：iPhone 应用若不加入 Apple MFi 配件计划，就无法打开 USB 串口设备，而 CoreBluetooth 无此要求。此时开发板的 USB 仅需用于供电。

```
POKELDN_BLE=1 idf.py -B ../../scratchpad/esp/build-ble \
    -D SDKCONFIG=../../scratchpad/esp/build-ble/sdkconfig \
    -D SDKCONFIG_DEFAULTS="sdkconfig.defaults;sdkconfig.defaults.ble" build
```

开发板以 `POKELDN-RADIO` 为名称广播，服务为 `7a1e0101-5d2c-4c3e-9f4b-504f4b454c44`：主机端向 `...0102` 写入 COBS 流（无响应写入），开发板通过 `...0103` 发送自身数据的通知。当中心设备订阅 `...0103` 时，线路数据便在此读写，USB 线缆保持静默；取消订阅后，线缆恢复原有连接。帧格式、CRC 和 CREDIT 均不变。开发板请求 15 毫秒连接间隔、2M PHY 和 247 字节 MTU。其 HELLO 文本以 `link=ble` 结尾，“开发板”页面会将其显示为蓝牙无线固件。`POKELDN_RADIO=esp32:ble`（或 `esp32:ble:NAME`）可从任意启动器打开它（`pokeldn/ldn/esp32_ble.py`，使用 bleak）。

经典 ESP32 上，双模控制器只剩 32 KB 可用堆，低于线路的 64 KB 下限，因此 `wire_send` 会拒绝每条消息，仅有绕过该下限的 CREDIT 能到达主机端。`sdkconfig.defaults.ble` 采用纯 BLE 控制器，并将静态 Wi-Fi 接收缓冲区从 25 个减为 10 个；`ble.c` 会释放经典蓝牙内存，并将自身接收缓冲区大小设为 10 KB（FLOW_WINDOW 加一帧）：最后一步前有 60 KB 可用，之后便足够。Mac 实测：连接并完成 HELLO 耗时 1.3 到 1.7 秒，每次 HELLO 往返 63 毫秒（连续 200 次），约为两个连接间隔。

无线模块通过软件共存机制让 Wi-Fi 与蓝牙共用天线，因此每次 BLE 连接事件都会占用主机所在信道的空口时间。对连接循环造成的影响尚未测量。

从 Mac 通过 BLE 运行《火红》主机端时，主机成功加入，却停在“正在等待 POKELDN 回应”，而主机端因确认落后 6 帧而保留帧等待。空口正常（`tx_eth_failed=0`）；主机端连接却不正常：`wire_dropped=7056`, `refused_queue=3112`, `queue_max=384`, `heap_min=29924`。开发板发往主机端的消息量超过通知所能承载的量，384 项队列因此溢出。其中 8031 条是 TX_DONE，即主机端从不读取的诊断消息。通过 BLE 时，开发板不再发送 TX_DONE，而且队列仍有更多帧时，写入任务会将多个帧合并到一次通知中：下一次运行没有丢弃消息（`queue_max=26`），主机以不到每秒一帧的速度到达房间。连接间隔为 15 到 30 毫秒时，HELLO 往返需 63 毫秒；固定为 15 毫秒（最小值等于最大值，这是 Apple 配件规则唯一允许的例外）时仅需 32 毫秒，随后从 Mac 通过 BLE 完成了《火红》主机端交换，玩家认为速度明显改善，主机之后也正常离开。

通过 BLE 的《火红》加入端未完成 RFU 握手；主机显示 2318-0013。使用 27 字节链路层包时，开发板每秒听到约 217 帧，而主机端仅收到 6522 帧中的 757 帧。数据长度扩展（251 字节包）使基准速度从 14.1 翻倍至 28.1 KB/s，下一次加入端运行交付了 796 条 RX_ETH 中的 776 条，但加入端仍每秒只发送 5 个 T 槽，主机则为 30 个，其 24 帧窗口几乎全满，开发板还因堆达到下限而拒绝了 581323 条消息（`heap_min=30296`）。经典 ESP32 是蓝牙 4.2 芯片，不支持 2M PHY。

在 XIAO ESP32C6（蓝牙 5）上，同一构建的基准速度为 33.6 KB/s，HELLO 往返 62 毫秒，并从 Mac 通过 BLE 完成了一次《火红》加入端交换：加入端与主机速度一致（各每秒 18 个 T 槽），但玩家认为比有线慢。C6 BLE 镜像将 1 MB 应用分区填得仅剩 13 KB。开发板广播中只包含名称：iOS 应用不使用服务过滤器扫描，并匹配 `POKELDN-RADIO`.

XIAO ESP32C6 若只在连接时请求 15 毫秒，实际会以 30 毫秒运行（iPhone 13 Pro 上每次 HELLO 为 61.5 毫秒，《火红》房间运行极慢）；在中心设备订阅后再次请求，则会获得 15 毫秒（`ble_itvl_us=15000`，见 STATUS；每次 HELLO 为 32.1 毫秒）。连接时的请求到达时，中心设备仍在发现服务。

macOS 上，如果进程的负责应用没有蓝牙授权，bleak 会中止（SIGABRT）；使用 `open -n -a Terminal FILE.command` 启动的脚本则使用“终端”的授权。

### USB 主机端连接

S3、C3 和 C6 通过 USB Serial/JTAG 使用相同的 COBS、CRC 和 CREDIT 协议。驱动的两个环形缓冲区均为 16 KB。IDF v6.1 的 `usb_serial_jtag_write_bytes` 要么将整个帧入队，要么在超时后返回零；写入任务每等待 20 毫秒便重试，连续 500 毫秒无进展后会计为一条丢弃消息。`write_max_us` 包含该等待时间。读取任务以 20 毫秒超时读取可用字节。此路径的 UART 溢出及帧格式计数器始终为零；它们无法衡量 USB 丢失。接收中断会在 16 KB RX 环形缓冲区满时丢弃一个 64 字节包，且不计数（`usb_serial_jtag.c:144` 忽略 `xRingbufferSendFromISR` 的返回值）。CREDIT 窗口可避免环形缓冲区填满；此处发生丢失时，只会表现为写入字节数超过开发板最后一次 CREDIT。`POKELDN_ESP32_BAUD` 在所有目标上都被接受，但仅改变经典 ESP32 的线路速率。

电脑端将串口写入超时设为 1 秒。写入失败或短写会通过与读取错误相同的开发板丢失处理函数结束会话，且不会将失败帧计入已写入数据。速率协商还会限制等待操作系统输出队列的时间，而不调用可能无限等待的 `flush()`。初始 HELLO 和速率协商完成后，若 1 秒内没有有效开发板帧，则会将 STATUS 探测入队；静默 3 秒后，会以 USB 错误结束会话，并要求用户拔下并重新连接开发板。空闲固件会重复发送 CREDIT，不会重复发送的旧固件则可回应 STATUS。格式错误的字节不能作为仍存活的证据。重复的 CREDIT 仍可修复线路丢失的字节，但完全静默的开发板不会被反复重新同步来接受更多写入。

若要在没有主机的情况下复现长时间上传，请使用原生 USB 端口和空 AP，运行两小时的主机端到开发板持续测试（将 `COM5` 替换为开发板端口）：

```
./.venv/bin/python tools/ldn/esp32_bench.py --port COM5 --bauds 921600 \
    --soak 7200 --size 1400 --rate 460000
```

该测试使用 CREDIT 流量控制发送 1400 字节以太网帧，目标为每秒 460000 个以太网字节，每 5 秒输出累计帧数、字节数、CREDIT 以及开发板 STATUS。如果开发板或主机端跟不上，实际速率可能更低。`--rate 0` 可取消速率控制。USB 持续测试只需一个波特率：原生 USB 忽略波特率值。最终开发板计数包含 Wi-Fi 发送失败，因此检查的是命令是否送达处理函数，而非是否经空口接收。USB 故障或最终帧计数不匹配都会以非零状态退出。请保留终端输出；`POKELDN_ESP32_TRACE` 还可记录线路消息，但数小时的完整载荷跟踪可能达到数 GB。持续测试成功后，应再执行一次超过所报告 54 分钟故障点的完整主机上传；空 AP 测试无法复现主机的确认行为或全部 Wi-Fi 负载。

USB 发送速度快于写入任务编码速度，因此在满速的开发板到主机端数据流中，写入任务从不休眠。USB 目标的读取任务优先级为 21，高于写入任务的 20；UART 构建仍为 19，因为线路速率会迫使写入任务休眠。在 XIAO ESP32S3 上，884 KB/s BENCH 期间每 15 毫秒发送一条 14 字节 ETH_TX（`esp32_bench.py --trickle 300 --flood`):

| 读取任务优先级 | `read_max_us` | 已计数的 ETH_TX |
| --- | --- | --- |
| 19，低于写入任务 | 53951079 | 3055 条中的 785 条，其余在主机端的 512 帧队列处被丢弃 |
| 21，高于写入任务 | 20493 | 3052 条中的 3052 条 |

BENCH 仍保持 884 KB/s；5000 条上行 ETH_TX 耗时从 13.5 秒变为 15.4 秒，无丢失。提高优先级后的《火红》加入端交换记录到全部 5629 条 ETH_TX。XIAO ESP32C6 使用优先级 21 时，在 820.6 KB/s BENCH 期间每 20 毫秒发送一条 14 字节 ETH_TX，读取间隔最长 19997 微秒，221 条全部被计数；随后完成一次《火红》主机端及一次《传说 Z-A》主机端交换，主机均无错误。

## 运行

`POKELDN_RADIO=esp32:` 会将每个启动器的 `ldn` 调用交给开发板执行。`esp32:auto` 会选取当前唯一的 USB 串口（`/dev/cu.usbserial-*`, `/dev/cu.SLAB_USBtoUART*`, `/dev/cu.wchusbserial*`, `/dev/cu.usbmodem*`, `/dev/ttyUSB*`, `/dev/ttyACM*`；Windows 上为 USB COM 端口），存在多个时拒绝自行选择，因为打开端口可能复位对应开发板。每个进程只打开一次端口，并释放 DTR 和 RTS；但 macOS 上的 CP2102 开发板无论如何都会在打开时复位。未复位的经典开发板会保留上一进程的 `BAUD`，因此主机端依次在 115200、`POKELDN_ESP32_BAUD` 以及应用提供的各速率（921600、1500000）下发送 HELLO，重复五轮，每次等待 0.5 秒，然后切换到所需速率；应用的开发板检查则保留检测到的原速率。仅以 115200 向仍处于 921600 的开发板发送 HELLO，会以 `no reply 0x81 to command 0x01` 结束。Windows 以独占方式打开 COM 端口：只要本进程或其他进程仍持有任意句柄，第二次打开就会失败并返回 `PermissionError(13, 'Access is denied.')`，因此始终不回应 HELLO 的开发板，会在启动器重试前关闭其端口。端口仍打开时移除 USB 设备，下一次读取会以同类错误失败（`GetOverlappedResult failed` 或 `ClearCommError failed`），其后每次写入也会失败；启动器随后以 `[esp32] The board disconnected from USB` 结束运行，而不是继续写入。

Windows 11 使用 Silicon Labs 驱动 11.6.0.420 时，通过 CP2102 连接的经典 ESP32 测得：

| 以下操作前的控制线状态：`open()` | 打开次数 | 复位启动信息 | ROM 下载模式 | 后续情况 |
| --- | --- | --- | --- | --- |
| DTR 和 RTS 均释放（主机端打开方式） | 40 | 0 | 0 | 收到运行中固件的 CREDIT 帧；HELLO 在 0.06 秒内回应，30 次全部成功 |
| pyserial 默认值，两者均置为有效 | 20 | 20, `rst:0x1 (POWERON_RESET),boot:0x13 (SPI_FAST_FLASH_BOOT)` | 0 | 打开后约 0.3 秒收到固件启动时的 INFO |
| DTR 释放、RTS 置为有效 | 20 | 0 | 0 | 端口打开期间没有任何字节：在双晶体管自动复位电路中，RTS 将 EN 保持为低电平 |

保持在 ROM 下载模式的开发板不会回应 HELLO，应用检查会报告没有 pokeldn 固件。其他进程占用端口时，打开操作会立即失败；应用会报告端口忙碌。

使用开发板时，启动器会跳过所有 nl80211 步骤：`--phy auto` 解析为 `esp32`，不删除任何 vif，不运行 `iw`, `ip`, `nmcli` 或 `sysctl`，加入端的 `--mac` 会成为开发板站点地址。macOS 上无需 root。扫描会跳过 5 GHz 信道（36 及以上）：开发板只支持 2.4 GHz，因此无法连接在 5 GHz 上创建会话的主机。FRLG 主机端不注入信标；开发板接入点会自行发送信标。

`POKELDN_ESP32_TRACE=FILE` 会逐行追加每条串口消息：Unix 时间、`>`（主机端）或 `<`（开发板）、类型，以及十六进制载荷。

### 无法解码 OFDM 的开发板

主机的广播信息采用 HT MCS 3（[发现](ldn.md#discovery)），因此无法解调 OFDM 的开发板只能听到其 DSSS 信标，听不到任何广播信息：`esp32_first_contact.py` 在每个信道上统计到的 LDN 动作帧均为 0。以下两项检查可将其与固件或主机端故障区分：

| 检查 | 正常开发板 | 无法解码 OFDM 的开发板 |
| --- | --- | --- |
| `tools/ldn/esp32_census.py`，放在主机或繁忙接入点旁边 | `OFDM` 和 `HT` 出现在正常帧中 | 正常帧全部为 `DSSS`；OFDM 帧失败并返回 `rx_state` 65 |
| 作为站点加入接入点后，接入点发给它的单播帧速率 | HT MCS 5 到 7（HT40 接入点） | 约 97% 为 DSSS 5.5 Mbit/s，从不高于 OFDM 6 或 HT MCS 1 |

此类开发板仍可成功完成站点关联和 ping：接入点的速率自适应会回退到 DSSS。一块通用 ESP32-WROOM-32 DevKit（ESP32-D0WD-V3 修订版 3.1、CP2102）即使运行非 pokeldn 固件也无法通过这两项检查；使用相同芯片的 WROOM-32E 开发板则两项均通过，可听到《剑》的礼物网络并完成神秘礼物分发（[问题 1](https://github.com/Decryptu/pokeldn/issues/1)).

该 [Android 开发者原型](https://decryptu.github.io/examples/android/README.md) 在运行 Android 16 的 OnePlus CPH2621 上，通过 USB-C 为 XIAO ESP32C6 供电，并使用原生 USB CDC 流运行现有 Python 主机端。《火红》交换成功，收到的 PK3 合法，完成存档同步屏障并正常离开房间。初始主机端约每秒处理 10 个父端槽，移动缓慢，动画等待很长。将 LDN 与游戏协议放在同一个 Trio 线程运行提高了循环速率；随后将 Python 线程限制在一个性能核心上，恢复了流畅的房间移动。重复交换正常完成，在 70 秒房间窗口和 30 秒动画窗口中，均测得每秒 51.1 个不重复父端 UNI 槽。收到的皮卡丘通过 PKHeX 验证，主机正常离开。在该手机单独进行的 300 包发送测试中，不限制核心的预热运行达到每秒 99 和 113 包；核心 6 达到 265 和 281 包，恢复原始 CPU 掩码后又回到较低速率。此测量不能证明其他 Android 设备也需要设置核心亲和性。

《火红》主机加入开发板接入点时，会列出该网络（接受零长度隐藏 SSID、速率顺序、能力值 `0x0431` 以及 WMM 元素），完成开放式认证，并在认证后 24 毫秒发送一个关联请求：能力值 `0x0431`、监听间隔 10、以 32 个十六进制字符表示的 SSID、速率 `02 04 0b 16 0c 12 18 24` 和 `30 48 60 6c`、功率能力 `00 14`、RSN 能力 `0x0000`、一个 WMM 信息元素、厂商元素 `00 22 aa 10 01 02`。其 LDN 身份验证请求会到达 `RX_ETH`，时间是在 `STA_JOINED` 后 40 毫秒。其最初的广播需要固件转发（[站点的广播](ldn.md#a-stations-broadcasts)).

《朱》作为加入端：开发板首次关联尝试便取得席位，从 `STA_JOIN` 到 `LINK` 耗时 0.35 秒；会话加入在 0.93 秒时得到回应，公告在取得席位后 5.8 到 7.7 秒到来。主机首批突发的 46 条记录（约 50 KB）使开发板到主机端线路达到 92 KB/s 的饱和速率。

### 加入

`STA_JOIN` 进行一次关联尝试：先在指定信道按 BSSID 快速扫描，然后执行开放式认证和关联。零售版《剑》的匹配网络在 10 次开发板加入中有 2 次失败，`LINK` 断开，原因为 `0xc9`（未找到接入点，发生在 `STA_JOIN` 后 2.4 秒）或 `0x2`（认证过期，发生在 1.3 秒后），但开发板仍能在该信道听到其广播信息；在相同搜索中再次执行 `STA_JOIN` 即可关联。成功加入时，会报告 `LINK` 为已连接，时间是在 `STA_JOIN` 后 0.23 到 0.34 秒。主机端会发送 `STA_JOIN`，在加入超时范围内最多三次（`pokeldn.ldn.esp32_wlan.JOIN_ATTEMPTS`）。尚不清楚为何主机网络会错过某次尝试。
