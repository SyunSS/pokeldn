# 传说 Z-A

《宝可梦 传说 Z-A》（游戏 ID 为 `0100f43008c44000`）是一款原生 Switch 游戏，Pia 静态链接在 `main` 中。其数据包头版本为 16，与 `pokeldn.ldn.crypto` 为 GBA 应用写入的版本相同。

## 转储

基础应用 `v0`（4.3 GB），更新 `0100f43008c44800` `v393216`（2.1 GB），超次元爆涌 DLC `0100f43008c45002`.

| NCA | ID | 容器偏移 | 分区密钥 |
| --- | --- | --- | --- |
| Program（更新） | `4a70b3ff963bfe412681185cea68bf55` | `0x2085d0` | `b9de1a0334576634f8fdafdd703f7f9a` |
| Control（控制数据） | `3e7ba1cd223145fa4f299a8f4cafd4cb` | `0xbd0` | `a8cb59338ce785237048d52452eb6adf` |

Program NCA 的分区 0 包含 exeFS，分区 1 包含 BKTR RomFS。exeFS 包含 `main`（33,970,422 字节）、`main.npdm` (1,700), `rtld`（8,550）和 `sdk`（6,247,676），不包含 `subsdk0`。解压后，`main` 的 text 段为 `0..0x3163f70`，rodata 段起于 `0x3164000`，data 段起于 `0x3bc2000`；本页地址均为该映像内的偏移。Control RomFS 数据位于 NCA 的 `+0x14c00`，分区计数器为 `0000000000000005`; `control.nacp` 给出的显示版本为 2.0.2，并在 `+0x30b0` 处给出八个本地通信 ID，全部为 `0100f43008c44000`.

## 数据包头

包头版本为 16，对应 wiki 表中的 Pia 6.39 至 7.2。布局为 `pokeldn.ldn.crypto.PiaHeader`（29 字节，魔数 `32AB9864`，版本字节在加密时带 `0x80`；参见 [Pia](pia.md)).

```
0x24fadbc   initializer: magic at object +0x08, 0x10 at +0x0c, memsets nonce +0x15 (8), tag +0x1d (16)
0x24faefc   validator: magic, (version & 0x7f) == 0x10, (length - 0x1d) >> 6 below 0x71
0x24fb1e0   receive path, branches on bit 7 of the version byte
0x24fb4b0   send path, writes 0x10 back to +0x0c when it seals nothing
0x24fb46c   padding-size setter: ORs into bits 4..7 of object +0x0d (wire byte 0x05)
```

对象中 nonce 和标签的偏移比其线上偏移高八字节，与传说 阿尔宙斯的版本 11 包头在以下代码中的处理相同：`pokeldn.ldn.pia6`.

## 广播

处于本地搜索界面的主机会创建网络并广播 112 字节：0x5C 字节的 Pia 系统属性块，以及 20 字节游戏数据。不随连接密码变化的字段如下：

| 字段 | 值 |
| --- | --- |
| 本地通信 ID | `0100f43008c44000` |
| LDN 协议 | 1 |
| 广播版本 | 4 |
| 场景 ID | 1 |
| 应用版本 | 6 |
| 安全模式 | 1 |
| 接受策略 | ALL（全部） |
| 参与者 | 1/2 |
| 系统／应用通信版本 | 22 / 6 |
| 玩家名 | 一字节空格，UTF-8 |

SSID 和信道按每次会话确定。游戏数据是 ASCII 编码的连接密码，以 NUL 补足十六字节，随后以小端序的 `u32` 保存其长度。布局和密码字段与传说 阿尔宙斯相同（[pla.md](pla.md)，广播中的连接密码）；Z-A 的游戏密钥生成的掩码为 `1068a742ac3a8787ab6066a161f5d5e1`. `pokeldn.za.build_advertise_data(code)` 仅根据连接密码即可复现每条广播；`tests/test_za.py` 对两者进行固定验证。

## 占据席位

搜索中的主机接受站点后立即开始 Pia 通信：首个数据报（109 字节）在 0.02 秒出现。数据包使用 `AES_ECB(game_key, ssid)` 验证，网络 ID 为 `CRC32(ssid[1:16])`（32 个全部成功解密）。未获回应时，它在协议 1（Net）上从自身可变 ID 向目标 0 发送：

| 消息 |  |
| --- | --- |
| `01 11 ...`，118 字节 | 连接状态，序列 ID 为 2 和 3，每秒两次 |
| `01 40 00 00` | 连接状态未获回应后，开始主机端迁移 |

连接状态采用 `pokeldn.ldn.pia_connect.parse_net_conn_request` 所读取的布局：四个槽位，其中两个已填充，端口均为 12345，主机端为 `169.254.x.1`，加入端为 `169.254.x.2`。约 14 秒后停止（实测 14.4 秒），但仍让站点保留席位。

```
0x251b1bc   LdnProtocol vtable 0x3c8aef8 slot 0x1d8: mov w0, #0x1f40
0x2513520   NetBackgroundProcessJob StartConnectNetwork: job+0xa0 = now + ticks_per_ms * 8000
0x25141c4   the WaitConnected step 0x25140bc, while the host is unknown: deadline against now
```

## 零售版主机上的会话

站点发送参考加入端的 Session 加入请求后会立即被接纳。主机发送的消息如下：

| 占位后时间 | 主机发送内容 |
| --- | --- |
| 0.02 秒 | Net 连接状态，118 字节 |
| 0.05 秒 | Session 加入响应，类型 2，37 字节，目标为加入端的可变 ID |
| 0.06 秒 | Reliable（协议 10），106 字节，以及两条 Broadcast Reliable（协议 11）消息 |
| 0.08 秒 | Net 属性更新，类型 0x50，150 字节 |
| 从 0.5 秒起 | RTT 请求，约每秒三次 |
| 1.12 秒起，重复发送 | Session 会话更新，类型 5，185 字节 |

除 Net 确认消息外，加入请求还必须包含：十种协议（`1:0 3:5 5:1 6:0 9:1 10:3 11:4 12:4 13:7 15:0`）、应用通信版本 6、标识令牌 `0x06` 后接零字节，以及名称为一个空格的 PlayerInfo。若加入请求列出 GBA 应用的六种协议和版本 0x58，则不会获得回应，主机会在占位后 8.7 秒开始主机端迁移。若加入请求包含上述十种协议，但游戏消息无人回应，则会在占位后 27 秒以主机端迁移和“未找到交换对象”结束。若加入端回应所有 Net、Session、RTT 和 Reliable 消息，但不回应任何游戏消息（`bin/za_join.py` 不带 `--game`），则可在零售版搜索中保持席位 150 秒，直到主动离开：主机约每秒发送 32 个数据包，回应离开请求后显示“未找到交换对象”。

若加入请求的协议数与主机端不同，类型 0 处理器 `0x254a030` (`0x254a090` 会将其丢弃，与 `0x256c9f0` 比较），不回应也不创建站点；若协议版本或应用版本错误，则返回一条 37 字节类型 2，结果为 3（`0x254a2e4`）或 4（`0x254a290`）。主机端的 WaitMember 随机取 3000 ± 999 毫秒（随机 u64 按有符号数读取）。到期时，若加入端仅位于 Net 层而尚未进入会话，LeaveMeshWithHostMigration 会轮询 8000 毫秒寻找下一任主机端（`0x255a520`），然后发送序列号 3 的 Net 0x11 和 Net 0x40。加入端若仅列出十种协议中的九种，零售版搜索不会返回任何 Session 消息；首个 Net 0x40 在占位后 8.74 至 11.01 秒出现（预测为 8.05 至 12.1 秒），随后主机以新 SSID 创建新网络并继续搜索。上文的 8.7 秒对应的就是这条路径。

同一加入端若不回应 RTT，因此在 1.16 秒的类型 6 之后不再发送任何消息，就会被踢出（参见“踢出”）：从 14.24 秒起发送 Session 类型 13，共九条，间隔约 0.5 秒；从 19.31 秒起每 0.5 秒发送序列号 3 的 Net 0x11；从 23.31 秒起每 0.3 秒发送 Net 0x40；最后一个数据包在 25.13 秒出现，随后主机显示“未找到交换对象”。27 秒结束的情况就是这个序列：加入端已连续 10 秒未从自身可变 ID 发送任何消息。

## 游戏自身的数据交换

在 Pia 之上，游戏使用 Reliable（协议 10）和 Broadcast Reliable（协议 11），子包头由 `pokeldn.ldn.reliable` 解析。一次交换携带下列应用载荷（参考捕获中有二十种不同载荷），每条都重发直至确认；除站点 ID 外，双方发送相同的一组载荷。按首次出现顺序列出消息 ID：

| ID | 字节数 | 承载内容 |
| --- | --- | --- |
| `1400` | 106 | 站点身份，玩家名采用 UTF-16 |
| `1403` | 9 | 身份数据的校验和（SyncDataSet），见下文 |
| `0100` | 1211 | 绘制选择界面所依据的记录 |
| `0101` | 354 | 交换提议：九字节头部、344 字节宝可梦记录、一个尾随字节 |
| `0102`, `0104` | 5 | 步骤消息 |
| `0200` | 5 | 确认步骤，最后一个字节为 3、6、0x0b、0x0e |

`pokeldn.za.reference` 随附身份数据、其后续消息、协议 11 开启消息及选择记录，录制自一对模拟主机，其玩家为 `Player`; `bin/za_join.py` 和 `bin/za_host.py` 负责发送它们（`--game-dir` 指定另一组）。

身份数据是一个 `b9` 二元组：先是一个 u32，然后是一个仅含单成员的元组，其中保存 0x5d 字节的 `bc` 数据块。该数据块是六元组，前四个成员分别为存档的训练家 ID（秘密 ID 位于高半字）、性别、语言和玩家名，随后是一个 32 字节零字段及其余内容。

游戏从存档训练家块中填入这四个成员，即 PKHeX 的 `MyStatus9a`，该块位于玩家状态对象的 +0x40：

| 成员 | 块内偏移 | 取值函数 |
| --- | --- | --- |
| 训练家 ID | +0x00 | `0x824b2c` |
| 性别 | +0x05 | `0x505c24` |
| 语言 | +0x07 | `0x23c398` |
| 姓名，13 个字符 | +0x10 | 由以下函数复制：`0xc90ce4` |

构建函数为 `0xc90b04`；它将该值存入某名称条目下，该条目由 GOT 保存在以下位置：`0x3ec7638`.

接收主机按相同顺序解码这些成员（`0x9131ec`）。其姓名框 `T_pname_%02d` (`0xb13fd4`）根据游戏语言表，将语言检查为 1 至 11（`0x33a308c`）；11 为拉丁美洲西班牙语。它将性别与姓名一起传入文本（`0x6b9fb8`).

记录的身份来自女性、英语存档：`0x378913cf`（5071 和 14217，即参考会话中宝可梦的训练家）、1 和 2。为接收玩家定制的礼物会读取全部四项（`reference.identity_trainer`, [为接收玩家定制](gift_simulated.md#made-for-the-receiving-player)).

```
1400 b902 82<u32> b901 bc5d b906 82<u32> 01 02 bc1a <name> bc20 <32 bytes> ...
```

姓名为 26 字节，采用 UTF-16LE 并以 NUL 填充：最多十二个字符，位于协议 10 消息的偏移 0x18（加上协议 11 的站点前缀后为 0x1c）。在该处使用记录的 `Player` 时，零售版主机将交换对象显示为 `Player`。两个启动器均向此处写入 `--trainer-name`（默认 `POKELDN`）（`pokeldn.za.reference.named`).

通道 0x14 承载游戏在站点之间保持同步的键值存储（`gfa::network::p2p`，构建位置 `0x7796a0`；消息 ID `0x1400 | index`）：1400 为 UpdateValue（`0xc1bdf4`），1402 为 DeleteAllValues，1403 为 SyncDataSet（`0xc4b1b4`）。身份数据外层的 u32 `0x2abe85e2` 是该值的键，是位于 `0xdf1b30` 的常量：即对 `UserData` 计算 FNV-1a 32，游戏以该名称保存身份数据。1403 携带一个针对发送端按键排序后的全部值计算的 u32，`h = crc32(le32(fnv1a32(value) + h))`，来自 `h = 0` (`0xc4b270`，FNV-1a 位于 `0xc4b31c`，标准 CRC-32 位于 `0xc4b420`）；对于身份数据，所计算的值是 `bc5d` 之后的 0x5d 字节。接收端重新计算，只有每个站点的结果都匹配才继续（`0xb8c724`, `0xb8c660`）。记录的 `Player` 身份数据得到 `1403b9018269fb308f`，即记录中的消息。若身份数据改名后仍发送旧的 1403，零售版主机会停在搜索界面：它发送自己的 1400 和 1403，却始终不发送 0100。`pokeldn.za.reference.sync_message` 为实际发送的身份数据构建 1403。

### 交换命令

交换会话初始化函数 `0xca2928` 在会话命令通道（session+0xc8）上订阅五种命令类型（名称取自 ctti 字符串）。ID 为 `0x100 | index`，即该类型在通道 +0x60 列表中的位置（`0x96129c`，一次 `strcmp` 遍历）。每个载荷都是一个 `b9` 结构体，以 u16 轮次开头。

| ID | 命令 | 处理器 | 处理器读取的载荷 | 处理器操作 |
| --- | --- | --- | --- | --- |
| `0100` | CommandReady | `0x2dc4c7c` | 轮次、1200 字节 | 将 1200 字节复制到 session+0x604，设置 session+0xf0 |
| `0101` | CommandSelectPokemon | `0xb2a44c` | 轮次、344 字节记录、一个字节 | 加载记录（参见“提供的宝可梦”）；若该字节的位 0 未置位，则表示选取 |
| `0102` | CommandConfirmTrade | `0xc8dda0` | 轮次 | 若 session+0x152 大于该轮次则忽略；否则将对方状态 +0x134 设为 4 |
| `0103` | CommandCancelTrade | `0x2dc51ac` | 轮次、u32 原因 | +0xab4 = 将原因中的 1 与 2 对调，其他原因设为 0；+0x152 = 轮次；+0x150 += 1；随后 `0x2dc41f8` |
| `0104` | CommandFinalAgreement | `0x2dc52b4` | 轮次 | 若 +0x152 大于该轮次，或自身状态 +0x130 不是 4 或 5，则忽略；否则将对方状态设为 5 |

取消发送函数 `0x964a60` 在自身状态 +0x130 为 2 或 5 时不发送任何消息；否则发送轮次 +0x150 + 1，设置 +0x130 = 2，推进 +0x150 和 +0x152，并将对方状态从 3..5 降至 2（原因为 0 时降至 3）。处理器仅拒绝严格小于 +0x152 的轮次，因此取消后过期的 ConfirmTrade 或 FinalAgreement 会被忽略，更高轮次则会接受。SelectPokemon 不读取轮次。

会话对象（0xab8 字节；`0xca2658`，由 `0xca2704` 构建，虚表 `0x3e3a6e8`）在 +0x40 保存配置（u16 0x201，低字节为通道），在 +0x48 和 +0x88 保存可调用对象，并将 +0x150..+0xab7 清零，因此两个轮次都从 0 开始，会话的首个 `0102` 和 `0104` 为 `b90100`. `0x964568`（自身状态 6；调用者 `0x9601dc`，位于实际交换路径 `0x95f8f4`）清除自身提议 +0x120 和对方 PokemonParam +0x128，将双方状态设为 2，清除 +0x118、+0x11a、+0xd0，并将 +0x150/+0x152 清零：同一席位的下一次交换从轮次 0 开始，而仍为轮次 1 的回应也会被接受。`pokeldn.za.host` 在每次交换时重置轮次。

| 自身状态 | 写入者 | 时机 |
| --- | --- | --- |
| 5 | 会话更新 `0x95f600` (`0x95f680`) | 自身状态为 3 或 4，字节 +0x148 已置位，定时器 +0x138 至少经过 1.5 秒，对方状态为 4 或 5，`0x963710` 为真 |
| 6 | 委托调用 `0xdfda8c`，填充于 `0x964e78` | 交换工作器的状态 6 委托 |
| 7 | `0x2dc4b94`，安装函数为 `0x964f0c` | 交换工作器的状态 7 委托；在 2.0.2 中不可达 |

`0x9610a4`（调用者 `0x95fdbc`）在自身状态至少为 5，且 +0xd0 处的工作器不存在，或其 +9 为 0 或 0x10 时运行：它以（+0x118、+0x120、+0x128）调用 session+0x48 处的可调用对象，构建交换工作器（`0x966af0`，0xb0 字节）存入 +0xd0，并向其提供状态 6 和状态 7 委托（`0x9649e0`, `0x964a20`），由 `0x9655a4` 存入 worker+0x20 和 +0x60。交换对象由 `0xc8ad1c` (`adr` 在 `0xca2578` 构建；构造函数 `0xc8ae70`，虚表 `0x3d8a0d0`：+0x68 为 `0xdd07cc`，+0x78 为 `0x2a67168`，+0x80 为 `0xcbc68c`）；将它写为 session+0x48 处可调用对象的操作尚未追踪。

### 踢出

若某站点自身的可变 ID 连续 10 秒未作为任何数据包的源，主机端就会将其踢出，不论玩家界面处于何处：发往该站点的 RTT 停止，并每 501 毫秒重复发送 Session 类型 13（0x0d、其八字节大端序固定 ID，总长十字节，原因字节为 1），消息组装位置为 `0x2551320`，位于 `0x25512b4` 中；其两个调用者 `0x255bad4` 和 `0x255bd70` 位于 `nn::pia::session::KickoutManageJob` (`vfunc6` `0x255bda0`）。0x0001 只能作为目标；加入端若以它为源发送，不会被任何一方接收。捕获中，踢出发生在占位后 18 至 25 秒。

### 保活

配置项 +0x290 是以毫秒计的发送静默时限（`0x257d12c` -> `0x256a238`；负数以 0x10407 失败，0 变为 1000）。`SessionPacketWriter`（虚表 `0x3c8da30`）的虚函数 7 `0x2544004` 调用 `0x256a2d0`，传入每次发送的站点掩码（`0x2568924`）：所有其他状态为 2、ID 不超过 0x17 且字节 +0xa0 未置位的站点（`0x25770d8`），在向其发送时记录 +0xb0；若 +0xb0 距今超过时限，则标记该站点（从未发送过的也包括在内）。被标记站点（`0x2568928`）会收到一个额外数据包（`0x256a89c(p, 0, 0)`）：其中只有一条 Pia 消息，协议 0、位 0x10 对应字节为 0xfd、端口 0、标志 0、载荷为空。因此，只要一秒内未向某个已占位站点发送任何内容，就会向其发包；目前尚未用捕获数据核对此行为。该消息的包头包含存在标志字节 `04` 和协议 `00`：写入函数 `0x256dccc` 仅输出与全新包头不同的字段（协议 0xFF、中间字节 0xFD、端口 0）。接收读取器按消息键（协议、中间字节、端口）将消息放入桶表，不检查协议（`0x2566844`, `0x25670f0`）；没有 Protocol 类的 ID 为 0，因此没有协议读取它。每个协议仅遍历自身键的链（Reliable `0x256fed0` 不移除任何内容）。PacketReader 虚函数 6 `0x2565ce0` 首先调用 `0x2566030` (`0x2565d34`，它是后者的唯一调用者）；后者将每个桶的所有节点解除链接，归还到池的空闲链表，并清零桶，因此未读取消息会在下一轮接收开始时回收，协议 0 消息不会累积。节点池满时（`0x10c10`）会丢弃数据包剩余内容。字节 +0xa0 标记正在被踢出的站点，仅由 `0x2577094` 设置，来源为 `0x255b4a0` 以及非主机端的清退路径 `0x2548b60`.

### 数据包 ID

每个发送端使用两个数据包 ID 计数器：一个用于目标 0x0001，另一个用于所有其他目标（0 和主机端可变 ID 共用它）。`nn::pia::session::SessionPacketReader::vfunc11` `0x2566920` 在所有协议处理之前检查：源未知或没有站点时接受；否则根据目标选择控制器（0x0001 使用 station+0x78，其他使用 station+0x50），然后 `0x2576ad0` 检查数据包 ID（线上偏移 0x0a）和大端序 nonce（线上偏移 0x0d）：

```
id == 0                                         accept, nothing recorded
last id == 0                                    last id = id - 1
last nonce == 0 and nonce != 0                  last nonce = nonce - 1
(s16)(id - last id) < 1                         reject
nonce != 0 and (s64)(nonce - last nonce) < 1    reject
otherwise                                       last id = id, last nonce = nonce if non-zero
```

被拒绝的数据包进入 `0x25655d8` 并被丢弃：包括重复 ID，或超前 0x8000 及以上的 ID。若加入端为目标 0 使用独立计数器，其所有 Net 0x51 都会被丢弃，直到计数超过主机端 ID 对应的计数器；主机端持续重发 Net 0x50，直到有一个通过（实测约 10 秒），其更新序列 1 也因此延迟。Net 0x51 处理器 `0x2504100` 不读取任何包头字段：它先反序列化（`0x250f930`），检查长度和类型 0x51（`0x2504150`），将来源与各站点匹配（`0x250c60c`, `0x24fba00`），再将站点及消息 +4 处已确认序列号传入 `0x250daa8`.

### 协议 10 上的交换

在选择记录之后，双方各发送一条 354 字节的 `0101`（实测约在 2.5 秒后）。提议最后一个字节在站点主动发送的预览中为 1（零售版主机每次在交换盒子中移动光标都会发送一条），在玩家选取时为 0；主机端根据该字节而不是计数判断。若选取消息以 1 发送，会获确认却不显示任何内容，对方会在“正在通信”界面等待，槽位为空。

加入端以自身选取回应主机端的选取，并用 `0102b90100` 确认；主机端用相同消息确认，双方均发送 `0104b90100`（主机端在加入端的 `0102` 后 1.5 秒发送），加入端再发送四个 `0200b901XX` 步骤：03 和 06 立即发送，0b 和 0e 在交换动画及工作器随机等待后发送（[交换命令](#the-trade-commands)）。主机端在协议 11 上发送 `0000000202`，并以 `0201b901XX` 回应每个步骤，附在自身前缀之后。`bin/za_join.py --trade-offer` 运行加入端。

## 与零售版主机交换

处于连接交换搜索中的零售版 Z-A 可与 `bin/za_join.py` 交换并保留构造的记录。交换后，主机在同一席位上返回交换盒子，并可再次交换：`0x964568` 将双方状态重置为 2，双方轮次重置为 0（[交换命令](#the-trade-commands)).

加入端接受重复的 `--trade-offer`：其第四个步骤之后 2.7 秒预览下一条记录，并在主机下一次选取时，以轮次 0 选取该记录。`bin/za_join.py` 和 `bin/za_host.py` 通过 ldn_mitm 按顺序交换记录队列（`tests/test_za_host.py` 以脚本驱动加入端一侧）；加入端已与零售版 Z-A 主机端在同一席位上交换了两条排队记录。

主机的交换动画在其第四个步骤之后运行，不携带交换命令。零售版 Z-A 加入 `bin/za_host.py` 时，从第四个步骤算起：动画在 1.1 秒时开始，收到的宝可梦约在 26 秒时出现（手动按键，可能晚至 2 秒），主机的下一条预览（`01 01`，354 字节）在 30.2 秒到达，玩家约在 31.7 秒恢复操作。期间主机不发送任何协议 10 消息。若席位在主机的主机端阶段后期才形成，就会触发交接：首个数据报较晚出现，之后没有更新序列 1，主机每秒重复 Session 类型 9（按 wiki 编号为开始主机端迁移；该编号将踢出列为 12，而 Z-A 使用 13），直到重新启动 Net（实测首个数据报在关联后 1.4 秒出现，正常席位则小于 0.1 秒；Net 在 6.5 秒时重启）。零售版朱在真实硬件上的搜索也表现相同；两侧代码均尚未追踪。

`0x961c80` 在字节 `0x3f9bf6a` 为 1 且 `nn::nifm::IsNetworkAvailable` 返回真时为真。

级别对战的匹配运行在第三种驱动器上。其页面更新 `0x2cc1d18` 在 +0x40 保存状态（跳转表 `0x33a2268`，70 个状态）；状态 0x31 调用“BattleRandom”请求 `0x2a48bf8` (`0x2cc287c`），该请求通过 `0xc8a224` (`ldr x0, [x0, #0x38]` 到达槽位 13，然后 `br` 到槽位 `+0x68`，即管理器当前驱动器）。在运行 0x2f 至 0x34 或 0x43 至 0x45 中的任何状态之前，更新函数读取 `0x6133018` (`0x2cc1e14`）：值为 1，或 `0x961c80` 为假时，将页面转到状态 4；值不为 3 时也相同（`0x2cc4760`）。状态 10 至 0x2f 及 0x3b 至 0x3e 同样要求值为 3，否则进入 `0x2cc5b5c` 和状态 6（`0x2cc1d58`）。值 3 表示最后提交的序列安装了模式 2 驱动器。第三种驱动器的槽位 13（`0x191fd30`）根据 `gflnet::npln` 的结果构建 StartupSession、JoinRandomSession、WaitMember、JoinRandomRecover 和 RandomMatchingCancel 步骤。没有在线服务的模拟主机会在匹配前从级别对战返回菜单。

没有调用以模式 3 构建该任务，因此 2.0.2 中永远不会安装 LAN 驱动器。在模拟主机上，于游戏第一条指令执行前设置断点后，经过启动、野外、连接游玩页面、连接交换页面及连接密码提示时，都未到达设置函数。确认密码 00000000 后，以模式 0 进入设置函数（返回地址 `0x1912240`），0.6 秒后从 `0x191213c` 以模式 1 再次进入并构建本地驱动器（`0x199eaa0`），再过 1.0 秒，本地驱动器槽位 13 运行（`x2` 2, `x3` 为 1），此时没有任何站点；加入端在四分钟后才启动。断点命中后若等 0.3 秒才重新设置，会错过第二次调用。

零售版主机连接交换搜索中，占位时广播策略为 0、节点数为 2 / 2，Pia 玩家数（广播数据 +0x16，`e1 01 01 00` 变为 `e1 01 02 00`，唯一发生变化的字节）变为 2；随后在主机那一条 Net 0x50（150 字节、序列号 1、接受状态 `02`）之前立即广播策略 1，并在已占位会话期间保持策略 1。此前没有主机端迁移，因此零售版的 `02` 来自 CloseParticipation，由槽位 13 步骤 `0x19d7a70` 启动，这是连接交换代码在本地驱动器上唯一能到达的构建函数。对加入端板解密的四个已占位会话实测：玩家数在 0.07 至 0.59 秒变为 2，策略 1 首次广播比 0.09 至 0.64 秒时的 Net 0x50 早 2 至 48 毫秒。参与者已满 2 / 2 时，该策略不会拒绝任何容量限制之外的连接。

## 离开

站点通过两种 `nn::pia::session` 任务之一离开，每种都等待另一站点回复。分派器 `0x2547490` 读取的 Session 类型如下（表 `0x336a9b7`，类型 0 至 17）：

| 类型 | 大小 | 发送端 | 消息 |
| --- | --- | --- | --- |
| 3 | 22 | 离开的加入端 | 离开请求：类型、随机 u32、自身固定 ID（8 字节，大端序）、自身可变 ID（2 字节）、地址类型 0、自身 IPv4、端口 |
| 4 | 15 | 主机端 | 离开响应：类型、随机 u32、从请求复制的离开者固定 ID 与可变 ID |
| 9 | 30 | 离开的主机端 | 开始主机端迁移：类型、主机端固定 ID 与可变 ID、0、主机端 IPv4 与端口、下一任主机端的固定 ID 与可变 ID，`00 01` |
| 10 | 21 | 类型 9 指定的站点 | 其确认消息：类型、自身固定 ID 与可变 ID，然后是主机端的固定 ID 与可变 ID |

`pokeldn.za` 构建全部四种消息（`build_leave_request`, `build_leave_response`, `build_migration_ack`).

### 加入端离开

`LeaveMeshJob::SendLeaveRequest` (`0x2557e54`）向主机端发送类型 3，并设置 500 毫秒期限；`WaitLeaveResponse` (`0x2558098`）在收到类型 4 时完成，并在每次到期时重发，总共发送四次（计数器 +0x9c，`cmp w8, #2; b.gt` 位于 `0x25581e0`），之后即使未收到回应也完成。类型 4 由 `0x25474f8` 接收，仅接受 15 字节且第 5 至 14 字节为站点自身 ID（+0x1b8、+0x1c0）的消息；它设置任务字节 +0x99。主机端的类型 3 处理器 `0x254c5ac`（22 或 34 字节，仅主机端）在 `0x254c740` 写入类型 4，并移除站点（`0x2548500`).

加入到不发送类型 4 的主机端时，零售版 Z-A 会发送四条类型 3，间隔约 0.5 秒，并在首条之后 2.0 秒解除认证（三次离开分别为 1.99、2.02 和 2.03 秒）。`bin/za_host.py` 对每条类型 3 都以类型 4 回应；`bin/za_join.py` 在因 `--hold` 或 `--hold-after-trade` 离开时发送自身类型 3，并在收到类型 4 或第四次发送后离开。

### 主机端离开

`LeaveMeshWithHostMigrationJob` 指定下一任主机端（`CalcNextHost` `0x255a6fc`），随后 `SendStartHostMigrationMessage` (`0x255a91c`）每秒发送一次类型 9，直到 5000 毫秒期限（`0x255a8c8`），之后任务以 `0x6c0e`. `WaitStartHostMigrationAck` (`0x255abb4`）失败；字节 +0xe0 一旦置位便完成。类型 10 读取器 `0x2550a64` 仅在主机端接受 21 字节消息，要求第 11 至 20 字节是主机端自身 ID；当第 1 至 10 字节是指定的下一任主机端 ID 时，通过 `0x255a630` 设置 +0xe0。

类型 9 未获回应时，主持交换的零售版 Z-A 在玩家退出后发送五条类型 9，间隔一秒；然后从源 0 每 0.5 秒发送序列号 3 的 Net 0x11，持续约 4 秒；再发送 Net 0x40 约 2 秒；在首个类型 9 后 10.82 至 10.86 秒停止发送（四次离开）；其中一次在板上追踪到网络于 11.26 秒后关闭。在模拟主机对中，加入端在收到类型 9 后 48 毫秒用类型 10 回应，主机端发送序列号 3 的 Net 0x11，加入端回应 `0112000000000003`；主机端网络在类型 9 后 0.25 秒消失。加入端的类型 10 和 0x12 使用包头标志 2、目标 0、数据包 ID 0，且无包尾。

若立即发送类型 10 和 0x12，零售版主机端会在类型 9 后 0.04 秒发送 0x11，随后每 0.3 秒发送 Net 0x40（`01 40 00 00`，源 0），持续 4.06 秒，期间加入端仍停留在网络中；不会出现第二条类型 9。

Net 0x11 是离开主机端在 `NetDestroyNetworkJob` (`0x2516444` 的迁移形式中发送的连接状态，标志位于 job+0xd8，当断开站点是主机端时置位，`0x2503c44`): `0x2501930` 推进序列号（NetProtocol+0x15c）；当 NetHostMigration 状态 NetProtocol+0x12d0 为 1 时，第 29 字节，即正在迁移字节，为 1（`0x250f084`）。它要求每个客户端回应该序列号的 Net 0x12；客户端保存序列号、设置 NetProtocol+0x308 并回应（`0x2503164`, `0x25035c0`）。主机端最多等待 4000 毫秒收齐所有 0x12，然后每 300 毫秒发送 0x40，持续 4000 毫秒，若此前等待超时则持续 2000 毫秒，直至仅剩自身，最后销毁网络（`0x251693c`, `0x25169f8`).

迁移形式与开场 0x11 有三处不同：序列号、第 26 字节（开场为 1，迁移为 2，含义尚未解析）和第 29 字节。零售版和模拟主机端均以源 0、目标 0、数据包 ID 0、包头标志 `0x3`（正在建立、已压缩）发送，无包尾；0x40 以相同方式发送，但标志为 2。类型 9 从主机端可变 ID 发往指定站点可变 ID，带包尾。

0x40 启动下一任主机端的工作：`0x2503d44` 在非主机端站点上调用 NetHostMigration 启动函数 `0x25099a4`，后者选定下一任主机端（`0x2505d10`）并运行 `NetHostMigrationJob` (`0x2509da0`）。在 LDN 上，它离开旧网络（`0x2503b14`）；下一任主机端开启网络（`0x2507050`）并等待其余客户端 6000 毫秒，未返回者会被移除（`0x250acf0`）；客户端等待 1000 毫秒后重新连接。成功会清除 NetProtocol+0x12d0，并在 NetProtocol+0x12d4 保存结果 1 或 2（主机端）或 3（客户端）；失败则保存 4，错误为 `0xc406`.

连接交换在交接时结束。类型 9 处理器 `0x2550684` 移除离开主机端的站点（`0x2548500`），然后才启动 `ProcessHostMigrationJob`，从而减少会话站点数（session+0x110）。交换场景更新函数 `0x95f398` 仅在该数量大于 1 时运行交换（`0x95f45c`），否则以原因 3 结束（`0x95f508`），对方的离开请求也会到达这一结束路径。在双站点交换中，离开者是唯一的交换对象，因此不论迁移结果如何，交换都会结束，离开的主机会销毁自身网络。

在两台模拟 Z-A 2.0.2 主机上实测（Ryujinx，LDN 经回环接口），双方停在交换盒子时，主机端玩家退出（B，然后“是”）：另一站点收到指定自身的 30 字节类型 9，以类型 10 回应；收到第 29 字节置位、序列号为 3 的 Net 0x11，以 0x12 回应；在类型 9 后 0.12 秒收到 0x40。它在 0x40 后 4 毫秒离开网络，再过 0.24 秒结束 LDN 服务，未创建网络。画面显示“交换对象选择退出交换。连接交换即将结束。”，按 A 返回连接游玩菜单。两次运行结果一致。

在首个 0x40 到来时离开，加入端会在类型 9 后 0.09 秒退出网络（未交换，玩家从盒子退出）。

`bin/za_join.py` 对指定自身的类型 9 用类型 10 回应，对随后的 Net 0x11 用 0x12 回应，并在首个 Net 0x40 到来时离开网络（或主机持续静默一秒后离开）。

`pokeldn.za.host.HostSession.leave` 运行相同的离开流程：类型 9（`build_start_migration`）每秒发送一次，直到收到类型 10 或经过 5 秒；迁移 0x11 每 0.5 秒发送一次，直到收到对应序列号的 0x12 或经过 4 秒；然后每 0.3 秒发送 0x40，持续 4 秒（始终未收到 0x12 时为 2 秒），或直到主机离开网络。未获任何回应时，在首个类型 9 后 11 秒结束。`tests/test_za_host.py` 将其与 `bin/za_join.py` 对测，并将类型 9 和两种 Net 消息与模拟主机对的字节核对固定。
