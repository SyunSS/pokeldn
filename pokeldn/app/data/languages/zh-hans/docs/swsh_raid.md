# 极巨团体战

本地极巨团体战是在 LDN 场景 60006 上运行、最多包含四个站点的《剑／盾》会话。主机端从巢穴选择“邀请其他人”开启会话；加入端在 YY 通讯列表中找到它，在主机端名字上选择“开始对战”加入。大厅运行于可靠广播协议 0x80，对战运行于 0x7C。`bin/swsh_connect.py --scene 60006 --raid-join --offer-slot N` 在主机的大厅中以加入端身份入座；大厅会显示它以及所选宝可梦。

## 网络

| 字段 | 值 |
| --- | --- |
| LDN 场景 id | 60006（野外场景中为 65535） |
| 参与者 | 刚开启时为 1／4 |
| 广播数据字节 `0x97` | `0x11` |
| Pia 会话最大值 | 4 (`0x0110e5e0`，在巢穴大厅中的以下位置调用：`0x01031c74`) |
| 广播 `0xb0` 和 `0xd4` | 首领与巢穴记录（[巢穴记录](#the-den-record)) |

巢穴大厅代码位于 `View_NestHole`, `StateGuestReady` 和 `StateHostReady` (`0x0102aba4..0x010370cc`）之间。极巨大冒险通过 `ChikaMatchingState*` (`0x00bd1978..0x00bda158`）进行匹配，后者从以下位置调用相同的 Pia 会话最大值设置函数：`0x00bd9b30`.

如果团体战广播携带加入端自身的设备 id 和账户 uid，加入端的 YY 通讯列表就会将其排除（[巢穴记录](#the-den-record)).

## 大厅消息

每条大厅消息的 id 都是 2000，`net_contents.nesthole.protocol_buffers.NestholeAsyncDataHolder`（描述符位于 `0x1bfde43` 和 `0x20677b0`，所在位置为 `main`）。每个字段都是一个持有器，其中只有一个 `bytes` 类型的字段 1。

| 字段 | 名称 | 大小 | 内容 |
| --- | --- | --- | --- |
| 1 | NestholeTimeLimit | 4 | u32 剩余秒数；主机端每秒发送三次 |
| 2 | NestholePlayerInfo | 40 | 8 个零字节、u32（零售版《剑》为 0x11，模拟运行的《盾》为 0x12）、13 个字符的 UTF-16 名字、`00 03` |
| 3 | NestholeBattleReady | 16 | 玩家按下准备后字节 8 为 1；对战开始后字节 12 为 1 |
| 4 | NestholeSelectPokemon | 352 | 8 个零字节，随后是所选宝可梦的加密同行队伍格式 PK8（0x158） |
| 5 | NestholeBattleStart | 32 | 参与者的 Pia 常量 id，四个 u64，主机端排第一，未使用的槽位为零 |
| 6 | NestholeBossPokemon | 364 | 19 个零字节和 `ff`，随后是首领的加密同行队伍格式 PK8 |
| 7 | NestholeRewards | 120 | 十五组 u32 对：道具 id、数量；未使用的配对为零 |
| 8 | NestholeBattleSeed | 16 | u64 种子，随后为 `00 ff ff ff 1e 00 03 00` |

PlayerInfo 使用 4 KB 窗口的 zlib 压缩发送（头部 `48 4b`），可靠标志为 0x10；其他消息不压缩。`pokeldn/swsh/raid.py` 构建所有字段；其输出与模拟运行的加入端（2、3、4）及主机端（5 至 8）的字节一致。

首领记录完整携带首领数据：种类、等级、招式、个体值和 PID。在两场模拟团体战中，将巢穴的团体战生成器应用于 BattleSeed 值，既得不到首领的加密常量，也得不到其 PID。该种子的用途尚未读明。

## 对战

主机端运行对战；加入端在 0x7C 上响应。`pokeldn/swsh/raid_battle.py` 是加入端实现，根据模拟《盾》加入端构建；`bin/swsh_connect.py --raid-join` 使用它作为模拟主机端的加入端，完整进行并赢得了一场团体战。

对战之前，从加入网状网络开始，加入端运行 SyncClockProtocol 0x1C（每秒一个请求），并发送一次 ClockProtocol 0x77 请求（`00` x16，然后为 `00 6f`），两者的目标位图均为 1。

| 端口 | 消息 | 加入端行为 |
| --- | --- | --- |
| 0 | 同步 80：ping、pingReply、pingSynced | 收到 ping 后回复 ping 和 pingReply，收到 pingSynced 后回复 pingSynced |
| 1 | 40000，内容 0 的框架：字段 2 为基值（10000 或 20000，为 0 时省略），3 为站点常量 id，4 为时钟，5 为消息体 | 发送自身的 pingSynced 后，发送三组 base-10000／base-20000 配对（消息体 `00000000`, `000018fc`），随后以自身站点 id 镜像主机端的每个 base-20000 消息体 |
| 0 | 10000，字段 3 {1 站点, 2 槽位, 3 版本} | 主机端列出自身座位后发送（基值 0，16 字节消息体：常量 id、槽位、版本字节 0x6e） |
| 0 | 10000，字段 1 为空 | 在主机端的 base-8 消息（24 字节消息体，对战种子）之后发送 |
| 0 | 20000，字段 1 {1 发送者, 2 槽位, 3 计数器, 4 数据} | 响应主机端的每条命令 |
| 0 | 20000，字段 3 {1 状态, 2 槽位} | 在行动前发送 {1: 2, 2: slot} |

主机端命令的数据以四个 u16 开头：序号、类型、长度、标签。加入端响应相同的序号、类型和标签，长度为 4，并带四个零字节，以下情况除外：

| 类型 | 加入端发送内容 |
| --- | --- |
| 0x02 | 先发状态消息，再发行动：序号、0x02、0x58、标签，随后 88 字节 |
| 0x21 | 结束：发送者 1，数据 `0000 1e00 0000 2f00` |

从主机端观察到的类型：0x01、0x0d、0x07（123 字节）、0x0e、0x02、0x10（47 字节）、0x09（本回合日志，zlib，0.4 至 2.4 KB）、0x04；加入端宝可梦倒下后有 0x11 和 0x0a，结束时有 0x21。

### 哪个站点充当服务器

服务器是 ServerVersion 记录在各主机维护的表中胜出的站点；Pia 主机端检查（`0x110e620`，对战或大厅代码中没有调用方）和 BattleStart 中的顺序都不直接决定它。

ServerVersion 是 `btl.net.protocol_buffers.BtlDataHolder`（id 10000）的字段 3：站点 id u64、客户端 id u32、版本 u32。每份游戏都发送版本 `0x6e` (`0x8b1778`）。主机维护八个 {站点, 客户端 id, 版本, 有效标志} 槽位（对战网络对象 `+0x190 + 16 * i`); `0x8b4030` 获取第一个有效且版本等于已知最高版本的槽位的客户端 id，`0x8b1990`（IsServer）将它与主机自身客户端 id 比较。收集站点将记录放入发送者 Pia 站点索引对应的槽位（`0x8b4440`, `0x6b5850`）；其他各主机以 40000 框架对象 0 至 7 的形式接收槽位，对象编号位于字段 2。在记录的团体战中，主机端发布对象 0（自身记录，客户端 id 0）和对象 1（加入端记录，客户端 id 1）。

主机的客户端 id 是它在 BattleStart 大厅成员中的位置（`0x1025120`, `0x10253bc`）。移除站点会清空其槽位并重新选择（`0x8b3f70`），且每台主机都持有一个备用服务器，在 IsServer 变为 true 时将其提升为活动服务器（`0x7f838c`, `0x7f87f0`).

### 行动

88 字节的行动由十一个 8 字节条目组成。同一加入端的四个招式之间，只有条目 2 发生变化：以小端序 u24 表示时，它为 `move id << 13 | target << 8 | 0xc1`.

| 招式 | 条目 2 | 目标 |
| --- | --- | --- |
| 拍击（1） | `c1 28 00` | 8 |
| 绑紧（20） | `c1 88 02` | 8 |
| 叫声（45） | `c1 a2 05` | 2 |
| 水枪（55） | `c1 e8 06` | 8 |

叫声命中所有对手，携带目标 2；单目标招式携带 8。加入端无法行动的回合将条目 2 发送为零。`raid_battle.action(move, target)` 构建它；`--raid-move N` 选择加入端宝可梦的招式槽位。

0x7C 确认携带 32 个槽位；只有槽位 0 跟踪加入端的数据流，其他槽位保存过时 id（观察到 34460）。如果使用各槽位最大值来决定重发，就永远不会重发。

## 巢穴记录

巢穴主机端的广播描述其团体战；加入端的 YY 通讯条目构建器（`0x00fa1560`）读取它。

| 偏移 | 内容 |
| --- | --- |
| `0x5F` 位 1 | 主机端的版本：未置位为《剑》，置位为《盾》 |
| `0xAF` | 活动种类：`0x11` 对应星级 0，`0x13 + 2 (rank - 1)` 对应更高星级；`0xFF` 从不列出 |
| `0xB0` | 显示的首领：u16 中包含种类（位 0 至 9）和形态（10 至 15），一个字节的位 4 和 5 表示 1 为普通、2 为超极巨化，随后是 u32 加密常量 |
| `0xD4` | 巢穴记录，相同的八字节布局 |
| `0xDC` | 高半字节：星级，0 至 4 |
| `0xDD` | 位 3 至 5：巢穴种类，0 表示普通巢穴 |
| `0xDE`, `0xE0` | u16 遭遇表，按主机端版本的表编号，以及 u16 槽位 |
| `0xE6` 至 `0xED` | 以下位置中文件 8、6、7 和 9 的 CRC16：`bin/archive/field/resident/data_table.gfpak` |

当 `0xD4` 处的种类非零时，加入端只有在自身表的 CRC 匹配、巢穴种类为 0，且主机端版本的表 `0xDE` 的槽位 `0xE0` 包含该种类、形态和超极巨化标志时才列出团体战（`0x00ea5160`, `0x00ea51d0`）。种类为 0 会跳过这些检查。当 `0x02510b2c` 处的字节为 1 或 2，且主机端不是好友时，星级不得超过加入端根据徽章数确定的自身等级。位于 `0xB0` 的记录仅检查数值范围。`pokeldn/swsh/data/nest_slots.json` 保存 1.3.2 的槽位（`scripts/gen_swsh_nest_data.py`); `raid.den_advert` 将巢穴记录指向包含该首领的槽位，或将其清零。

如果站点的设备 id 和账户 uid（`0x1F` 至 `0x3E`）均等于加入端自身值，则加入端会丢弃该站点（`0x0111b160`).

### 首领记录

加入端在发送表示已开始的 BattleReady 之前检查 BossPokemon 和 Rewards（`0x01030d14`，状态 10）；检查失败时以 2-ALZAA-0016 退出。

| 检查项 | 代码 | 通过条件 |
| --- | --- | --- |
| 首领 | `0x01032270` | 种类、形态和同行队伍的 `+0x156`（1 为普通，2 为超极巨化）等于巢穴记录指定条目的值：种类 0 使用所广播版本的基础表 `0xDE`，槽位 `0xE0`；种类 1 至 3 使用加入端自身保存的活动遭遇，槽位 `0xE0`；种类 4 使用其保存的结晶遭遇 |
| 奖励 | `0x01032570` | 每组同时具有道具和数量的配对，要么是该槽位额外奖励表中的一行，且数量恰好等于所广播星级的数量；要么是掉落表中在该星级有概率掉落的道具（数量不限） |

不会比较等级、招式、个体值、PID、特性、异色和训练家字段。全零巢穴记录表示种类 0、表 0、槽位 0（无畏小子）。基础巢穴不包含传说或幻之宝可梦，因此托管的首领必须是 `nest_slots.json` 所列出的种类、形态和超极巨化状态之一；`raid.den_advert` 在只有另一版本包含该首领时切换广播版本；活动首领则以包含其种类、形态和超极巨化状态的基础巢穴槽位显示。`raid.reward_choices` 列出该槽位在某星级允许的内容（每种额外奖励道具使用规定数量，每种掉落道具数量不限）；`raid.den_rewards` 据此构建该槽位自身的奖励行。

在以下情况中，零售版《剑》加入端会在处理 BossPokemon 时以 2-ALZAA-0016 退出：首领采用交换记录（含训练家、版本、相遇数据和精灵球），其同行队伍极巨化类型（`+0x156`）为 0，或广播的巢穴记录为零（基础巢穴均不包含的首领：在已接受记录上的梦幻，或者活动超极巨化颤弦蝾螈，无论是否设置超极巨化位）；尽管这些团体战都会被列出。记录的两个巢穴首领均不含训练家数据，极巨化类型为 1。只更改种类的巢穴首领记录，以及由 `raid.boss_record` 构建的等级 20 首领（在巢穴首领记录上设置宝可梦的种类、形态、招式、个体值、基础点数、性格、特性、PID、加密常量和同行队伍能力值），都被接受。

记录的三个巢穴首领（模拟运行的极巨化等级 1 豆豆鸽和等级 2 咕咕，以及零售版主机的等级 7 煤炭龟）中，同行队伍 HP 能力值和当前 HP 等于普通 HP 能力值乘以 `(150 + 5 * Dynamax level) / 100`，向下取整；其余五项能力值不变。极巨化等级位于 `+0x90`，特性槽位位于 `+0x16` 的位 0 至 2，经验值为该等级的最低值。

## 作为主机端

`bin/swsh_host.py --raid-boss PK8 --raid-console-serves` 托管一个巢穴大厅，主机从 YY 通讯列表加入（`pokeldn/swsh/raid_host.py`）。广播和快照来自模拟《盾》的巢穴主机端，已重命名并移除账户 id（`pokeldn/swsh/data/raid_advert.bin`, `raid_snapshot.bin`; `--advert` 和 `--snapshot` 将其替换）。广播发送时包含新的站点资料、开发板名称、首领以及对应巢穴记录（[巢穴记录](#the-den-record)); `--raid-boss` 接受任意 PK8，并通过 `raid.boss_record` 发送。快照在加入端快照之前发送。`--raid-reward ITEM:COUNT` 填充 Rewards，`--raid-seed` 填充 BattleSeed。如果某个 `--raid-reward` 奖励行不属于所广播巢穴槽位在该星级提供的内容，主机端会拒绝它，并打印该槽位实际提供的内容；不符合条件的活动奖励行会被排除。

应用的“极巨团体战（主机端）”工具使用这些标志运行，并提供首领（或旷野地带活动及其中一个基础巢穴包含的首领，`raid_event.hostable`）、我方宝可梦以及最多 15 行奖励；不提供奖励行时，主机端发放该巢穴槽位自身的奖励。奖励编辑器仅提供所选首领广播所用巢穴槽位中的道具（`raid.boss_den`, `pokeldn.app.raid_rewards.swsh_den`），固定额外奖励道具的数量，并在首领变化时同步更新；如果基础巢穴不包含该首领，则保持为空。通过应用运行，使用等级 20 的毛辫羊首领，将“此巢穴的全部奖励”模板设为 7，零售版《剑》赢得团体战并收到全部十行奖励：经验糖果 XS x5、经验糖果 S x1 和极巨糖果 x1（额外奖励行），以及七种各 7 个的掉落道具。

使用 `--raid-console-serves` 时，加入的主机充当对战服务器，主机端以客户端 1 身份响应（`raid_battle.Master`):

| 步骤 | 主机端行为 |
| --- | --- |
| BattleStart | 首先列出加入的主机，因此该主机的客户端 id 为 0 |
| 0x7C 端口 0 | 发送 ping；响应主机的 ping 和 pingSynced |
| 框架对象 | 发布对象 0 = 主机的 ServerVersion 记录，对象 1 = 自身记录 |
| 0x7C 端口 0 | 发送自身的 ServerVersion（客户端 id 1） |
| 基值 20000 | 发布计数器和自身消息体：0000 / 00000100，然后 0100 / 01000100、01000200、0200 / 02000200；每一步都在主机镜像上一个消息体后执行 |
| 对象 8 | 由主机发布（24 字节，一个种子）；主机端回复 EmptyCommand（10000 字段 1） |
| 对战命令 | 按加入端的方式响应，行动指定主机端宝可梦的第一个招式 |

模拟《盾》加入端和零售版《剑》都曾以此方式担任服务器，完成并赢得一场团体战，收到主机端的 Rewards，随后发送网状网络离开请求。

### 多台主机

最多三台主机共享一个托管大厅（`raid_host.RaidParty`）。所有已加入的主机均按下准备后，主机端开始对战；BattleStart 先按加入顺序列出各主机，最后列出主机端。第一台主机担任服务器。主机端将框架对象 k 发布为主机 k 的 ServerVersion 记录，最后发布自身记录；每当所有主机均镜像其消息体后，推进 base-20000 屏障。

| 层 | 第二台主机需要 Pia 主机端提供的内容 |
| --- | --- |
| 本地协议 | 会话更新必须送达；使用回环时，每个站点都获得独立副本 |
| 网状网络加入响应 | 字节 8，即活动站点最大值，必须大于已入座站点数：为 2 时，第一个加入端以结果 1 响应第二个加入端的连接请求，后者显示错误 2618-0502 |
| 0x84 | 在发送者数据流对应端口上确认；站点的数据流使用其站点索引对应端口（主机端 0，第一个加入端 1，第二个 2），未确认的数据流会无休止重复 |

各加入端直接相互连接：发送站点连接请求，在 0x84 上交换各自快照，并在 0x80 上发送同时面向主机端和另一个加入端的大厅消息。两个模拟《盾》加入端加入同一托管大厅，准备并参与由第一个加入端担任服务器的团体战，直至十回合结束（命令 0x1e），然后两者均发送网状网络离开请求。

## 活动团体战

旷野地带活动是通过 BCAT 投递的巢穴遭遇表和奖励表，每次投递对应一个编号索引。Project Pokemon 的 EventsGallery 将每个索引保存在 `Released/Gen 8/SwSh/Wild Area Events/Index NNN/` 下，其 `readme.md` 列出每个索引所携带的活动名称。`pokeldn/swsh/raid_event.py` 读取其中一个；`pokeldn.app.events_gallery` 将一份副本保存在游戏 `swsh`.

| 文件 | 内容 |
| --- | --- |
| `normal_encount` | 旷野地带巢穴的活动遭遇 |
| `normal_encount_rigel1`, `normal_encount_rigel2` | 铠之孤岛和冠之雪原的活动遭遇（Index 080 和 117 中有，010 中没有） |
| `drop_rewards`, `bonus_rewards` | 本次投递的奖励表 |
| `dai_encount` | 极巨结晶遭遇 [pkNX `NestHoleCrystalEncounterArchive`]；此处尚未读明 |

每个文件以 0x20 字节头部开头：偏移 0 为 u8 BCAT 索引，`ff ff ff ff` 位于 4，u32 `0x20` 位于 8，u32 文件大小 - 4 位于 `0x10`。FlatBuffer 从 `0x20` 延伸到文件末尾前四个字节，这四个字节保存 CRC [pkNX `GameDumperSWSH.GetDistributionContents`].

遭遇文件是表的向量（字段 0）：TableID u64、GameVersion u32（1 为《剑》，2 为《盾》）、两个字节以及 Entries（字段 4）。Index 010 的各表均有 30 个条目；每个条目的虚表含 37 个字段，此处按如下方式读取（字段编号、类型、内容）。

| 字段 | 类型 | 内容 |
| --- | --- | --- |
| 0 | i32 | 条目索引，1 至 30 |
| 1, 2, 3 | i32 | 种类、形态、等级 |
| 4 | u16 | 极巨化等级 |
| 5 至 10 | u32 | Index 010 的所有条目均缺失 |
| 11 | u8 | 特性：0、1、2 分别表示第一、第二、隐藏特性；3 为前两者之一；4 为任意 |
| 12 | bool | 超极巨化 |
| 13, 14 | u64 | 掉落和额外奖励表 id |
| 15 | [i32] | 五个百分比概率，对应星级 1 至 5；每个版本的每一星级概率之和为 100 |
| 16 | i8 | 性别：0 为随机，否则等于记录性别 + 1 |
| 17 | i8 | 满个体值数量 |
| 18 | u8 | 异色：0 为随机，1 为从不，2 为必定 |
| 19, 20 | u8 | Index 010 中为 3 或 2；尚未读明 |

| 22 | i32 | Index 010 中为 0 |

Index 010 解码为其 readme 所描述的旷野地带活动 #7：星级 3 至 5 的超极巨化颤弦蝾螈（《剑》中形态 0，《盾》中形态 1），所有星级的超极巨化小仙奶，《剑》中的巨钳蟹和长毛巨魔，《盾》中的以欧路普和布莉姆温。其 5 星颤弦蝾螈（等级 60、极巨化等级 10、五项满个体值、招式 786、586、482、506）就是 PKHeX 的 `encounter_sw_dist.pkl` 中索引 10 的记录。

投递奖励文件是表的向量（字段 0）：TableID u64 和 Entries（字段 1），每个条目含五个对应星级 1 至 5 的 u8 值（字段 0 至 4）以及一个 u16 道具（字段 5）。游戏自身的表，即 `data_table.gfpak` 文件 7（掉落）和 6（额外奖励），包含 TableID，随后是由 u32 条目索引、u32 道具和含五个值的 u32 向量构成的条目（`pokeldn/swsh/data/nest_rewards.json`, `scripts/gen_swsh_nest_data.py`）。遭遇通过 id 在两类表中指定所用表，优先使用游戏自身的表 [pkNX `NestHoleDistributionEncounterTable`]；Index 010 中每个首领的额外奖励表，以及除小仙奶之外的所有掉落表，都属于游戏自身的表。

额外奖励值表示数量，掉落值表示百分比概率。模拟运行的 1 星巢穴主机端的 Rewards（`raid.DEN_REWARDS`）首先包含游戏额外奖励表 `0xf966212316b78eb6` 在星级 1 时对应数量的奖励行（经验糖果 XS x5、S x1、极巨糖果 x1），随后包含两种道具，各一个。`raid_event.rewards` 先构建额外奖励行，然后为每种掉落构建一行，按各自概率随机判定或全部保留。

`raid_event.boss_pk8` 在巢穴首领记录上构建首领，该记录是 `raid.boss_record` 的起始模板：使用表中的种类、形态、等级、招式、超极巨化和极巨化等级，以及表允许的特性、个体值、性格、性别和 PID，还有 [首领记录](#the-boss-record) 中的同行队伍能力值，个体数据表来自 `pokeldn/swsh/data/species.json` (`scripts/gen_swsh_species_data.py`).

```
bin/swsh_host.py --raid-event "FOLDER/Index 010" --raid-stars 5 --raid-event-boss 4 --raid-console-serves
```

未指定 `--raid-stars` 或 `--raid-event-boss` 时，主机端列出可接受的内容。`--raid-version` 选择表的版本（默认为广播的版本），`--raid-area` 选择巢穴区域，`--raid-event-drops all` 选择全部掉落；`--raid-reward` 奖励行替换活动奖励行。

### 托管冒险

`bin/swsh_host.py --lair-legendary SPECIES [--lair-seed N]` (`pokeldn/swsh/lair_host.py`）基于模拟《盾》主机端的广播来广播极巨巢穴网络（场景 50000），按连接交换的方式交换快照，然后发送模拟主机端的大厅消息：PlayerInfo、BattleReady 和 BigBoss，每秒三次的剩余时间，以及准备状态；加入端准备后发送 BattleStart、BattleSeed、RentalPokemonSeed 和 PlayerNumber；加入端回复已开始后，发送表示已开始的 BattleReady 和 BigBossFixed。五秒后，它按《剑》主机端的方式离开（[离开](swsh_session.md#leaving)）：MIGRATION_START `44 00 01`、带主机迁移字节的会话更新、每 0.33 s 一次的 START_HOST_MIGRATION；主机离开后或 10 s 后关闭网络。

应用的“极巨大冒险（主机端）”工具使用这些标志运行：传说宝可梦、可选连接密语和冒险种子。种子选择器显示 `lair.adventure` 根据种子给出的三只租借宝可梦和十次遭遇，可抽取新种子，并搜索随机种子，寻找候选中含有所选租借宝可梦的种子（约每 75 个种子中有一个提供指定租借宝可梦）。

以此方式加入的模拟《盾》显示的三只租借宝可梦，与 `lair.adventure(seed)` 对位置 0 至 2 给出的结果相同。租借按顺序选择，主机端先选：网络关闭前，界面一直显示“POKELDN 正在决定……”；随后电脑伙伴接替 POKELDN 的座位并选择租借宝可梦，玩家再选择自己的。地图终点的传说宝可梦种类由 BigBossFixed 指定（超梦，150），加入端自身的 BigBoss 则全零。零售版《剑》通过 ESP32 开发板以相同方式加入，准备并回复已开始，网络关闭后冒险仍继续；地图最后的宝可梦携带 BigBossFixed 指定传说宝可梦的属性（洛奇亚，249）。

极巨巢穴连接密语通过接待员处的 + 按钮设置。广播携带该密语十进制数值的 CRC32，舍弃前导零（`7777` 对应 0000 7777）；零售版《剑》使用 0000 7777 搜索时加入了广播该密语的大厅，不使用密语搜索时则从未列出该大厅。设置密语时，如果主机端未发送 MIGRATION_START 就关闭网络，加入端会在租借界面出现错误 2618-0006（2 次中 2 次）；采用移交后，加入端在 MIGRATION_START 后 0.1 s 离开网络，冒险继续。不设密语时，两种离开方式都能继续。

### 冒险种子

冒险中的宝可梦来自 RomFS 的 `bin/appli/chika/data_table/underground_exploration_poke.bin`，这是一个有 273 行的 FlatBuffer：先是 226 行等级 65 的租借宝可梦与遭遇，再是 47 行等级 70 的传说宝可梦（首领标志置位）。每行包含种类、形态、等级和四个招式。

ChikaBattleSeed 决定六只租借候选和遭遇；`lair.adventure(seed)` 计算它们。Xoroshiro128+ 使用该 u64 和 `0x82A2B175229D6A5B` 初始化。每次选择都用下一个 32 位输出为 MT19937 设种，打乱 273 个行索引（索引 i 与 i 加上一个不大于 272 - i 的随机数交换，随机数使用 `0x1ff` 掩码，超限则重抽），取第一个不是传说宝可梦且尚未选中的行。先选择四次，然后在后续两次选择之前及其后分别额外抽取一次 0 至 2，条件分别为当前电脑伙伴数量多于 2、1 和 0；接着抽取 0 至 2 和 0 至 9，然后进行十次遭遇选择，每当该行具有两种属性时，随后再取一个输出。若有三个电脑伙伴，则最先抽取一次 0 至 27。

| 种子 | 伙伴数 | 候选，位置 0 至 2 | 实测 |
| --- | --- | --- | --- |
| `0x000000000a577170` | 2 | 霜奶仙、长耳兔、长毛巨魔 | 主机端选择位置 0，加入端选择位置 2；首战为洛托姆 |
| `0x2721e8ab192583ff` | 2 | 雪绒蛾、鲶鱼王、虫电宝 | 模拟《盾》加入端的候选 |
| `0x0bdda7b984481ac3` | 2 | 铁螯龙虾、太古盔甲、呆呆王 | 在零售版《剑》上，占我方座位的伙伴选择铁螯龙虾，玩家选择呆呆王 |
| `0x0e9dfb0030f07a8e` | 2 | 火伊布、白蓬蓬、百变怪 | 零售版《剑》的候选，种子在应用中为百变怪而选定 |

该零售版种子的位置 3 至 5 为双剑鞘、灯火幽灵和力壮鸡；另外两个电脑伙伴带来大王铜象和大宇怪，因此它们的宝可梦来源尚不清楚。被选走的租借宝可梦会在下一位玩家的界面上被替换。使用种子 `0x0e9dfb0030f07a8e`（位置 3 至 5 为霸王花、冰鬼护和以欧路普）时，零售版《剑》在我方座位的伙伴选走白蓬蓬后，用冰鬼护替换它，然后在玩家选走百变怪后，用咚咚鼠替换；替补的抽取机制尚不清楚。ChikaRentalPokemonSeed 不会给出上述任何结果。某加入端替换获得的雷伊布不在其种子的十次遭遇中；路径实际对应哪些遭遇仍未知。

## 离开

玩家离开奖励界面后，零售版《剑》主机端以每 0.33 s 一次、持续 10 s 的 START_HOST_MIGRATION 流程关闭网络，与连接交换结束时相同（[离开](swsh_session.md#leaving)）。不离开的加入端会使主机端玩家冻结在野外场景中，直到超时；`--leave-with-host` 在收到第一个消息时就离开。
