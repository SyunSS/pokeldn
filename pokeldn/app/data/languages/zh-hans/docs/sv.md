# 朱与紫

《宝可梦 朱》（`0100a3d008c5c000`）和《宝可梦 紫》（`01008f6008c5e000`）是原生 Switch 游戏，Pia 链接在其 `main` 中。两者均可用两种角色与零售版主机交换：`bin/sv_host.py` 作为主机端，供主机的离线连接交换搜索发现；`bin/sv_join.py` 加入主机的网络。零售版《紫》会加入广播《朱》本地通信 ID 的主机端，它自身的搜索网络也广播《朱》的 ID（`0x0100a3d008c5c000`，应用版本 21，场景 4）。

两个启动器也都能以任一角色运行本地太晶团体战（[太晶团体战](sv_raid.md)），主机端还可将官方礼物宝可梦交换给主机（[模拟神秘礼物](gift_simulated.md)). [集友圈](sv_union_circle.md) 以加入端身份加入主机的集友圈，向其主机端报告蓝乐活任务完成情况，并在主机端玩家周围生成用户自定义的野生宝可梦。

地址均为解压后的 `main` 中的偏移量，版本为 4.0.0 更新（`tools/switch/nso_read.py`）：text `0x0..0x343fc90`，rodata 从 `0x3440000` 开始，data 从 `0x4383000`.

## 搜索中的主机广播什么

连接交换搜索交替进行建网（每次使用新 SSID）与扫描，并在信道 1、6、11 之间跳转；实测一次建网阶段约五秒。

```
local_communication_id  0x0100a3d008c5c000, Scarlet's, on both versions
ldn protocol            1            advertisement version 4
scene_id                4            app_version 21
security_mode           1            accept_policy ALL
participants            1/2
application_data        132 bytes
```

应用数据由 0x5C 字节的 Pia 系统属性块和 40 个游戏字节组成：

| 字段 | 值 |
| --- | --- |
| 系统通信版本 | 0x15 |
| 应用通信版本 | 0x15 |
| 用户密码 | 未设置连接密码时为十六个零字节 |
| 启用玩家人数限制 | 1，玩家人数为 1，站点入席后变为 2 |
| 玩家名称 | 一个字节，即 UTF-8 空格 |
| 40 个游戏字节 | 全零，或游戏数据的 `+0x21` (`fb149700` 处为非零值，已观测到上述值），每隔几秒交替一次；第二台主机对两者都能关联 |

`pokeldn.sv.build_advertise_data` 逐字节复现这两种信标。

## 游戏运行的协议

对一对零售版主机的被动抓包显示 Net、RTT、0x80 和 0x81，均发往会话 `/24` 的广播地址，并在明文尾部附上接收方的可变 ID。其余六种为单播（两台 Switch 2 主机间使用 802.11ax），未出现在抓包中。

游戏的设置函数 `0x17ff030` 按以下顺序创建：端口 0 上的 Reliable `0x7C` 和 BroadcastReliable `0x80`、Unreliable `0x68`、端口 1 和 2 上的 Reliable 与 BroadcastReliable、`[0x44dfcd0]` 个 StreamBroadcastReliable `0x81` 端口（线上为八个）、Clone Clock `0x77` 和 Clone Atomic `0x74`。Pia 会添加 Net、RTT、Session `0x98` 和 MonitoringData `0xA4`；NatTraversalResult `0xA0` 仅在网络工厂启用 NAT 穿透时添加（`0x6d3138`），本地网络不会启用。

| ID | 协议 | 版本 |
| --- | --- | --- |
| `0x2C` | Net | 0 |
| `0x58` | RTT | 3 |
| `0x68` | Unreliable | 1 |
| `0x74` | Clone Atomic | 0 |
| `0x77` | Clone Clock | 0 |
| `0x7C` | Reliable | 2 |
| `0x80` | BroadcastReliable | 3 |
| `0x81` | StreamBroadcastReliable | 3 |
| `0x98` | Session | 0 |
| `0xA4` | MonitoringData | 0 |

零售版《传说 阿尔宙斯》在加入请求中列出同样的十个版本。一对零售版主机的开场过程如下（时间取自一次抓包）：

```
+0.00   the joiner associates
+0.06   host: Net 0x11 (station list), 0.12 s later Net 0x50
+0.14   host: acks all eleven streams, opens two
+0.89   joiner: RTT request, acks all eleven, opens two
+0.97   host: first records on 0x81 port 0
+1.26   joiner: first records on 0x81 port 1
```

### Net 0x11：站点列表

布局与《传说 阿尔宙斯》相同，包含四个 21 字节的站点槽位：

```
01 11 0054          version 1, type 0x11, payload size 0x54
00000002            sequence id
9141                host variable id, fresh every session
eb9b2220f1480000    host constant id, the LDN MAC reordered
0000000097392e8a    network id, the low four bytes crc32(ssid[1:16])
01                  is network open
0004                station slots
00                  is migrating host
...                 four stations: migration state, ranking (host 0, joiner 1, empty 0xff),
                    one byte, 16 address bytes, big-endian u16 port (12345)
```

`01 40 00 00` 是不带额外数据的 NetStartHostMigration，由正在移交角色的主机端发送。零售版《朱》从搜索状态充当主机端时，会对正在移交给加入端的席位重复发送它（[席位由什么决定](#what-decides-a-seat)).

主机端必须写入四个站点槽位（Pia 的数量，而非游戏的两人限制）。若仅写两个，加入中的游戏不会发送任何内容，并在关联后 5 秒断开（49 次加入中为 4.98 至 5.01 秒）；零售版主机会以 ICMP 端口 12345 不可达响应 Net 0x11。若写四个，则响应 Net 0x12 并发送 Session 加入请求。开场标志为 0x31（零售版）或 0x01 并无区别。

### 十一条流

```
0x80  BroadcastReliable         ports 0, 1, 2
0x81  StreamBroadcastReliable   ports 0 to 7
```

两个站点均约每秒使用一次 `pokeldn.ldn.reliable5` 的批量确认来确认全部十一条流：四个条目，站点字节为零，第 *k* 个条目比站点 *k* 的最高序号大一，目标位数为 3，位图中置位对端对应的位。站点用十一字节的 INITIALIZED 消息打开两条流，并在与自身站点索引相同的端口上发送记录（参见 `pokeldn.pla.data_exchange`).

| 站点 | 打开 | 记录发送端口 |
| --- | --- | --- |
| 主机端，索引 0 | 0x81 的端口 1 和 5 | 0x81 的端口 0 |
| 加入端，索引 1 | 0x81 的端口 0 和 4 | 0x81 的端口 1 |

打开流的负载在端口 0 和 1 上为 `0000000000f38800000000`，在端口 4 和 5 上为 `00 00 00 0ff0 0800000000`：类型 0 的 StreamData，用于提交大小为 0xF388（传输 0）或 0xFF008（4 和 5）的接收。交换中从不发送 0xFF008 传输。`pokeldn.sv.streams` 构建上述全部内容；`tests/test_sv.py` 将其固定为与零售版字节一致。

### Pia 消息标志

两个零售版站点均发送以下内容（不使用《阿尔宙斯》主机端的建立标志）：

| 消息 | 标志 |
| --- | --- |
| RTT、流打开、记录的首次发送 | 0x00 |
| 再次发送的记录 | 0x40 |
| 批量确认 | 0xA0 |
| 主机端的 Net 0x11 和 0x50 | 0x31 |
| NetStartHostMigration | 0x11 |

消息目标字段始终为零。标志 0x40 为 `w4 = 1`，来自 `ReliableSlidingWindow` 发送循环 `0x6f0638`（发送计数 `[slot+0x14]` 为零时取 0，`0x6f0908`；重发 `0x6f0a9c` 或提前发送 `0x6f0c38` 时取 1），由 `0x6e7250` 存储为数据包写入器选项块的第 0 字节。

### RTT

十一字节：类型、大端序 u64 时钟、大端序 u16 目标。请求的类型为 0、目标为 0；应答类型为 1，携带相同的时钟及请求方的可变 ID，零售版在 20 毫秒内应答。

RttProtocol（虚表 `0x43e5a28`）在 `[proto+0x60] + index*0x40` 为每个站点保存一条 0x40 字节记录：采样数 `+0`、环形缓冲区头 `+4`、位于 `+0x10` 的容量 9，其后内嵌环形缓冲区；中位数缓存在 `+0x3c`，对应的计数位于 `+0x38`。采样值为当前时钟减去回显时钟（`0x6f34b4`）；小于等于零的采样会被丢弃（`0x6f34e0`）。在所有环形缓冲区填满前，请求按间隔 `[0x46d1528]` 发送，之后按 `[0x46d1520]` = 500 发送（写入位置为 `0x6f2fcc`，游戏另在 `0x1e7c2bc` 写入）。站点事件 0 或 1 会清空该站点记录（vfunc11 `0x6f3bd8`）：新席位没有采样。

GetRtt（`0x6f4498`; `0x6f44bc`，指定数量 *n*）在没有采样时返回 -1，否则返回最近 min(count, *n*) 个采样的中位数；最小值 `0x6f44e4`、最大值 `0x6f4508` 和采样数 `0x6f452c` 位于其旁边。仅有的调用方是 SessionTransportAnalyzer 的监测副本（`0x6f9ab0`..`0x6f9ad4`）以及 `ReliableSlidingWindow` 重传截止时间 `0x6f0d14`，后者的调用来自发送循环，位置为 `0x6f073c`:

```
deadline = now + [window+0x80] + 1.4 * (max over the destinations of GetRtt(count))
```

没有采样时，`0x6f0d14` 返回未调度标记 `[window+0x5c]`：消息入队时发送一次（`0x6f1bbc`..`0x6f1bd4`），随后在 `0x6f0a18` 处跳过，直至采样使其重新就绪（`0x6f09f4`..`0x6f0a08`）。没有 RTT 采样的窗口从不重传。

构造函数 `0x6eeea8`（调用方 `0x6e69f8`, `0x1800038`）将 `[window+0x80]` 设置为 `ticks_per_second * 33 / 1000` (`0x6eef34`..`0x6eef74`；633,600 个时钟周期，在 19.2 MHz 下为 33.0 毫秒），标记 `[+0x5c]` 设为 0，基准序号 `[+0x30]` 设为 1，自身索引 `[+0x10]` 设为 0xfd，压缩 `[+0xa4]` 设为 1，提前发送限制 `[+0x88]`, `[+0x89]` 设为 0。此后唯一的写入方是 vfunc17 `0x6f1fc8` 中的 `0x6f1f98`（来自 `ReliableProtocol::vfunc17` `0x6eebbc` 和 `BroadcastReliableProtocol::vfunc17` `0x6e6818`，无已知调用方）。发送循环每个 16.7 毫秒帧运行一次，因此重发会在达到或超过 `33 + int(1.4 * RTT)` 毫秒的第一帧发出：RTT 为 34 毫秒时是 83 毫秒，RTT 为 358 毫秒时是 550 毫秒。

### 记录

一条记录是一条带 ZLIB 标志的可靠消息，即使用 4 KB 窗口的 zlib 流（`484b`），解压后为 1395 字节，`[window+0x70]`：Pia 的 StreamData 头部之下的一个 0x81 传输分块（[协议 0x81](pia.md#protocol-0x81-the-stream-broadcast-reliable-transfer-pia-6)):

```
+0x00  1   StreamData kind: 1 the first chunk of the block, 2 a later chunk
+0x01  1   transfer id, 0
+0x02  1   percent of the block delivered after this chunk
+0x03  4   zero, the capacity field of a kind 0
+0x07  4   big-endian u32 0x00000568, the 1384 bytes that follow
```

一个站点的数据块大小为 0xF388（62,344）字节：45 个 1384 字节分块和一个 64 字节分块，ID 为 1 至 46，百分比字节为 `floor(k * 1384 * 100 / 62344)`（2、4、6、8、0x0b、……，第 25 块为 0x37，第 37 块为 0x52，第 46 块为 0x64）。第一个分块携带屏幕上显示的伙伴信息：

```
+0x0b  4   trainer id, then secret id
+0x0f  1   version: 50 Scarlet, 51 Violet
+0x10  1   gender
+0x11  1   language
+0x12  1   ball-throw style, 1 the original
+0x13  26  the player name, UTF-16 little-endian, NUL-padded; --trainer-name on both launchers
+0x2d  22  the account identifier, ASCII, `u-` and twenty characters
+0x53  8   story progress, little-endian: 1 the main story cleared, 4 The Indigo Disk cleared
```

该数据块在 `0xa52f88`..`0xa530a0` 处的栈上构建：先是存档中的训练家，然后是另一存档块中的投球风格（`0xa53054`），接着是账号标识符（`0x1a61a00`），最后是进度字，它是游戏在 `0x473a040` 保存的脚本函数的返回值（在 `0xa5309c` 调用）。原生函数 `f20A702BD` (`0x877560`）负责安装它；在 3.0.1 脚本转储中，`BattleNetworkNetReceiver` 传入一个初始值为 0 的函数，在 `FSYS_SCENARIO_GAME_CLEAR` 置位时将其设为 1，在 `FSYS_SCENARIO_GAME_CLEAR_SU2` 置位时再按位或入 4。零售版《朱》发送 5，零售版《紫》发送 0 且账号标识符全零，参考实现发送 1。

游戏脚本通过按以下顺序注册的原生 getter 读取站点玩家：`PlayerId`, `RomCode`, `Sex`, `LanguageId`、投球风格、`NameStrBuf` (`RegisterPlayerData` 以及 3.0.1 脚本转储中的对战设置；投球风格就是存档自身的 `ballThrowId` 填充的槽位）。在《朱》和《紫》各一个零售版存档上，ID 对、版本、语言和名称均与各自捕获的宝可梦一致；即使拿出收到的宝可梦，名称仍为该存档名称。为接收玩家制作的礼物会读取这些字段（`reference.identity_trainer`, [为接收玩家定制](gift_simulated.md#made-for-the-receiving-player)).

分块 2 至 24 为高熵数据；25 至 46 全零。站点一次发送整组，通常第一包包含 ID 1、25、26 至 36 和 46，第二包包含 2、37 和 38 至 45，之后 3 至 24 每包一个（48 组零售版数据中有 41 组如此）。相同的零分块跟在 0x00 存在字节之后传输，继承所有头部字段（[消息封装](pia.md#message-framing)）。一组通常在 0.2 秒内发出（52 组零售版数据中，46 组在 0.19 秒内）。`pokeldn.sv.streams.decompress` 负责读取。

`pokeldn.sv.reference` 附带一个站点的 44 条记录以及其在 0x7C 端口 0 上的两个身份片段，录自玩家为 `Player` 的模拟版《朱》，未设置账号标识符。`bin/sv_host.py` 和 `bin/sv_join.py` 会发送它们，除非指定 `--record-set`, `--send-on-open` 或 `--no-identity`.

### 零售版确认与大量重传

零售版站点确认对端记录流时，确认 ID 比连续区间末尾大一，字段 0x50 与其相等，并附带掩码，其中位 *b*（属于字节 *k*）表示 ID `ack_id + 1 + 8k + b`：持有 ID 1 至 4 和 7 至 38 的主机端发送了 `0005 0005 feffffff01`。低于对端自身 `lowest_pending` 的 ID 视为已持有。`pokeldn.sv.streams.ack_position` 构建此内容（固定在 `tests/test_sv.py`); `bin/sv_join.py --ack-highest` 则发送已见最高 ID 加一。

主机端会在 RTT 截止时间到达时重发每条未确认记录，标志为 0x40，每轮一包、从最低 ID 开始，随着确认到达而缩减。若遍历消息时在 0x00 存在字节处停止，就只能读取每轮第一条记录，需要 19 轮；`--ack-highest` 会将 `lowest_pending` 一次从 1 推进到 38。未收到确认时，主机端每轮重发所有待处理记录；RTT 较小时每秒达数百条（HT MCS3 下为 435 至 494 条，约占 3% 空口资源），足以占满开发板串口的 150 KB/s（[串口上限](hardware_esp32.md#the-serial-ceiling)）。轮次间隔为 `[window+0x80] + 1.4 x RTT` 向上取整到帧，与加入端应答延迟的对比如下：

| 应答延迟 | 估计 RTT | 轮次间隔，各次入席的中位数 |
| --- | --- | --- |
| 0.000 秒 | 0.013 至 0.017 秒 | 0.065 至 0.069 秒 |
| 0.000 秒 | 0.033 至 0.038 秒 | 0.078 至 0.116 秒 |
| 0.000 秒 | 0.053 至 0.059 秒 | 0.115 至 0.221 秒 |
| 0.318 至 0.328 秒 | 0.354 至 0.363 秒 | 0.532 至 0.555 秒 |

随着 RTT 环形缓冲区填满，记录间隔逐渐收敛于该值（4 至 5 次应答时为 0.19 秒，8 至 18 次时为 0.10 秒，20 次时为 0.082 秒）。构造函数 `0x6eeea8`、发送缓冲区 `0x6e6e94`、入队 `0x6f1994` 和发送循环 `0x6f0638` 在 unicorn 下单次发送 46 条记录，截止时间前不再发送。节奏由主机端自身处理决定：无论确认延迟如何，其 `lowest_pending` 都在整组发送后约 0.5 至 1.0 秒才离开 1（每帧均在 7 毫秒内确认时为 0.73 至 0.81 秒），确认掩码约每 0.19 秒推进一步。主机端在加入端打开流并发送记录组后约 0.1 秒发送自身记录组（`--open-delay`, `--record-delay`）。此前收到的 RTT 应答使轮次间隔低于该延迟，导致它重发加入端已经持有的记录；将 RTT 应答延迟 0.3 秒可避免此情况。零售版入席测量如下：

| 发送记录组前的 RTT 应答数 | 应答延迟 | 入席次数 | 在 `lowest_pending` 离开 1 之前重发的记录数 | 离开 1 所需时间 |
| --- | --- | --- | --- | --- |
| 0 或 1 | 0 | 3 | 两次为零，一次为 138 | 0.78 至 0.81 秒 |
| 3 至 6 | 0 | 4 | 122 至 137，每个 ID 每 0.18 至 0.20 秒一次 | 0.73 至 0.80 秒 |
| 0 | 0.3 秒 | 4 | 无 | 0.91 至 1.01 秒 |
| 1 至 7 | 0.3 秒 | 9 | 无 | 0.50 至 0.58 秒 |

`--rtt-delay 0.3` 延迟 0.3 秒应答 RTT 请求，使轮次间隔始终高于主机端确认延迟。`--leave-on-migration N` 在主机发送 Session 类型 7 后 N 秒结束入席，而 `--announce-timeout SECONDS` 会离开未被通告的席位；两者都会重新扫描。`bin/sv_join.py` 立即确认新记录，对重复记录则每条流每 50 毫秒最多确认一次（`--repeat-ack-gap`），每个数据包中每条流一个确认。

没有 RTT 采样时，0x81 流从不重传（[协议 0x81](pia.md#protocol-0x81-the-stream-broadcast-reliable-transfer-pia-6)）：空口丢失的记录会一直处于待处理状态，主机端的 `lowest_pending` 停在其 ID，对端永远不会被通告。

RTT 采样用于启用重传；通告作业没有 RTT 门槛。不丢包的模拟版《朱》4.0.0 主机端即使不收发 RTT 请求或应答，也能通告并完成交换。缺失身份记录会使 BoxTrade 作业停留在状态 1（`+0xb8`）；位于 `0x1e51ae8` 的已完成槽位计数维持在 1，而要求值为 2，直至重传补齐整组。

两个启动器均重试待处理的身份记录。初始化器丢失及中间记录丢失的情况，可通过启动器在 `tests/test_sv_identity_loss.py` 中完成。打过补丁的模拟器在这些丢失情况下完成了交换；零售版主机在每个角色下各完成两次交换，待处理身份记录经重试并确认，随后正常离开。对于先前那个确认已达到 47 但未被通告的席位，没有独立空口抓包能确定究竟是否有某个出站分块丢失，以及丢失的是哪块。

### 抓包中的 A-MSDU 帧

两台主机都会将多个 MSDU 封装到一个 A-MSDU 帧中。被动抓包必须解包子帧，否则会遗漏多数 Pia 数据包（一次抓包中，不解包可读 313 个，解包后为 3667 个）。

## 连接密码

连接密码在广播中出现两次；场景 ID 保持为 4。用户密码为连接密码本身，以 NUL 补齐至十六字节，再与 `e5ab19ed742b6d40885998bf968aa166` 异或；这是相同游戏密钥下《传说 阿尔宙斯》使用的掩码（[docs/pla.md](pla.md)）。游戏字节在 +0x00 以明文携带连接密码，在 +0x24 以 u32 携带其长度。`pokeldn.sv.build_advertise_data(code=...)` 逐字节复现零售版主机使用 12345678 搜索时的数据。

搜索中的主机只加入广播相同连接密码的主机端（`bin/sv_host.py --code`）。使用连接密码充当主机端的零售版主机，接受了未广播密码的加入端。`bin/sv_join.py --code` 只加入使用该连接密码搜索的主机。

只有搜索中的主机会检查连接密码，检查对象是扫描到的网络。其选择器 `0x26e955c`（由 `0x272d838` 在加入前调用）在带密码搜索时跳过无密码网络（`0x26e95f4`），在无密码搜索时跳过有密码网络（`0x26e960c`）。随后，它使用 FNV-1a 64 对 +0x00 起至第一个 NUL 的游戏字节和自身连接密码分别计算哈希（质数 `0x100000001b3`，偏移基值 `0xcbf29ce484222645` 在 `0x26e96c8` 加载，并非标准基值），两者不相等就跳过该网络（`0x26e972c`）。它既不读取密码的值，也不读取 +0x24 处的长度。

主机端不比较加入端发送的任何内容。LDN 关联使用固定口令，Session 加入请求中没有密码字段。Pia 对连接站点的密码检查，即 Net 0x32 处理函数 `0x69ec50` (`0x69ee5c`, `0x69ee70`）中的结果 7，需要收到 Net 0x32；而其唯一发送方 `0x69d42c` 受协议 vfunc 48 控制：在 `LdnProtocol` (`0x6a2fac`）中为 0，在 `LanProtocol` (`0x6ba278`）中为 1。加入侧的 LDN 连接会运行 Pia 网络检查 `0x6a22c4`，但其中的密码比较（`0x6a24a4`）被关闭（`0x6b0d90`).

已加入的主机不会再次检查连接密码。Net 0x50 处理函数 `0x69ea3c` 校验系统属性大小（0x5c）、应用数据大小（最多 0x124）和四个 Pia 身份字段（`0x69d9d8`），将字节复制到网络属性中（`0x69d8a4`），并以 Net 0x51 确认；它不比较系统属性或游戏字节中的任何字节。在 LDN 下，该副本写入缓存广播数据，并在下一次 `nn::ldn::GetNetworkInfo` (`0x6b30d4`）时被覆盖。游戏只在选择器及 UpdateSessionSetting（`0x26e63b8`）中读取会话的前 0x28 个游戏字节，后者会重写自身会话；另外两个读取方（`0x268e988`, `0x268e9bc`）只读取 +0x28 之后的数据。加入中的主机将其连接密码保留为自身的 Pia 站点密码（加入对象 vfunc `0x274bdb8`，设置器 `0x6a208c`），只在自己充当主机端时广播。连接交换的端口 2 类型 1 来自 BoxTrade 作业的状态 2（`0x1e51b68`）：种类为 1，静态空名称 `[0x46d3e30]`，无数据。

## 入席与其后的大量身份数据

上述加入请求使站点入席：零售版《朱》主机端在 16 毫秒内接受，发送 41 字节加入响应（状态 1，无路由字节）和无路由站点更新，并在 0x81 端口 0 上流式发送身份信息，每条记录一次。不接受加入端确认的主机端会重发每条记录，直至席位结束（[让主机端认可确认的标志](#the-flag-that-makes-the-host-count-an-acknowledgement)）：零售版约每秒 350 条记录，每条最多重传七十次；面对无损局域网上的模拟版《朱》时，59 秒内每条记录重传 676 次。主机端也可能发送 Session 类型 7（`LeaveMeshWithHostMigrationJob`），将主机端角色交给加入端，每秒一次，直到收到类型 8 应答（[席位由什么决定](#what-decides-a-seat)).

### 让主机端认可确认的标志

带标志位 5，即 ZLIB（`[msg+0x29]`, `0x6efc80`）的消息，会在解析站点前在 `0x6e9984` (`0x69804c` 中解压，zlib inflate 为 `0x2801d0`）；失败返回 0x2C03（`0x6efd5c`）。标志为 0xA0 的未压缩批量确认会在此失败（模拟主机上 600 次全部失败）。零售版 0xA0 确认携带 zlib 消息体：三份零售版加入端抓包中的 1,774 条全部解压为 99 字节；以 `484b62606008` 开头的 38 字节消息体，可用记录所用的 4 KB 窗口、等级 5 和 sync-flush 封装复现。同样的 99 字节在标志为 0x00 时走另一条路径：主机端每条记录只发送一次（每秒 6.3 条，随后不再发送；而未压缩 0xA0 为每秒 115 至 257 条）。两个零售版站点都为批量确认设置 0xA0 标志，并发送到其 /24 子网的 LDN 广播地址；`bin/sv_join.py` 设置位 5 时会压缩消息体（`--ack-flags`, `--ack-entries`, `--ack-dest-bits`, `--ack-sweep`).

### 流上的第一条记录携带 INITIALIZED

站点的第一条记录同时携带 INITIALIZED、START、END 和 ZLIB，标志为 0x1F；后续记录为 0x17。首条记录以 0x17 发送时始终不被确认（发送 198 次）；以 0x1F 发送则在 90 毫秒内得到确认。采用 zlib 批量确认且首条记录带 INITIALIZED 后，加入端的全部 44 条身份记录除源可变 ID 和 nonce 外，与配对加入端逐字节一致。模拟版与零售版主机端均将其确认至 47（随后附掩码 `feffffffff01`, `field_0x50`），各记录发送一次，并发出列有双方站点及其玩家块的类型 5 站点更新。

### 最低待处理记录与 5、6 处的缺口

站点从不发送 ID 5 和 6（线上共 44 条记录），其余乱序发出（配对主机端：1、2、3、46、4、7、8、19、9、15、10、16……）。每条记录声明 `lowest_pending` 为 1，目标位数为 3，位图 `[2]`，流 ID 为 0。发送方在同一条流上的下一个批量确认会填平缺口，其中 `lowest_pending` 从 1 跳至 47；对端随后以空掩码将整组确认至 47。若仍为 1，对端在整个会话中都会应答 `ack_id` 为 5、掩码为 `feffffffff01`。无缺口的 ID 1 至 44 也会被接受，但没有零售版发送方使用这种形式。

发送方只能将 `lowest_pending` 推进到已确认记录之后。在初始突发后直接推进到 47 可能掩盖身份分块丢失：对端虽确认 47，但 StreamData 数据块仍不完整，站点始终不会被通告。

两个 SV 启动器都为身份记录组维护一个 `reliable5.SendWindow`。对应的批量确认条目会释放低于其 `ack_id` 的记录及其选择性掩码指定的记录。每 250 毫秒以原始序列 ID 和 Pia 消息标志 `0x40` 重发未确认记录。出站数据及批量确认头部声明仍待处理的最低记录；整组全部确认后则为 47。这样既保留有意设置的 5、6 缺口，也保留实际丢失的记录。

首条 INITIALIZED 记录丢失会导致全部 44 条记录均不被确认，需要重试整组。中间记录丢失则只单独重试该条。

```
b9 06 ...   the type-1 body as a tuple of six: kind, capacity, a zero byte, the name as a
            nine-byte string, the data as a 128-byte string, the data length
key         body +0x8e, the relay's counter +0x1c4 before it steps
index       body +0x8f, the relay's counter +0x1c0 masked to seven bits, before it steps
b9 01 ...   a tuple of one u64, the station id of the type 1's sender
0           body +0x98
```

类型 9 是由加入请求的槽位键、结果字节以及包含一个 u64 的元组组成的元组。

类型 7 是转发后的类型 1：类型 1 处理函数 `0x18ceb70` 无条件复制 0x8e 字节消息体，写入键和索引，递增两个计数器，追加发送方站点 ID，并将其放入类型 7 构造器的队列（队列 `+0x200`，步长 0xa8）。`0x18d5a58` 向一个站点发送端口 2 消息，目标为自身时通过 `0x1954aec` 分发，因此主机端会转发自己的类型 1。

类型 1 消息体（`0x18ab760`):

```
+0x00  kind
+0x01  the slot's capacity: 2 for kinds 1 to 3, 4 for kinds 4 to 8 and 12, 0 for kinds 9 to 11
+0x02  zero
+0x03  a name of up to eight characters, NUL-terminated in nine bytes
+0x0c  up to 128 bytes of data
+0x8c  the data length
```

交换的类型 1 为种类 1、容量 2、空名称、无数据。槽位将消息体保存在槽位 `+0xd0`（构造函数 `0x18b73a0`），因此其键 `0x12fcabc`（槽位 `+0x15e`）就是消息体 `+0x8e`。每次转发类型 1，无论自身还是对端的，都会递增键；只有 `0x12fbef0` 会将计数器清零。像 `03b90200bc09` 那样指定键 0 的加入请求，只匹配计数器清零后的第一次通告。

类型 3 处理函数 `0x1981e94` 将加入请求的首个字段与槽位键比较（`0x1981ed4`），接受时将类型 9（`+0x270`）入队，否则在 `0d b9 01` 上发送类型 0x0D、`+0x350`:

| 代码 | 拒绝原因 |
| --- | --- |
| 1 | 没有槽位具有加入请求的键（`0x1981ffc`），或 `0x279c8fc` 拒绝 |
| 2 | 槽位已满：`0x18f80c8` 与容量 `0x1e64914` 读取值比较，或 `0x279c9a0` 返回 0xfd |
| 3 | 加入名称的 FNV-1a 64 哈希与槽位的不同（`0x1e648a0`) |
| 4 | 槽位已关闭（`0x1e64924`，槽位 `+0x160`，创建槽位时清零） |

类型 0x0D 交给 `0x1954f3c`，它要求 `0xb9`，解码单元素元组（`0x279c0e8`）并调用接收器 `0x279c1ac` (`0x1954f78`):

```
0x279c1b8  ldr  x8, [x0, #0xb8]     the pending request
0x279c1bc  cbz  x8, ret             none: nothing happens
0x279c1d0  strb w9, [x8, #0x43]     result = the code
0x279c1d8  strb #1, [x8, #0x42]     done
0x279c1dc  bl   0xc8e6c4            wakes the request's waiter at +0x48
```

它既不检查请求类型 `+0x40`，也不检查完成字节，因此加入端发来的 0x0D 会用其代码完成主机当前持有的任何请求。类型 9 接收器 `0x18b65c8` 根据槽位字节选择对象、应用消息；除非 u64 等于站点自身 ID，否则丢弃 `[[0x46d0a08]] + 0xb8`.

站点 ID 是按大端序 u64 表示的 Pia 固定 ID（`7f00020000020000`，对应 MAC `02:00:7f:00:00:02`）；与零售版主机交互时，类型 9 携带其 Session 加入请求中的固定 ID。`pokeldn.sv.port2` 构建这三种消息（固定在 `tests/test_sv.py`); `bin/sv_host.py --announce` 在入席后发送类型 7，并以类型 9 应答类型 3。

### 发送通告的交换作业

连接交换在 `0x1e2ea54` 创建作业：配置 `BoxTrade` (`0x3aefac8`），工厂 `0x1e2f3d4`，模式 4，所需数量 2。两个脚本绑定可到达此处：`0x1e2e9bc`（GOT `0x46d6608`，由 `0x1b9c8c4` 存储到 `0x4717068`，尾调用）和 `0x1e2ec84`（GOT `0x46d6610`, `bl` 位于 `0x1e2ee40`）。该作业（构造函数 `0x1e3bd10`，虚表 `0x44568a8`，Update `0x1e51a04`）：结果 `+0x40`，状态 `+0xb8`，会话句柄 `+0xc0`，模式和所需数量以 u16 位于 `+0xc8` 和 `+0xca`，槽位对象 `+0xd0`，请求句柄 `+0xf8`.

| 状态 | 地址 | 执行内容 |
| --- | --- | --- |
| 1 | `0x1e51a84` | 站点计数 `[[0x46d0a08]]+0xe0` 低于所需数量时结果为 3；若 `0x18ab520` 拒绝该模式（0、5、大于 8），结果为 1；否则无超时等待 `need` 个完成的身份数据块（`0x1e52004` 遍历 `[[job+0xd0]+0x10] - 0x28`），随后主控端进入状态 2（`0x1639910`：自身 ID `+0xb8` 等于主控 ID `+0xc0`），客户端进入状态 4 |
| 2，主控端 | `0x1e51b2c` | 种类 `0x18ab550(mode)`（模式 1 至 8 分别得到 2、3、4、1、0、5、5、8），然后请求 `0x18ab658`；为 null 则以结果 8 结束 |
| 3，主控端 | `0x1e51ca8` | 等待请求，无超时；结果 0 进入状态 6，否则作业通过 `0x1e5086c` |
| 4、5，客户端 | `0x1e51b8c`, `0x1e51c74` | 相同等待，时限 15 秒 |

| 结果 | 含义 |
| --- | --- |
| 1 | 成功，或模式被拒绝 |
| 2 | 会话处于状态 3 |
| 3 | 站点数低于所需数量 |
| 4 | 客户端 15 秒超时 |
| 8 | 无会话，或请求被拒绝 |

请求函数 `0x18ab658` 构建类型 1 消息体，并通过 `0x18ab83c` 发送；若转发器的待处理请求 `[relay+0xb8]` 的完成字节 `+0x42` 仍为 0（`0x18ab860`, `0x18ab8e8`）或发送失败，则返回 null。否则清除 `+0xb8` (`0x18ab894`），存储新请求（`0x18ab8a8`; `0x18abec0`: `+0x40` 类型，通告时为 0，`+0x42` 完成标志，`+0x43` 结果），并向主控 ID 发送类型 1（`0x18d58b8`），在主控端即发送给自身；发送失败则清除 `+0xb8` (`0x18ab900`).

`0x18ab658` 有四个调用方：`0x1e51b68`（BoxTrade 状态 2）、`0x18ab34c`（同级作业中的对应部分，虚表 `0x4456490`), `0xa188f0`（虚表 `0x4452e68`）和 `0x1d99568`（虚表 `0x44536d8`）。只有四个请求创建器会写入 `+0xb8`; `0x18ab83c` 和 `0x2799b10` 在请求待处理时拒绝：

| 创建器 | 请求类型 | 存储位置 | 唯一调用方 |
| --- | --- | --- | --- |
| `0x18ab83c` | 0，通告 | `0x18ab8a8` | `0x18ab6bc`，位于 `0x18ab658` |
| `0x2799b10` | 2，客户端加入 | `0x2799bd8`（保护条件 `0x2799b2c`..`0x2799b40`) | `0x1e635fc` |
| `0x2799c44` |  | `0x2799cfc` | `0x1e639ec` |
| `0x2799d6c` |  | `0x2799e30` | `0x1e63c88` |

最后三个调用方各自位于一个函数中，该函数的唯一调用方均位于 `0x1d98xxx` (`0x1d986d8`, `0x1d98990`, `0x1d98c20`).

在连接交换中，类型 2 创建器从 BoxTrade 状态 4 的 `0x1e51c40` 处，经由 `0x1d986d8` 和 `0x1e635fc` 到达。它只在主控端槽位已存在后在客户端运行（`0x1d999f4`, `0x18c7a40`），将请求保存在作业 `+0xf8`，并进入状态 5。其余对 `0x1d98698` 的调用方属于其他作业类。

排空函数 `0xe44cf0` 依次遍历队列 `+0x1c8`, `+0x200`, `+0x238`, `+0x270`, `+0x2a8`, `+0x2e0`, `+0x318`, `+0x350`；构造器返回 false 会结束本帧排空，因此卡住的类型 7 会阻塞其后的类型 9 和 0x0D。类型 7 构造器 `0xe45740` 在站点数为 1 时只做本地分发；否则询问 `BroadcastReliableProtocol::vfunc20` (`0x6e6638`）0x80 端口 2 能否发送，使用 `0x107e060` 发送，只有两者均成功才进行本地分发。目标列表 `[window+0x40]` 中未设置任何条目时，vfunc20 以 0x2c27 拒绝（`0x6efb98`）；窗口容不下片段时为 0x4c0d（`0x6f1ef8`）；无会话或窗口时为 0x10408。Pia 在站点加入事件中填充目标列表（[窗口向谁发送](pia.md#who-a-window-sends-to-pia-6)).

类型 7 接收器 `0x18b566c` 创建并应用槽位；对于待处理的类型 0 请求且站点 ID 为主机自身（消息体 `+0x90`），以结果 0 完成：主控端会停留在状态 3，直到自己的类型 7 已在线上发出。从转发器到实际发送之间没有任何地方读取 RTT 或计时器。

0x81 身份信息为每个站点一个数据块，走与其索引相同的端口（句柄 `0x475ea48 + 4*index`），通过流发送 API `0xe22188` 和接收 API `0xe22458` 传输，用于三个布局相同的对象：

| 对象：Update、虚表 | 发送 | 接收 | 数据块 |
| --- | --- | --- | --- |
| `0xe21104`，是以下对象的槽位 13：`0x4455ec0` | `0xe21a44`, `bl`，位于 `0xe21dc4`, `w2 = 0xf388`，位于 `0xe21db8` | `0xe2150c`, `0xe2170c`, `w3 = 0xf388`，位于 `0xe21708` | 0xF388 = 62,344 |
|  | `0xa62c5c`, `w2 = 0xff008` | `0xa64ddc`, `w3 = 0xff008` | 0xFF008 = 1,044,488 |
| `0x1e5f87c`，是以下对象的槽位 13：`0x4458698` | `0x1e617a8`, `0x1e61980`, `w2 = 0x97e08` | `0x1e61a74`, `0x1e61c0c`, `w3 = 0x97e08` | 0x97E08 = 622,088 |

交换时只有 0xF388 数据块在线上传输，因此作业的 `+0xd0` 对象属于该类（实例未追踪；通过 `0x1e34b6c` -> `0x1e35e88`).

`0x1e52004` 统计位于 `+0xd0 + 0x30*k` 的槽位（四个），它们持有对端指针且字节 `+0xd8` 已置位。主机自身槽位在 `0xe21154` (`memcpy(slot, [+0x90], 0xf388)` 中、位于 `0xe21248`, `+0xd8 = 1` 中、位于 `0xe21258`；调用来自 `0xa536e0`, `0xd6dc88`, `0xe21128`, `0x195160c`）。对端槽位在 `0xe212b8`（调用来自 `0xa536f0`, `0xd6dc98`, `0xe21138`）中设置该值，条件是向对端发送（`+0xda`）和从对端接收（`+0xd9`）均已开始，自身 0x81 流处于状态 3（`0xe2144c`，自身所有分块均已确认），对端流处于状态 6（`0xe21404`，对端所有分块均已收到）；状态 7 清除一个标志（[协议 0x81](pia.md#protocol-0x81-the-stream-broadcast-reliable-transfer-pia-6)）。0x97E08 类有相同的一对函数：`0x1e60284` 和 `0x1e615e8`.

在线上，类型 7 通常紧随主机自身记录组的最后一条记录，在 0.11 秒内发出（40 个已通告席位中，37 个为 0.020 至 0.106 秒；其余为 0.545、0.864 和 3.902 秒）。

转发器是一个 0x388 字节对象（虚表 `0x44e56f8`），单例为 `[0x46da9c0]` = `0x4739430`，由 `0x165a200` 从 `0x1659b70` 创建，且仅在尚不存在时创建（`0x1659b18`）。其站点事件处理函数为 `0x12fbb90`，通过跳板函数 `0x2b71650`:

| 事件 | 效果 |
| --- | --- |
| 0，站点加入，主控端上 | `0x12fbf8c` 向其发送当前槽位，除非它就是主控端 |
| 1，自身 ID | 尚未完成的待处理请求以结果 5 完成（`0x501`，位于 `+0x42`），然后 `0x12fbef0` |
| 1，主控端 ID | `0x12fbef0` |
| 1，任意站点，主控端上 | 然后 `0x12fcebc` 丢弃其转发的元素 |

`0x12fbef0` 通过 `0x12fc644` 删除所有槽位（完成键匹配的待处理类型 1 请求），清空七个队列（除 `+0x1c8` 外的全部），并清零 `+0x1c0` 和 `+0x1c4`；保留位于 `+0xb8` 的请求。类型 0 请求只由类型 7 接收器、类型 0x0D 接收器和自身离开事件完成；类型 2 由类型 9 接收器 `0x18b6710` 完成，类型 3 由类型 0xA 接收器 `0x1945404` 完成，类型 4 由类型 0xB 接收器 `0x279be18`.

位于 `0x12fbc3c..0x12fbc4c` 的自身离开路径会以结果 5 完成客户端待处理的类型 2 请求（`+0x40..+0x43 = 02 00 01 05`）。下一个创建器可直接替换该已完成请求，无需重启游戏，包括在类型 9 接受前断线的情况。只有主控端 ID 的离开事件不会完成请求：`0x12fbc70..0x12fbc84` 只调用 `0x12fbef0`。客户端 BoxTrade 作业仍在 15 秒时以结果 4 结束，因为状态 5 会先检查时钟（`0x1e51c74..0x1e51ca4`，基准 `+0x108` 在 `0x1e51c6c` 设置），然后才通过弱引用 `+0xf8` (`0x18ab588`, `0x18ab614`）轮询请求。无论超时路径 `0x1e51d50`，还是作业析构函数 `0x1e51740`（它只通过 `0x18ccdb4` 释放弱引用），都不会触及转发器请求。它仍待处理于转发器 `+0xb8`，而 `0x2799b10` 和 `0x18ab83c` 会拒绝，直到类型 9 或类型 0x0D 接收器，或客户端自身离开事件将其完成。

转发器一直存活至应用退出，因此在 `+0xb8` 处待处理的请求会跨越每次入席、搜索及菜单，直到完成处理运行。其持有器 `0x4739430`（GOT `0x46da9c0`，保护变量 `0x4739440` 通过 GOT `0x46da9b8`）仅由赋值函数 `0x165a2b4`（来自创建器，`bl` 位于 `0x165a230`）、重置函数 `0x279d610` (`str xzr` 位于 `0x279d62c`，随后析构并释放）写入；该重置仅可由转发器自身销毁槽位 `0x279d5ac`（槽位 3）与 `0x2b71660` (`+0x20` 接口槽位 1）到达，二者均无直接调用方；另有静态析构函数 `0xa15f74` (`__cxa_atexit`）。静态分析无法排除对槽位 3 的通用虚调用。虚表 `0x44e56f8`：槽位 0 `0x279a7b0`（析构函数），1 `0x2b7164c`, 3 `0x279d5ac`, 4 `0x12fbb90`；接口 `+0x20` 的槽位 `0x2b7165c` (`ret`）与 `0x2b71660`；接口 `+0x28` 的监听器跳板函数 `0x2b71650`。基类构造函数 `0x165b0c8`（来自 `0x165a998`）安装第二张虚表 `0x44e5768`，具有相同销毁槽位，并设置 `[holder+8] = 1`.

创建器将 `+0x20` 接口通过 `0xf0ba9c` (`bl` 在 `0x165a244`）注册至终结器列表（位于 `0x4763a18`，最多 0x400 项，计数 `0x4765a18`），仅由 `0x27aff48`（槽位 0）和 `0x27b0054`（槽位 1，随后将计数清零）逆序遍历；两者均仅由 `0x20e9c78` 调用，它是虚表 `0x44e6be0` 的槽位 5，位于从 `0x92d648`（`0x443ffd0` 的槽位 5）到 `nn::account::CloseUser` 的路径上：即应用的终结过程。

| 时间 | 站点 | 端口 | 字节 |  |

端口 1 为通道表（《阿尔宙斯》的机制）：站点只有在对端通告某个键后才会在该键上发送。加入端的表与主机端逐字节相同；在其到达前，主机端一直停在搜索画面。主机端必须先打开键 0x80：如果加入端在此之前绘制了交换画面，它就永远不会发送首条游戏消息，对宝可梦按 A 也不会出现菜单。0x7C 可靠头部为九字节，无位图，序号和最低待处理序号均为消息自身序号；打开时标志为 0x0F，后续更新为 0x07。

通道必须在交换画面绘制前打开。若打开较晚，模拟版《朱》4.0.0 的交换盒子中不会出现选择光标；截止时间取决于对端。一台零售版主机在入席后 9.15 秒打开自己的键 0x80：主机端在 6.0 秒打开时会绘制菜单，11.0 秒打开则不会。

主机端将首条游戏消息发送四遍（两个片段，再以下两个 ID 重发，标志 `0x1b`, `0x15`, `0x13`, `0x15`），且只在站点通告键 0x80 后发送；若提前发送，端口 0 上不会分发任何内容；若只发两个（如配对主机端对其克隆实例所做），站点应答 `ack_id` 5, `lowest_pending` 为 5（配对加入端为 4 和 3），游戏永远看不到下一条消息，主机一直停在“正在等待回应”（`--send-on-open`).

主机端在 0x7C 上的确认中，`lowest_pending` 字段携带自身下一个序号，与 0x81 相同。若改为站点最后序号加一，站点会等待该号码，并在 `0x6f03cc` ([接收器会静默丢弃什么](pia.md#what-the-receiver-discards-in-silence)）丢弃主机端接下来序号更小的消息；双方编号在提交时分离，因为站点先提交。`8001` 步骤成对运行：01 与 02，第四字节依次为 03、06、0B、0E；交换在这些步骤中生效，双方画面返回交换菜单。

与 `bin/sv_host.py` 交互时，主机端交换流消息编号为 5（提供宝可梦）、6（确认）、7（提交）、8 至 15（步骤）；主机为 5、6、7 和 8 至 11，其键 0x180 的打开和关闭分别为端口 1 消息 3 和 4；对主机端所提供宝可梦的确认中，`ack_id` 6, `lowest_pending` 为 5。两个完全相同的训练家可以交换。

### 在站点自身提供宝可梦前发送确认

绝不要在提供宝可梦消息 `80000300` 仍在队列中时发送确认 `80000200`：按此顺序接收消息的零售版主机会崩溃（黑屏、系统错误），记录本身未经检查就被保存。`--offer-after-open` 在两个启动器上均以对端的键 0x80 通告为提供消息的发送条件；对于同一站点和端口，都不会将交换消息排到已入队消息之前。

交换动画跟在主机最后一步 `8001010e` 之后，不携带交换消息。在其状态 `b90101b902b90280800100` 之后，主机不再发送应用数据，直到玩家退出。

### 一次入席中的多次交换

键 0x0080 始终保持打开；键 0x0180 每次交换都会打开再关闭。第二次交换重复此循环，序号继续递增（主机端提供消息 16、确认 17、提交 18、步骤 19 至 26），无需新的关联、Session 交互或身份信息。`TradeStage` 和 `JoinerTradeStage` 接受记录列表，每次交换一条；`--trade-offer` 可重复指定。主机请求主机端迁移后能否保留席位，尚未验证。

### 首条游戏消息及其携带内容

`80 00 01 00` 与 2557 字节，分为两个可靠片段，先 START 后 END（配对主机端压缩后 238 字节，零售版主机为 195 字节），各自为独立 zlib 流（`484b`）；消息由两次解压结果拼接而成：

```
b9 02          a tuple of two fields
bc 81 f6 09    a blob, 0x9f6 = 2550 bytes
...            2550 bytes
04
```

该数据块为 850 个小端序三字节值，大部分为 1，其余为位掩码（`0x0fffff`, `0x0002ff`, `0x00003f`、0），每个站点独立：不同站点数值不同（零售版主机与配对主机端之间有 38 个条目不同；条目 36 为 `0x040000` 与 `0x0fffff`）。索引代表什么尚不清楚。它不携带训练家字段：零售版主机的数据中既无 ID 对也无名称。重放配对主机端的四个片段可被零售版主机接受。

### 交换消息携带的记录

一条 `80 00 02 00` 消息的 348 字节消息体由常量 `bc 81 58 01` 和一条采用第八世代加密方式的 344 字节第九世代同行宝可梦记录（PKHeX 的 PK9）组成（`pokeldn/gen8.py`）：从 0x08 开始的四个 0x50 字节块按 `(EC >> 13) & 31` 置换，LCG `seed = seed * 0x41C64E6D + 0x6073` 作用于各 16 位字，并对解密后的消息体截至 0x148 计算 16 位校验和。0x148 处的同行数据尾部不参与置换和校验和，且从加密常量重新初始化 LCG 种子。

```
0x000  u32  encryption constant, in the clear
0x004  u16  sanity, 0 on every record measured
0x006  u16  checksum, in the clear
0x008       four 0x50-byte blocks, encrypted and permuted        -> 0x148
0x148       level, a pad byte and the six stats, encrypted       -> 0x158
```

字段映射采用 PK9 的定义 [`PKHeX.Core/PKM/PK9.cs`]; `pokeldn/gen9.py` 负责读写。

### 构造的记录

由 `pokemon.build` 从零字节构造，或使用 `bin/sv_host.py --offer-set` 编辑（昵称、昵称标志、性格值、个体值）的记录，可交换到零售版《朱》存档中，概要各字段均与构造时一致。交换画面显示构造记录时不做合法性检查；主机端写入校验和。概要中的训练家 ID 为 `(TID16 | SID16 << 16) % 1000000`（12345 和 54321 显示为 993401，8131 和 64817 显示为 855043）；个性描述由加密常量与个体值决定。

等级由经验值决定：0x148 字节为 100 但经验为零时，收到后为等级 1；经验为 1,000,000 时为等级 100。六条成长曲线（`PKHeX.Core/PKM/Util/Experience.cs`）在等级 100 时分别需要 1,000,000、600,000、1,640,000、1,059,860、800,000 和 1,250,000 经验。种类表 `personal_sv`（每种宝可梦及形态 0x50 字节，`PersonalInfo9SV.cs`）在 0x00 保存种族值，0x0C 保存性别比例，0x0F 保存成长曲线，0x12 保存三个特性（种类 132：曲线 0，特性 7、7、150）。接收游戏重新计算同行宝可梦能力：

```
HP    = (2 * base + IV + EV/4) * level / 100 + level + 10
other = ((2 * base + IV + EV/4) * level / 100 + 5) * nature
```

一只满个体值、无基础点数、无能力修正性格的百变怪，即使能力字段全零，等级 1 时也显示 HP 12、其余五项各 6，等级 100 时显示 HP 237、其余五项各 132；等级 1 时发送的 HP 99/99，收到后变为 12。

### 加入端按什么顺序发送

配对加入端在首条游戏消息前的发送过程，时间取自一次抓包：

| 时间 | 消息 |
| --- | --- |
| 0.04 | Session 加入请求 |
| 0.17 | Net 0x12，回显主机端 0x11 的序号 |
| 0.38 | Net 0x51，回显主机端 0x50 的序号 |
| 1.63 | Session 类型 6，确认站点更新 |
| 1.68 | 十一条批量确认，以及 0x81 端口 0 和 4 上的流打开消息 |
| 1.68 | 0x7C 端口 1 上的通道表 |
| 1.82 | Clone Clock 0x77，十八个零字节；主机端应答 1、十六字节和一个尾字节 |
| 2.03 | 0x81 端口 1 上自身的 44 条记录 |
| 2.43 | 0x7C 端口 2 上的打开消息 |

未获应答时，主机会重复 Net 0x11 和 0x50；0x12 与 0x51 可使其停止（一次入席中，无应答时 212 条 Net 消息，有应答时 2 条）。

### 加入端一侧的交换

配对加入端完整的 0x7C 交互流程，各消息标注其端口上的序号：

| 端口 | 序号 | 消息 |
| --- | --- | --- |
| 1 | 1 | 通道表、主机端的四个键、INITIALIZED |
| 2 | 1 | 类型 3 加入，`03b90200bc09` 和九个零字节 |
| 0 | 1 至 4 | 首条游戏消息，发送两遍 |
| 1 | 2 | `b90101b902b90280800001`，键 0x80 打开，在第四个片段之后 |
| 0 | 5 | 提供交换的宝可梦 |
| 0 | 6 | 确认 |
| 0 | 7 | 提交，先行发送 |
| 1 | 3 | `b90101b902b90280800101`，键 0x0180 打开，在主机端自身打开之后 |
| 0 | 8 至 11 | 回显每个步骤的 `8001 01 SS`（03、06、0B、0E）；对于 `8001 02 SS` |
| 1 | 4 | `b90101b902b90280800100` 不发送内容，关闭 |

身份信息在主机端打开键 0x80 后 0.15 秒发送，加入端再过 0.21 秒打开自身通道。

上述 `lowest_pending` 规则同样约束加入端：0x7C 上为自身下一个序号，0x81 批量确认上为自身最高记录 ID 加一。使用主机端编号中的数字会使主机端接收基准越过加入端后续消息，后者在 `0x6f03cc`.

`pokeldn.sv.trade.JoinerTradeStage` 将此侧实现为状态机，由 `bin/sv_join.py --trade-offer` (`--send-on-open` 运行，身份片段受键 0x80 打开条件控制）。`tests/test_sv.py` 使用配对消息中的主机端部分驱动它，并固定验证加入端部分。

### 交换会重写什么

将构造记录交换至零售版主机再由其提供回来，有 27 个字节、七个字段不同：

| 字段 | 发送时 | 返回时 |
| --- | --- | --- |
| `current_handler` | 0 | 1 |
| `ht_name` | 空 | 主机玩家名称 |
| `ht_language` | 0 | 接收主机的语言（3，法语） |
| `ht_friendship` | 0 | 50 |
| `nickname` | 空 | 主机语言对应的宝可梦种类名称 |
| `current_hp` | 0 | 计算后的最大 HP（237，等级 100 的百变怪） |
| `stats` | 零 | 游戏计算的六项能力值 |

其余全部保持发送时的值。空名称返回时变为种类名称，与《剑》的神秘礼物记录相同（`docs/swsh_gift.md`).

若记录的初训家就是接收存档的训练家，经手者保持为 0，且无经手训练家名称，与《传说 Z-A》相同（[交换会写入已接收记录的内容](za.md#what-the-trade-writes-into-a-received-record)）。根据零售版《紫》存档捕获的宝可梦，为其训练家定制的神秘礼物宝可梦（[为接收玩家定制](gift_simulated.md#made-for-the-receiving-player)），从该主机返回时正是如此。

### 加入搜索中的主机：交换及席位决定机制

`bin/sv_join.py` 与从连接交换搜索中充当主机端的零售版《朱》交换，编号方式与配对加入端相同。它将站点更新视为入席，以类型 3 加入应答主机的通告，在主机打开键 0x80 后发送四条身份消息，并应用上述 `lowest_pending` 规则。

#### 席位由什么决定

从搜索中充当主机端的零售版主机，要么运行游戏，要么将主机端角色交给加入端。游戏每尝试浏览 3 至 7 次后建网一次（`RandomMatchingSeq` `0x26e182c`，计数器 `rand%5+4`），等待成员的时间为 3000 + rand%1000 毫秒，每加入一个成员再增加 5000 毫秒（WaitMember，`0x26df898`）。等待超时会进入 JoinRandomRecover `0x26f507c`，该状态离开会话。主机端离开且会话中还有其他站点时，运行 `LeaveMeshWithHostMigrationJob`（仅从网状网络离开 `0x6d4040` 启动）：向 Net 排名最低的站点发送 Session 类型 7（`0x6a012c`），随后每 0.3 秒发送 NetStartHostMigration `01400000`，最多持续 4 秒（[离开](#leaving)）。在 WaitMember 期间加入获准的加入端会看到游戏运行；在其后离开过程中获准的加入端，则在接受后一两帧收到类型 7。加入端的开场内容不影响此决定。`--join-delay 5` 首次与零售版《朱》入席时收到了类型 7；主机玩家在通告后退出时也会发送它。

移交角色的主机会销毁自身网络并重新浏览。`--take-host`（默认）使 `bin/sv_join.py` 在通告前收到类型 7 时，使用该席位的信道、连接密码及应用的主机端标志运行 `bin/sv_host.py`，与 `bin/pla_join.py` 对《传说 阿尔宙斯》的处理相同；零售版《朱》加入了该主机端并完成交换。

运行游戏时，主机依次发送：

|  |  |
| --- | --- |
| 入席 | 类型 5 站点更新，列出加入端的可变 ID 及其请求声明的玩家 ID，随后是 41 字节加入响应 |
| 开场 | 全部十一条流上的批量确认、0x81 端口 1 上一条 11 字节记录及端口 5 上另一条记录 |
| 身份信息 | 0x81 端口 0 上的 46 条记录，并将加入端的 44 条记录确认至 47 |
| 通道表 | 在 0x7C 端口 1 上，键为 `0x007b`, `0x0132`, `0x0232`, `0x0332` |
| `0db90101` | 在 0x7C 端口 2 上，代码为 1，仅用于应答在通告前发送的类型 3 加入请求 |
| 通告 | 在 0x80 端口 2 上，zlib，解压后 167 字节：类型 7，种类 1，容量 2，以及主机站点 ID |

加入端以类型 3 加入请求应答通告（`--port2-now` 则随通道表一起发送）。零售版主机仅用站点更新就使加入端入席，早于任何加入响应；若加入端等待加入响应，整个会话都不会发送内容。

## 离开

退出席位的主机根据自身角色运行两种 Pia 作业之一。两者均等待对端，并在计时器到期后放弃。

已加入的主机运行 `LeaveMeshJob`。SendLeaveRequest `0x6db590` 发送 Session 类型 3 离开请求（布局见 [docs/pla.md](pla.md#leaving)），并设置 500 毫秒截止时间（`0x6db6a0`）；WaitLeaveResponse `0x6db7b0` 在到期时重发，在第四次发送后完成（`[job+0x6c]` 超过 2，`0x6db8e8`），或在 `[job+0x69]` 置位后立即完成。Session 分发器（`0x6d4960`，表 `0x3c0cd3b`，类型 0 至 0xA）将类型 4 交给 `0x6d7b10`；若为 17 字节消息，且第 5 至 16 字节是站点自身的位置 ID，它便设置 `[job+0x69]`：

```
04 | u32 random | location id (12), copied from the request
```

主机端的类型 3 处理函数 `0x6d7894` 在通过固定 ID 和可变 ID 找到站点后，恰好写出上述形式（类型字节位于 `0x6d7a50`，从 `0x6c70a8` 获取一个新的 xorshift 随机值，在 `0x6d7ad8` 发送）。未获应答时，零售版主机会以 0.49 至 0.54 秒间隔发送四次离开请求，并在首次请求后 2.04 秒解除认证（一次追踪会话）。获应答时，只发送一次离开请求，并在 0.04 秒后解除认证。`bin/sv_host.py` 应答第一次请求（`--no-leave-response` 则不应答）；`tests/test_sv_departure.py` 在 unicorn 下通过 `0x6d7b10` 运行该应答。

从搜索中充当主机端的主机会移交主机端角色。`LeaveMeshWithHostMigrationJob` 向下一个主机端发送 Session 类型 7，并每秒重发一次（`0x6df050`），直到类型 8 指定该站点（`0x6ded94`），5 秒后放弃（`0x6defb8`）。类型 7（写入器 `0x6d8de0`）为 34 字节：

```
07 | host location id (12) | 00 | host IPv4, port | next host's location id (12) | u16
```

最后的 u16 为作业的 `+0xe0` (`0x6d8ea8`），三份零售版消息中为 0 或 1。然后 `NetDestroyNetworkJob` 以主机端迁移形式等待所有客户端收到连接状态更新（最多 4 秒，`0x6ac68c`），每 300 毫秒发送 NetStartHostMigration `01400000`（仅由 `0x69d310` 写入，仅从 `0x6aca54` 调用）（`0x6aca98`），直至网络站点数为 1（`0x6acaf4`）或超过截止时间（4 秒；若更新等待已超时则为 2 秒，`0x6ac984`），随后销毁 LDN 网络。在线上，该更新为设置 is-migrating 的 Net 0x11；加入端的 Net 0x12 之后 45 毫秒出现首个 NetStartHostMigration。客户端收到 NetStartHostMigration 后启动哪种作业尚未追踪；`NetHostMigrationJob` 以 DisconnectNetwork 或 EmulateDisconnection 开始（`0x6a93c4`).

若加入端立即应答类型 7 并保持席位，主机会发送 12 至 14 次 NetStartHostMigration，最后一次在类型 7 后 3.5 至 4.1 秒；一次已追踪席位中，主机网络在类型 7 后 4.3 秒关闭，此前发送了以太类型为 `88b7` 的 LDN 广播。若加入端在类型 7 后 3.0 秒离开，主机广播会在 0.5 秒内消失，早于主机自身的 4 秒截止时间。`bin/sv_join.py` 在首个 NetStartHostMigration 时离席（`--stay-on-host-migration` 则保持席位）；类型 7 后 0.14 秒便离网，此时仅发送了一次 NetStartHostMigration。

完成交换后，两个启动器都会在主机离开时退出。若席位未完成任何交换，`bin/sv_join.py` 可恢复扫描（[结束运行](architecture.md#ending-a-run)).
