# 太晶团体战

本地太晶团体战是一个运行于 LDN 场景 7、最多包含四个站点的《朱／紫》会话。主机端管理大厅，随后向每位参与者发送一条引导消息，其中包含四位玩家的宝可梦、首领及其 RaidPoint，各主机随后独立进行战斗。`bin/sv_host.py --raid-seed` 创建供零售版主机加入的团体战，`bin/sv_join.py --raid-pokemon` 则加入主机创建的团体战；两种情况下，程序玩家都会在战斗开始时离开，其宝可梦则继续作为主机的 AI 伙伴战斗。地址均为相对于解压后的 `main` 的偏移，对应《朱》4.0.0，即本文测量所用零售版《朱》的版本；《紫》4.0.0 在相同偏移处具有相同代码（[docs/sv.md](sv.md)).

## 作为主机端

主机端广播场景 7、四名参与者及连接密码 4970。主机通过 X、宝可入口、太晶团体战、离线搜索加入。`--raid-seed` 配合四个上下文标志选择团体战（[种子](#the-seed)), `--raid-pokemon` 是我方玩家携带的同行宝可梦记录（由 PKHeX 检查），而 `--raid-reward ITEM:QUANTITY` 可重复指定，用《朱／紫》背包可容纳的道具条目替换种子的奖励（PKHeX 辅助工具的 `bag` 列表：包含除重要物品外的所有口袋，排除未发布道具）。`--raid-partner TRAINER` 对主机留空的每个槽位最多指定一次（一台主机时两个，两台时一个），按槽位顺序安排这些 NPC 伙伴，而 `--raid-partner-progress STAGE` 选择它们所属的进度阶段（[伙伴](#partners)）。应用的“太晶团体战（主机端）”工具包含下述标志。

```
--channel 1 --scene-id 7 --max-participants 4 --code 4970 --scarlet-response --session-flags 0
--session-packet-id 1 --no-session-ack --join-seq 0 --update-seq 0 --update-delay 0.02
--rtt-probe --clock --net-stations 4 --record-delay 0.1 --record-spacing 0.003
--host-player-id 00000000000000010000000000000000
```

团体战模式下，主机端在寻址对象和发送时机上与交换主机端不同：

|  | 团体战主机端 |
| --- | --- |
| 网状寻址消息（RTT、0x80、0x81）、Session 站点列表 | 发往子网广播地址，而非主机地址（在 ldn_mitm 下使用单播，因为它不向对端转发广播） |
| Net 0x11 | 同一序号，持续重复直到收到 0x12 |
| 站点列表中的主机条目 | 使用主机加入请求指定的玩家；若使用占位玩家，主机虽入席却不会出现在大厅中 |
| 站点列表 | 每 2 秒重发，直到收到主机的类型 6 |
| 开场 | 仅在该类型 6 之后：首批十一条批量确认、0x81 端口 5 打开及一个 RTT 请求合为一包；然后是 0x81 端口 1 打开、通道表及端口 2 类型 6；再过 20 毫秒发送身份信息，每 3 毫秒一条记录 |
| 端口 2 类型 3 | 以两个类型 9 应答：主机端站点使用代码 0，主机站点使用代码 1 |

开场的 0x7C、0x81 端口 5 和 0x80 端口 2 消息每 0.25 秒重复一次，直到确认；主机端发出的每个确认都声明该流最低未确认序号。

### 多台主机

`--raid-players N`（1 至 3，应用中的“加入的主机数”）可在同一大厅安排最多三台主机，每台分配最低空闲站点索引 1 至 3。各主机共享大厅与开场；从首回合起，各自独立战斗，拥有自己的 NPC 伙伴并获得自己的奖励（[哪个站点运行服务器](#which-station-runs-the-server)）。主机端为每台主机分别维护一套流，与单主机情况相同，只是把单主机团体战中所有索引 1 替换为该主机索引：

|  | 索引为 *k* |
| --- | --- |
| 加入响应 | 站点索引与加入顺序均为 *k* |
| 站点列表 | 包含所有已入席站点，我方在前；每次新入席或离开大厅，均以下一序号向所有已入席主机发送列表，并重发直到各自返回类型 6 |
| Net 0x11 | 我方站点在前，随后按索引列出已入席主机，最后为加入端；每次席位变化都以各自下一个序号发送给所有已入席主机 |
| 目标位图 | `1 << k`，目标位数为三 |
| 批量确认 | 条目 *k* |
| 开场 | 0x81 端口 *k* 和 4 + *k*，即主机发送所用端口 |
| 端口 2 类型 6 | 按加入顺序列出我方与已入席成员，包含各自代码和计数 |
| 端口 2 类型 9 | 我方使用代码 0，各已入席成员使用自身代码，最后为该主机，使用代码 *k*；每个已入席成员都会收到该主机的条目 |
| 引导消息 | 其宝可梦位于槽位 *k*；空闲席位对应空槽位 |

所有席位均已占用或开始之后到达的加入请求，不予应答；没有空闲席位的主机不会收到 Net 0x11。主机端丢弃头部及尾部未指定自身可变 ID 的每个数据包，以及位图不含站点 0 的每条可靠消息：同一大厅内的主机通过同一个广播地址彼此寻址。

端口 2 槽位在槽位 `+0x170` 处保存成员，以 u8 代码和 u64 站点 ID 表示；`0x138d208` 返回站点代码，非成员返回 0xfd。零售版主机端的类型 3 处理函数 `0x1981e94` 选择 0 至 7 中未被成员持有、也未被排队类型 9 指定的最低代码（`0x279c9a0`），随后为每个成员广播一条包含其代码的类型 9，再为加入端广播一条。接收器 `0x18b68fc` 追加尚未列出的 `(code, id)`，从不改变已列成员的代码；对于自身 ID，它为其余每个成员触发成员加入事件，并将该代码设为自身代码。类型 6（`0x12fbf8c`，构造器 `0xe457cc`，仅发给加入中的站点）在 `+0xa0` 携带成员 ID，在 `+0xc0` 携带其代码，在 `+0xc4` 携带计数，在 `+0xc5` 携带关闭字节；其接收器 `0x279b9c4` 为每个成员重放一条类型 9。

大厅参与者就是端口 2 成员：Lua 大厅（代码块 `be21e654`，接收器 `0.15829`；这里的 `0.N` 表示代码块主函数中从 0 计数的第 N 个函数原型）按发送方代码归档每条消息，无代码发送方归在 253 下。各主机进入大厅时向其他主机发送自身状态 0x18 与宝可梦；站点收到 0x18 后，以自身准备状态和宝可梦应答；同一大厅的主机会彼此交换宝可梦信息。

可靠头部的接收检查（`0x6f0410`..`0x6f0430`）在目标计数为 1 至 23 时，都测试接收器自身的位，即字 `index & 31` 中的 `index >> 5`（第 0 位对应站点 0）。无论站点数量多少，零售版发送方都写入三，即站点容量 4（`0x44dfcb0`）减一（`0x6e71c4`）。

主机端将网络交给仍在网络中的最低索引站点，与单主机情况相同；其余主机收到带 is-migrating 的 Net 0x11 和 NetStartHostMigration，但不收到 Session 类型 7。发给每台主机的 is-migrating 0x11 会为每个已入席站点排名（排名决定下一个主机端），且只有在下一个主机端返回类型 8 后才发送给其余主机；所有主机均以 0x12 应答各自的 0x11 后，才发出 NetStartHostMigration，此后不再发送普通 Net 0x11。所有主机均已离网或各次移交均超时后，本次运行结束。

决定主机是否继续处于同一场战斗中的条件：

| 条件 | 代码 |
| --- | --- |
| 主机看到另一台离开时，只有处于迁移中才保留它：`[net+0x249]` 由 is-migrating 0x11 设置，或 `[net+0x1c0]` 由 NetStartHostMigration 设置；否则从会话中移除它并重置其 Net 站点 | 站点离开处理函数 `0x69d08c`, `0x69d174` |
| 序号更新的 Net 0x11 会移除所有标记为已离开的站点 | `0x69e008`, `0x6b5074` |
| 下一个主机端最多等待 8000 毫秒，让每个 Net 站点达到状态 2（在其新网络上被发现）；随后移除仍处于状态 1 的站点，发送 Net 0x11，等待所有 0x12，然后发送 Session 类型 5 | NetHostMigrationJob `0x6a9cd4`, `0x6aa2a8`; `0x6d44f0` |
| 另一台主机等待该类型 5，10000 毫秒后失败 | `0x6dc024`, `0x6dc124` |
| 类型 7 的最后一个 u16 不大于下一个主机端已应用的列表序号 | `0x6d9164` |

两个模拟版《朱》以此方式移交后，在下一个主机端网络上组成同一会话（以类型 6 应答类型 5，双方画面均无错误），并与空闲席位中的 NPC 一同继续战斗。

LDN 参与者每次变化时，Pia 主机端都会向每个站点发送新的 Net 0x11：`0x69c310` 比较先前和当前的连接状态，`0x69c79c` 递增唯一计数器 `[NetProtocol+0x60]`，并向除自身外的每个站点发送全部槽位，排名按 IPv4 升序排列（`0x6a05ec`）。在 LDN 上，加入端的 0x11 接收器 `0x69db14` 不会根据其中的条目创建站点（`0x6a2fac` 返回 0）：它保存主机端地址和 ID，将排名复制到已有站点，并应答 0x12。加入端站点来自 LDN 节点列表（`nn::ldn::GetNetworkInfo`, `0x6b43a8`），端口为 12345。

类型 5 接收器 `0x6d7f8c` 仅在新列出站点的 IPv4 和端口存在于节点列表时，才在 `0x6d840c` 中创建该站点（`0x6a8320`）；否则不发送类型 6，并将已应用序号重置为 0xffff（`0x6d81a4`），使之后收到的同一列表副本可再次评估。

Session 类型 9（`0x6d4ef0`），由加入端发给主机端，`09 | its constant id | count | count constant ids`，指定尚未收到其消息的站点（`0x6d4a60`），每 3000 毫秒重复一次。主机端接收器 `0x6d940c` 将单个被指定站点交给踢出作业（`0x6dc878`），并向每个站点重发站点列表。

主机加入后，团体战主机端发送数据包 ID 0，否则已入席主机会丢弃较高 ID 后续的数据（[docs/pia.md](pia.md#version-11-what-a-receiver-drops-scarlet-400)）：在 ID 87 的包之后以数据包 ID 1 重发站点列表，会使双主机大厅的第一台主机保留旧列表（零售版和模拟版均如此），第二台则显示“正在通信……”直到报告第一台无响应。将后续列表以数据包 ID 0 发送后，两台模拟主机及两台零售版《朱》均能列出彼此，并在主机端离开后保持同步进行同一场团体战。

形如 `10 00` 加十四个随机字节的随机玩家 ID 无法使零售版主机返回类型 6；匿名 ID `00000000000000010000000000000000` (`pia_connect.DEFAULT_PLAYER_ID`）则能使其入席。

## 大厅

团体战消息是 0x80 端口 0 上的游戏消息：一个 u16 处理器键、一个种类字节、一个步骤字节（[交换](sv.md#the-trade)），随后是游戏序列化器的头部和负载。

| 字节 | 字段 |
| --- | --- |
| 0 | 处理器键，u16 |
| 2 | 种类、步骤：合为一个 u16 消息 ID（0x012f 为引导消息，0x0193 为战斗开始） |
| 4 | 每个发送方独立的 u16 计数器，每次发送由 `0xa583fc` 递增：零售版主机端大厅从 0x0105 到 0x010e，加入端为 1、2、3…… |
| 6 | 压缩方式，u32：0 无压缩，2 LZ4 |
| 10 | 负载明文大小，u32 |
| 14 | 网络对象 ID，u16，默认为零，除非发送方的 `0x14ede48` 找到一个对象 |
| 16 | 构造函数从不写入的两字节填充（零售版消息中为堆残留数据） |
| 18 | 负载 |

| 键 | 种类 | 作用 |
| --- | --- | --- |
| 0x3380 | 0x2c | 团体战描述符：种类（DevID）、形态、星级、太晶属性、性别、遭遇记录编号 |
| 0x3380 | 0x2d | 参与者状态：0x00 未准备，0x01 已准备，0x0c 主机端开始，0x0d 加入端对此的应答，0x18 进入大厅，0x1e 主机端拒绝迟到站点（`0.30822`) |
| 0x3380 | 0x2e | 参与者的宝可梦，其加密后的 344 字节同行记录 |
| 0x3380 | 0x2f | 战斗引导消息 |
| 0x3380 | 0x30 | 大厅计时器，剩余秒数（从 0x91 向下递减） |
| 0x0132 | 0x6e、0x73 | 主机正在加载战斗，随后加载完成 |
| 0x3480 | 0x93 | 战斗开始 |
| 0x007b | 0x13 | 主机端在 0x3480 之后发送的战斗开始消息 |

零售版加入端进入大厅时发送 0x18 与自身宝可梦，玩家按下准备时发送 0x01：七次零售版团体战中，四个加入端在宝可梦信息后 1.9 至 3.6 秒发送 0x01，三个在主机端于 5.39 秒开始前未发送；七个全部以 0x0d 应答开始并进入战斗。

头部为消息对象的 `+0x40..+0x4f`。接收路径 `0x18bec54` 将 ID、计数器和对象 ID 复制回对象，不比较其中任何字段；不检查 LZ4 返回值，明文大小仅用作输出容量。

键 0x007b 上的战斗开始帧由 12 字节端口地址（三个 u32）、一个 u32 长度和负载组成；负载前 32 字节为头部结构，由 `0x1227714` 原样复制：0x00 处为 u32 类型，0x08 和 0x10 处为 u64，0x18 和 0x19 处为 u8，0x04 及 0x1a..0x1f 为填充。消息 15 在 0x18 携带 `05 05`，随后是填充 `07 26 5a 00 00 00`；消息 16（类型 0x46，构建器 `0x2898350`）在构建器从不写入的填充区域携带 `ceaf29`。读取器 `0xf5a2fc`（+0、+8、+0x10、+0x18，接受 5 或接收器自身索引）和类型分支 `0xe10088`（0x46 处理函数 `0x2897afc`）都不读取填充。`0x14ab234` 会丢弃帧，除非接收器的某个端口已注册其地址：消息 15 地址为 (0x2713, 1, 2)，消息 16 至 20 为 (0x2713, 3, 5)，其中 0x2713 是某对象 `+0x40` 处的运行时 u32，其写入方未追踪。向模拟版《朱》4.0.0 提供填充清零的消息 13、15、16 后，每条战斗开始消息首次发送就得到确认，并使用主机端宝可梦开始战斗，与使用零售版字节相同。模拟版《朱》4.0.0 在主机端发送消息 15、16 后走了保留分支 `0x14ab210`，间隔 13 毫秒：`0x14ab234` 匹配了战斗开始帧的地址，而 `0x14ab298` 保存了它。

战斗根据类型读取消息 16。读取器 `0xe0fd68` 弹出一帧；头部 +0x08 的 u64 为 0 时，按 +0x00 的类型分支（`0xe10088`）：类型 0x46 调用 `0x2897afc`，唯一参数为 `[reader+0x48]`，然后 `0x2897afc` 在其 `+0x71` 处存入 1。该参数是逐帧更新函数 `0x289358c` 自身的对象：`0xfa4bb4` 使用初始化器 `0x28950c8` (`+0x40` 构建它；战斗状态机在这里为 `sm`; `+0x48`，被逐步执行的对象为 `[sm+0xa8]`, `+0x50`，读取器为 `[sm+0xb0]`），将其保存于 `[sm+0x148]` (`0xfa4c18`），并在 `reader+0x48` (`0x2892ab4` 处赋给 `0xfa4c68`）。状态 `0x28932a4` 使用 `[sm+0x148]` (`0x28932d0`）调用更新。更新读取 `+0x71`：该字节为 0 时驱动读取器（`0xe0f014`）并调用 `0xfc363c([+0x48], 0)`；为 1 时停止驱动，每帧调用 `0xfc363c([+0x48], 1)`，而 `0x28935b8` 在其返回 true 时清除此字节。为 1 时，`0xfc363c` 从 `+0xa8` 处的源取出一项，交给位于 `+0xa0` 和 `+0xb8` 的接收端，条件是 `[+0xb8]+0xa0` 处的接收端为空。接收端持有双端队列（映射表 `+0x60`，起点 `+0x98`，大小 `+0xa0`），每帧执行各元素的 vf `+0x68`（`0xfc38dc`）。更新结果未被使用（`0x28932d4`），此路径没有任何位置写入状态机位于 `+0x68` 的状态。模拟版《朱》4.0.0 在类型 0x46 分支弹出一帧，其中携带主机端写入消息 16 填充区域的标记（`46000000 d16a1616`, `0500 161616161616`）：该帧确为消息 16。弹出发生在网络关闭后、错误 7 对话框后、首个指令菜单前，由更新自身的驱动流程触发（返回地址 `0x28935d0`，随后 `0x28932d4`).

4.0.0 中没有任何判定读取填充。接收路径加载序列化头部最后两字节（`0x18bec98`），并存入 `+0x4e` (`0x18bece4`），不作比较；49 个消息类中，仅序列化器 `0x290b150` 和 `0x14c7904` 会加载 `+0x4e`，用于写出头部。战斗开始读取器 `0xe0fd68`, `0xe106a4`, `0xf5a2fc`, `0xf5a810` 和 `0xf5bc10` 读取 32 字节头部的 +0x00、+0x08、+0x10、+0x18 和 +0x19；`0xf5a454` 和 `0xf5ae40` 将全部 32 字节复制到帧中，由 `0xf5bb4c` 重发，不比较任何字节。传输层复制函数（`0x14ab150`, `0x14ab234`, `0x16a319c`）只比较 12 字节地址。

团体战主机端在 0x7C 端口 1 通告的通道表包含六个键，使用 zlib 压缩：连接交换的四个键（`0x007b`, `0x0132`, `0x0232`, `0x0332`）以及 `0x3380`, `0x3480`。零售版加入端分两条消息通告它们：先四个，再于 0.79 秒后通告团体战的两个。端口 2 承载主机端的类型 6：类型 7 的会话块，种类为 5、容量为 4，随后为四个槽位的列表，第一个放主机端站点 ID（`port2.build_session`).

计时器表示距主机端大厅截止时间的剩余秒数：零售版主机端建立 180 秒大厅，每秒发送一次该值（`0.27104`），因此表中的 0x91 出现在大厅建立后 35 秒。我方计时器在第一台主机应答时从 180 开始；加入已运行大厅的主机会收到当前值。主机的 0x00 或 0x18 会撤销其 0x01；宝可梦消息不会，因为已准备主机会向每个新加入者重发它。

游戏代码中，加入端立即以 0x0d 应答 0x0c，不检查是否准备；计时器到 0 的加入端会等待引导消息（`Raid_Start_Ready`, `0.27137`）：只有主机端启动战斗。已收到引导消息但未准备的加入端会在计时器到期前结束大厅（`0.27104`），并以相同方式进入战斗。零售版主机端在玩家第一次选择时准备，第二次选择时发送 0x0c（`0.27095`). `Raid_Start_Ready` 在进入时关闭菜单前三项（`f6277C172(false)`），主机端和加入端均如此；在主机端上，只要其余所有成员已准备，就重新启用第一项（开始项）及菜单，某成员未准备时再关闭：玩家只有在所有加入端均准备后才能开始。`f6277C172(false)` 究竟隐藏菜单项还是将其置灰，尚未确定。计时器为 0 时，若无人准备则解散大厅，否则开始。`Raid_Start_Go` (`0.27140`）重复发送 0x0c，直到每个成员都应答 0x0d，然后发送引导消息，槽位 *k* 放置代码为 *k* 的成员宝可梦；我方也等待每台主机的 0x0d，在全部准备后开始，或在计时器为 0 时带已准备者开始。

受条件控制的消息在对应里程碑后 50 毫秒发送；Net 0x50 和站点列表每 0.5 秒重复直到应答，团体战消息每 0.5 秒重复直到确认。一次零售版主机以 0x73 应答引导消息而未发送 0x6e，因此消息 13 等待任一者。

最后一台主机的消息 20 之后五秒，主机端像正在离开的零售版主机端那样，将网络交给主机（[docs/sv.md](sv.md#leaving)）：每秒发送指定该主机的 Session 类型 7，直到收到其类型 8；每 0.5 秒发送 is-migrating 形式的 Net 0x11，直到收到其 0x12；每 0.3 秒发送 NetStartHostMigration `01400000`，直到主机离网或经过 4 秒。若改为在消息 20 后 5 秒直接销毁网络，四次零售版团体战中有一次在开战时主机画面出现 2318-0006，之后战斗以离线方式继续。

Net 0x50 使用交换主机端的属性消息体（`NET_PROPERTY_BODY`），序号为 1，带网络 ID，第 27 字节设为 7，+38 处为主机端 132 字节应用数据，以 zlib 压缩并带消息标志 0x31。在 0x31 下不压缩发送时，未得到 0x51。

## 战斗引导消息

消息 0x2f 携带一条 0xaa0 字节记录，使用 LZ4 压缩（仅块格式，`pokeldn.sv.lz4`):

| 偏移 | 大小 | 内容 |
| --- | --- | --- |
| 0x000 | 4 × 0x158 | 四名参与者的加密同行宝可梦记录，主机端位于槽位 0 |
| 0x560 | 0x158 | 首领的同行宝可梦记录 |
| 0x6b8 | 0x3e8 | RaidPoint |

序列化器 `0xe327fc` 写出来自消息对象以下字段的五条记录：`+0x440`, `+0x448`, `+0x450`, `+0x458` 和 `+0x50`，使用的写入函数为 `0xe329b4`（每条 0x158 字节）；然后写出来自以下位置的四个四字：`+0x58`，以及来自以下位置的 0x3c8 字节：`+0x78`。对象（0x460 字节）由 `0x18bb4fc` 创建，由 `0x18bb5f8`; `0x1592b7c` 写入序列化器头部并选择压缩方式，`0x1592dac` 和 `0x1592e80` 执行 LZ4（`0x71d940`）。RaidPoint 整体复制：`0x1bae670` 调用 `0x1bae760`，后者通过反射字段 getter `0x1baff98` 获取它（位于 `+8` 的指针，或一个清零的 0x3c8 字节单例），复制到 `+0x78`，复制操作由以下函数完成：`0x1bb0018`.

空参与者槽位包含种类 0、等级 1、昵称为 `Egg`、太晶属性 19、语言 2、当前 HP 11、能力 11/5/5/5/5/5 的记录，每份零售版引导消息中都相同；空槽位全零的引导消息会使零售版主机在开战时崩溃。加入端的槽位 1 使用其大厅消息 0x2e 中的记录。零售版主机端在 1395 字节处拆分消息，第二个片段使用 zlib 压缩。

团体战表中每条六星记录的 `raidTimeData` 均启用，`gameLimit` 为 450，`commandLimit` 为 60；每条一星记录均未启用，`gameLimit` 为 300，其余为零；零售版黑色点位（记录 6045）携带 1、450、0、60，零售版三星点位（记录 3019）携带未启用的 bool 字节，后跟三个残留字节，再后为零。两个零售版点位的 0x3b5..0x3b7、0x3d4..0x3d7 和 0x3e4..0x3e7 均含残留字节。

行动配置按顺序取自游戏团体战表中记录的 `bossDesc`；行动为 0 无、1 重置首领能力变化、2 重置玩家能力变化、3 招式、4 吸取太晶珠能量，时机为 0 无、1 时间、2 HP。行动数值表示触发该行动的首领 HP 或剩余时间比例，护盾的前两个值表示启动护盾的 HP 和时间比例，任一满足即可；2026 年 8 月七星仆刀将军在 Serebii 上列出的脚本行动，从其记录读取的结果相同。一至六星的 HP 系数依次为 500、500、800、1200、2000 和 2500。

零售版点位的奖励行依次为种子的固定行、抽奖结果、主机端加成行：适用对象 4 下三行、适用对象 5 下一行。固定行的适用对象来自奖励表的 `SubjectType`（0 所有玩家，1 主机端，2 加入端，3 仅一次）；游戏枚举 `RaidRewardItemSubjectType` 不包含 4 或 5。两个零售版点位中，适用对象 4 的行均为在同一生成器上额外抽取三次种子抽奖表的结果；适用对象 5 的行为首领的太晶碎块，数量由 `RaidGemItemRewardBoost` 根据难度给出（一至七星分别为 0、0、2、5、10、12 和 0；三星为 2，六星为 12）。食力表读取器 `0xef885c` 读取一个团体战字段，`AddRewardSlots`。奖励行的第三个字在银色王冠抽奖行中为 1，其余为 0。

给模拟版《朱》4.0.0 加入端分别发送适用对象 0 至 5 各一行后，其奖励画面列出 0、2、3、5，省略 1 和 4。启用餐点的幽灵属性团战力 Lv. 1 后，面对钢太晶首领时省略适用对象 4，面对幽灵太晶首领时列出；此时发送三行适用对象 4，只列出首行。面对幽灵太晶首领发送四行适用对象 4，食力等级 2 时列出前两行，等级 3 时列出前三行。

生效食力在内存中保存为 u32 种类、u32 属性、u32 等级和 f32 剩余秒数，进食时为 1800，在野外倒计时。上述等级 2 和 3 测试及下述测试，均修改了火腿黄油三明治的幽灵属性团战力 Lv. 1 记录中的等级字与属性字。

在黑色结晶点位（种子 `09F3E337`，妖精太晶仆刀将军）中，启用妖精属性团战力 Lv. 3 后，同一加入端列出该点位 19 行中的 18 行：全部适用对象 0 行、适用对象 2 行、三行适用对象 4，以及适用对象 5 的妖精太晶碎块 ×12；省略适用对象 1。唯一带稀有道具标志的行，即适用对象 4 的银色王冠，出现在画面首位；其余保持点位顺序。该点位来自 `raid_point`，仅替换行动配置（HP 系数 100，其余零），让单个加入端能够获胜；星级、结晶、`raidTimeData` 和奖励行均保持种子原值。

《朱》4.0.0 的 Lua 奖励过滤器 `C07C34FC3B976E5A7.F316609DEA110601D`（按其字节码记录为第 78707 至 78765 行）对所有玩家保留适用对象 0，对主机端保留 1，对加入端保留 2，在其一次性奖励资格参数为 true 时保留 3。它保留前 N 行适用对象 4，其中 N 为与首领太晶属性匹配的生效团战力最高等级。食力种类 5 为团战力；属性 18 匹配所有太晶属性。适用对象 5 要求接收玩家背包中有道具 2481，即晶耀护符。每遇一行适用对象 4，行计数器都会递增。用测试框架提供原生环境 getter，执行未修改的 Lua 函数时，无论主机端或加入端、有无护符，等级 0 至 3 分别保留零、一、二、三行适用对象 4。属性不匹配时保留零行；存在多个匹配食力时使用最高等级。

要匹配零售版奖励构建方式，主机端须保留每条固定行的适用对象及每行稀有道具标志，将普通抽奖行写入适用对象 0，再追加三次连续抽奖结果于适用对象 4。若对应难度的太晶碎块加成数量为正，则追加至适用对象 5。各接收方自行应用食力与护符资格判定。

计时器初始化器 `C2D7F486425487755.F0C64BA9B6853E61A`（按其字节码记录为第 79486 至 79513 行）在 `raidTimeData.active` 为 true 时使用提供的时间字段；为 false 时，多人战斗使用游戏时限 300、指令时限 60、客户端时限 0、复活时间 30、AI 间隔 17 和 AI 间隔随机量 6。用六星表数据执行其未修改的 Lua 函数，依次得到 450、60、0、0、0 和 0；清零的 RaidPoint 则得到默认值。两个函数都在 Lua 代码块 `be21e65463b9a98f` 中，SHA-256 为 `c1a4f4e2625912cf0b739a642a79ba3357df0557a544b92da22a6cb139de2815`.

`raid_point` 按零售版主机端方式构建种子奖励行：每条固定行的表适用对象、抽奖表稀有标志、适用对象 4 下额外三次抽奖，以及适用对象 5 下对应难度的太晶碎块加成。种子 7B741233（三星）和 09F3E337（黑色）的 45 行与零售版点位逐字节相同。向持有晶耀护符的零售版《朱》加入端发送种子 7B741233 的奖励行后，列出冰太晶碎块 ×1 和 ×2：包含适用对象 5 行，不包含主机端的适用对象 1 的 ×1 行。自选奖励置于适用对象 0，且无加成行，因此加入端会收到全部奖励。将某行改为先机球 ×500，清除其余行但保留一条加成行后，零售版主机按写入值发放奖励。

## 伙伴

每台主机都用相同的 NPC 训练家填充未被大厅成员占据的参与者槽位；抽取依据是 Lua 称为 `randSeed`（0x3d8 处 u64）和 `raidNpcGroupID`（0x3e0 处 u32）的两个 RaidPoint 字段（`0.4453`）。其 getter 背后的原生函数读取 RaidPoint 前 0x20 字节之后的 0x3c8 字节结构中的 +0x3b8（`0x1be5ac0`）和 +0x3c0（`0x1be5c20`）。加入端引导处理器读取两者（`0.15829`）；零售版主机端每次开始时生成新的 `randSeed` 并写入两者（`Raid_Start_Go`, `0.27140`）。整个 u64 用作 xoroshiro128+ 种子（原生函数 `0x17ebec0`），第二个字为 `0x82A2B175229D6A5B`。主机抽取三名训练家（`0.7804`），每次以 `next_int(n)` 从池中剩余 n 名训练家中抽取（按 n − 1 所需位数掩码，值大于等于 n 时重抽），并将选中者移出池，因此完整池的上界依次为 18、17、16。空槽位按槽位顺序使用抽取结果（`0.4455`）：只有一个空槽位时，无论位置在哪都使用第一次抽取。

伙伴记录从同一个 `randSeed` 中进行五次 xoroshiro128+ 抽取，一场战斗中的所有伙伴共享这些结果（`raid_partners.identity`）：第 0 次为加密常量（为 0xffffffff 则重抽），第 1 次为 TID | SID « 16，第 2 次为 PID（若会成为异色，则翻转第 28 位），第 3 次为身高，第 4 次为体重，后两者均为 0x30 + next_int(0xa0)。其余字段均来自训练家条目（见下），语言为 2，亲密度使用该种类的基础亲密度。仅依据种子、阶段和等级，这些规则即可得出五场模拟团体战中全部十条伙伴记录，每条 0x148 字节。

团体战开始函数（`0.4455` -> `0.4459` -> `0.4901`）将每个伙伴的 `poke1` 表、等级以及 `randSeed` 交给 Lua 绑定 `f92C18AA6` (`0x1905a10`）。它构建种子为 `randSeed` (`0x1905ce0`）的 pml InitialSpec，将表转换进该对象（`0x160ffd0`），再创建 PokemonParam（`0xdebe4c` -> `0xdec698` -> `0xdef2b8`）。已设置种子的 `0xdef2b8` 使用自身 xoroshiro128+ 进行全部抽取（`0xdf78bc`, `next_int` `0xdf78d8`），依次处理规范中未设置的字段：EC、ID、PID、个体值、特性、性别、性格、身高、体重、体型比例（`0xdf011c`）。绑定第三个参数为 true，因此转换器将仍为随机的身高、体重或体型比例转换为体型类别 M（SizeType 3，`0x1611cc4`），由 `0xdf011c` 按 0x30 + next_int(0xa0) 抽取；随机类别则为 next_int(0x81) + next_int(0x80)。在 unicorn 下执行，`0xdef2b8` 仅使用体型类别 M 才能复现十条记录的 EC、PID、身高与体重，其他类别均不行。

对于 `sex` 为 0 的条目，转换器在抽取加密常量前根据该未设置字段确定性别：种类的雌性百分比至少为 (2^64 - 1) mod 100 = 15 时为雌性，低于 15 时及等于 50 时为雄性（50 时由绑定第四个参数 0 决定）；单一性别或无性别种类保持自身性别（`0x1611d1c`）。卡蒂狗和风速狗为雌性，小磁怪、三合一磁怪和青铜钟无性别，其余伙伴为雄性。`gemType` 为 0 时，太晶属性交由 `0xe78418` 读取的按种类表决定，键为 species x 10000 + form；双斧战龙取龙，土王取地面。

0x3e0 处的 u32 选择池，即数据表字段 `difficulty_0`*N+1* (`0.7797`）、训练家及其宝可梦（下表）：0、1 为前 16 名训练家，2 为全部 18 名，3、4 也为全部 18 名。池来自 RomFS 表 `world/data/raid/raid_trainer_01`（16 行，阶段 0、1）、`_02`（18 行，阶段 2）和 `_03`（18 行，阶段 3、4）。一行包含 `raidTrainerInfo`、训练家 ID `raid_assist_NPC_1` 至 `_52`, `npcPresetIndex`（该行索引，由 `0.4459` 传入训练家模型）以及 `nameTextLabel` (`TRNAME_RAID_ASSIST_01`，每个池均从第 0 行起）。训练家的唯一宝可梦为其在 `poke1` 条目中的 `world/data/trainer/trdata/trdata_array`，类型为 `PokeDataBattle`：种类、形态、等级 16、40 或 80，`tokusei` 为 2 至 4（特性槽位 1、2 或隐藏特性），三个招式，`gemType`（2 + 太晶属性），个体值 31/10/31/31/10/31（HP 攻击 防御 速度 特攻 特防），基础点数为 HP 252、防御 128、特防 128，勤奋性格，精灵球，非异色，`sex` 为 0，体型比例 128，无携带道具。`raid_trainer_04` 至 `_07` 列出野外训练家（`area04_trainer_*`, `area05_trainer_*`）；其读取方未知。`scripts/gen_sv_partner_data.py` 将池解码至 `pokeldn/sv/data/raid_partners.json` (`raid_partners.game_pool`）。伙伴宝可梦构建等级为 int(0.8 × 战斗槽位 0 中主机端宝可梦的等级)，而非预设等级（`0.4455`, `0.4901`），因此 Serebii 的等级 16、40、80 分别对应等级 20、50、100 的主机端。在 pokeldn 团体战中，槽位 0 放置 `--raid-pokemon`。零售版《朱》在等级 100 的宝可梦旁显示伊莱的等级 80 沙奈朵，在等级 37 的旁显示等级 29 沙奈朵，与自身宝可梦等级（100 和 84）无关；初期阶段的伊莱奇鲁莉安与夏洛特姆克鸟在等级 100 的旁也为等级 80，超过其池中的 16。阶段为 5 时，零售版《朱》的伙伴变为以首领命名的皮卡丘，随后战斗崩溃，因此 `raid_point` 拒绝大于 4 的阶段。

## 种子

团体战由 32 位种子及主机状态抽取：版本、地区（帕底亚、北上、蓝莓，表前缀 `""`, `su1_`, `su2_`）、剧情进度和结晶。xoroshiro128+ 从种子及常量 `0x82A2B175229D6A5B` (`0xe29340`）初始化；首次抽取一百种值，按剧情阶段边界决定普通结晶星级（黑色结晶为六星），第二次按该星级及版本的概率选取遭遇。`0xe29404` 用 `%sdifficulty_%02d` 构建表名，并将记录传给 `0x1eab5e4`，后者读取其 `raidEnemyInfo`; `0x2935b68` 遍历全部三个前缀与六个等级。随后，以同一种子重新初始化 xoroshiro 来抽取首领：EC（种子低半部加 `0x229D6A5B`，因此可从首领记录反推出种子）、伪训练家 ID、PID、满个体值项、其余个体值、特性、性别、性格（颤弦蝾螈从对应形态列表中选择）、身高、体重及体型比例，与 PKHeX 的 `Encounter9RNG.GenerateData` 相同；太晶属性和奖励抽奖各自另用新的生成器。

`pokeldn.sv.raid_encounter` 基于 `pokeldn/sv/data/raid_base.json` 实现上述逻辑，后者由 `scripts/gen_sv_raid_data.py` 根据 Tera-Finder 遭遇列表和奖励表、PKHeX 个体资料表，以及游戏 RomFS 中十八张 `raid_enemy_XX_array` 表构建（`arc/worlddataraidraid_gem_item_reward_boostdata.bin.trpak`，带有独立 `.bfbs` 模式定义的 FlatBuffers）。在所有上下文中测试超过 12600 个种子，首领各字段均与 PKHeX.Core 26.8.26 相同，包括帕底亚六种遭遇（记录 5094 至 5099），其零售版表中太晶规则为 0（种类自身属性），PKHeX 则记为规则 1（任意属性）。结晶构建器 `0xe26ff0` 读取 `gemType`，对 0 和 1 均从 18 种属性中任选（`cmp w9, #2` 位于 `0xe27414`，重抽直到小于 18），与 PKHeX 相同；通用转换器 `0x160e108` 将 0 视为种类自身属性，但团体战不经过该路径。由种子 `BD13FB43`（《紫》、帕底亚、四星）构建的首领记录与零售版引导消息逐字节相同；由 `7B741233`（《朱》、帕底亚、五星）构建的记录，除昵称和语言外，与法语零售版《朱》相同：零售版主机端写入自身语言及该语言的种类名称（`Embrylex`、3），生成器则用英语（2）。无论哪种情况，主机都以自身语言名称显示首领。

团体战表的种类使用游戏 DevID：截至 916 为全国图鉴编号，从 917 起使用游戏自定义顺序（小锻匠 957 对应 1000），与 `gen9.internal_index` 相同。描述符及 RaidPoint 也携带 DevID：向零售版《朱》提供种类为 1000 的描述符与 RaidPoint，会列出并对战小锻匠。黑色结晶记录包含等级 90 的战斗等级及基础点数（例如防御 128、特防 128），捕获等级为 75；普通记录的两种等级相同，基础点数为零。引导消息的首领记录与 RaidPoint 概要携带战斗等级及基础点数，RaidPoint 的 `+0x2c` 携带捕获等级：由 `09F3E337`（《朱》、帕底亚）构建的黑色首领，除昵称与语言外，与法语零售版《朱》相同。

## 活动团体战

一份宝可入口新闻分发包含五个文件：`raid_enemy_array`, `fixed_reward_item_array`, `lottery_reward_item_array` 和 `raid_priority_array`，它们是与基础表布局相同的 FlatBuffers，以及 `event_raid_identifier`，一个重复优先级表 `VersionNo` (`20221202`）的 u32。从 1.3.0 起，分发还会按适用补丁再次携带各文件（`_1_3_0`, `_2_0_0`, `_3_0_0`），旧副本被置为占位；读取最新副本。一条 `raid_enemy_array` 记录以普通记录为基础，额外包含 `RomVer`（0 两个版本，1 《朱》，2 《紫》）、`DeliveryGroupID`, `Difficulty` 作为星级（7 为七星团体战）、`CaptureRate`（0 从未捕获，1、2 仅可捕获一次）及自身奖励表名称，其 `BossPokePara` 固定普通首领原本需要随机抽取的字段：

| 字段 | 活动记录 |
| --- | --- |
| `Sex` | 0 随机抽取；1 雄性，2 雌性，跳过性别抽取 |
| `Seikaku` | 0 随机抽取；否则为性格加 1，不抽取 |
| `TalentType` | 1: `TalentVnum` 个满个体值；2：`TalentValue` 中的六项个体值，不抽取 |
| `RareType` | 0 随机抽取；1 永不异色：若 PID 对伪训练家为异色则翻转第 28 位；2 必定异色：重写其高半部，使异色异或值为 0 |
| `ScaleType` | 0 抽取两次；1 至 5 分别在 0-15、16-47、48-207、208-239、240-255 中抽取一次；6 `ScaleValue` |
| `Item`, `EffortValue` | 首领携带道具与战斗基础点数（七星皮卡丘携带电气球） |

记录的 `TimeDesc` 就是其 `raidTimeData`，RaidPoint 在 0x030 携带它：每条七星记录都启用，`gameLimit` 为 450 至 900，`commandLimit` 为 60；五条五星记录也启用（`gameLimit` 为 320 至 450）；其余 420 条记录未启用（2026-09-06 图库）。

巢穴属于一个分发组，编号 1 至 10；`raid_priority_array` 统计各组巢穴。由种子初始化的 xoroshiro 先抽取普通结晶星级所用的百面随机数并丢弃，再从满足主机版本且星级在剧情阶段允许范围内的组内记录总权重中抽取，按表顺序选择权重区间包含该值的记录 [PKHeX `EncounterDist9.GetIsPossibleSlot`]:

| 进度 | 阶段 | 可抽取星级 |
| --- | --- | --- |
| 初始、太晶团体战 | 0 | 1, 2 |
| 三星 | 1 | 1 至 3 |
| 四星 | 2 | 1 至 4 |
| 五星、六星 | 3 | 3 至 7 |

权重为 0 的记录永不抽中。首领及其太晶属性按普通团体战方式抽取，并应用记录固定字段；奖励先取记录固定表，再从该分发自身表中抽奖，七星抽取次数按六星计算。有权重但无道具的抽奖槽位计入总权重，却不给奖励，数量为 0 的行同样如此。《朱》中 2023 年首轮索财灵抽奖表就是这种异常结构，每个槽位均为空或数量为 0，因此其团体战只发固定行。

`pokeldn.sv.raid_event` 读取分发文件夹（一个 [EventsGallery](https://github.com/projectpokemon/EventsGallery) 活动，或其 `Files`），并生成 `Raid`，供主机端提供：

```
./.venv/bin/python bin/sv_host.py ... --raid-pokemon FILE --raid-seed 52E6B438 \
    --raid-event "EventsGallery/Released/Gen 9/SV/Raid Events/002 Charizard the Unrivaled" \
    --raid-version scarlet --raid-progress 6star [--raid-event-group 1] [--raid-catch-normal]
```

RaidPoint 携带记录的捕获率，结晶字段则使用存档的团体战内容类型：2 活动，3 七星活动（Tera-Finder `RaidContent`).

模拟版《朱》4.0.0 加入端均进行了战斗。伊布大量出现（20221125），种子 `00000002`，初始进度、结晶 2：一星伊布，成功捕获，奖励画面按顺序列出种子奖励行。最强的喷火龙（20221202），种子 `00000001`，六星进度、结晶 3，且 `raidTimeData` 为 1、600、0、60：首领名为“最强的喷火龙”，计时条每分钟减少约十分之一，时限 600 秒，而主机自身默认是 300 秒。零售版《朱》通过 ESP32 开发板也进行了相同两场团体战：战胜一星伊布后提供捕获机会并发放种子奖励；最强的喷火龙显示七星，计时条缓慢缩短。它还进行了普通黑色团体战（种子 `00000004`，啪嚓海胆），其 RaidPoint 携带记录的 `raidTimeData` 1, 450, 0, 60.

应用的“太晶团体战（主机端）”工具从自身下载并更新的图库副本选择活动，并将团体战版本、进度和结晶限制为该活动可生成的范围（[团体战活动](gui.md#raid-events)）。提供的结晶选项来自 `raid_event.dens`：优先级表中有巢穴且该版本有记录的分发组；波荡水大量出现活动对《朱》提供组 1，对《紫》提供组 2。

捕获率为 2 表示每个存档仅可捕获一次：所有七星记录均如此，各轮大量出现中的五星波荡水与铁斑叶、帝牙卢卡与帕路奇亚，以及异色烈空坐也如此。存档保存已捕获的记录编号，每条八字节，含编号和捕获标志（块 `0x8B14392F`；从 2.0.1 起，击败标志属于 `0xA4BA4848`，PKHeX `RaidSevenStar9`）；复刻沿用编号（波荡水七轮均为 2023022801），因此任一轮捕获后其他轮也无法捕获。异色灾祸之宝大量出现活动记录为 0：不可捕获。主机端概要会说明规则（`caught once per save`, `cannot be caught`).

主机根据大厅描述符（0x2c）的记录编号检查该列表。一台已捕获最强的超梦（2023090101）的零售版《紫》，收到对应主机端描述符后，在大厅提示“无法捕捉这只太晶宝可梦”；无论 RaidPoint 捕获率写为 1 还是 2 都一样，因为开战前不发送 RaidPoint。对于存档已捕获的最强的鲤鱼王（2026071701），同一主机的结果如下：

| 描述符记录编号 | RaidPoint 捕获率 | 大厅 | 获胜后 |
| --- | --- | --- | --- |
| 2026071701，记录原编号 | 2 | 无法捕获 | 不提供捕获 |
| 2026071701 | 1 | 无法捕获 | 不提供捕获 |
| 2026071799，替代编号 | 1 | 无警告 | 成功捕获 |
| 再次使用 2026071799 | 1 | 无警告 | 成功捕获 |

若记录编号在存档中已标为捕获，无论 RaidPoint 捕获率是什么，获胜后均阻止捕获（第二行）。捕获率 1 下的捕获不会将替代编号加入列表（第四行）。`--raid-catch-normal` 将只能捕获一次的记录以普通捕获形式提供：RaidPoint 捕获率为 1，描述符使用替代记录编号，即记录日期后缀改为 99（`raid_event.stand_in`：2026071799）。没有分发使用该后缀（所有后缀最多为 14）。概要显示 `served as a normal catch of record 2026071799`。不可捕获记录仍保持 0。

替代编号仅出现在描述符中：首领记录及除捕获率外的 RaidPoint 均与活动逐字节相同，PK9 没有字段保存记录编号。PKHeX.Core 26.8.26 的团体战遭遇（`EncounterDist9`, `EncounterMight9`）也不包含它，只有分发组，因此捕获合法性不可能依赖该编号。图库中除仆刀将军第二轮（晚于该版本）外的每条只能捕获一次记录，在其可生成的每个版本中各取三个种子，并对鲤鱼王使用 `000FD5D7`，共 331 场团体战：将主机端发送的首领记录，按 PKHeX 自身遭遇转换方式赋予测试训练家后，与 PKHeX 从同种子捕获该团体战所得记录相同且合法。七星捕获只有带最强之证才合法（`RibbonMarkMightiest`），主机会赋予该证章：主机在 2026071799 下捕获的鲤鱼王确实具有它。

固定奖励行的适用对象 3（`Only Once` 位于 `Encounters.txt`：七星团体战的招式学习器和特性膏药）是独立规则；`raid_point` 写入表中的适用对象，由各主机奖励过滤器应用。活动首领可以是任意种类，因此超出普通团体战首领范围的个体资料、招式 PP 和名称来自 `pokeldn/sv/data/species.json` (`scripts/gen_sv_species_data.py`，它是以下版本的 PKHeX 修订版：`raid_base.json`).

针对 EventsGallery 的 153 个分发文件夹（2026-09-06）：每张表解码结果均与其 JSON 一致；pkNX 提取器生成的分发与七星遭遇，全部对应 PKHeX.Core 26.8.26 的 174 和 55 条（仆刀将军第二轮晚于该版本，`000 Base Data` 为游戏自身占位项）；对每个活动、版本、阶段及分组取四十个种子，共 20 080 个首领，与 PKHeX 的 `GenerateSeed32` 各字段一致，PKHeX 在对应阶段允许每条记录；并且 `scripts/check_sv_raid_events.py` 发现全部分发的 537 条遭遇及其抽取团体战均与其 `Encounters.txt` 一致，索财灵的异常轮次除外。PKHeX 全部 229 条遭遇在种子 `00000001`, `12345678`, `9ABCDEF0`, `DEADBEEF`, `52E6B438` 和 `0000F00D` 下，均给出与 `boss_fields` 从图库对应记录抽取结果相同的加密常量、个体值、特性编号、性别、性格、身高、体重及体型比例。

## 寻找种子

应用的团体战种子字段显示工具当前上下文中该种子生成的首领和奖励；“查找团体战”从输入或随机选取的起始种子开始，在过滤器保留的全部上下文（`pokeldn.sv.raid_search`）中，按种类、星级、太晶属性、性格、性别、异色、体型证章及个体值范围搜索。结果按首领能力评分（HP 乘双防之和、单项防御、较高的攻击能力或总和）或期望奖励排序（下述“最多期望奖励”）。未指定种类时，每种宝可梦仅保留一个结果。

### 体型证章

PKHeX 允许在《朱》或《紫》中停留过且体型比例为 0 的宝可梦获得迷你之证，比例为 255 时获得巨大之证（`MarkRules.IsMarkAllowedMini`, `IsMarkAllowedJumbo`）。查找器的“体型证章资格”要求首领体型比例为 0（迷你之证）、255（巨大之证）或任一者（任意证章）。体型比例在身高、体重之后抽取（`boss_fields`):

| 体型比例规则 | 体型比例 | 为 0 或 255 的概率 |
| --- | --- | --- |
| 两次抽取（规则 0），所有普通及黑色结晶首领 | `next_int(0x81) + next_int(0x80)` | 各为 1/16 512 |
| 活动区间从 0 起（规则 1）或从 240 起（规则 5） | `next_int(16) + low` | 其覆盖的端点概率为 1/16 |
| 活动指定值（规则 6） | 记录的 `scale` | 必定或不可能 |

`raid_search.size_marks` 指出所选结晶、星级及种类的活动首领可获得哪些证章，查找器将其余选项置灰。

### 期望奖励

“奖励”区默认折叠，展开后可设置期望奖励：每行包含道具及团体战至少需给出的数量，同一道具的团体战数量求和，同一道具的两行要求也累加。结果随后显示奖励。折叠后行仍保留，但搜索忽略它们。可选道具及数量均来自所搜索团体战能给出的范围（`raid_search.reward_choices`）：对上下文可抽取的每种遭遇（该进度、版本允许的星级，或活动巢穴），按所选星级、种类、太晶属性缩小范围，取固定行加上从零到最多抽奖次数的任意次同道具抽取（若抽奖表没有其他道具，则恰为实际抽取次数）；首领每种可能太晶属性对应其碎块，种类对应其掉落物。一次涵盖所有帕底亚、北上及蓝莓上下文时，约一秒列出 343 种道具，因此列表在页面外生成。搜索先跳过无法提供期望奖励的遭遇，再先抽种子奖励、后抽首领。

“最多期望奖励”按要求顺序排序：第一种道具更多者优先，再比较第二种，每行最低数量仍是最低要求。团体战某道具的总数视为一个数位，其值是该数量在搜索团体战可给出的所有总数中从小到大的位置（`raid_search.ranked_rewards`）：黑色结晶掉落物数量为 8 至 30、每次增加 2，共 12 档。前几项道具的数位组成一个小于 2^31 的分数，辅助程序将其与种子一起保存在 64 位排名值中；后续道具仅检查最低数量。全部已知团体战都能容纳五种道具（活动经验糖果 L 最多有 59 种总数，是最多的道具），黑色结晶可对四种秘传调味料、膏药或王冠及四种掉落物排序。

### 辅助程序的扫描

PKHeX 辅助程序使用所有核心扫描种子（`services/pkhex/RaidScan.cs`，由 `pokeldn.sv.raid_scan` 打包并发送，在独立辅助进程中运行）：处理种子遭遇、首领直到体型比例、评分、全部过滤器及奖励，使用 `select`, `boss_fields`, `rewards` 和 `tera_type` 在上下文表上执行。它返回上下文最佳种子（或各个种类的最佳种子），然后 `search` 用纯 Python 代码构建团体战，因此结果、顺序及种子和上下文之间的同分处理均与 Python 扫描一致（`tests/test_sv_raid.py` 比较两者）。

扫描在遭遇阶段就排除大部分种子。每次请求只计算一次各遭遇行的理论最佳排名：保证满个体值在可能位置取 31，其余个体值取过滤器允许的最佳值，性格取最佳者；按奖励排名时则取该行各道具最大数量。如果种子所属行无法超过已保留排名，就在此停止；通过后，在保证满个体值生成后及全部个体值生成后，分别按这些个体值在任意性格下的最佳能力再次检查（性格改变十分之一能力，且每种评分都随各能力增加）。按奖励排名时先抽奖励，每次只检查可给出期望道具的抽奖行；当剩余抽取无法使第一种道具达到已保留排名首位数时停止。每次请求携带先前请求保留的排名（每种首领一个结果时为各个种类排名）；只有搜索首次请求携带上下文表，辅助程序按摘要缓存它们。

一次请求包含 16 777 216 个种子，之后调整为辅助程序约四分之一秒能扫描的数量，最多 268 435 456。每个上下文最多搜索 4 294 967 296 个种子，上下文数量可自由选择（`most_seeds`）；查找器默认提供一亿，“全部种子”搜索所有种子。“首个匹配即停止”返回首个匹配团体战，不考虑评分，而非最佳结果（`stop_at_first`）：依次搜索上下文，返回首个存在匹配结果的上下文中最早种子。没有辅助程序时（尚未构建辅助程序的源码检出），Python 每秒扫描约 22 000 个种子，最多一百万个种子与上下文组合，查找器默认提供 100 000。

## 主机之间的战斗

在两个模拟版《朱》4.0.0 之间测量，一个创建四星结晶团体战，一个从宝可入口加入，两个空席位为 NPC 伙伴。主机端在整个战斗中保留会话。每条战斗消息都是键 0x007b 上的战斗开始帧，地址为 (0x2713, x, y)，32 字节头部中 +0x00 为类型，+0x08 为 u64 步骤计数器，+0x10 为 u64 轮次，+0x18 和 +0x19 分别为 5 和战斗者或站点字节：

| 类型 | 来源 | 大小 | 内容 |
| --- | --- | --- | --- |
| 0x01、0x05、0x11、0x15、0x25、0x29、0x47、0x49 | 主机端，地址 (0x2713, 1, 2) | 50 至 20626 | 一个步骤；各加入端用相同计数器、类型加 1 应答 |
| 0x02、0x12、0x16、0x26、0x2a、0x48、0x4a | 每个站点，地址 (0x2713, 3, 5) 或 (0x2713, 2, 2) | 50 | 对步骤的应答 |
| 0x06 | 站点为自身战斗者发送；主机端为自身、每个 NPC、以及加入端再发送一次 | 250 | 一个战斗者的指令；+0x19 为战斗者槽位（0 主机端，2 加入端，3、4 NPC） |
| 0x15 | 主机端，每名行动战斗者一条，包含首领 | 20626 | 轮次：+0x20 处有五个 0x70 字节行动块（槽位 0 主机端，1 首领，2 加入端，3、4 NPC），+0x250 处每槽位一字节表示其块内行动数（[行动](#actions)），+0x258 为服务器指令队列长度，+0x25c 起为队列；deflate 压缩后 123 至 802 字节 |
| 0x46 | 主机端，开始时 62 次 | 54 |  |
| 0x51 | 主机端 | 86 |  |

约 4 分钟内，加入端双向在 0x80 端口 0 上传输 475 条可靠消息，线上共 27979 字节，单向每秒最多 80 条。仅主机端发送 NPC 指令及类型 0x15 记录。

战斗采用服务器与客户端架构。主机端构建器 `0x113c8a0`（类型 0x15 位于 `0x113c908`）复制行动块，运行轮次（`0x113e3d0`），追加生成的服务器指令队列；主机端 AI 生成 NPC 指令，首领行动只有通过 0x15 才能到达加入端。加入端播放队列，并对类型 0x13、0x15、0x17、0x19、0x1f、0x23、0x25、0x4d，使用同一构建器根据主机端行动块重建消息体，比较大小及字节（`0xf5cfa4`）；不匹配则进入 `0xf5bfd4`，即接收超时处理函数。充当战斗主机端的站点必须从相同状态生成与《朱》自身引擎相同的队列。

### 哪个站点运行服务器

战斗服务器是端口 2 成员列表的首个条目；每台主机都根据大厅主机端的 Session 类型 6 构建该列表（成员位于 `+0xa0`，代码 `+0xc0`，计数 `+0xc4`；构造器 `0xe457cc`）和类型 9 接收器 `0x18b68fc`; `pokeldn.sv.port2.build_session` 将主机端放在首位。

| 步骤 | 代码 |
| --- | --- |
| 团体战开始函数 `0.4455`（Lua）将服务器槽位设为 0：`setup:f4891D27C(0)` | `0x182ca10` -> `0x2d36398`，设置 `+0x94` |
| 对于成员 i，将 i 映射为槽位 0、2、3、4，将成员代码保存于 `+0x99+slot`，对于自身代码，将槽位保存于 `+0x90` | `0x1ccd15c` 遍历端口 2 的成员向量，位于 `+0x170`; `0x2d363a0`, `0x130ea2c` |
| `0x2a1cd74` 将设置 `+0x94` 复制到 `net+0x58`，并将 `+0x90` 复制到 `net+0x5c`，仅在战斗开始时一次 | 来自 `0x18915c4` |
| 主机在以下条件下是服务器：`!setup.710 && slot == net+0x58` | 网络 vf `+0x78` = `0x2a1d994`；配置 `+0x2c` 经由 `0xfa363c`，保存在服务器 `+0x490` |
| 仅在不是服务器的主机上安装 0x15 检查器 | `0xfb0ee8` |
| 接收超时或检查失败会调用网络 vf `+0x70` = `0x2a1d920`；在团体战中它设置 `net+0xca`，并由 `0x18e217c` 将 `net+0x58` 设为主机自身槽位（`net+0xf0`，在 `0x2a1cda8`) | `0xf5bfd4` |

设置 `+0x710` 仅由 `0x7faed0` 从 Lua 绑定 `f3AF42713` 设置，条件是构建器字段 22 为 true；团体战开始从不设置它。没有消息指定服务器，决定因素是成员顺序。主机失去与服务器的连接时，会在剩余战斗中将自己设为服务器，每台主机独立如此。排在首位的大厅主机端停止发送后，各主机分别独立战斗。

成员向量只追加，有三个写入方，均通过 `0x18b65c8` -> `0x18b68fc`：类型 6 或 7 的会话块（`0x18b566c`，条目 `(block+0x98 code, block+0x90 host station)`，首先追加）、类型 6 的成员重放（`0x279ba2c`）和类型 9（`0x1954bac`）。任何会话块到达前的类型 9 均被丢弃（`0x18b65e4`）。每台主机的条目 0 都是其首个会话块指定的主机端。在两个模拟版《朱》4.0.0 上实测：

| 大厅主机端发送内容 | 主机行为 |
| --- | --- |
| 类型 6，其块中的主机端为接收主机自身站点 | 不发送端口 2 加入请求，错误 7 |
| 端口 2 类型 10（`0a b9 02 b9 01 `，解析器 `0x279bbdc`，删除 `0x194562c`），在大厅中指定会话块主机端 | 离开会话 |
| 引导消息后的同一类型 10 | “团体战已被取消！” |
| 主机报告 320173（加载完成）后的同一类型 10 | 各自与两名 NPC 伙伴独立战斗 |
| 成员代码指向引导消息中的空参与者 | 战斗加载中止（2162-0001） |
| 五名成员，第五名为一台主机（Lua 仅重映射索引 1 至 3，因此将其映射到槽位 0） | 大厅不列出任何成员；开始及引导消息后，两台主机均在任何战斗帧之前离开 |

引导消息参与者 k 属于代码为 k 的成员。故障接管的主机使用自身 AI 控制其余所有战斗者：逐槽位读取器仅为战斗开始时已是服务器的主机构建（`0xfa52b0`, `0xfa5314`）。自身代码为向量中首个自身站点条目的代码（`0xd5f3b4`），Lua 槽位循环（`0.4455` @1206..@1248）没有 break，因此最后一个匹配条目决定主机槽位。

### 战斗随机数

每个轮次的全部随机抽取来自一个 0x28 字节 xoroshiro128+ 对象（虚表 `0x4500bd0`):

| 偏移 | 大小 | 内容 |
| --- | --- | --- |
| 0x00 | 8 | 虚表 |
| 0x08 | 2 × u64 | 状态 |
| 0x18 | u64 | 种子 |
| 0x20 | u64 | 已进行抽取次数 |

服务器主模块（0x378 字节，构造函数 `0x12742d0`）在 `+0x10` 持有它；轮次代码通过 `[[x+0x10]+0x10]` (`0x11440e8`）访问。模块初始化器 `0x127d824` 将状态设为种子与 `0x82A2B175229D6A5B`，计数设为 0（`0x127d9a8`），种子取自参数块的 `+0x20`。加入端检查器从战斗设置的 `+0x718` (`0x2891748`）填充该字；团体战开始函数 `0.4455`（@1152..@1157）通过 Lua 绑定将 `+0x718` 设置为 `fAF4A81E0`（设置器 `0x7faf1c`）所取得的 RaidPoint 的 `randSeed`。伙伴种子同时也是战斗种子，由写入引导消息的站点选择。服务器构建的逐槽位模块（`0x126ba88`，来自 `0xfa9f90`）使用种子 0 初始化。

模拟版《朱》4.0.0 参与以 `randSeed` `D64EB3974D89705E` 创建的团体战时，在较后轮次中，服务器随机对象保存该种子，状态等于从种子推进七步，计数为 7；该轮次抽取了四次。

一次抽取将 `s0 + s1` 相加并推进状态；计数按调用次数而非重抽次数增加：

| 函数 | 抽取 |
| --- | --- |
| `0x11440f0(rand, n)` | 小于 n 的 u64：`s0 + s1` 按 n − 1 所需位数掩码，大于等于 n 时重抽；n 小于 2 则返回 0，不抽取 |
| `0x114da8c(rand, p)` | `(s0 + s1) & 0x7f` 大于等于 100 时重抽；小于 p 时为 true |

许多轮次函数将状态推进内联，而不调用这些函数。

### 每次招式的伤害及抽取

对随机宝可梦参加普通团体战的参考战斗进行测量（233 场，其中 29 场记录每次抽取）。一次招式使用按以下顺序抽取：

| 抽取 | 时机 | 决定内容 |
| --- | --- | --- |
| `chance(25)` | 使用者麻痹时 | 是否因麻痹无法行动 |
| `chance(accuracy)` | 招式具有命中率；即使为 100 也抽取 | 是否命中 |
| `below(24)`, `below(8)`, `below(2)` | 伤害招式，根据击中要害等级 0、1、2 | 为 0 时击中要害 |
| `below(16)` | 伤害招式 | 随机值 r：伤害乘以 (100 − r) / 100 |
| `chance(p)` | 概率为 p 的追加效果（泰山压顶为 30） | 是否触发效果 |

对首领的畏缩追加效果不进行抽取（[轮次队列中的招式](#a-move-in-the-round-queue) 中有此规则）。100% 降低能力的追加效果（灵魂冲击、重踏）在某些轮次抽取 `chance(0)`，其他轮次则不抽取。两个战斗者速度相同时，在首个招式前抽取 `below(2)`。

一场战斗在首轮前抽取一次 `below(100)`。伤害采用 Showdown 的第九世代公式（数据来自 Pokemon Showdown 的 `moves.json` 和 `typechart`），使用同行记录的能力，首领防御属性仅按太晶属性计算：首领未发生能力等级变化前的 1346 次命中中有 921 次符合；记录全部抽取的 140 次命中中，137 次可由记录的伤害随机值与要害抽取结果得出实测伤害。不符合的命中发生在首领护盾期间（约为公式结果的 0.45），或来自具有独立规则的招式（扑击、电力上升、连续攻击招式），或受到剩余 HP 上限限制。

首领总 HP 为记录 HP 乘 RaidPoint 的 HP 系数再除以 100（[战斗引导消息](#the-battle-bootstrap)）：获胜的参考战斗中，一星 78 场、二星 84 场、三星 125 场、四星 35 场，恰在 `0x37 (2, 2, damage)` 中累计造成记录 HP 的 5、5、8、12 倍伤害后结束；其余所需更少，涉及护盾及具有独立规则的招式。

### 轮次队列中的招式

轮次队列中，一名战斗者的招式是一串指令。战斗者 1、3、4、5 的客户端位置为 0 至 3，首领为 4；A 为使用者，T 为目标，M 为招式，`type` 为招式属性索引，`cat` 为分类（1 物理、2 特殊）。以下测量来自玩家招式命中首领、首领反击命中玩家的参考轮次：

| 指令 | 含义 |
| --- | --- |
| `0x05 (A, 0, pp)` | 玩家招式开始，消耗 PP（目标具有压迫感时为 2，否则为 1）；首领招式无此项 |
| `0x07 (A, 0)` | 使用招式 |
| `0xc9 (A, 0, M, T's position, 0)` | 招式及其目标 |
| `0x7b (M, n, A)` | n 为本轮之前的轮次数 |
| 六组 `0xcf` 零值 | 20、5、5、5、19、20 字节 |
| `0x7e (0, ...)`, `0x7e (1, 0, 0, 0, 0, 0)`, `0x7e (2, e, e, e, e, e)` | 第一组：T 的位置 + 1 处为 1；第三组：每个位置一个相性代码，7 表示无修正 |
| `0x8b (A's position, T's position, M, type, 0, 0, 1, tera, 0, 0)` | 命中；`tera` 在首领使用自身太晶属性的伤害招式时为 1（448 次此类命中全部如此），否则为 0 |
| `0x37 (T, 2, damage)`, `0x37 (T, 5, 1)`, `0x02 (T, A, damage, 3)` | 伤害 |
| `0xd0`，字节为 `T, e` | e 为相性：7 普通，6 效果不好，8 效果绝佳 |
| `0x8e (1, 1, M)`; `0x8e (1, 3, M)` 和 `0xca (A, 575, 0xffff0000)`，效果不好时；`0x8e (1, 2, M)` 和 `0xca (A, 574, 0xffff0000)`，效果绝佳时 | 相性消息 |
| `0x20 (A, 24)` | 仅效果绝佳的命中 |
| `0x42 (T, A, A's position, type, cat, M, damage)` | 命中记录 |
| 吸取，在招式可吸取且使用者 HP 未满时 | `0xa7 (T, 51)`, `0x03 (A, heal)`, `0x9a (A, heal)`, `0xcb (A, 290, T)`；回复量为伤害乘吸取比例，四舍五入，上限为使用者缺失 HP |
| 追加效果，如有 | 例如麻痹：`0x13`, `0x90`, `0xa7`, `0xcb (2, 92, T)` |
| `0xd1`，字节为 `01 00`, `0x2e (2, A − 1)` |  |
| `0x85 (7, damage)` | 仅对首领造成伤害时 |
| `0x7c ()`, `0x08 (A, 0)`, `0x1d (A, T's position, type, 1, 0, M, M)`, `0x5b (A, M)` 两次，`0x1e (A, 0)` | 招式结束 |

轮次结束时，对每个行动过的战斗者执行 `0xb2 (0)`, `0x37 (b, 7, 1)`，再按速度顺序对每个战斗者执行 `0x75 (3, n)`, `0xc5 (1)`, `0x43 (b)`（同行记录中的速度，包含首领），然后按 ID 顺序对本轮每名行动者执行 `0x23 (b)`，战斗首轮则对全部五名执行，最后 `0x2d (0)`; `0x75 (3, n)` 记录截至当前、包含本轮的轮次数。

击倒首领的命中会使战斗获胜。在其 `0x42` 之后，按 ID 顺序对每位玩家执行 `0x49 (2, A, M)`, `0x09 (A, 0)`, `0x37 (2, 1, 1)`, `0xcb (2, 0, 2)`, `0x94 (2, 0)`, `0x37 (2, 8, 1)`, `0x5f (2)`, `0x62 (2)`, `0x6c (2)`, `0x5d (2)`, `0x41 (b, 2)`，接着 `0x33 (2, k)` 对 k 0 至 13（除 8 外）执行，随后 `0x80 (2)`, `0x29 (2)` 和 `0x38 (A)`，再正常结束招式。此后无人行动，轮次结束时只有仍站立战斗者的 `0x43`、`0x23` 列表和 `0x2d (0)`。`0x85 (7, damage)` 及伤害指令携带首领剩余 HP。

前缀以 `0xb5 (0)` 开始，然后对本轮行动者按 ID 顺序执行一次 `0x51 (b, 1)`，再按行动顺序执行一次；第二次中，具有慢出特性（特性 100）的战斗者最后行动，并携带 `0x51 (b, 0)`。所选招式会注册独立处理器的战斗者，在每次遍历后按该次顺序追加 `0x5a (b, M, speed)` 和 `0x5b (b, M)`，再按行动顺序额外执行两次。首名以外的每名战斗者行动前，所有此类战斗者再重复一遍该对；若行动者招式注册处理器，则追加 `0x5a (b, M, 0x72000 + speed)`，紧接在其以下操作之前：`0x05`。哪些招式注册处理器，通过在参考战斗中使用每个招式并观察 `0x5a` 来测量：已见使用的 631 个招式中有 347 个注册（包含硬撑、泰山压顶，不含暗袭要害）。

首领从开始就已太晶化：威力低于 60、无优先度且单次命中的自身太晶属性伤害招式，按威力 60 命中，这是第九世代太晶规则（迷你芙的一般太晶撞击造成 4 点，而威力 40 仅为 2 点）。招式各追加效果按 Showdown 顺序分别抽取 `chance(n)`，但针对首领的畏缩不抽取：玩家冰冻牙攻击首领只抽冰冻概率（冰冻显示为 `0x13 (2, 3, 0, 1, 4)`，带消息 97、98，首领行动前抽取 `chance(20)` 判定解冻），首领冰冻牙攻击玩家则两种都抽。击倒首领的命中会先抽取 `chance(0)`，无论有无追加效果。

依据 Showdown 招式数据及第九世代伤害公式按此构建，554 场参考战斗中有 56 场首轮与参考结果逐字节相同，已处理部分无差异；其余包含被拒绝处理的情况。从开始消息体连续运行至击倒首领，有 20 场完整战斗的每个轮次均与参考结果相同。使用同一脚本控制主机端到端运行时，按此构建的服务器在双方均成功提供的 19 场战斗中，逐帧、按同一顺序发送参考服务器的每一帧（第 20 场参考服务器失败）。若行动者或被命中者具有 Showdown 回调可改变轮次的特性或道具，就拒绝该轮次（活力的攻击、斗争心的威力、友情防守的 0.75、胆怯在恶属性命中后加速、疾风之翼的优先度），除非测试语料已测得该特性或道具此时不生效；若战斗含有入场时生效的特性也拒绝（威吓会在首轮前降低攻击者攻击）。

### 行动

轮次行动头部（请求块，0x238 字节）为五个 0x70 字节块，每个客户端槽位一个，每块最多七个 16 字节行动（u64 行动字、u32 行动者战斗者 ID、四个无代码写入的字节）；+0x230 处每槽位一字节计数块内行动数。服务器按槽位顺序将其解码为 0x8c 字节行动条目（`0x1145e40`，解码器 `0x11461b4`）。行动字的低四位为种类：

| 种类 | 条目种类 | 字内字段 |
| --- | --- | --- |
| 1 | 1，招式 | 第 4..7 位为目标战斗位置，8..23 位为招式，第 25 位为标志 |
| 2 | 2 | 第 4..19 和 20..27 位；下一个 u32 |
| 3 | 3，替换 | 第 4..7 位为同行索引（行动者即该同行成员），8..11 位、第 12 位 |
| 4 | 6 | 第 4..11、12..15 和 16..23 位 |
| 5 | 4 | 第 4 位 |
| 6 | 5 | 第 4..11 位 |
| 7, 10, 11 | 7, 8, 9 | 无 |
| 9 | 10 | 第 4..11 位 |
| 12 | 11 | 第 4..11 位；下一个 u32 |
| 13 | 14 | 第 4..7、8..11、12..15、16..27、32..43、44..55、56..59、60..63 位 |

若某字第 0..3 位为 3 且第 12 位置位，则跳过，种类 0、8、14、15 也跳过。记录的玩家行动 `41 67 03 00 ...` 为招式（种类 1），目标位置 4，招式 871（闪焰高歌）。

团体战中的战斗者 ID：1 为槽位 0 宝可梦，2 为首领，3 为槽位 2，4 为槽位 3，5 为槽位 4。站点类型 0x06 指令为 0xe8 字节：0x20 字节头部（+0x19 为槽位），+0x20 为计数字节，+0x28 起为 (u64 行动字, u64 行动者) 对。它携带该槽位自身行动及首领对该槽位的反击：加入端槽位 2 指令含有 `move 871 at position 4 by battler 3` 和 `move 204 at position 1 by battler 2`。站点选择首领针对自身宝可梦使用的招式。

服务器为每个行动槽位填充一个轮次请求块：

| 步骤 | 代码 |
| --- | --- |
| 提交者栈上一个 0x240 字节块：所有行动字及行动者清零，计数清零，+0x238 为种类（0x15） | `0xf6e6a8`，位于逐槽位读取器的步骤 `0xf6df44`; `0xf71d10`，其他种类使用 |
| 复制槽位的类型 6 消息（读取器 +0x30 为存储，u32 +0x38 为槽位）：清除计数字节，追加每对的 u64 行动字及行动者低 u32，再递增计数；无边界检查，计数超过 7 会进入下一个槽位 | `0xf702ec` -> `0xf7065c`（键 6，0xe8 字节消息）；键 0x10 进入 `0xf72038`（包含一个行动的 0x30 字节消息，仅在槽位最多持有六个行动时取入） |
| 将 0x240 字节作为类型哈希为 `0xae1b39fccfd09053` | `0xf6ffb8` 的作业提交，作业类虚表 `0x4494198`（构造函数 `0x17b52a4` 将 0x240 字节复制到作业 +0x78） |
| 作业将块复制到服务器对象的 +0x210（构建器的 [o+0x40]） | `0x16e4f84` -> `0x113bac0` |
| 递增步骤计数器 +0x198；若该步骤已收到消息体（`0xe63734` 遍历 [[server+0x448]+0x38] 的双端队列），则替代构建；否则调用种类 0x15 的构建器 | `0x113bad8` -> `0x113c8a0` |

因此一个轮次块包含一个槽位的行动。各行动未写入的四字节及字节 0x235..0x237 来自提交者栈，并原样进入类型 0x15 消息体；轮次不读取其中任何内容。两个模拟版《朱》4.0.0 之间的每条类型 0x15 记录，除这些字节外，都等于根据行动槽位类型 6 指令构建的块（指令在线上传输的 10 条记录全部如此；首领自身槽位 1 的块没有此类指令：[首领行动](#the-bosss-actions)）。四次模拟会话的轮次仅根据行动运行，除这些字节外，得到与主机相同的 20576 字节消息体。

### 服务器指令队列

类型 0x15 记录的队列（消息体 +0x23c，长度在 +0x238）是一串指令。指令为大端序 u16 ID，随后按该 ID 格式将参数打包成单个大端位流，在前部补齐至整字节（写入器 `0x119bf58`，跳转表 `0x3c6aa7c`）。ID 至格式映射由 `0x3c6abe4` 处 208 行 (u16 ID, u8 格式, u8 0) 构建，同 ID 后出现的行优先；ID 为 0 至 205。ID 0xce 至 0xd4 由读取器 `0xe515f0` 自身读取（跳转表 `0x3c6a90c`):

| ID | 消息体 |
| --- | --- |
| 0xce | 无：队列结束 |
| 0xcf、0xd2 | 一组：一个 u8 字节计数，后跟对应数量的字节 |
| 0xd0 | 一个 u8 计数，最多 4，后跟对应数量的字节 |
| 0xd1 | 两字节 |
| 0xd3 | 一字节 |
| 0xd4 | 无 |

格式字节及其参数位宽：

| 格式 | 位宽 | 格式 | 位宽 |
| --- | --- | --- | --- |
| 0x00 | 无 | 0x57 | 32, 8, 8, 8, 8, 8, 8 |
| 0x01 | 8 | 0x62 | 32, 16 |
| 0x02 | 8, 8 | 0x63 | 8, 8, 32 |
| 0x04 | 5, 3, 8, 16 | 0x65 | 32, 16, 16, 16, 16 |
| 0x10、0x20 | 32、16，随后八个 32 | 0x66 | 8，随后五个 32 |
| 0x11 | 16 | 0x67 | 32，随后六个 16 |

### 战斗开始消息体

消息 0x11 的消息体是不带长度字的指令队列（[服务器指令队列](#the-server-command-queue)）。战斗者 ID 为：槽位 0 对应 1，首领（槽位 1）对应 2，槽位 2 对应 3，槽位 3、4 对应 4、5；战斗者位置为 ID − 1。消息体先按 ID 顺序派出每个战斗者，再运行入场事件，最后以 `0x2b (0)`:

| 指令 | 内容 |
| --- | --- |
| `0x3d (pos)`, `0x16 (pos, 0, 0, 0)`, `0x5e (id, ability)`, `0x61 (id)`, `0x6b (id)`, `0x4e (id)` | 派出一名战斗者；`ability` 是其特性 ID |
| `0x25 (id)`, `0xc7 (id, 0)`、效果、`0xc8 (id)` | 特性发动 |
| `0xcb (id, text, params..., 0xffff0000)`，用零补齐至十个参数 | 战斗消息 |

| 入场事件 | 效果 |
| --- | --- |
| 压迫感（46） | 在 `0xcb (id, 162, id)` |
| 威吓（22） | 对每个目标，在 `0x0d (target, 1, 1)`, `0x93 (target, 1, 1, 0)`, `0xcb (id, 32, target, 1)` |
| 察觉（119） | 在 `0xcb (0, 146, id, target, item)` 周围包裹发动指令，每个携带道具的对手一次 |
| 紧张感（127） | `0x25 (id)`, `0xc7 (id, 127)`, `0xca (id, 679, side, 0xffff0000)`, `0xc8 (id)`，在其他所有事件之前；`side` 对玩家紧张感为 1，对首领紧张感为 0 |
| 危险预知（107） | 在 `0xcb (id, 145, id)` 周围包裹发动指令，条件为对手会使用对自身效果绝佳的伤害招式或一击必杀招式 |
| 携带气球（541） | `0xcb (id, 137, id)`，在战斗者特性之后 |

233 场参考战斗中，224 场事件按战斗者速度顺序运行（同行记录速度）。其余 9 场涉及优先发动的紧张感（127）或同速。同批战斗中，161 种特性不产生入场事件，道具吃剩的东西（234）、生命宝珠（247）、270 和气势披带（275）均不产生。

威吓以 `0x25 (I)` 和 `0xc7 (I, 0)` 开始，随后按 ID 顺序对每个对手（首领对应四名玩家，玩家对应首领）执行 `0x0d (F, 1, 1)`, `0x93 (F, 1, 1, 0)` 和 `0xcb (I, 32, F, 1, 0xffff0000)`，最后以 `0xc8 (I)` 结束。具有我行我素的对手在其中以自身的 `0x25`/`0xc7`, `0xcb (F, 69, F, 0xffff0000)` 和 `0xc8` 应答，不降低任何能力。具有不服输的对手在能力降低后以 `0x0c (F, 1, 2)`, `0x92 (F, 1, 2, 0)` 和 `0xcb (F, 18, F, 0xffff0000)` 应答。察觉以 `0xcb (0, 146, I, F, item, 0xffff0000)` 指定首个携带道具的对手，以 `0xca (0, 752, F, item, 0xffff0000)` 指定后续每个对手；若对手均无道具则无事件。不服输、怪力钳、笨拙、轻金属、自信过度、毒手、风力发电没有开始事件。按此构建，554 个参考开始消息体中有 420 个完全相同，已处理部分无差异。

### 首领行动

团体战首领额外行动等待在一个最多四项的列表中（+0x5c + 8i 为 u8 种类，+0x60 + 8i 为 u32 数值，+0x7c 为计数），其前方 +0x10 处为 RaidPoint 行动配置副本。轮次引擎列表为 `[module+0x1b0]` (`0x16e5c90`），每轮重置；服务器逐帧状态机保留独立列表。

| 种类 | 入队条件 | 数值 |
| --- | --- | --- |
| 1 | 护盾（`0xf6f87c`）：未启动前，剩余时间百分比小于等于配置 +0x14，或 HP 百分比小于等于 +0x12 | `0xf70af0`，按时间触发时为计时器对应值，按 HP 触发时为 0 |
| 2 | 护盾结束（`0xf6f87c`, `0xf70010` 与 +0x18 比较） | 1 |
| 3 | `0xf6dd84`，时间检查发现剩余不超过 10% 时 | 1 |
| 4 | 六个额外行动（`0xf6fa5c`：种类、时机 1 时间／2 HP、阈值、+0x24 + 8i 处的招式），各一次（记录 +0x86 + i） | 行动索引 |
| 5 | 双重行动（`0xf6de7c`）：HP 不高于配置 +0x54 | 0 |

这些都不抽随机数：每个触发条件都是首领 HP 比例或剩余时间阈值（`0xf91070`，作用于战斗计时器）。作为请求块行动（`0x114fb2c`），行动字种类为 12，第 4..11 位为列表种类，第 32..47 位为数值，行动者为团体战战斗者 ID（`0x114fc70`).

轮次中，空列表根据 HP 触发条件填充（`0x11425b0`）；其中没有护盾时，行动就在该轮运行（`0x1145be0`）。轮次后，结果字节 `0xc4a5` 选择下一步骤；ServerCommand（`0x16e4f6c`）在构建器的 `0xc4a4` 置位时改为传入 8；团体战行动原样传该字节（`0x16e4ff0`，跳转表 `0x3c61c38`）：0 无，4 空轮次（`0x16e5cac`），6 含护盾的轮次列表（`0x16e5ad0`），7 战斗结束（[战斗结束](#the-battles-end)）。团体战行动（`0x18c92a8`，负载由 `0x17b5f3c` 复制）在四个状态中运行：

| 状态 | 服务器行为 |
| --- | --- |
| 0 | 向每个站点发送消息 0x47；以原因 0 暂停战斗计时器（`0x18c9a68`) |
| 1 | 等待每个已入席槽位发送该步骤消息（`0xe63380`) |
| 2 | 构建槽位 1 包含行动的请求块（计数字节 +0x231）；以原因 0 恢复战斗计时器（`0xe63ac4`）；将块作为轮次（0x15）发送 |
| 3 | 采用轮次结果的下一步骤，清空列表（`0xfaf024`），删除各槽位的 0x47 及其应答 0x48 |

不含护盾的列表从状态 2 开始。首领列表为空时，逐帧状态机在列表副本上检查配置的时间触发条件（`0xf6d62c`）；某条件触发就将副本作为消息 0x51 发送（`0xf71b74`）。0x51 通过服务器自身槽位返回状态机并填充其列表（[服务器流程](#the-servers-flow)）；状态机列表包含行动时提交团体战行动（`0xf6d8d4`).

两个模拟版《朱》4.0.0 之间，四星首领使用配置（时间 80% 时行动 3 大晴天，HP 75% 时行动 1，HP 40% 时行动 2，HP 50% 或时间 30% 时护盾），产生三个槽位 1 轮次：先单独种类 4 数值 0（无 0x47，同时发送 0x51），随后加入端攻击后出现 0x47 及种类 1 加种类 4 数值 2，再次为 0x47 与种类 1。75% 行动在跨过该阈值的槽位 0 轮次内部执行。

### 战斗计时器

战斗计时器为服务器上下文 +0x38 处一个 0x28 字节对象（逐帧状态机及每个作业的 `[+0x40]`，其中 +8 还存有 N，+0x10 为服务器模块，+0x18 为服务器）：

| 偏移 | 字段 |
| --- | --- |
| +0x00 | u64 起始时刻，以 `nn::os::GetSystemTick` 的纳秒表示；暂停时为 0 |
| +0x08 | u64，上次暂停前累计纳秒数 |
| +0x10 | u64，上次暂停时刻 |
| +0x18 | u8，是否已启动 |
| +0x19、+0x1a | u8 暂停原因；两者均为 0 时计时器运行 |
| +0x20 | 创建时使用的时限 |

| 事件 | 代码 |
| --- | --- |
| 若时限 N+0x8a 非 0，在战斗首个作业中创建、启动并立即以原因 0 暂停 | `0xf70864`, `0xf70a58` |
| Wild::Setup 结束时以原因 0 恢复（从未启动的计时器在此启动） | `0x2a1fbfc`，属于 `0xe63a6c` |
| 从团体战行动消息 0x47 起至其轮次执行前，以原因 0 暂停 | `0x18c9a68`, `0xe63ac4` |
| 读取：时限加上位于 `[[module+0x1b0]+8]` 的 i16，减去自启动以来运行的整秒数及累计整秒数；暂停时为时限减累计秒数；零时限返回 1 | `0xf91070` |

逐帧状态机仅在计时器已启动（+0x18）且设置 +0x499 的位 2 已置位时检查时间触发条件（`0xf6d538`）。P% 时间触发条件在整数除法 100 x 剩余时间 / 时限 小于等于 P 时触发：300 秒计时器的 80% 条件在剩余 242 秒、运行 58 秒后触发。下述实际提供的战斗中，计时器在最后一个站点对消息 0x11 的应答到达服务器时启动，80% 行动在 58.1 秒后发出。

### 战斗计时器耗尽

逐帧状态机（`0xf6d538`）每帧开始时，使用时限 N+0x8a 及 [[module+0x1b0]+8] 的 i16 读取战斗计时器（`0xf91070`）；有符号结果小于等于 0 时，在首领列表与读取器处理之前进入时间耗尽分支 `0xf6d830`：

| 步骤 | 代码 |
| --- | --- |
| 若尚无结果，将结果 0 及 N+0x94 = 2 保存在 N 中（非强制覆盖） | `0xe7d570(N, 0, 2, 0)` |
| server+0x208 处的 0x29 消息体：N 自身槽位、结果（`0x166882c`）、N+0x94 | `0xe7d4c8` |
| 设置 +0x499 的位 2 置位（团体战）时：提交带消息 0x2b 的 ExitBattleEnd | `0x201602c`（哈希 `0x2da7b4584624a364`，构造函数 `0x1882dbc` 将消息保存在 +0x78） |
| 否则：提交种类 0 的 AddExpBattleEnd | `0x16e5230`（哈希 `0x23607a0597b3a656`) |

状态机仅在无作业运行时执行，因此轮次或团体战行动期间计时器耗尽，要等作业结束后才能被发现。ExitBattleEnd 向每个站点发送 0x2b 并等待全部应答；0x2b 不同于 0x29，因此之后无 RaidCapture，淡出发送 0x35 再发送 0x37（[战斗结束](#the-battles-end)）。团体战时间耗尽时不发送 0x25。

在下述 rme10 会话中，使用截至 416.5 秒的记录消息，随后站点对除 5 和 0x37 外的所有奇数消息在 0.1 秒后应答，且不发送指令，将时钟以 10 秒步进推进到 700 秒：unicorn 下游戏自身服务器代码与 `Server` 向每槽位按相同顺序发送相同消息，除未写入字节外逐字节相同。先是首领最后一个定时行动的轮次（种类 3，剩余时间 10%），随后是消息体为 `00 00 00 00 02 00` 的 0x2b（槽位 0、结果 0、由 2 决定）、0x35 和 0x37。

首领获胜的团体战以相同方式结束。在同一会话从 414.5 秒开始，让站点对每个请求均以指令应答：自身宝可梦对首领使用叫声（招式 45），首领以招式 0x1cc 攻击该宝可梦，游戏服务器代码与 `Server` 向每槽位以相同顺序发送同样的 1311 条消息。玩家宝可梦每次濒死使 300 秒计时器减少 75 秒（[[module+0x1b0]+8] 的 i16 降为 -75、-150，随后在 439.7 秒为 -225），在 -225 时，时间耗尽分支发送 0x2b（槽位 0、结果 0、由 2 决定）、0x35 和 0x37。宝可梦濒死的槽位会经历读取器子状态（[服务器流程](#the-servers-flow)):

| 消息 | 目标 | 内容 |
| --- | --- | --- |
| 0x21 | 仅濒死槽位，只有头部 | 槽位无可战斗成员时发送；其应答 0x22 启动读取器计时器（reader+0x50，时限来自 `0x1ffe4e8`) |
| 0x23 | 每个槽位，20608 字节 | 该计时器到期后（`0x2016bc8`，种类 0x23 的块，仅包含该槽位一个行动，计数 1，行动种类 8），由种类 35 构建（`0x1153350`，与种类 37 相同，但使用 `0x288d734` 代替 `0x114c390`）：恢复成员 HP（`0x288cde8`，vf 0x2e8 与 0x488）并执行指令 3（战斗者、HP），随后将成员重新派回原位置（`0x2887044`, `0x11482a0`：指令 0x98，触发 0xc、0x16、0x20）并执行入场步骤 |

一次复活轮次将 `3 (5, 277)`, `cb`, `3d (4)`, `16 (4, 0, 0, 113)`, `5e`, `61`, `6b`, `4e`, `98 (4, 0, 0, 1)`, `20 (5, 0x12)`, `25`, `c7`, `cb`, `c8` 加入队列。测试也会将 `Server` 与游戏在此战斗中的消息比较。

### 服务器流程

主机上各步骤为作业：先 Wild::Setup，再 ServerRequest（`0x138d178`，向一个槽位发送消息 5）、ServerCommand（`0x16e4f10`，将已提交请求块作为轮次，再按结果执行下一步骤）、RaidAction，以及战斗结束。Wild::Setup（`0x2a1f54c`，十一个状态，跳转表 `0x3c61c1e`）发送消息 1，等待所有槽位应答，再发送 0x11（设置种类 4 则改用 `0x2017ba4`；团体战设置 +0x30 为种类 0，即获胜时发送 0x29 的种类，抓包中的 0x29 也证明这一点），等待全部应答，清空各已入席槽位发送内容（`0xe0f5f8`）；0x11 结果字节为 1 时发送消息 3（应答后再发 0x13；该字节为开始标志 [[o+0x40]+0x28]，仅由 `0x2840fac` 设为 1，经由 `0x2840f70` 从七处调用（`0x284b710`, `0x284b8f0`, `0x285c5d0`, `0x286d480`, `0x286d784`, `0x286d9b0`, `0x28780f8`）；测量的团体战开始均未设置），删除各已入席槽位的 3、4，并启动战斗计时器。逐帧状态机（`0xf6d538`）逐步执行五个逐槽位读取器（`0xf6df44`）及首领列表。服务器一侧玩家槽位读取器的行为：

| 读取器状态 | 条件 | 随后 |
| --- | --- | --- |
| 0 | 槽位已发送条目中不存在 5、0xd、0xb、0xf、9、7、0x21、3、0x23、0x15、0x17、0x19、0x13、0x47、0x1f、0x1d 中任何一项 | 为槽位提交 ServerRequest（`0xf70078`），状态 1 |
| 0 | 否则 | 从两个条目删除每对已应答消息（`0xf6edf4`，适用于 0x15/0x16、0x23/0x24、0x11/0x12、0x13/0x14、0x17/0x18、0x19/0x1a、0x1b/0x1c、0x1d/0x1e、0x25/0x26、0x1f/0x20） |
| 1 | 已向槽位发送 5，且槽位已发送 6 | 清零数据块并收集槽位指令（`0xf6e6a8`, `0xf702ec`，键 6，完成键 5），作为 ServerCommand 提交，状态 2 |
| 2 | 槽位已应答轮次（0x15 / 0x16） | 状态 0 |

按表 `0x3c6a45a` (0, 1, 0, 0, 0) 与 N+0x95 比较，确定槽位是否属于首领阵营；其读取器仅删除已应答消息对。读取器（`0xf6df44`..`0xf6edf0`）还有表外路径：发送 4 的槽位以种类 0x13 块应答；团体战中位于 N 阵营时，运行 reader+9 的子状态（0 通过哈希为 `0x935acb1823e1803f`, `0xf6f6d8` 的八字节请求询问槽位 {slot, 0x21}；3 在 reader+0x50 创建计时器，时限由 `0x1ffe4e8` 从表 `0x3c69d1c` 读取；1 在计时器到期后提交种类 0x23 块，`0x2016bc8`；2 等待 0x23/0x24）；0xd/0xe 提交种类 0x1b 块，若 0xe 消息体首字节为 0 则提交请求 {slot, 7}；7/8、0xb/0xc、0xf/0x10 和收到的 0xa 分别提交种类 0x17、0x19、0x15、0x17 的块。提交块中种类之后的 +0x23c..+0x23f 字节为栈内容。

每帧，团体战运行步骤 `0x2d383b8(N)` 在 `0x2d38694` 处执行服务器入站链路（`0xe0f040`, `0xe0fd68`, `0xe0f854`，作用于 [N+0xb0]），再执行作业图 `0xfc363c(G, 1)`，G = [N+0xa8]（0xe8 字节，虚表 `0x44ee6e8`；其 +0x40 为作业上下文，虚表 `0x44ee808`):

| G+ | 对象 |  |
| --- | --- | --- |
| 0x98 | 请求工厂（0x48 字节） | 提交的请求为 0x50 字节消息对象：作业类型哈希、计数器、作业负载 |
| 0xa0 | 调度器（0x78 字节，虚表 `0x44eea68`) | 提交请求保存在 +0x40..+0x50 向量中，由 `0x1479b10` |
| 0xa8 | 源（虚表 `0x44947d8`) | vf 0x68 `0x14641ec` 选择要启动的请求 |
| 0xb0 | 逐帧状态机（虚表 `0x4493530`，由 `0x17e1c5c`) | vf 0x68 `0xf6d538`；+0x40 为上下文，+0x48 为工厂，+0x50 为调度器 |
| 0xb8 | 执行器（虚表 `0x4493688`) | 作业栈（双端队列，计数 +0xa0） |

`0xfc363c(G, 1)` 执行器持有作业时只运行执行器。执行器为空时，先运行状态机，再由源挑选：团体战（设置 +0x498 的 0x400 位）优先选择首个哈希为 `0x5c307d44ea569b63` 的已提交请求（团体战行动，`0xf71928`），模块开始标志（[[module+0x1f0]+8]）置位前选择首个哈希为 `0x2e9e7a3009002c36` 的请求（Wild::Setup，`0xf7093c`），否则选择首个已提交请求。所选请求离开调度器（`0xfc3f58`），执行器 vf 0x68 `0x17b410c` 创建其哈希指定的作业并压栈，然后运行执行器。执行器（`0xfc38dc`）运行栈顶作业 vf 0x68：0 结束本帧；2 弹出作业，若存在后续处理 [job+0x70] 则压栈，然后结束本帧；其他值再次运行栈顶作业。因此状态机与读取器只在无作业的帧运行，每帧只启动一个已提交请求，晚于其他请求提交的团体战行动反而先启动；这解释了抓包中团体战行动后三个指令作为轮次发送的顺序。

状态机定时检查将首领列表副本作为消息 0x51（`0xf71b74`）送入服务器自身槽位的入站链路（`0xe0f440(server, N+0x95)`, `0xf71980`）；下一帧，入站链路步骤将其交给状态机 vf 0x78 `0x2016290`，后者将其 0x24 字节复制到状态机首领列表 [+0xf8]+0x5c，状态机再从此提交团体战行动。状态机 vf 0x70 `0x20162bc` 接受另外两种消息，通过其 +0x40 的 u64 区分：`0x0ab4bce035f3012b`（0x2588 字节负载，作为 `0x201665c` 作业提交）和 `0xde3856ecc4fe200c`（包含一个种类 14 行动的请求块，作为 ServerCommand 提交）。

在引擎构建的会话上，unicorn 下《朱》自身服务器代码（`scratchpad/battle/timeup/gameserve.py`: `0x2d383b8` 以每秒 30 帧逐帧运行，站点消息按转发顺序在抓包时刻送入）向加入端发送与主机相同的 24 帧，除头部及请求块未写入字节外逐字节一致。缺少入站链路步骤时，0x51 副本永远无法到达首领列表，80% 行动也不会触发。

`Server` 将此流程移植为 Python，在已构建会话上，以服务器运行步骤部分（`0xe0f040`, `0xe0fd68`, `0xe0f854`, `0xfc363c(G, 1)`，以及 `0x2898350`，当该步骤推进时）逐帧运行，按状态机时钟每秒 30 帧推进至每条输入消息的时刻，并在每条之后再运行一个帧周期。不能将任何帧当作空闲跳过：等待濒死槽位计时器的读取器会使状态机每帧报告推进，每个这样的帧都在服务器自身链路排入消息 0x46。unicorn 下全部 216 个已移植函数的游戏原代码，在记录战斗、计时器耗尽、胜利结束以及首领获胜战斗（下述）每个事件后留下的内存页，均与移植版本相同。

主机端将服务器收到的每条消息，无论本地客户端还是加入端的，都通过同一队列转发给加入端（地址 x 为 3，每 0.05 至 0.15 秒一帧，也包含加入端自身消息），因此队列顺序就是服务器读取顺序：加入端比本地客户端早 0.5 秒发送的应答，也可能更晚到达服务器。根据模拟主机端自身引导消息（抓包中的 0x2f）及按转发顺序、在状态机时钟对应抓包时刻送入的站点消息，服务器以相同顺序向加入端发送主机全部 24 帧：类型 1、0x11、四个请求、13 个轮次（其中三个为首领）、两个 0x47，随后 0x25、0x29、0x49。除头部及请求块未写入字节外，每条均与主机逐字节相同（[行动](#actions)）；首领定时行动从计时器自身启动时刻起，在与主机相同的帧触发。unicorn 下每个提取步骤的游戏原代码，在整场提供的战斗中留下相同内存页。

### 复现轮次

将模拟主机暂停在构建器 `0x113c8a0` 的类型 0x15 处，可在 unicorn 下精确重放轮次：重放首次访问内存页时，逐页从 GDB stub 获取；`tpidrro_el0` 背后的线程本地页由替代页提供，其 `+0x1f8` 指向伪线程，SVC 0x10、0x11、0x12、0x1a、0x1b、0x1d、0x1e 均返回 0。十一轮重放与主机随后自行构建的消息体逐字节一致；每轮访问 159 至 353 页。

服务器的 Python 移植版本运行此过程，一个游戏函数对应一个 Python 函数，以其相对 main 的偏移为键。构建器 `0x113c8a0` 在 Python 中处理消息种类 1、5、17、21：轮次驱动器 `0x113e3d0`，包含招式选择、伤害 `0xf7c344`、濒死 `0x1144df8` 和回合结束 `0x114a094`，以及战斗开始 `0x113dca8`，包含派出、道具、特性及入场处理器。在 86 个暂停主机实例中（49 个轮次、5 次战斗开始），移植版本留下与游戏原代码相同的消息体和内存页，没有将任何调用交回游戏。分配所用堆是 SDK 的 `nn::mem::StandardAllocator`，基于线程缓存，连同缓存创建及其 TinyMT32 键一起移植（`0x525f448`）。战斗状态构建步骤 `0x2891748`, `0x2892ac0`, `0x2d381a4` 和 `0x2892dd4` 也在 Python 中运行，包含入口，并留下与游戏相同的内存页。`__cxa_guard_acquire` (`0x53c49a0`）在保护变量第 0、1 字节均未设置时返回 1，并将第 1 字节设为 2。

一次祸不单行轮次读取 16838 个非自身写入字节：静态映像 1496，指令格式映射 5372，服务器对象 2926（后两者由 `0x2d381a4` 创建），战斗者及其宝可梦 2414（由 `0x2892ac0` 创建），主模块族 1756（由 `0x2891748` 创建），数据表 2278，轮次行动块 576。

数据表是由函数局部静态对象持有的 romfs 文件：

| 静态对象 | 文件 | 对象 |
| --- | --- | --- |
| `0x47420b8` | `avalon/data/personal_array.bin` | 映射表，键为 species * 10000 + form（u32） |
| `0x47420d8` | `avalon/data/growTable.bin` | FlatBuffers 根节点，通过 [T+0x30] 的 vf +0x70 |

映射表为位于 +0x68 的 libc++ `unordered_map`：桶 +0x68，桶数 +0x70（不小于记录数的下一个质数），首节点 +0x98，大小 +0xc0，负载因子 +0xc8（1.0），默认记录 +0xd0（键 0 记录）。节点为 {next, hash = key, key, 指向已加载文件的记录指针}；+0x30 为文件资源（FNV 哈希 +0x48，路径 +0x50）。道具数组（由 `0x1821674` 填充）从 +0x28 起包含 0x18 字节条目：u32 索引、u32 0、u64 哈希、u16 道具、六个零字节；条目 i 为文件记录 i，哈希来自 main 的 `0x3c61260 + 8 * index` 处 u64。文件从 `arc/data.trpfs` (`tools/switch/trpfs_read.py` 提取；Oodle 条目经游戏自身的 `OodleLZ_Decompress`，位于 `0xcc8750`），97 个暂停主机实例持有的每个文件字节均与提取文件一致。

移植版本也能在没有暂停主机时运行战斗开始。仅凭静态映像和 romfs，它构建游戏堆、“Application”计数分配器（`0x3b78d3d`，上限 0xa0000000，基于 GlobalHeap 分配器 0x4763918）、弱句柄表（`0x165dd08`）及五个数据表（个体资料 `0x164498c`，ID 哈希 `0x1730f6c`）。随后会话及服务器对象 N 由游戏原创建器生成（下述），团体战开始设置字段来自引导消息。之后 N 开始状态运行四个构建步骤，再运行类型 0x11 构建器。五个会话的战斗开始消息体（268、345、328、422、268 字节）与主机相同，后续九轮的 20576 字节消息体也相同，每轮由其行动槽位的两个行动构建（[行动](#actions)），仅请求块未写入的栈字节除外。改变战斗种子不改变开始消息体，但改变轮次的 123 个字节。堆地址和弱句柄 ID 均不进入消息体：主机 ID 为第 3 代的 0x1b5xx，移植版本为 0..0x58，且全部对象地址均不同。

N 的开始状态 `0x1269824` 随后执行：状态 0 将设置时限（+0x48a..）复制到 N+0x8a，将选主对象移入 N+0x138，将 [N+0x48]+0x140 移入 N+0x190，运行服务器构建 `0x2891748`，以 setup+0x718 初始化随机持有器（N+0x1a0）种子（`0x281c260`，其中会抽取一次），将 N+0x30 设为该种子，创建 N+0x120 的 6 × 5 组指令对（`0x132ecfc`），并将 u32 setup+0x2c 连同 N+0x120 以及管理器的通信持有器交给 [N+0x110]（`0x169ffa0`）。状态 2 根据模式选择步骤状态机（`0x2d380a4` 用于团体战），状态 3 则运行它：其状态 0 根据规则和 N+0x95 设置格式字节 N+0x98..，然后执行步骤 `0x2892ac0`, `0x2d381a4` 和 `0x2892dd4`.

这 29 个命名参数由代码提供：`0x146496c` 按表中顺序，为 main 中 `0x3c60f80` 的每个 0x10 字节条目存储一个 u32（先是名称哈希，然后在 +8 处存储相同的值）。

团体战启动时，通过设置对象的绑定，从 Lua（0.4455 -> 0.4893 -> 0.4945）写入设置。四台主机的设置中，下列字段具有相同的值：u32 +0x2c 为 10003（`fD8E195CA`，也就是构建函数在 [N+0x110]+0x40 读取的 0x2713），u32 +0x34 的模式为 2，+0x8c 为 1，+0x8d 的规则为 5，u32 +0x90 的主机槽位为 2，u32 +0x94 的服务器槽位为 0，成员代码 +0x99.. 为 (0, 0xff, 1, 0xff, 0xff)，+0x488 和 +0x489 为 1，+0x498 为 0x400，u32 +0x4b0 为 12000，u32 +0x4b4 为 400，+0x4dd 和 +0x4df 为 1，u32 +0x4ec 为 0，+0x706 为 1，+0x714 为 8；每个参与者还具有从 +0x18 开始的六个 0x1c 字节条目，其中 u16 +0x10 为 30（首领为 26），u8 +0xd 为 1（主机端的条目 1 至 5，加入端的条目 0 至 5）。引导数据提供种子（+0x718）、时限（+0x48a、+0x48c、+0x48e）、首领的行动配置（+0x514）和队伍持有器（+0xa0..）。在 unicorn 下，游戏自身的代码根据这些字段创建的管理器、S、N+0x48、N 以及状态 0 的写入结果都与移植版相同，唯一例外是游戏从栈填充区域复制的字节。

有四部分仍不包含在内：S 的作业（`0x159f018`；其构造函数需要引擎的作业调度器，而且没有战斗代码读取 S+0x40）、作业图连接（`0x1193e44`, `0x11fd13c`）、资源系统（setup+0x720 通过 `0x1ffbb68`，加载器 N+0x1a8 通过 `0x1802edc` 和 `0x1929dc4`，状态 1 会等待它），以及 Pia 网络管理器 `[[0x46d6ca0]]`，它为选主对象提供站点 ID。

数据系统的初始化函数 `0x1641afc` 运行 `0x1643a48`（个体数据、成长数据）、`0x1641cf0`（招式）和 `0x1641d78`（特性）。每张表都由分配器创建，重置到其静态存储位置（`0x1643e68`），并通过 `0xf0ba9c` 追加到位于 0x4763a18 的注册表中（计数为 u32 0x4765a18，最多 0x400 项）。先预留文件的记录数量，再按文件顺序插入记录，即可得到主机上的节点列表。静态映像和五张表来自玩家自行提取的数据：main 和 SDK 来自 v4.0.0 更新的 ExeFS（main 的构建 ID 为 `421c5411b487eb4d049dd065fec9547773e8e598`），每个 NSO 的各段按其内存偏移放置并包含 .bss；RELATIVE 重定位位于 main `0x8504000` 和 SDK main + `0x4e6d000`，之后将 GLOB_DAT、JUMP_SLOT 和 ABS64 槽位绑定到首个导出对应符号的模块，main 优先于 SDK；各表使用更新的 RomFS 覆盖基础游戏的 RomFS（`arc/data.trpfs`，Oodle 通过 `0xcc8750`）。在 M4 上读取它们需要 3 秒；构建会话和 N 的开始状态需要 2.4 秒。

弱句柄条目占 0x20 字节：u64 ID（u32 索引 | u32 代数 « 32），+8 为解析后的值，+0x10 为对象，u16 +0x18 为弱引用计数，u16 +0x1a 为强引用计数，u32 +0x1c 为状态（-1 表示已释放，-2 表示存活）。每块包含 0x400 个条目（`0xc1adec`）；释放的 ID 放入一个 `deque`，通过以下函数扩容：`0xb44724`.

### 服务器流程的实测结果

以下规律适用于参考服务器与“[提供战斗服务](#serving-the-battle)”中的脚本控制主机交互的情况；根据这些规律构建的服务器，在玩家获胜的九场完整战斗中，向主机发送的帧与参考服务器完全相同，通知也不例外：

| 规则 | 实测结果 |
| --- | --- |
| 头部计数器 | `step` 每次发送增加 1，无论是广播还是单个请求；`round` 在消息 1 中为 0，从 0x11 开始为 1，每个 0x15 以及 0x25 都使其增加 |
| 每帧一个作业 | 消息 1 启动 Wild::Setup；所有槽位都应答 1 后，它发送 0x11，并在所有槽位都应答 0x11 后的下一帧结束 |
| 请求 | 在没有作业运行的帧中，为没有待应答消息的槽位投递请求（5）；请求每帧启动一个，槽位顺序为 0、2、3、4 |
| 一条指令 | 槽位的消息 6 被作为作业投递，该作业将回合（0x15）发送到所有槽位 |
| 再次请求 | 若某槽位已应答发送给它的所有回合，则在下一帧再次向其发出请求 |
| 获胜 | 在获胜回合后的下一帧，发送空回合 0x25（20576 个零字节），随后发送消息体为 `00 00 01 00 01 00` 的 0x29，以及 0x49、0x35 和 0x37；每条消息都在所有槽位应答前一条后发送：对于 0x25 和 0x49，在最后一次应答后 2 帧发送；其他情况则在最后一次应答的同一帧发送 |
| 时间耗尽 | 0x2b，消息体为 `00 00 00 00 02 00`（233 场战斗中有 63 场） |
| 通知 0x46 | 每个启动作业的帧发送一次；没有作业运行时，每个读取回合应答（0x16）的帧也发送一次 |

### 提供战斗服务

`bin/sv_host.py --raid-serve [NAME]` 在战斗期间保持网络，并通过 `pokeldn.sv.raid_battle.RaidBattle` 从主机端站点提供战斗服务：使用插件的战斗服务器（[战斗服务器](plugins.md#a-battle-server)），根据引导数据和两个 NPC 伙伴构建，并保留主机端主机为自身占用的站点。pokeldn 不自带战斗服务器；如果没有插件提供服务器，该标志会被拒绝。提供服务的会话为我方宝可梦、首领、站点索引 1 的一台主机（引导参与者 1，槽位 2）和两个 NPC 伙伴安排席位，因此该标志只接受一台主机。

| 部分 | 主机端发送的内容 |
| --- | --- |
| 服务器发给主机的消息 | 寻址为 (0x2713, 1, 2) 的帧 |
| 槽位 0、1、3 和 4 | 每个奇数步骤都在 0.05 秒后以类型 + 1 应答；对槽位 0、3 和 4 的请求（5），使用类型 6 的指令应答，其中该槽位的宝可梦对首领使用第一个招式，首领也对该宝可梦使用第一个招式（[行动](#actions)) |
| 服务器读取的每条消息，包括主机自身的消息 | 转发给主机，寻址为 (0x2713, 3, 5) |
| 每个推动战斗进展的服务器帧 | 在该帧的消息之后，从槽位 0 发送通知 0x46（步骤 0，消息体为 4 个零字节），寻址为 (0x2713, 3, 5) |

每帧都通过 0x80 端口 0 发送，作为一条经过 deflate 压缩的可靠消息（标志 `COMPLETE_ZLIB`）；观察到的最大帧压缩后为 903 字节。复现《朱》4.0.0 行为的服务器，其最初六帧会按相同顺序发送零售版主机端发送的六条战斗开始消息（`raid.HANDOFF`），只有栈填充的头部字节不同，因此 `--raid-serve` 会发送这些消息来替代 `HANDOFF`.

主机端在主机应答 0x37 后，或发送 0x37 满 5 秒后停止服务，并关闭网络。应答 0x37 本身会在服务器上再次触发时间耗尽流程（[服务器流程](#the-servers-flow)），因此本地站点不应答它。发生故障时（服务器抛出异常或构建失败），服务会停止，并像未使用该标志的主机端一样交接网络；主机随后进行故障转移并自行处理战斗（[由哪个站点运行服务器](#which-station-runs-the-server)).

## 加入

`bin/sv_join.py --raid-pokemon FILE` 加入场景 7 的网络并作为加入端参与。主机上的玩家打开结晶，选择“大家一起挑战”并等待；应用中的“太晶团体战（加入）”工具负责运行该流程。`pokeldn.sv.raid.RaidGuest` 和加入程序依次执行以下操作：

| 步骤 | 加入端 |
| --- | --- |
| Net | 以消息标志 0x11 应答 0x11 和 0x50 |
| Session | 不应答加入响应附带的站点列表，在至少 1 秒后的重传到来时确认，之后确认每份列表，并发送将字节 9 置位的时钟请求 |
| 通道 | 将主机端包含六个键的表拆为四个通用键和两个团体战键，宣告四个通用键，0.24 秒后加入端口 2，并在收到表后 0.79 秒宣告团体战键；将其 0x7C 确认延迟 0.25 秒 |
| 身份 | 标准记录集（`pokeldn.sv.reference`），在入席 0.44 秒后发送，其中记录 1 使用训练家名称 |
| 大厅 | 再过 0.27 秒发送状态 0x18 和自身宝可梦；2 秒后发送状态 0x01 |
| 开始 | 收到主机端状态 0x0c 后发送状态 0x0d；曾有加入端将 0x0d 作为准备就绪状态发送，虽然收到确认，却始终未显示为已准备 |
| 战斗 | 确认主机端的 0x3480 0x93，每 0.5 秒发送一次 Session 类型 3 离开消息，直到收到类型 4（最多发送四次），然后离开网络；战斗中的零售版《朱》未应答这四次消息中的任何一次 |

与零售版主机端交互时，加入端以训练家名称出现在大厅中，进入准备就绪状态，并允许主机端开始；其宝可梦留在了战斗中。
