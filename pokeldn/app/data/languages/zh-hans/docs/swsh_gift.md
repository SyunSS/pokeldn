# 神秘礼物菜单的本地无线分支

《剑／盾》的神秘礼物菜单通过本地无线接收神奇卡片：分发端广播一个 LDN 网络，其广播数据以分片形式携带卡片。除非标明为《剑》，地址均来自《盾》1.3.2 的 `main`；空中传输行为以零售版主机的实测结果为准。

## 菜单

接收方式选择器 `StateSelectReceiveDataBase` 为每个菜单按钮设置一个子类（`L_mystery_top_btn_00` .. `_04`):

| 状态 | 方式 |
| --- | --- |
| `StateSelectReceiveDataInternet` | 通过网络 |
| `StateSelectReceiveDataSerial` | 序列号或密语 |
| `StateSelectReceiveDataLocal` | 本地无线 |
| `StateSelectReceiveDataFromBall` | 精灵球 Plus |
| `StateSelectReceiveDataRankMatch` | 级别对战奖励 |

接收状态为 `StateReceiveBase`, `StateReceiveInternet`, `StateReceiveSerial`, `StateReceiveLocal` (`0x01004938`，其自身代码仅引用其进度条布局）、`StateReceiveFromBall`, `StateReceiveRankMatch`, `StateReceiveNews` 和 `StateReceiveComplete`。游玩记录键 `fushigi_net`, `fushigi_serial` 和 `fushigi_p2p` 按渠道统计接收次数，与 `yy_battle_single_p2p` / `_net`.

### 应用的状态机

分派器 `0x00FE6F80` 读取位于 `app+0x718` 的请求对象：就绪标志位于 `+0x60`，下一状态的 id 位于 `+0x64`。当标志置位且 id 不大于 16 时，它通过 `0x020641A4` 跳转并构建该状态。`SetNextState(id)` 为 `0x00FF0DE0`，共有 63 个调用点。

| id | 状态 | id | 状态 |
| --- | --- | --- | --- |
| 0 | TopMenu | 9 | SelectReceiveDataSerial |
| 1 | ReceiveMenu | 10 | SelectReceiveDataRankMatch |
| 2 | ReceiveLocal | 11 | SelectReceiveDataFromBall |
| 3 | ReceiveInternet | 12 | ConfirmGift |
| 4 | ReceiveSerial | 13 | ReceiveNews |
| 5 | ReceiveRankMatch | 14 | ReceiveComplete |
| 6 | ReceiveFromBall | 15 | ConnectPalma |
| 7 | SelectReceiveDataLocal | 16 | （默认，TopMenu） |
| 8 | SelectReceiveDataInternet |  |  |

本地无线先进入状态 2 进行搜索，然后进入状态 7，从分发端提供的内容中选择。使状态从 2 推进到 7 的机制尚未读明；`StateReceiveLocal` 本身不设置下一状态。`0x00FE700C` 为 `mov w8, w21`，即分派器的跳转表索引；将其修补为 `mov w8, #N` 可强制进入状态 N。强制进入状态 7 会绘制一个空列表，且完全不触及网络（不调用 `Connect`, `OpenStation`，不创建会话，不更改最大值、注册表或广播字节；修补最大值后让站点入座并等待超过 100 s 也一样），因此列表是在进入该状态前填充的。

该类的主虚表为 `0x025737C8`；其组基址 `0x025737B8` 仅保存在 `main+0x2624698` 中，而构造函数 `0x00FE5D60` 没有调用方（小程序框架通过虚表构建应用）。`main` 中没有任何内容指向该应用；需要扫描堆中的虚表来找到它。映像中没有神秘礼物的 protocol-buffer 模块：每个 `.pb.cc` 都属于 `gflnet3` 的 p2p 框架，或属于交换、三个对战模块、巢穴、地下、露营、`comp_organize` 或 `btl_spot`.

## 礼物界面的网络

在本地无线界面，主机广播其始终开启的本地游玩网络：本地通信 id 为 `0x0100ABF008968000`（两款游戏均相同），版本 4，场景 id 为 65535（连接交换时为 60001），接受策略为 ALL，`NodeCountMax` 为 2，广播数据长 384 字节，密码 CRC 为零。游戏只在加载后几秒创建一次该接入点（实测为 16 至 31 s）；进入或离开神秘礼物均不发起 LDN 调用。礼物界面只设置其广播数据并启用 Pia 加入过滤器。

在该界面中，游戏每分钟调用 `nn::ldn::Scan` 约四十次（40 s 的 IPC 跟踪中为 33 次），期间交错调用 `SetAdvertiseData` 和 `GetNetworkInfo`，但从不调用 `Connect` 或 `CreateNetwork`。扫描在 802.11 层是被动的。其过滤器仅指定本地通信 id 和网络类型；`SessionId` 和 `SceneId` 均不过滤。

主机在信道 6 充当主机端时，以监听模式抓取的结果：

| 信道 | 来自该主机的信标 | LDN 广播动作帧 | 探测请求 |
| --- | --- | --- | --- |
| 1 | 0 | 90 s 内 153 个 | 0 |
| 6 | 70 s 内 339 个 | 70 s 内 435 个 | 0 |
| 11 | 0 | 90 s 内 95 个 | 0 |

### 模式字节

`session_config+0x70` 是本地游玩模式。`0x01096730` 通过跳转表将其映射为 Pia 场景 id 和参与者数量，跳转表为 `0x02066C14`; `0x010961a8` 将其映射为广播数据字节 `0x97`（广播 `0xAF`；游戏数据从 `0x18` 开始），所用映射为 `0x02066C40`:

| 模式 | 场景 id | 参与者 | 广播数据 `0x97` |
| --- | --- | --- | --- |
| 0 | 无，创建函数在以下位置返回 false：`0x01096764` |  | 0xFF |
| 1 | 60021 | 2 | 0x01 |
| 2 | 60001 | 2 | 0x0D |
| 3 | 60002 | 2 | 0x0E |
| 4 | 60003 | 2 | 0x0F |
| 5 | 60004 | 4 | 0x10 |
| 6 | 60005 | 2 | 0x1E |

连接交换使用模式 2（实测为 0x0D）；礼物界面运行于模式 0（实测为 0xFF），该模式不创建会话。进入应用时读取模式（`0x01096d20`），将其保存到 `app+0xFE8`，并设置为 0（`0x01022f08`）；离开时将其恢复（`0x01023198`）。在空闲、离开和重新进入期间，该字节始终为 `0xFF`。极巨团体战主机端广播 `0x11`，此值不在表中。

对同一台主机的五次交换广播和四次礼物广播进行比较，另一个随界面而变化的字节仅有 `0xB9`（礼物为 0x00，交换为 0xAA），其含义尚未读明；其余内容要么固定，要么按会话随机生成。LDN 的 `SceneId` 在扫描到的连接交换网络中为 60001，在礼物界面中为 65535（[入座](swsh_session.md#taking-a-seat)).

## 礼物界面的 Pia 网状网络

此界面的网状网络不允许任何加入端进入，强制入座的站点也收不到任何内容；卡片使用 [信标传输](#the-card-travels-in-beacon-advertise-data).

加入端在 0x14 上完成站点握手（主机的连接请求、结果为 0 的响应、其类型 5 确认、其 840 字节的类型 2 站点记录）后，在 0x18 上发出的网状网络加入请求遭到拒绝：

```
02 00 ff ff 01        JOIN_RESPONSE, refused, reason 1
```

对连接交换发出同样的加入请求会得到 148 字节的响应。随后 0x58、0x7C 或 0x80 上均无后续流量。保持连接但不发送加入请求时，握手后主机只发送会话更新，其中将加入端列为座位 1，且 `allow_participating` 已置位。

`ProcessJoinRequestJob` 执行 `InitialStep`, `CheckApprovalJoin`, `SendJoinRefused`, `SendJoinResponse`, `WaitResponseAck` 和 `JoinSucceeded`。原因 1 仅来自应用回调；其余原因由传输检查给出。

|  | 《剑》 | 《盾》 |
| --- | --- | --- |
| 状态名称字符串 | `0x03ad0f4e`..`0x03ad1010` |  |
| `CheckApprovalJoin` | `0x01553d20` | `0x017cc450` |
| 原因 1 的写入位置 | `0x01553d58 strb w9, [x19, #0xbc]` | `0x017cc59c strb w9, [x19, #0xba]` |
| `MeshProtocol` 全局变量 | `0x04c4db60` |  |
| Pia 跳板位于 `MeshProtocol+0x60` | `0x0157fcfc`，全局变量 `0x04c4b848` | `0x018414b0`，全局变量 `0x02616a30` |
| 跳板的安装方 | `0x0171a0b4`，来自槽位 `0x04c513f8` |  |
| `SendJoinRefused` | `0x01553d80`; `0x0154cd00` 写入 `0xFFFF0002`，然后在偏移 4 处写入原因 |  |
| 传输检查 | `0x0154806c`: `0xFF`，或原因 0、2、4、5 | `0x017bb2e0` |

```
0x01553cc0  ldr  x8, [x8, #0x60]      ; the approval callback (Sword)
0x01553cc4  cbz  x8, #0x1553d34       ; no callback installed -> accept
0x01553d2c  blr  x8
0x01553d30  tbz  w0, #0, #0x1553d4c   ; bit 0 clear -> refuse
0x01553d54  mov  w9, #1

0x018414b0  adrp x8, #0x2616000 ; ldr x8, [x8, #0xa30] ; ldr x8, [x8]    (Shield)
0x018414bc  ldr  x1, [x8, #0xb0]
0x018414c0  cbz  x1, #0x18414c8      ; null -> mov w0, #1 ; ret
0x018414c4  br   x1
```

当其对象的 `+0xb0` 为空时，跳板批准加入，否则对其执行尾调用。游戏通过 `0x01841490` (`str x1, [x0, #0xb0]`）写入该字段，调用位置为 `0x006b47b0`，使用过滤器 `0x006b41c0`，来自槽位 `0x02616a38`；并通过 `0x018414a0` (`str xzr`）清除该字段，调用位置为 `0x006b5340`；这两个调用点都由模式切换函数到达，该函数为 `0x006a9af0`.

### 加入过滤器 0x006b41c0

`manager` 为 `[0x02610000 + 0x4b0]`，而 `session`（游戏会话）为 `[manager+0x58]`。过滤器依次执行四道检查；下列数值是在搜索界面实时读取的：

| 顺序 | 位置 | 检查 | 实时值 | 判定 |
| --- | --- | --- | --- | --- |
| 1 | `0x006b4204` | 屏蔽列表已启用（`manager+0x21C`）且非空（`+0x1C0`，每个条目 16 字节，由以下函数遍历：`0x006be4a0`) | 已启用，空 | 通过 |
| 2 | `0x006b8260`，位于 `0x006b8230` | Pia 站点数 `pia_obj+0x1A8` 小于 `session+0x1F0`，无符号 `b.lo` | 数量 1，最大值 0 | 拒绝 |
| 3 | `0x006b827c` | 招募判定条件，`session` 虚表 `+0xB0` = `0x006ccb00` (`ldrb w0, [x0, #0x4f5]; ret`）；非零时遍历允许列表，地址为 `session+0x4c0`，数量为 `+0x4c8` (`0x006b8290`) | 标志 0 | 批准 |
| 4 | `0x006b4248` | `cbz`，作用于身份数据中以下位置的半字：`+0x10`；否则在以下位置查找：`[manager+0x2b0]`（数量 `+0x2b8`），并与以下值比较：`[manager+0x220]` | 任何 IPv4 站点均为 0 | 批准 |

允许列表标志 `session+0x4f5` 由 `0x006b86c4` 和 `0x006cc7bc` 设置，并在以下位置清除：`0x006ca848`，紧接着会在 `LdnCreateSessionSetting` 的构建位置 `0x006ca86c` 进行构建。条目通过 `0x006b5c80` -> `0x006b9920` 追加，通过以下函数清空：`0x006b5c70` -> `0x006b9910`.

身份数据由 `0x0177b7b0` 构建，并由 `0x017b1bd0` 填充，后者从以下偏移复制 32 字节：`+0x10`，源为加入端的网状网络站点位置条目（其中 `+0x448` 是站点，且 `+0x440` 为 3）：

```
0x017b1c50  add x1, x23, #0x10 ; mov w2, #0x20 ; mov x0, x20 ; bl 0x18fde50
```

`InetAddress`（反序列化函数 `0x01767a10`）具有一个填零的 16 字节地址字段，位于 `+0x08`，除非大小字节为 0x12，否则其中保存大端序 IPv4，端口位于 `+0x18`。位置数据将其公网地址保存在 `+0x00`，私网地址保存在 `+0x28`，因此身份数据位于公网地址中，且身份数据的 `+0x10` 是地址字节 8，对于 IPv4 为零；回调遍历的列表以加入端的地址为键。版本 4 的位置反序列化函数（`0x0185eff8` 及其后续代码）将中继端口存放在 `+0x60`，常量 id 存放在 `+0x68`，变量 id 存放在 `+0x70`，服务变量 id 存放在 `+0x74`，NAT 四元组存放在 `+0x78`..`+0x7b`，都在所复制的范围之外。常量 id `0x1249a221d8580000` 在礼物场景中遭到拒绝，在交换场景中被接受。

最大值 `session+0x1F0` 仅由 `0x006b9900` (`str w1, [x0, #0x1f0]`）写入，通过未被调用的 thunk `0x006b5c00` 和包装函数 `0x0110e5e0` 到达，后者的两个调用方（`SetMax(GetCount())`）分别是极巨大冒险匹配（`0x00bd9b30`，属于 `ChikaMatchingState*` 状态 `0x00bd1978..0x00bda158`）和极巨团体战巢穴（`0x01031c74`，属于 `View_NestHole`, `StateGuestReady`, `StateHostReady` `0x0102aba4..0x010370cc`）。在同一个运行中的游戏内实时读取时，该值在礼物界面为 0，在作为连接交换主机端时为 2，在作为极巨团体战主机端时为 4，三者均启用相同的过滤器。团体战主机端广播的 `NodeCountMax` 为 4；礼物界面广播为 2，但 Pia 最大值为 0。

`game_session+0x3F8` 在礼物界面为 1，在两个接受加入的会话中均为 0。`+0x365`, `+0x33D` 和广播 `+0xF9` 在团体战后仍保留团体战时的数值，因此它们是模式残留值。`manager` 在礼物界面和交换主机端之间逐字节完全相同。

### 传输检查

`0x017bb2e0` 在 `CheckApprovalJoin` 中于回调前执行，返回 `0xFF` 或原因字节，并原样发送：

```
0x017bb358  bl   0x017bab70        the live station count
0x017bb35c  ldrh w9, [x19, #0xa8]  the maximum
0x017bb368  b.hs 0x017bb380        count >= max, reason 0
0x017bb370  bl   0x017bb5a0        the index of the first free station slot
0x017bb378  cmp  w8, #0xfd         no free slot, reason 0
```

其对象为 `read_u64(read_u64(main + 0x0262F7B0))`，与 `pia_obj` (`main + 0x02616A30`）和 `game_session`.

| 字段 | 宽度 | 保存的内容 |
| --- | --- | --- |
| `+0xA8` | u16 | 最大站点数 |
| `+0xAA` | u8 | 启用字节；为零时，在任何其他检查前返回 2 |
| `+0xAB` | u8 | 选择计数时读取哪个位掩码字 |
| `+0xAC` | u8 | 计数时遍历位掩码的位数 |
| `+0xC4` | u32 | 占用位掩码，在以下条件下读取：`[0xAC] == [0xAB]` |
| `+0xC8` | u32 | 其他情况下使用的占用位掩码，也是空闲槽位搜索唯一读取的位掩码 |

计数结果为 1 加上置位位数（`0x017bad94`）；空闲槽位搜索返回第一个未置位的位，或 `0xFD`。在模拟器的连接交换界面实时读取，空闲时及 49 次尝试中均为：最大值 8，启用 1，选择值 0，位数 0，`+0xC4` 0, `+0xC8` 为 1，因此前两项检查通过。另有三个出口返回 0：

| 位置 | 检查条件 |
| --- | --- |
| `0x017bb380` | `count >= max`，或空闲槽位搜索返回 `0xFD`；实测通过 |
| `0x017bb498` | 位于 `mesh_obj+0x370` 的表：先将其大小与以下位置的 u16 比较：`read_u64(main + 0x02616710) + 0x70`，再与以下位置的容量比较：`table+0x48`；表中已有的加入端跳过这两项检查（`0x017bb41c`) |
| `0x017bb4d4` | 位于 `mesh_obj+0x132` 的字节，由以下位置的处理函数设置：`mesh_obj+0x120`，对应类型 0x18 事件，且在读取时清除 |

当 `+0xAA` 为零或某个预先判定条件成立时返回 2；当 `mesh_obj+0x131` 被类型 0x19 事件置位时返回 4。

## 接收任务与导入器

gfl 网络管理器为 `read_u64(read_u64(main+0x0261CBA8))`（虚表 `0x025819A0`）；每个发送桩函数都以全局变量为空作为无会话的防护条件。它在 `+0xD0`/`+0xD8` 处没有条目数组。进入本地无线分支时，`StateReceiveLocal` 的驱动函数 `0x01004C80`（基于 `state+0x2A0` 的分支状态机）通过 `0x010B7100` 构建接收任务（构造函数 `0x010B73E0`，虚表组 `0x0257DD88`，轮询函数 `0x010B74D0`），将其链接到 `manager+0x68`，并在以下位置安装接收委托：`state+0xB0` (`0x0100504C` 组）。

任务在 `job+0x60` 处保存数据接收器（目标 `0x01005BC0`），在以下位置保存进度回调：`job+0xE0` (`0x01005C70`），以及消息来源，即位于 `job+0x08` 的会话对象（虚表 `0x0250DAE0`）。它在搜索界面打开时出现，关闭时释放。注意：重新进入界面会在新地址重建该任务以及接收器的对象。

接收器尾调用 `0x00FF0E00` -> `0x00FF1FB0` -> `0x00FF2170`，即导入器。如果消息体长度不是 0x2D0 字节记录的整数倍，导入器会拒绝它（720 字节，即 PKHeX 中第 8 世代神奇卡片的大小；应用也在以下位置分配一个 0x2D0 大小的对象：`0x00feba7c`):

```
0x00ff22e4  umulh x8, x21, x8        ; x21 = the length
0x00ff22e8  lsr   x28, x8, #7        ; x28 = length / 0x2d0, the record COUNT
0x00ff22ec  mov   w8, #0x2d0
0x00ff22f0  msub  x8, x28, x8, x21   ; the remainder
0x00ff22f4  cbnz  x8, #0xff272c      ; not a whole number of records -> refuse
```

每条记录都要通过以下检查：[记录必须携带的内容](#what-a-record-must-carry)，位置为 `0x00FF2354`，经由 `0x01449820` 过滤，并由 `0x00FF3EC0` 实例化。未接收到任何内容时，强制进入 `StateConfirmGift`（12）会因空卡片而发生异常（`0x015C9230 ldrb w8,[x0,#0x1AC]`，来自控制器 `0x015BFFA0`，经由应用 `0x00FFA458`），而 `StateReceiveComplete`（14）会绘制空面板。

导入器的第二个参数是接收途径。它原样经过 `0x00FF0E00` 和 `0x00FF1FB0` 传给 `0x00FF2170`，后者将其保存在 `[sp+0x35c]`；它成为卡片的 `+0x64` (`0x00FF3F5C`），并作为 `route != 0` 成为头部的 `+0x0E` (`0x010B5FAC`）。每个调用方都是接收状态虚表槽位 16 中的 lambda：

| 状态 | 途径 | 调用点 |
| --- | --- | --- |
| `StateReceiveLocal` | 0 | `0x01005bf8` |
| `StateReceiveInternet` | 1 | `0x01011588`, `0x010115f0` |
| `StateReceiveSerial` | 2 | `0x0100a268`, `0x0100a2d0` |

## 卡片在信标广播数据中传输

分发端不加入任何网络。它广播一个在广播数据中携带卡片的网络，接收端从其 `Scan` 结果中重新组装卡片。

礼物功能使用 gflnet3 核心，与交换同步泵分离（注册数组 `0x006db3b0`，管理器 `read_u64(read_u64(main+0x02616750))`，在礼物界面为空）；后者从 0x7C/0x80 读取带 4 字节头部的数据。核心管理器 `read_u64(read_u64(main+0x02616B80))` 将自身命名为 `BeaconCommunication` (`0x02068858`，并在 `conn+0x278` 和 `conn+0x308`）处驱动 `nn::ldn::Scan`, `GetNetworkInfo`, `SetAdvertiseData` 和 `OpenAccessPoint`（包装函数 `0x017978F0`, `0x01794C3C`/`0x01799BE0`, `0x017961B0`, `0x01794CF0`）。其位于 `core+0x50` 的连接对象在任何对端出现之前就已存在，其发送门控 `+0x2FA` 始终未启用；加入 Pia 网状网络也只会更改其中镜像的 LDN 节点数。核心发送函数 `0x006C2840` 在以下位置入队：`core+0xF8`。在发送路径上，`0x136` 是一个 `memset` 长度，位置为 `0x010F7E00`，而消息 id 来自以下 getter：`0x010F7050`.

## 信标消息体的帧结构

LDN 广播数据共 0x180 字节，由 0x18 字节的头部和经信标核心封装的 0x168 字节消息体组成。

| 消息体内偏移 | 大小 | 字段 |
| --- | --- | --- |
| `+0x00` | 2 | 对以下范围计算的 CRC-16/ARC：`body[2:0x168]`，初始值 0，无最终异或 |
| `+0x02` | 12 位 | 网络 id，低 8 位位于 `body[2]`，高 4 位位于以下字节的低半字节：`body[3]` |
| `+0x03` 的高半字节 | 4 位 | 每次抓包中均为零 |
| `+0x04` | 1 | 每次抓包中均为零 |
| `+0x05` | 最多 0x163 | 应用负载 |

在神秘礼物、连接交换和极巨团体战界面抓取的每个信标中，网络 id 均为 `0xD70`。负载边界值为 `cmp x2, #0x163`，检查位置为 `0x006c2174`，用于保护 `memcpy` 到 `body+5` (`add x0, x8, #5`, `0x006c2148`).

校验和例程 `0x0065dcb0` 采用查表方式；`0x0065def0` 在 `0x02615fd8` 的控制下延迟构建查找表。这是多项式 `0xA001` 对应的反射型 CRC-16/ARC 表，更新方式为 `crc = T[(crc ^ byte) & 0xFF] ^ (crc >> 8)`，从 0 开始。抓取的四十个消息体均可重算出所存储的校验和，并能从解码字段逐字节重建。

构建器 `0x006c1fa0` 将消息体清零，使用位打包写入器在 `body+2` 写入网络 id，该写入器为 `0x006c1830`，将负载复制到 `body+5`，并对 `body+2`, `0x166` 字节计算校验和，存放于 `body+0`；如果负载缺失或过大，则改为存入 `0xFFFF`（`0x006c21d4`).

## 轮询函数重新组装的消息

负载字节 0 是消息类型。`0x010f6600` 为每种已知类型构建一个带类型的视图，指向 `payload+1`:

| 类型 | 视图 | 传给 |
| --- | --- | --- |
| 0 | `0x010f8730` | `0x0110f270`，并附带 `0x02610958` 后的对象；接收端自身的信标（站点信息） |
| 1 | `0x010f8830` | 位于 `[manager+0x68]` 的任务，虚表槽位 `+0x38` |

在礼物界面，这个任务就是接收任务，而槽位 `+0x38` (`0x0257dd88+0x48`；虚表指针为组基址加 0x10）是其轮询函数 `0x010b74d0`，因此类型 1 的负载会进入导入器。

轮询函数在 `payload+1` 处通过 `0x010f7bf0` 读取十字节头部（字段访问器 `0x010F7A40..0x010F7A80`；发送端在以下位置布置该头部：`0x010F7C08`）；分片紧随其后：

| 偏移 | 大小 | 含义 |
| --- | --- | --- |
| `+0` | 4 | 必须为零，否则轮询函数立即返回 |
| `+4` | 2 | 消息总长度 |
| `+6` | 1 | 分片数 |
| `+7` | 1 | 本分片的索引，只有小于分片数才接受 |
| `+8` | 2 | 重组消息的 CRC-16/ARC（`0x0065dcb0`) |

每条传输中的消息对应一个 0x88 字节的重组上下文，位于 `job+0x160` 和 `job+0x168`. `0x010f7550` 根据除索引外的所有头部字段将分片匹配到上下文；匹配失败时，`0x010f7360` 追加一个上下文，将字段存放于 `+0`, `+8`, `+0x10`, `+0x18`，根据长度设置 `+0x20` 处的缓冲区大小（`0x010f6fa0`），并根据分片数设置 `+0x58` 后的到达位图。`0x010f7430` 接受分片，`0x010f7100` 将其复制到 `index * 300`，最后一个分片占用剩余部分；索引超出缓冲区或对应位已经置位时丢弃。消息最大为 65535 字节、256 个分片；720 字节的卡片分为 300、300 和 120 字节三个分片。

当 `0x010f7610` 报告所有位均已置位时，`0x010f7680` 比较 `context+0x18` 和 `0x010f71e0`（缓冲区通过 `0x0065dcb0` 获取），不匹配时返回 null。收到 null 时，轮询函数跳过接收器（`0x010b77fc`），无论结果如何，都会在这一次轮询内移除该上下文。

| `+0x10` | 1 | 标志：位 0 跳过每卡一次表，位 2 表示每个卡片日期一次 |
| `+0x11` | 1 | 礼物种类，1 至 5 |
| `+0x12` | 1 | 每卡一次限制 |
| `+0x13` | 1 | 每卡一次标签 |
| `+0x15` | 1 | 标题索引 |
| `+0x1C` | 1 | 保存在头部 `+0xf` |

版本掩码：导入器调用 `0x007d4270`（《盾》：`mov w0,#0x2d; ret`），当值为 `1 << 1` 时，将 `0x2D` 与掩码进行测试，否则为 `1 << 0` (`0x00ff2330..0x00ff2358`）。《盾》使用位 1；`0xFFFF` 可通过任一版本；零值会跳过。

每卡一次表：当 `+0x13` 非零时（`0x00ff236c`), `0x01449820` 会检查礼物相册 `+0x1660` 处的表（块 `0x112D5141`，偏移 `0x1600`；五十个四字节条目，每个包含一个半字卡片 id 和一个字节），若条目匹配 `+8` 处的卡片 id 及 `+0x13` 处的字节，则拒绝该记录。保存时，`0x00ff1544` 在 `0x014494a0(album, record)` 满足 `+0x12` 非零且 `+0x10` 的位 0 未置位时调用（`0x00ff152c`）：它将五十个条目向下移动，在 `{card id, +0x13}` 处追加 `+0x1724`，当该 id 中字节非零的条目数达到 `+0x12` 时，将前 49 项中的这些字节清零。当 `+0x13` 或 `+0x12` 为零，或者 `+0x10` 的位 0 已置位时，卡片每次都会被导入。

最近接收表：`+0x10` 的位 2 会使保存路径调用 `0x01449560(album, record)` (`0x00ff1548`, `0x00ff1558`）：礼物相册 `+0x15c0` 处的十个 16 字节条目，在 `+0` 处保存 u64 日期，在 `+8` 处保存 u16 卡片 id。已有该 id 的条目会采用记录日期（`0x01449650`）；否则，第一个日期更早的条目（`0x016cc1f0`，无符号比较）接收 id 和日期（`0x01449804`, `0x0144980c`）。空条目会被采用，因为其零日期更早。

已接受的记录被复制到一个 `0x338` 字节结构中（开头 `0x68` 字节清零，记录位于 `+0x68`, `0x00ff2380`），并以长度 `0x2D0` 交给验证器 `0x010b5de0`。构建出的卡片对象大小为 `0x3A8` 字节，并将该结构保存在 `+0x70`.

`0x010b5de0` 将记录复制到其栈上，清零 `+0x2CC`，然后对全部 0x2D0 字节计算 CRC-16/CCITT-FALSE：查找表以最高有效位优先，根据多项式 `0x1021` (`0x010b5e60`）生成，初始值 `0xFFFF`，更新方式 `T[(byte ^ (crc >> 8)) & 0xFF] ^ (crc << 8)` (`0x010b5f54`）。对于空指针或长度不等于 `0x80000000` 的输入，它返回 `0x2D0`, `0x80000001`；校验和不匹配时返回以下值（导入器在此处将其映射为 1：`0x00ff23d0`），否则返回 0，即使种类不在 1..5 范围内也如此（`0x010b6004`）；种类 1 和种类 4 构建器的结果会被丢弃。它填充 `0x68` 字节头部（`0x010b5f98..0x010b5fbc`）：卡片 id 写入 `+8`, `+0x15` 写入 `+0xa`, `+0x11` 写入 `+0xc`, `route != 0` 写入 `+0xe`, `+0x1C` 写入 `+0xf`。在模拟环境下，带正确校验和的记录被接受，并携带来自 `+0x20` 的字进入种类 3 路径；相同记录未补齐校验和时，以及全零记录，均返回 `0x80000001`.

卡片 id：导入循环之后，`0x00ff2760` 收集 id 匹配的卡片；`0x00ff2f50` 读取记录 `+0x08` (`0x00ff30c0`, `ldr w8,[card+0xe0]` 处的 u32），与 16 位 id 比较，因此只要 `+0x0A` 或 `+0x0B` 非零，就不会匹配任何内容，导入器报告 2（无法在本游戏中领取的礼物）。在零售版主机上，`80 06` 位于 `+0x0A` 时便以这种方式被拒绝；`+0x0A` 为零，且 `a5 6a` 位于 `+0x0C` 时则可以接收。已读取的代码没有任何部分触及 `+0x0C`。projectpokemon 的 EventsGallery 中全部 161 张 SwSh 卡片在 `+0x0A` 处均为零，而在 `+0x0C` 处为 3 或其标题索引。

标题：`+0x15` 用于索引 PKHeX 随附的标题表 `text_wondercard8_.txt`，在卡片被接受之前显示于列表中。构建器使用的索引：1 为宝可梦的蛋，3 为道具名称，21 为“{species}（超极巨化宝可梦）”，34 为零花钱，36 为服装，39 为对战点数。索引 0 仅显示种类名称（某条记录在 `0b 00` 处为 `+0x0C`，标题为 0，列表中显示为“皮卡丘”）；索引 11 为“{original trainer} 的 {species}”，在法语主机上列出并保存为“Pikachu de POKELDN”（POKELDN 的皮卡丘）。

种类：1 至 5 通过 `0x02067620` 分派；其他值返回成功，但不构建任何内容。种类 3 和 5（`0x010b5fd8`）将 `+0x20` 处的字保存在头部 `+0x30` 中，且不构建任何内容。种类 1 进入 `0x010b58f0`，种类 2 复制其道具对，种类 4 进入 `0x010b5bb0`.

解析器不读取等级或相遇等级。这两个偏移来自卡片，而不是代码：`+0x244` 和 `+0x249` 是 `0x238..0x272` 中仅有的能预测两张已领取卡片不同等级的偏移（等级为 28 和 63，相遇等级为 32 和 59）。

等级 0：构建器抽取 `r = random & 0x7f`，直到 `r <= 99`，再取 `r + 1`，在 1..100 上均匀分布（`0x010b6218`）；同一条记录先后产生 20 和 35。蛋（`+0x245` = 1）无论如何都获得等级 1（`0x010b6400`）。随机生成的宝可梦显示相遇等级 0，即空的 `+0x249`。经验值始终符合该种类的成长组（立方曲线的种类在等级 20 时为 8000，较慢的一种在等级 4 时为 96）。

个体值：构建器按 HP、攻击、防御、特攻、特防、速度顺序检查六个字节；第一个落在 `0xFC..0xFE` 范围内的值会将满个体值数量 `byte - 0xFB`（1 至 3）存放到 `[sp+0x110]`，并将规格中的全部六个个体值设为 `0xFFFF`，丢弃其余值（`0x010b6300..0x010b63c4`）。否则，大于等于 32 的字节变为 `0xFFFF`，小于 32 的字节保留。该规格经由 `0x007667a0` 通过 `0x007662a0`, `0x00777f40` 和 `0x00766660` 传递，后者将等级上限设为 100（`0x00766a14`），并在数量为 1 至 5 时向相应数量的不同随机位置写入 31（`0x00766a50..0x00766b04`）；数量为 6 或更大时（卡片无法达到）不赋予任何 31（`0x00766a2c..0x00766a44`）。所有仍为 `0xFFFF` 的个体值均随机生成为 0..31（`0x00766de8`, `0x007660d0(0x20)`，游戏生成小于以下值的随机数：`n`）。因此，在任意个体值字节中设置 `0xFC`, `0xFD` 或 `0xFE`，恰好会产生 1、2 或 3 个随机位置的 31 个体值。

在 unicorn 中运行构建器表明，保持全零的记录会产生雄性、勤奋性格、第一特性且个体值为 0 的宝可梦。`pokeldn.swsh.wc8.pokemon_card` 写入性别 3、性格 `0xFF`、特性 3，以及每个个体值字节 `0xFF`，除非已经给定相应字段，因此游戏会随机生成这些值。

性别 3 在每次构建时随机生成一次，而领取过程会构建宝可梦两次：展示状态 `0x00fe3720` 根据记录构建一个宝可梦（`0x00fe3a50`）并读取其性别来选择模型；兑换函数 `0x010159d0` 则构建实际加入同行队伍的宝可梦（`0x01015a0c`）。在零售版《剑》中，一次领取显示了雌性，却给了雄性。性别 0、1 或 2 会跳过随机生成（`0x00766d94`），所以两次构建结果一致；零售版《剑》在值为 0 时显示并给予雄性，为 1 时显示并给予雌性。应用和 `bin/swsh_gift_host.py` 在构建卡片时按游戏的方式随机生成一次性别（当 `r + 1 < ratio`, `r` 小于 253 时为雌性，该值为 PKHeX 中该种类的个体性别比例）；`--set gender=3` 恢复由游戏自身随机生成。

## 信标投递卡片的端到端流程

将一条 720 字节记录拆为三个分片，通过合成信标提供，即可在未经修改的模拟主机上送达导入器，无需任何内存或代码修补。导入器的结果位于 `bound+0x2C0`, `bound`，其中 `job+0x80`。两条仅版本掩码不同的记录：

| 版本掩码 | 结果 | 主机消息 |
| --- | --- | --- |
| `0x0000` | 2 | 已收到礼物，但无法在本游戏中领取 |
| `0xFFFF` | 1 | 接收礼物失败 |

`0x00ff1fb0` 在导入器返回非零时返回其值，否则在卡片列表为空时返回 2：被掩码过滤掉的记录会使列表保持为空。`0xFFFF` 记录在 `+0x2CC` 处的校验和为零，验证器的 `0x80000001` 最终返回为 1。两者均未发生异常。

带正确校验和的种类 3 记录可以被列出、确认并保存。界面根据 `+0x11` 处的种类显示标题，根据 `+0x20` 处的字显示数量；日期全零时显示 2070 年 1 月 1 日；标识符为零时不发放任何内容。

## 投递到零售版主机的卡片

| --- | --- |
| LDN 协议 3（GBA 应用使用的协议），广播数据以 24 个零字节开头 | 否 |

种类 2 记录只需要种类、道具对和数量。解析器恰好从记录 `+0x20..+0x37` 复制六组 id／数量对到头部 `+0x30..+0x47` (`0x010b6024..0x010b6080`），并将头部 `+0x0D` 设置为非零数量的个数（`0x010b6084..0x010b60e4`）；兑换时，对每个数量非零的配对调用 `Bag::AddItem`（`0x01015d00..0x01015dd0`）。1.3.2 的道具表有 1607 个条目；其中名称在 `bin/message//common/itemname.dat` 中以 `★` 开头的条目是占位项（包括 1279 至 1578）。PKHeX 将这 1607 个 id 中的 51 个命名为 `???`；应用的道具选择器列出 `ItemStorage8SWSH.GetAllHeld()` 中的 817 个 id，这也是其卡片检查接受的集合。

种类 4 是服装（[服装](#clothing)）。种类 3 和 5 将 `+0x20` 处的字加到状态对象中有上下限限制的计数器上，状态对象为 `[[0x2610798]+0x208]`:

```
kind 3  0x01015e00   [status+0x17c] = min(old + amount, 9999)                  0x014390fc
kind 5  0x010160b0   [status+0x64]: an amount above 9,999,999 sets 9,999,999;

```

`status+0x64` 是零花钱：`AddPocketMoney_` (`0x014ad5e0`）调用相同的 `0x01438f20` (`0x014ad624`），而 `GetPocketMoney_` (`0x014ad700`）通过 `0x01438ef0` 读取它。两种兑换都从头部加记录的 `+0x88`（记录 `+0x20`）读取数额。在 unicorn 中，`0x010160b0` 对数额为 100,000 的种类 5 记录执行后，金钱从 0 变为 100,000，从 9,950,000 变为 9,999,999。EventsGallery 中没有种类 5 卡片。

种类 1 的兑换函数 `0x010159d0` 构建宝可梦（`0x010b6110`；为空则返回 0），并尝试放入同行队伍（`0x01015b78`，虚函数 `+0x28`）。如果同行队伍拒绝，则向盒子存储区 `[[0x2610798]+0x220]` 请求一个空闲槽位（`0x01408000`, `0x01015bd0`），仅在存在空位时放入（`0x01406b00`, `0x01015c08`）。放入同行队伍时返回 `{1, 0}`，放入盒子时返回 `{1, 1}`，未放入时返回 `{0, 1}`（`0x01015cd0`, `0x01015cf4`）；调用方将其存到 `+0x78` 处，对象由 `0x00feb610` 返回（`0x01014fe4`），但从不检查该值。未通过空间检查的卡片不会到达此处（[菜单会拒绝的情况](#what-the-menu-refuses)).

### Pokémon HOME

Pokémon HOME 将礼物直接发到其自身的盒子中，而不是以神奇卡片形式发放。此分组收录社区为这些礼物制作的卡片，即卡片库中用于《剑／盾》的 `HOME Simulated WCs`（卡片 id 从 9000 起，PKHeX 的 `WC8.IsHOMEGift`），每张都与 PKHeX 活动数据库中的卡片逐字节一致。列表采用 projectpokemon 的标题：具有隐藏特性的 HOME 初始伙伴妙蛙种子、小火龙和杰尼龟，首次登录的皮卡丘，全国图鉴的玛机雅娜，首次奇迹盒的伊布，首次 GTS 的洛托姆，首次挑战的皮丘，隐藏特性的敲音猴、炎兔儿和泪眼蜥，异色捷拉奥拉，Pokémon GO 的美录梅塔，超极巨化妙蛙种子和杰尼龟，以及异色凯路迪欧。卡片 9000 至 9007 的第一修订版将所有 PID 固定为 0；保留的第二修订版改由游戏随机生成。

通过这些卡片收到的宝可梦不带 HOME 追踪标识，而 PKHeX 要求 HOME 发放的礼物具有该标识：宝可梦由主机生成，因此无论 HOME 追踪标识设置如何，PKHeX 都会标记追踪标识缺失（[HOME 追踪标识设置](gui.md#the-home-tracker-setting)），而 Pokémon HOME 目前接受这种宝可梦。应用以琥珀色边框标示这些卡片，并说明这一点。

位于 `+0x10` 的标志决定主机接收卡片的频率（[菜单会拒绝的情况](#what-the-menu-refuses)):

| 标志 | 卡片数 | 接收规则 |
| --- | --- | --- |
| 位 0 | 130 | 每个卡片 id 一次，此后以消息 7 拒绝 |
| 位 2 | 13 | 每个卡片日期一次，每天最多十次 |
| 两者皆无 | 46 | 每次均可接收 |

两张宝可梦卡片的版本掩码为 1 或 2，会被另一版本跳过。

## 服装

种类 4 记录从 `+0x20` 开始携带十二组 u32 对，每组依次为类别和索引：状态字节 `+0x20..+0x4F` 为零的玩家使用前六组（`+0x105`），否则使用后六组（`+0x50..+0x7F`）。该字节由 `0x01424c20` 在状态对象 `[[0x2610798]+0x1e8]` 上读取。PKHeX 的 `MyStatus8` 将玩家性别保存在存档块偏移 `0xA5`, `0x60` 处，位于它下方；该对象是否在 `+0x60` 处保存此块尚未验证。

解析器 `0x010b5bb0` 将玩家对应的六组配对复制到头部 `+0x30..+0x5F`，并将索引不为 `0xFFFFFFFF` 的配对数量复制到头部 `+0x0D`。兑换函数 `0x01015eb0` 根据同一条件再次读取记录中的配对（`0x01015f14`；记录 `+0x20` 对应头部加记录的 `+0x88`），并对每个索引不为 `0xFFFFFFFF` 的配对，调用 `0x0143a450(wardrobe, category, index, 1)`，操作衣橱 `[[0x2610798]+0x218]`。该设置函数拒绝大于 14 的类别或大于 1023 的索引，否则设置字节 `index & 7` 中的位 `wardrobe + 0x68 + category * 0x80 + index / 8`。配对 `(0, 0)` 会设置类别 0 的位 0；使用以下索引跳过槽位：`0xFFFFFFFF`.

在 unicorn 中将状态字节分别设置为 0 和 1 运行后，对于应用提供的每套服装，验证器、解析器和兑换函数都恰好把记录的前六组和后六组配对设置为衣橱位（`tests/test_swsh_gift.py`）。这些配对来自 projectpokemon EventsGallery 的十四张官方服装卡片：

## 菜单会拒绝的情况

兑换所选卡片之前，`0x01014a60` 读取种类 `card[+0x7c]` (`0x01014bcc`), `w25 = 0x00ff1750(card) - 1` (`0x01014bd4`, `0x01014be4`）及记录标志的位 2 `[card+0xe8]` (`0x01014be8 ubfx w24,w8,#2,#1`），并对种类 1 执行空间检查 `0x013adee0` (`0x01014d68`）。依次如下：

```
0x00ff1750 returned 1, 2 or 3    message 7, 0x10 or 0x11     0x01014d9c cmp w25,#3; table 0x02065360 = 7, 16, 17
kind 1 and no room               message 8                   0x01014c14 mov w21,#8
flag bit 2 set                   message 0xF, then state 3   0x01014d38 mov w1,#0xf; continuation 0x010156f0
otherwise                        state 3, the redemption     0x01014e70
```

`0x02064f80` 保存 `mystery.tbl` 标签哈希，每个消息索引对应一个 u64；从 `0x01000718` 开始的初始化器将条目 k 解析到 `owner+0x5f8+8k`，再由 `0x01002da0` 读取。以下来自 1.3.2 英文版的 `mystery.dat`:

| 消息 | 标签 | 文本 |
| --- | --- | --- |
| 7 | `msg_o_mystery_win_13` | 你已经收到过相同的礼物，因此无法领取此礼物。 |
| 8 | `msg_o_mystery_win_14` | 已经没有空间容纳更多宝可梦了。请在同行队伍或宝可梦盒中腾出空间，然后重试。 |
| 0xF | `msg_o_mystery_win_34` | 此礼物每天只能接收一次。接收后，必须等到第二天才能再次领取。 |
| 0x10 | `msg_o_mystery_win_35` | 此礼物每天只能接收一次。你今天已经领取过了，请明天再来。 |
| 0x11 | `msg_o_mystery_win_36` | 每天最多只能接收 10 份礼物。你今天已经领取了 10 份，请明天再来领取更多礼物。 |

拒绝后的延续函数 `0x01015740` 向 `+0x80` 存入 0，即菜单的首个状态。被拒绝的卡片既不会发放也不会保存；拒绝原因消除后即可重新领取。

`0x013adee0` 当盒子存储区没有空闲槽位（`0x013adfb4 cset w20,eq`）且同行队伍报告已满时，返回 1（无空间）（同行队伍虚表 `+0x60`，槽位 12，`0x013adfc4`; `0x013adfd0 and`).

`0x00ff1750`，仅由 `0x01014bd4` 调用，是接收检查。当 `[card+0x60]` 或 `[card+0x68]` 为零时（`0x00ff1750..0x00ff1770`）立即返回 1；对于途径 0 至 2，继续经由 `0x00ff17b4` 进入 `0x00ff1a30`:

```
data = album+0x60 (0x014480e0)
record flag bit 0, and the card id's bit set in the bitmap at data+0x1450 (album +0x14b0)   -> 1
record flag bit 2 clear (0x00ff1ab0)                                                       -> 0
the record's day invalid (0x00ff1b84)                                                      -> 3
ten entries of 0x10 bytes from data+0x1560 (album +0x15c0), 0x00ff1b88..0x00ff1c70:
    entry id == card id and card day <= entry day (0x016cc210, cset ls)                   -> 2
    card day > entry day (0x016cc1f0, cset hi): a free entry
a free entry                                                                               -> 0
none                                                                                       -> 3
```

读取位图时取字节 `id >> 3` (`0x00ff1a8c ubfx x9, x23, #3, #0xd`），没有边界检查：位图为 0x100 字节（id 0 至 2047），因此带标志位 0 且 id 大于等于 2048 的记录会越界读取位图，id 从 13000 起还会超出该块的 0x17C8 字节。标志位 0 未置位的记录从不读取它。接收时会设置该位；写入方尚未定位。在零售版《剑》中，EventsGallery 的精灵球 x100 卡片（id 0x6A，标志 1）经本地无线第二次发送时，以消息 7 被拒绝并从列表移除；标志 0、id 0x270F 的记录则成功接收了十次。

这些条目仅由 `0x01449560` 写入，其唯一调用方 `0x00ff1558` 位于 `0x00ff154c tbz w8,#2` 之后，在 `[card+0xe8]` 上执行，且存储的是记录自身的日期（`0x01449570`, `0x01449648`），而非接收时间。带标志位 2 的卡片按每个卡片日期接收一次，每天最多十次；日期不变时再次发送，只要条目仍存在，就会以消息 0x10 拒绝。

保存路径 `0x00ff13f0` 只有一个调用方，即 `0x01014f74`，位于兑换函数 `0x01014eb0` 中，在放入宝可梦之前（`0x01014fb0 bl 0x010159d0`）。其函数体 `0x00ff14c0`（唯一调用方 `0x00ff1404`）调用 `0x01449470`, `0x014494a0`, `0x01449560`, `0x01444f80`, `0x018fdc60`, `0x01444d60`, `0x01445000` 和 `0x01444de0`，它们均不读取宝可梦；`0x00ff13f0` 随后将当前时间（`0x01449ca0` -> `0x01900050`）写入 `card+0x70`，适用于途径 1 至 4；对于途径 0，则将 `card+0xd8` 复制到此处，然后存档卡片（`0x014480f0`）。保存路径不检查任何合法性。

构建和兑换均不检查招式、回忆招式、性格、精灵球、携带道具或形态是否符合种类。构建器 `0x010b6110` 只有一个出口，不会拒绝：它原样存储四个招式和四个回忆招式（`0x77bfb0`, `0x77b9a0`；存储位置为 `0x770c7c`），招式 id 大于 826 只会改变 PP 查找（`0x00781490`）。兑换函数 `0x010159d0` 只检查种类字节、构建结果非空，以及同行队伍（`0x7840f0` 拒绝种类 0 或已满队伍）或盒子中的空间（`0x1406b00` 需要空闲槽位）。在 unicorn 中使用 1.3.2 个体数据表运行时，构建器原样保留了皮卡丘的非法招式 14、337、57、900，回忆招式 1、2、3、9999，性格 200，精灵球 200 和道具 9999。

唯一的种类检查位于 PokemonParam 构造函数 `0x777f40` (`0x778118..0x778148`）：如果某种类的个体数据条目中，字节 0x21 的位 6 未置位（`0x764990`, `0x77f530`），则设置记录 `+0x04` 字的位 2（`0x76eb40`）。该位置位后，每个访问器都读写一个静态替代对象，其种类为 0x383（`0x776c50`，由 `0x776bc0` 填充）。该位就是游戏的坏蛋标志：`0x77d610(pp, mode)` 通过 `0x767f40` 读取它（模式 0 表示是蛋且非坏蛋，模式 1 表示坏蛋，模式 2 表示任意一种），而 `0x77f600` 将大于 0x382 的任何种类命名为文本 0，即 1.3.2 英文版 `monsname.dat` 中的“Egg”（蛋）。菜单路径中没有任何部分拒绝这种卡片：验证器 `0x010b5de0` 只在校验和与头部复制中读取种类（`0x010b59b8`），`0x01014a60` 的所有分支都不读取它，同行队伍添加函数 `0x7840f0` 接受种类 0x383，图鉴登记在检查蛋字节后返回（`0x01434b24`），而复制函数 `0x766390` 保留原始 0x148 字节，包括标志和记录的种类。在 unicorn 中，种类 19 和 493 会被标记，种类 25 和 1000 不会；验证器接受小拉达记录。向模拟运行的法语《盾》1.3.2 提供该记录（种类 19，游戏中不存在）后，游戏将其列为“Rattata”（小拉达），完整播放展示过程，显示“Vous avez reçu un Rattata !”（你收到了小拉达！），并在礼物相册中保存“小拉达”，但同行队伍中放入的条目名称为“Egg”（蛋），模型也是蛋，语言标签为 ANG，能力页面所有字段均为空。游戏在接收时保存；同行队伍槽位保留了种类 19，且 `+0x04` 的位 2 已置位。大于 898 的种类会读取标记为存在的个体数据条目 0，而形态大于等于该种类形态数量时会读取基础种类，因此两者均不会被标记。切勿发送《剑／盾》中不存在的种类；桌面应用的 PKHeX 检查会拒绝它。

性别是构建过程唯一会纠正的字段（`0x777490`，个体数据字段 0x14，在以下位置读取：`0x7774a4`）：比例 0、254 和 255 分别强制为雄性、雌性和无性别（表 `0x1c4d2d0`）；对于其他比例，请求值 2 会变成 0（`0x7774d8`）。构建器将记录性别 3 转为 0xFF，即随机（`0x010b62ac`).

## 卡片的日期

记录的前八个字节是礼物相册显示的日期，以小端序 u64 位字段保存绝对 UTC 时间。已发布的字段映射均未说明它；PKHeX 的 `WC8.cs` 从位于 `+0x08`.

| 位 | 字段 |
| --- | --- |
| 0-5 | 秒 |
| 6-11 | 分钟 |
| 12-16 | 小时 |
| 17-21 | 月内日期 |
| 22-25 | 月份，1 至 12 |
| 26-39 | 年份，绝对值 |

`0x016cc5e0` 使用 days-from-civil 算法将其转换为 POSIX 时间（其中包含 `146097`, `1461` 和除以 100 的常量），当值等于 `main+0x2616900` 后的哨兵值时返回 0。礼物相册绘制函数 `0x00ffbaa0` 将其传给 `nn::time::ToCalendarTime` (`0x00ffbaf0`），因此会应用主机时区，回退到 `ToCalendarTimeInUtc`。年份以两位数显示。

| 记录字节 | 法语零售版主机上的显示 |
| --- | --- |
| 零 | 01/01/2070 01:00 |
| 10 月 18 日，16:26 UTC | 18/10/2018 18:26 |
| 8218 年 | 2018 |
| `01 02 03 04 05 06 07 08`（321 年的第 0 月） | 01/12/2020 15:53 |

只有本地无线卡片保留原日期。所有其他途径都会用 `nn::time::StandardNetworkSystemClock::GetCurrentTime` (`0x00ff3f8c` -> `0x01449ca0`；PLT `0x01900050`，GOT `0x0260fbb8`）覆盖这八个字节，由 `0x016cbfd0` 和 `0x016cc1d0`.

分发端在发送卡片之前，立即使用计算机当前 UTC 时间填充空日期，然后重新计算校验和。分发端提供的非零日期会保留。官方活动文件往往含有八个零字节，因为在线途径会提供接收时间。此回退机制也能让这些文件在本地无线中具有日期。导出的文件保留原始日期，主机礼物相册中已保存的卡片保持不变。宝可梦自身的相遇日期与礼物相册日期相互独立。

## 礼物相册保存卡片的位置

礼物相册是存档块 `0x112D5141`（PKHeX 的 `KMysteryGift`), `0x17C8` 字节，由 `0x01447eb0` 加载到位于 `+0x60` 的礼物相册对象中，并由 `0x01449d90` 写回。它保存重新编码的头部，从不保存 720 字节的传输记录或其中的字符串。`tools/switch/swsh_save.py` 读取一个 `main` 并将其解析成各个块（PKHeX 的 SwishCrypto：对整个文件应用静态异或掩码，每个块使用以其键为种子的 XorShift32 流，对两个常量之间的加密消息体计算 SHA-256）；`--key 112d5141 --out FILE` 写出此块，而 `--patch KEY OFF HEX --write OUT` 重写块内字节并重新封装文件校验。

```
0x0000  50 slots of 0x68 bytes, newest in slot 0; an insert moves every slot down one
        (0x01449880 indexes them, cmp w1, #0x31; a slot is in use when its +0x0C is non-zero)
0x1450  0x378 bytes, zero in every save read; the last-receipt table is 0x1560..0x15FF
        (album +0x15c0) and the once-per-card table 0x1600..0x16C8 (album +0x1660)
```

一个槽位就是导入器根据记录填充的 `0x68` 字节头部：

```
+0x00  8    the record's date bitfield (zero draws 1 January 2070)
+0x08  u16  card id
+0x0A  u16  the record's byte at +0x15 (0 on Pokemon cards, 1 on kind-3, 3 on an item card)
+0x0C  u8   kind: 1 Pokemon, 2 item, 3 the empty kind
+0x0D  u8   kind 2: how many of the six item quantities are non-zero; 0 otherwise
+0x0E  u8   1 when the card came by any route but local wireless
+0x0F  u8   the record's byte at +0x1C (1 on kind-3 cards)
+0x12  u16  level (kind 1)
+0x30  u32  species (kind 1); kind 2: the item pairs (u16 id, u16 quantity) as at record +0x20
+0x38  4 x u32  moves (kind 1)
+0x48  26   nickname, UTF-16 (kind 1)
+0x62  u8   3 on every Pokemon card
```

将槽位的 `+0x0C..+0x62` 清零会从礼物相册中移除卡片；该卡片发放的道具仍保留在 `MyItem` (`0x1177C2C4`).

## 清空存储区的逐帧更新

`0x010f65a0` 是 gfl 网络管理器的逐帧更新，从 `0x0261cba8` 传入管理器调用。它读取单调时钟，通过交换操作从 `manager+0x60` 处取尽接收器内容，交换函数为 `0x006c5300`，遍历条目，并在每轮发现存储区非空时将时钟读数写入 `manager+0x80`。围绕导入器 `+0x80` 的 `0x00ff2170` 访问则是另一回事：线程局部的防护栈，由 `nn::os::GetTlsValue` 返回；在存储区追加位置前后也有相同的入栈和出栈操作，位置为 `0x006c54a4`.

某些会话中，存储区从不被取尽：接受的消息体不断累积（第一个消息体在 27 分钟后仍然存在），`manager+0x80` 保持不变，且 `job+0x160` 保持为空。其他会话则正常取尽；原因尚未解决。注意：解读任何信标结果之前，先检查 `manager+0x80` 是否持续推进。

是什么驱动该更新仍未解决。它的唯一调用方是 `0x01109240`，一系列逐子系统更新，位于 `0x00f1df30` 内；后者既没有 `bl` 调用方，也不占虚表槽位，而是通过已注册回调到达。
