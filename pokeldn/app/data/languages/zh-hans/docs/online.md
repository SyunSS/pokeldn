# 在线交换

在线交换将相隔很远的两位玩家连接起来。每位玩家的开发板作为主机端，与各自的主机建立本地交换；两个应用通过公共 Nostr 中继相遇，并把各自主机出示的宝可梦传给对方。每台主机看到的都是普通本地交换，只是伙伴的宝可梦来自远端主机。本项目不拥有任何服务器：中继是公共基础设施，而且中继始终只处理加密事件。代码：`pokeldn/online/`；启动器标志为 `--online` 和 `--online-code`.

## 房间

两个应用运行同一游戏并使用相同密码时就会相遇。房间为

```
sha256("pokeldn online 1|<game>|<code or 'open'>")
```

，表示为 64 位十六进制数字。密码为空表示开放房间：所有未设密码、在线交换该游戏的玩家都会进入。《火红》和《叶绿》共用 `frlg`，《朱》和《紫》共用 `sv`，目录中的其他游戏亦以此类推。游戏有连接密码时，这里使用主机本身的连接密码，因此玩家需要在主机和应用中各输入一次。八位数字提供 10^8 个房间：输入同一密码的人会相遇，与游戏本身相同。

## 中继

所有事件均为类型 21059 的 Nostr 事件（NIP-01），位于 20000-29999 的临时事件范围：中继将其转发给当前订阅者，不存储任何内容。每个事件携带标签 `["t", ]`，面向单个应用的事件还携带 `["p", ]`。每个应用建立一个订阅，请求带房间标签、类型为 21059、时间从自身启动前十秒开始的事件。

每个会话都用新生成的 secp256k1 密钥签名（BIP-340 Schnorr，`pokeldn/online/schnorr.py`，已对照 19 个 BIP-340 测试向量验证），因此两个会话不共享任何内容。应用把每个事件发布到其连接的全部中继，并丢弃同一事件 ID 的重复副本。

| 中继 | 每 2 s 一个事件，共发送 8 个 |
| --- | --- |
| relay.primal.net, relay.snort.social, offchain.pub, relay.nostr.net, nostr.oxtr.dev, nostr-pub.wellorder.net | 送达 8 个 |
| relay.damus.io | 送达 4 个；对地址限速，随后临时封禁 |
| nos.lol, nostr.mom | 因限速被拒绝，未送达任何事件 |
| nostr.wine | 拒绝（付费中继） |

第一行是默认中继集合；`POKELDN_RELAYS`（逗号分隔的 URL）会替换它。offchain.pub 会拒绝未知密钥的突发消息（“不在我们的信任网络中”），但接受有节奏发送的事件。通过这些中继，第二个应用到达后 0.4 s 两个应用完成配对，344 字节记录的传输约需 0.15 s。

一台零售版《朱》和一台零售版《紫》，各自由自己的开发板作为主机端，通过中继完成交换：双方主机都显示了对方出示的内容，双方确认后，各自收到对方的宝可梦，两块屏幕均无错误。一台零售版《火红》和一台零售版《叶绿》也完成了同样测试：双方整支队伍逐对传输，包括邮件和奖章，耗时约 4 s；交换后重新传输的队伍再次进入交换菜单。

同一桌面上的两台主机会直接找到彼此：例如《朱／紫》使用相同密码搜索，或《火红》玩家选择“成为领队”。此类测试中，每台主机使用各自的本地密码（或加入某块开发板创建的群组），再用 `--online-code` 将两块开发板置于同一房间。

### 存储事件

在线交换不存储任何内容。使用类型 30402 的挂牌事件（NIP-99）和类型 1059 的封装事件（NIP-59），在七个中继（relay.primal.net、relay.nostr.net、nostr.oxtr.dev、nos.lol、nostr.mom、offchain.pub、nostr-pub.wellorder.net）上测量了事件存储行为，每项均使用新密钥：

| 行为 | 结果 |
| --- | --- |
| 新密钥发出的事件 | 35 个中 35 个被接受并可读取返回 |
| 一个带 NIP-40 `expiration`、于 2 h 后到期的 30402 | 1.1 h 时仍可读取；到期后 6 min 没有中继再提供它 |
| 重新发布一个 30402，沿用相同的 `d` | 一分钟内所有中继都只提供较新版本 |
| 一个类型 5 事件，通过以下字段指定某个 30402：`e` 和 `a` | 一分钟内所有中继都只提供类型 5 事件 |
| 通过其 `p` 键读取类型 1059 事件 | 六个中继可提供；relay.nostr.net 要求 AUTH，并拒绝所有类型 22242 事件（“中继需要配置 serviceUrl”） |

尚未测量中继对无到期时间事件的保留时长。

## 相遇

每个事件的内容都使用房间密钥 `sha256("pokeldn room key|" + room)` 进行 AES-256-GCM 加密。内部内容如下：

| 消息 | 发送时机／对象 | 内容 |
| --- | --- | --- |
| `here` | 每 2.5 s，发往房间 | 协议 1、X25519 公钥、训练家名称、应用版本、忙碌状态 |
| `invite` | 发往单个应用 | 训练家名称 |
| `yes` / `no` | 应答 | 训练家名称 |
| `bye` | 发往并非自身伙伴的应用 | 原因 |

应用只邀请签名密钥大于自身、处于空闲状态且已观察最久的应用；同一时间只保留一个邀请，最多等待 6 s。已发出邀请的应用对其他邀请均回复 `no`。邀请被拒绝或无人应答后，会跳过该应用 10 s。中继不保证顺序，因此伙伴的第一条信道消息可能早于其 `yes` 到达；该消息可视为 `yes`.

## 信道

配对后的应用发往伙伴的消息有两层加密封装：外层使用房间密钥进行 AES-GCM 加密，包含发送方的 X25519 密钥；内层使用以下密钥进行 AES-GCM 加密：

```
sha256("pokeldn pair|" + room + "|" + sorted("<signing key>:<x25519 key>" of both) + shared secret)
```

每条消息携带 `s`，即其编号，以及 `a`，即已按序收到的最大编号。未确认消息每 2 s 重发；消息到达后 0.3 s 发出确认，因此一次确认可覆盖一同到达的多条消息。每 4 s 一次 ping 维持配对；伙伴沉默 45 s 即视为丢失。若双方均未出示任何内容之前伙伴就丢失，应用会寻找其他人替代。

| 消息 | 含义 |
| --- | --- |
| `hello` | 训练家名称和应用版本，仅发送一次 |
| `offer` | 第 *r* 次交换：本地主机出示此记录（base64） |
| `withdraw` | 第 *r* 次交换：本地主机撤回出示内容 |
| `accept` / `unaccept` | 第 *r* 次交换：本地主机确认，或撤回确认 |
| `refused` | 第 *r* 次交换：伙伴的应用拒绝本方记录及其原因 |
| `done` | 第 *r* 次交换已在本地主机完成；下一次交换为 *r* + 1 |
| `ping`, `bye` | 保活；离开 |

## 传输什么

只传输主机出示的记录和交换状态，绝不传输密钥、存档或文件。各应用在本地主机看到收到的记录之前，先使用 PKHeX 检查它（`pokeldn.online.session.checker`):

| PKHeX 检测结果 | 记录处理方式 |
| --- | --- |
| 无法解析、校验和错误、游戏中不存在该物种或形态，或招式、道具、球种 ID 超出游戏表范围 | 拒绝；发送方应用显示原因 |
| 游戏从未开放的携带道具或招式（“未发布”；《剑》的道具截止于 1607） | 拒绝 |
| 其他任何合法性标记 | 允许出示，并向接收玩家显示 PKHeX 的标记 |

零售版主机交换过的记录也可能无法通过 PKHeX 合法性分析，因此仅有标记本身不会导致拒绝。

《火红》和《叶绿》在玩家入座时交换整支队伍，因此每台主机都能看到伙伴队伍，与两张卡带直接交换相同。每个主机端向本地主机请求一对队伍数据块，并保留自己的数据块，直到伙伴主机发送了同一对；主机等待两个块时没有定时器 [trade.c:1478]，因此两个主机端不会互相等待。只有 PKHeX 读出块中每只宝可梦后，队伍块才会到达主机。选择先以 `pick`（主机光标）的形式传输，之后才是出示记录。

伙伴离开或沉默 45 s 时，视为撤回出示内容：每个主机端从本地主机撤回伙伴宝可梦，除非交换已越过不可撤销点。《火红／叶绿》的领队只能应答跟随方的操作，因此伙伴离开后，主机当前及后续每次选择都会收到 `PLAYER_CANCEL_TRADE`（“已取消”，返回菜单），即领队选择“取消”时的应答 [trade.c:1712]；随后在菜单选择“取消”即可离开。伙伴在队伍传输中途离开时，该传输以空队伍完成。玩家在菜单选择“取消”会立即通知伙伴。零售版《火红／叶绿》配对测试中，一位玩家选择宝可梦，另一位取消并离开；第一台主机显示取消消息、返回菜单，再选择“取消”后离开房间。

《剑》的连续交换本来就会出示不同于快照槽位的记录（[《剑》的交换](swsh_trade.md)），实际交换的是 content 50 中的记录。

## GTS

GTS 在从不同时在线的玩家之间交换已入库宝可梦。玩家从 [Bank](gui.md#the-bank) 中挂牌一只宝可梦，并指定想要的物种及等级范围；另一玩家用自己的宝可梦应价；挂牌者下次打开应用时完成交换。不涉及任何主机：收到的宝可梦进入 Bank，再由 Bank 转移到游戏。代码：`pokeldn/online/gts.py`（事件）、`pokeldn/app/gts.py`（Bank 侧），以及应用的 GTS 页面。

| 事件 | 类型 | 签名方 | 内容 |
| --- | --- | --- | --- |
| 挂牌 | 30402（NIP-99），`d` 为随机 ID | 为该挂牌新生成的密钥 | JSON：协议 1、游戏、PKHeX 读取的宝可梦信息（物种、等级、性格、特性、球种、道具、招式、初训家）、记录的 SHA-256、想要的物种和等级、训练家名称、状态、获选应价 |
| 应价 | 1059, `p` 为挂牌密钥 | 为该应价新生成的密钥 | 加密封装：挂牌的 `d`、游戏、记录、训练家名称 |
| 答复 | 1059, `p` 为应价密钥 | 挂牌密钥 | 加密封装：应价 ID，以及挂牌记录或拒绝信息及原因 |
| 删除 | 5（NIP-09） | 其指定事件所使用的密钥 | 无 |

挂牌携带 `["t", "pokeldn-gts"]`, `["t", "pokeldn-gts-has-"]` 和 `["t", "pokeldn-gts-wants-"]`，使中继可按任一物种筛选；还携带 NIP-99 定义的 `title`, `summary`, `status` 和 `published_at`，以及一个 NIP-40 `expiration`，到期时间为 30 天后。封装消息体使用 `sha256("pokeldn gts|" + x)` 进行 AES-256-GCM 加密，其中 x 是一端私钥与另一端仅含 x 坐标的公钥执行 ECDH 后所得乘积的 x 坐标（`schnorr.shared_x`）。应用在信任存储事件之前，会检查每个事件的 ID 和签名。

| 步骤 | 行为 |
| --- | --- |
| 存入挂牌 | PKHeX 必须判定宝可梦合法；其记录及 `.json` 从 Bank 移入 GTS 文件夹；挂牌发送到每个中继 |
| 应价 | 宝可梦必须合法且满足所需物种和等级；它移出 Bank，加密封装的应价发往挂牌密钥 |
| 挂牌者打开应用 | 请求发往其挂牌密钥的封装消息；按最早优先的顺序应答已存储应价；首个合法且满足挂牌条件的应价会完成交换，其余全部拒绝 |
| 交换 | 答复携带挂牌记录；重新发布挂牌，将状态设为已交换并附上获选应价 ID；收到的记录存入 Bank |
| 应价者打开应用 | 将答复中的记录与挂牌 SHA-256 核对后存入 Bank；若被拒绝、挂牌与另一应价成交或挂牌已撤下，则把自己的宝可梦放回 Bank；删除自身应价 |
| 挂牌到期 | 30 天后，挂牌宝可梦返回挂牌者 Bank，不再与任何应价交换；到期一小时后，中继发送完全部已存储答复且没有针对该应价的答复时，应价宝可梦返回 Bank |
| 撤下 | 重新发布挂牌，将状态设为已撤回，并返还其宝可梦；后续应价均拒绝 |

每个挂牌和应价都对应 `Documents/pokeldn/GTS` (`GTS` 内的一个文件夹，位于 `POKELDN_DATA`，若已设置则使用该位置），其中包含 `state.json`（私钥、已签名事件、每条已发送答复）和记录。答复先写入再发布，每个仍有效的事件都会重新发送到每个新连接的中继，因此传输中丢失的答复会在下次打开应用时送达。已完成文件夹在最后修改 60 天后删除。

两个应用使用各自 Bank，通过七个中继进行交换，且每个应用只在另一个关闭时打开：七个中继均存储了挂牌、应价和答复（OK true）；挂牌者应用打开时完成交换，应价者应用打开时将挂牌记录存入 Bank；删除后，七个中继对测试密钥只提供类型 5 事件，不再提供其他内容。整轮约需 30 s。

使用的中继是“[存储事件](#stored-events); `POKELDN_GTS_RELAYS`”中的七个；使用逗号分隔列表可替换。relay.snort.social 不保存任何内容，因此不包含在内。

应用遵循这些规则，但修改版应用未必遵循。挂牌者应用可能保留应价宝可梦而不返回任何内容，挂牌也可能展示挂牌者并未持有的宝可梦；SHA-256 只能事后揭示，无法事前证明。没有可信第三方，就无法保证公平交换（Pagnia 和 Gaertner，1999）。
