# 传说 阿尔宙斯

《宝可梦 传说 阿尔宙斯》（2022 年，游戏 ID 为 `01001f5010dfa000`）是一款原生 Switch 游戏，Pia 静态链接在 `main`.

地址均为 1.1.1 更新中解压后的 `main` 内的偏移，布局以 `tools/switch/nso_read.py` 的加载结果为准（text 段 `0x0..0x32a5690`，rodata 段起于 `0x32a6000`，data 段起于 `0x401a000`).

## 无线通信层

|  | 值 |
| --- | --- |
| Pia 包头版本 | 11，属于 wiki 所述的 Pia 6.16 至 6.23 区间（剑为 4，晶灿钻石／明亮珍珠为 9，GBA 应用为 15/16） |
| 包头大小 | 0x1C |
| 线上传输的 GCM 标签 | 8 字节，由 16 字节截断而来 |
| LDN 口令 | 与剑／盾相同，采用 `HGhG` 这一拼写（wiki 的 `HGHG` 一行有误） |
| Pia 游戏密钥 | `p1frXqxmeCZWFv0X`，与剑／盾及朱／紫相同 |
| LDN 本地通信 ID | `0x01001f5010dfa000`，即游戏 ID |

游戏密钥和口令位于 rodata 中的 `0x3985308` 和 `0x3985319`，以 NUL 结尾。位于 `0x2c1e684` 的 LDN 初始化代码从 `x3` 中取得本地通信 ID（即 `mov`/`movk` 处的 `0x264082c` 指令序列），并在以下位置安装游戏密钥：`0x2c1e880`.

位于 `0x6f0744` 的包头初始化函数将魔数 `0x32AB9864` 写入对象的 `+8`，并将 `0x0b` 写入 `+0xc`；位于 `0x6f07d0` 的验证函数检查魔数、`(byte & 0x7f) == 11`，以及数据包长度减去 0x1C 后是否小于 0x5a5。数据包缓冲区位于 `+0x30`（容量 0x5c0），长度位于 `+0x5f8`；位于 `0x6f0878` 的复制赋值操作确定了各字段的大小：

```
wire  object  size  field
0x00  +0x08   4     magic 0x32AB9864, big-endian
0x04  +0x0c   1     0x80 (encrypted) | version (0x7F) = 11
0x05  +0x0e   2     destination variable id
0x07  +0x10   2     source variable id
0x09  +0x12   2     packet id
0x0b  +0x14   1     footer size
0x0c  +0x15   8     AES-GCM nonce
0x14  +0x1d   8     AES-GCM tag, truncated from the 16 the object holds
0x1c                ciphertext, then the footer
```

包尾不在加密范围内。加密路径 `0x6f09f4` 减去包尾大小，用 0xFF 填充至分组大小，从缓冲区 `+0x4c` 开始加密，将标签写入 `+0x1d`，所用的 AES-GCM 入口为 `0x6e68d0`，标签长度为 8（`mov w4, #8` 位于 `0x6f0b24`），随后将 `0x80` 按位或入版本字段。

## 接收路径及断点位置

```
0x6ff6d8   nn::pia::local::LocalInputStream::vfunc4, the socket read
0x6f07d0   the header validator (five callers; 0x6ff6fc is the input stream's)
0x6f0b84   the packet decrypt, through the GCM entry at 0x6e6aac; failing here is key, IV or tag
0x6f09f4   the packet encrypt
0x7015b4   LdnBackgroundProcessJob::WaitConnected, the step body a stalled joiner sits in
0x70c304   LdnProtocol vfunc18, which that step requires to return 0
```

## 加入端会停在哪道关卡

判定函数 `0x6f63fc` 读取 LdnProtocol 对象上的两个端点槽位：`+0x98` 和 `+0xb8`（每个 0x20 字节：16 字节地址位于 `+8`，原生字节序的 u16 端口位于 `+0x18`):

```
0x6f0ee4(a)     -> set: port non-zero and address not the sixteen zero bytes at 0x3972091
0x6f0f48(a, b)  -> equal: same port, same sixteen address bytes
0x6f63fc(obj)   -> 0 unless both are set, then 0x6f0f48's answer
```

加入端连接后，两者都保存主机自身的地址和 Pia 端口，函数返回 1；只有在一次拆除与下一次加入之间，这些槽位才为零。这道关卡不会阻塞加入端。

## 消息按什么路由

分派键是数据包的源可变 ID：若消息来自未在注册表中登记的站点，则在检查其协议之前就会跳过该消息；可变 ID 在每次会话中都会重新生成。消息标志 `0x01` 表示“跳过源可变 ID 检查”，用于对端尚不认识发送端时发送的消息；`bin/pla_host.py` 在它的两种探测消息上都设置此标志。

## Net 协议的实测结果

自行创建网络的主机会以 `NetUpdateNetworkConnectionStatusMessage`（协议 0x2C，类型 0x11）开始通信。它符合 wiki 中 6.16 至 6.39 的布局，其网络 ID 由广播的 SSID 派生而来：

```
01 11 002a          header version 1, type 0x11, payload size 0x2a
00000002            sequence id
eb6f                host variable id, a fresh value every session
ac56011000020000    host constant id, ldn_constant_id of 02:00:ac:10:56:01
000000004f264487    network id, the low four bytes being crc32(ssid[1:16])
01                  is network open
0002                number of stations
00                  is migrating host
...                 two NetStation entries
```

在这一版本区间，NetStation 为 21 字节，而 6.39 中为 22 字节：

```
+0x00  1   host migration state
+0x01  1   host migration ranking
+0x02  1   one byte where 6.39 has two, disconnection candidate and kicking
+0x03  18  station address: 16 bytes of address, then a big-endian u16 port
```

两个条目的端口均为 12345；主机的排名为 0，加入端为 1。

主持交换的主机不会回应发往其可变 ID 的任何 Session（0x98）加入请求（下文的读取关卡会将其丢弃）。它会要求已加入的站点接任主机端：

| 加入端行为 | 主机 |
| --- | --- |
| 以 0x12 确认消息回应 0x11 | 再次发送 0x11，使用新的序列 ID，且 `is migrating host` 为 1，随后发送 `01 40 00 00`（仅含 `NetStartHostMigrationMessage`），频率约为每秒两次 |
| 发送加入请求，从不回应 0x11 | 每 0.5 秒发送相同的 0x11，随后 `is migrating host` 被置位，之后是 `01 40 00 00`，随后网络断开（关联后 8.6 至 10.1 秒、13.5 至 14.1 秒，以及 16.8 至 17.5 秒） |
| 以下列消息回应：`NetUpdateNetworkHostMessage` | 持续重复发送 0x40 |

若加入端向目标 0 发送加入请求并占据席位，在主机发出首个 0x11 后保持 4.5 秒，便会在站点列表之后 0.02 秒收到指定其为继任者的 Session 类型 7 消息（模拟主机上 4 次占位全部成功；通过 ESP32 板连接零售版主机时成功占位 1 次）。新主机端通过以相同密码创建网络来完成迁移：原主机在发出请求后 3 至 6 秒关闭自身网络，加入新网络，并作为加入端进行交换。`bin/pla_join.py` 在收到首个 0x40 时离开席位，然后运行 `bin/pla_host.py`，使用相同密码和信道；也可通过 IP 运行，使用 `--ip-join` (`--take-host`，默认启用）。与模拟主机通信时的顺序为：类型 7、类型 8，加入端在其最后一个数据包后 5.2 秒建立主机端网络，原主机在 0.02 秒后加入（[加入主机的网络](#joining-a-consoles-network)).

每种 Net 消息都有具名包头类及其序列化器。`NetUpdateNetworkHostMessageHeader` (`0x6fe03c`）：线上偏移 +4 处为 u64，+0xc 处为 u64，+0x14 处为 u16，大小为 0x16，采用大端序。0x11 包头（`0x6fd9dc`）将对象偏移 +0x0c、+0x10、+0x18、+0x20、+0x28、+0x2a 分别映射至线上偏移 +4、+8、+0xa、+0x12、+0x1a、+0x1b。`nn::pia::session::ClusterPacketWriter`（0x732264 至 0x7336e8）以内联方式写入 Session 消息。

主持搜索的主机通过离开来交出主机端角色。`Session::LeaveAsync` 启动 `LeaveSessionJob`，其中的 DisconnectNetwork 步骤（`0x72c9dc`）调用网络门面的槽位 15；在网络主机端上，这会启动 `NetDestroyNetworkJob` (`0x7069d0`），只要 `NetProtocol+0x248` 已置位，就会执行主机端迁移；构造函数 `0x6f48fc` 将其设为 1（`0x6f4a14`），且这是唯一写入它的位置。该任务发送使用新序列 ID 的 Net 0x11，并设置 `is migrating host` 1 (`0x6f6af0`），最多等待 4000 毫秒以收齐所有 0x12（`0x706b34`），然后发送 `NetStartHostMigrationMessage` (`0x6f7674`），每 300 毫秒一次，直到仅剩自身一个站点或到达截止时间：若 0x11 获得全部确认，则等待 4000 毫秒；若其等待确认超时，则等待 2000 毫秒（`0x706df0`, `0x706e98`）。之后它销毁 LDN 网络，仍留在网络中的站点继任主机端。对一个 `bin/pla_join.py` 共进行十四次占位，其 Session 加入请求均被主机丢弃（未收到加入响应）；首次迁移用的 0x11 出现在占位后 8.3 至 10.3 秒，重复发送 4.0 秒，随后发送 0x40 持续 2.0 秒。

只建立关联却不发送 Session 加入请求的站点，会以这种方式结束槽位。在主持搜索的模拟主机上，使用 `bin/pla_join.py --join-delay 20` 时，WaitMember 定时器到期事件（`0x2bdb7a0`）在占位后 0.99 秒触发；2 毫秒后，匹配序列的错误处理器构建离开请求（`0x2c27fb8`，调用位置为 `0x2c4ee60`，条件是捕获错误的类型名不匹配，`0x2c4ee3c`). `Session::LeaveAsync` (`0x72a6dc`）在约 1.4 秒时随后发生。`LeaveSessionJob` 接着运行 `LeaveMeshWithHostMigrationJob` (`0x72c640 -> 0x734c8c -> 0x73eee4`），它会轮询寻找下一任主机端，直到 8000 毫秒后的截止时间（`0x73efb4`）；没有 Session 路由的站点（路由字节 +0x90 和 +0x91 为 0xfd）永远不符合条件，因此断开和迁移用的 0x11 会在这 8 秒之后发生：不设置断点时，为占位后 10.48 秒。

主机以全网状网络主机端身份创建网状网络（`CreateSessionJob`，不等待）。加入的主机从自身的可变 ID 向包头目标 0 发送 Session 加入请求。主机端的 `ClusterPacketReader` 关卡 `0x744644`（通过虚函数 `0x98`, `0x731edc` 调用，调用位置为 `0x743ec0`）在各站点中查找单播数据包的源可变 ID（`0x744718`，管理器虚函数 `0x48`），若无匹配项就丢弃数据包（`0x7447a8`）；目标为 0 或 1 且无包尾的数据包，或源可变 ID 为 0 的数据包，会跳过该查找。因此，尚未登记的加入端向主机端可变 ID 发送的加入请求，会在解密后、到达 Session 分派器之前被丢弃。若将请求发送至目标 0，则会收到加入响应和类型 5 站点列表。主持搜索的模拟主机，在加入端以这种方式占位但不发送数据交换记录时，会在约 10 秒后迁移并离开，然后返回搜索界面，不显示错误。

## 数据包加密

|  |  |
| --- | --- |
| 会话密钥 | `AES-128-ECB(game key)` 对网络 SSID 的一个分组进行处理 |
| 网络 ID | 去掉首字节后的 SSID 的 CRC-32，`ssid[1:16]` |
| GCM 初始化向量（IV） | `u32be(network id XOR source IP)`，随后接包头中的八个 nonce 字节 |
| 包头 nonce | 每个数据包递增的计数器，大端序 |
| 标签 | GCM 标签的前 8 字节，位于包头中 |

`0x70d61c` 派生会话密钥：它重复长度不足十六字节的种子（`0x10 / len` 位于 `0x70d66c`），并用位于 `LdnProtocol+0x238` 的游戏密钥加密一个 ECB 分组。位于 `LdnProtocol+0x234` 的加密模式 0 会让密钥保持全零。

`nn::pia::local::LocalOutputStream::vfunc3` (`0x711710`）构建 IV：`0x6ed380` 将大端序的异或结果写入 `IV[0]`，随后将包头中的八个 nonce 字节写入 `IV[4]`。发送端为每个数据包递增 nonce，并通过 `0x6ed360` 写入。GCM 加密配置为 `{mode +0, IV pointer +8, IV length +0x10, key pointer +0x18, key length +0x20}`：模式 1，IV 长度 12，密钥长度 16。

`pokeldn/ldn/crypto.py` 对整个 6.16 至 6.42 区间采用相同的派生方式。

## 数据包之上的协议

Pia 6.16 至 6.30 在会话层以下沿用 5.29 至 5.45 的 ID，并以单个 Session 协议取代站点协议和网状网络协议。到 6.32 时，ID 再次发生变化：

| 协议 | 5.29-5.45 | 6.16-6.30 | 6.32-6.40 |
| --- | --- | --- | --- |
| Net（网络） | 无 | 0x2C | 1 |
| RTT（往返时间） | 0x58 | 0x58 | 3 |
| Unreliable（非可靠传输） | 0x68 | 0x68 | 5 |
| Clone（克隆），从原子模式到时钟模式 | 0x74-0x77 | 0x74-0x77 | 6-9 |
| Reliable（可靠传输） | 0x7C | 0x7C | 10 |
| Broadcast Reliable（广播可靠传输） | 0x80 | 0x80 | 11 |
| Session（会话） | 0x94 | 0x98 | 13 |
| 监控数据 | 0xA4 | 0xA4 | 15 |
| 站点、网状网络、同步时钟、本地 | 0x14, 0x18, 0x1C, 0x24 | 无 | 无 |

`pia_connect.py`（6.32 中的 Net、Session、RTT）在重编号 ID 后适用于这一区间；`station_protocol.py` 和 `mesh_protocol.py` 实现的协议在此处不存在。

主机的加入请求列出了它的协议版本：

```
Net 0x2c v0   RTT 0x58 v3   Unreliable 0x68 v1   Clone 0x74 v0   Clock 0x77 v0
Reliable 0x7c v2   BroadcastReliable 0x80 v3   0x81 v3   Session 0x98 v0   Monitoring 0xa4 v0
```

### Session 加入请求

来自 `ClusterPacketWriter` 的 115 字节 Session 类型 0 消息：类型字节、协议数量、上面的十组 `(id, version)`，然后是：

```
+22  4   random, fresh on every repeat; Scarlet seeds it from the system tick
         (`docs/sv.md`, The Session join request)
+26  8   source constant id, ldn_constant_id of the console
+34  2   zero
+36  2   source variable id, the joiner's own, fresh per session
+38  1   NAT mapping
+39  1   private-IPv6 flag
+40  32  identification token, all zero on a codeless join
+72  1   address kind, 0 for IPv4
+73  4   source station address, IPv4
+77  2   source station port, 12345
+79  8   destination constant id, the host's
+87  2   zero
+89  2   destination variable id, the host's, `00c6`
+91  1   player count, 1
+92  1   a flag, 1
+93  22  one player record: id `00..01 00..00` (two big-endian u64, 1 and 0), a big-endian u32
         name length of 1, a kind byte of 1, the name, a single space
```

位置 ID 在线上传输时为 12 字节：大端序 u64 固定 ID、两个零字节、大端序 u16 可变 ID。每次重发的消息标志均为 `0x01`。`pokeldn.ldn.pia6.build_session_join` 复现这 115 字节（`tests/test_pla_session_v11.py`).

### Session 加入回复

加入端在 `0x737534` 解析确认消息，在 `0x7379c0` 解析加入响应；两者均从接收循环 `0x7353a0` 经位于 `main+0x3973f19` 的类型表分派。每个处理器都比较四个 ID，若有不匹配便静默丢弃消息：主机端将请求的目标 ID 原样返回为自身 ID，将请求的源 ID 原样返回为主机的 ID。

确认消息为 Session 类型 1，共 25 字节：类型字节、主机端位置 ID、主机位置 ID。它设置 `JoinMeshJob+0x69`，并将加入截止时间 `job+0x80` 延长 8000 毫秒；它本身不会使任何步骤完成。

加入响应为 Session 类型 2，共 43 字节：

```
+0x00  1   02
+0x01  1   protocol id 0x98, read only when status is 3
+0x02  1   Session version, read only when status is 3
+0x03  1   status, 1 is the accept path
+0x04  8   unread on the accept path
+0x0c  12  host location id, four-field compare
+0x18  12  console location id, four-field compare
+0x24  1   route byte A, stored to the self station +0x90
+0x25  1   route byte B, stored to +0x91
+0x26  1   station index, sets bitmap bit [+0x788][index]
+0x27  2   join order, big-endian u16, stored to +0xf8
+0x29  2   sequence id, big-endian u16, stored to +0xde
```

分配字段未经验证便被保存（主机的写入函数 `0x736cec` 会为首个加入端写入路由 `00 01`、索引 1、加入顺序 1）。状态 1 设置 `JoinMeshJob+0x68` 并停止重复请求（每个时间窗口约重复十六次）。完成标志 `JoinMeshJob+0x7c` 由类型 5 更新 `0x738740` 设置，条件是已应用一个序列号达到 `+0x29` 的更新；加入端以 13 字节的 Session 类型 6 回应：类型字节、主机固定 ID、两个零字节、序列号。

### 类型 5 站点列表更新

`0x7404a8` 在 `0x73897c` 读取更新之前将其重组；一个分片就能容纳整个更新。七字节分片头依次为类型字节、大端序 u16 序列号、分片数量、分片索引、大端序 u16 偏移。缓冲区预先写入类型和序列号，因此载荷从主机端固定 ID 开始，偏移为 3。重组后的消息体如下：

```
+0x00  1   05, the reassembly byte
+0x01  2   sequence id, big-endian u16
+0x03  8   host constant id, big-endian u64
+0x0b  4   host variable id, a [0000, u16] big-endian u32
+0x0f  1   station count, at most 0x18
+0x10  n   IPv6 bitmap, (count + 31) / 32 * 4 bytes, little-endian u32 words, bit i set for an
           IPv6 station
   ...     station entries
```

每个站点条目由 `0x739050` 读取，其 IPv4 形式如下：

```
+0x00  8   constant id, big-endian u64
+0x08  4   variable id, a [0000, u16] big-endian u32, the low half passed to the admit
+0x0c  4   IPv4 address
+0x10  2   port, big-endian u16
+0x12  1   route byte A
+0x13  1   route byte B
+0x14  1   station index
+0x15  2   join order, big-endian u16
+0x17  1   NAT mapping
+0x18  1   private-IPv6 flag
+0x19  32  identification token
+0x39  1   player count
+0x3a  1   participant count
+0x3b  ..  player records, each a 16-byte id, a big-endian u32 name length, an encoding byte, and
           the name
```

IPv6 站点以 18 字节地址取代那六字节。主机端的路由为 `00 00`，索引为 0，加入顺序为 0；首个加入端为 `00 01`、1、1。玩家记录与加入请求中的相同。`0x738bc0` 根据固定 ID 更新或创建每个站点，然后设置 `JoinMeshJob+0x7c` 并发送类型 6。已加入的主机随后运行 RTT、Clone Clock 和 Stream Broadcast Reliable 流。

## 维持网状网络

已加入的主机会在游戏的 DataExchangeStart 步骤超时时离开，即加入请求后 10.2 秒，除非 0x81 数据交换先完成（[游戏的读取器及处理器之前的阶段](#the-games-reader-and-the-pre-handler-phase)）。RTT（0x58）为 11 字节：种类、八字节时间戳、两字节目标；目标为 0 的种类 1 回显会被接受。

Stream Broadcast Reliable（0x81，流式广播可靠传输）承载 `pokeldn/ldn/reliable5.py` 滑动窗口：9 或 13 字节包头，随后是应用数据；若应用数据标志未置位，则随后是长度为 `2 + 21 * count` 字节的批量确认。确认消息开头的类型字节仅会读取位 0；每个 21 字节条目包含一个站点字节、一个大端序 u16 确认 ID、一个大端序 u16 和一个 16 字节掩码。消费端（`BroadcastReliableSlidingWindow`，虚函数 13 为 `0x742730`）读取自身站点索引对应的条目，并要求其中的站点字节等于发送端索引：主机端确认索引 1 的加入端时，至少发送两个条目，且每个站点字节均为 0。ID 和掩码遵循以下规则：[确认机制](#acknowledgement).

消费端将每个条目的第二个半字存入 `[window + 0x528 + 2 * station]` (`0x742828..0x742830`），根据类型位 0 设置 `[window+0x4b8]`，并通过 0x7c 窗口的 `0x74f0ec` (`0x742880`）应用该 ID。发送路径虚函数 11 `0x742304` 会从目标位图中移除所有半字为 `0xffff`、半字大于等于窗口基准值，或槽位为空的站点（`0x74238c..0x74242c`），然后将位图交给确认发送函数 `0x74ea00`：若 `[window+0x4b8]` 未置位则不执行任何操作；若位图为空，则清除此标志并记录 `[window+0x4c0]`；否则生成 AckMessage，序列号为 `0xffff`，长度为 `2 + 21 * count` (`0x74eb64..0x74eb94`），每个已占用站点一个条目（`0x74eba0..0x74ec2c`，由 `0x74ec80`, `0x743160` 序列化）。这个半字只控制确认消息，不控制重传。在所有捕获到的加入过程（30 次）中，主机的 0x81 应用消息序列号均为 1，因此主机端确认消息填写 `ack_id 2`；主机端确认的仍然是已接收最高序列号的下一个值。

主机以一条带 INITIALIZED 标志的数据消息（标志 `0x0f`，序列号 1）和第二条数据消息开启流；它约每秒发送一次确认，确认中携带的主机端流 ID 会在主机端静默期间持续增长。若主机端数据的目标位图设置了该主机站点索引对应的位（位 1，数量 2），则会应用数据；位设置错误会导致数据在发送端站点检查处被丢弃。

### 静默站点检查

Session 启动函数 `0x729d3c` 将启动配置的 `+0x28c` 复制到 `SessionProtocol+0xd8` (`0x72a098`），不设下限（Z-A 的下限为 4000 毫秒），并将 `+0x290` 传给发送静默时限（`0x746fe4`：负数会以 0x10407 失败，0 会变为 1000 毫秒）。每次更新 `0x73564c` 都会列出状态为 2 且最后一个数据包（`ClusterStation+0x88`）距今超过 `[SessionProtocol+0xd8]` 毫秒的站点，主机端和加入端都如此。一旦首个条目已存在 3000 毫秒（`0x735364`), `0x7359ac` 就会处理该列表：主机端将每个站点交给 `KickoutManageJob` (`0x73cad4`）；若加入端的列表中包含主机端，就会将主机端视为已离开（`0x735b28`）。配置项的 `+0x28c` 读数为 10000 毫秒（`w9 = 0x2710` 位于 `0x72a09c`，在主持搜索的模拟主机上测得），与 Z-A 相同。在盒子界面上，静默的主机端会在约 13 秒时引发“对方已离开”提示，即 10000 毫秒加 3000 毫秒宽限期。

## 游戏的读取器及处理器之前的阶段

游戏在 `main+0x2ca4f30` (`0x741494`）轮询其读取器（在一个实测时间窗口中调用了 365 次）：0x7C 和 0x80 两个循环共用一个处理器表。0x81 上的主机端数据永远不会到达这里。消息的前八字节是由两个 u32 构成的处理器键；匹配的处理器接收其余部分，不匹配的键则被丢弃。

在交换搜索界面，处理器表为空（`ldr x8, [x19+0xd0]; cbz x8`，读取之后），因此所有消息都会被取出并丢弃，而不作解析。`0x2ca5264` 在流程步骤 0x1e 注册处理器，超时会话永远不会到达该步骤；离开菜单时，处理器数组指针被置空。实测空闲时读取循环约每秒运行 2.5 次。游戏的九个 Pia 调用点仅解析 0x68、0x7C 和 0x80（三个读取循环、四条发送路径）；0x77 时钟通信属于 Pia 自身。

## 游戏的可靠通道

数据交换完成后，交换流程到达 `0x13d5cac`，它会检查游戏网络对象上的 `[net+0xb8] > 1`。该对象根据游戏从 0x7c 读取的内容推进：通过 `0x26d9170` 从状态 0 变为 1，在 `[net+0x78]` 时从 1 变为 2；该值由接收处理器 `0x26da310` 在选择器 1 时设置（跳转表索引 1，`0x26da3a4`).

分派器 `0x2ca4a88` 将消息的八字节键与每个通道的 `+0x6c` 匹配，并提交消息体。共有两个通道，两者都通过 `0x2bcb8c8` 注册：键 `00 00 00 00 00 00 00 00` 用于交换盒子（`0x26d8c2c`), `01 00 00 00 00 00 00 00` 用于阶段协议（`0x26d7aa0`).

端口 0 和端口 1 是两个 Reliable 实例，在 `0x2bba180` 的协议序列中注册为 `0x7c000000` 和 `0x7c000001`（流式广播：`0x80000000`, `0x80000001`）。句柄存入位于 `0x4308a80` 的表，按端口索引（`0x4308a84` 是 0x7c 端口 1）。`0x2ca4a88` 读取 0x68、0x7c 和 0x80 的端口 0；0x7c 的端口 1 则由下文的通道表经此表读取。

两个端口都以 `reliable5` 流开启（没有目标位图，目标为对端的可变 ID，序列号 1，带消息开始、消息结束和已初始化标志）；每个站点用一个条目确认对端的消息，并在同一端口返回相同消息：

```
port 0    key eight zero bytes      body 0100        the host opens it
port 1    b9 01 01 b9 02 b9 02 00 00 01              the joiner announces the zero key open
```

### 确认机制

`ReliableSlidingWindow`（虚表 `0xc5b4d98`）在虚函数 12 `0x74ee1c` 中构建确认消息：以接收窗口的 `+0x50` 作为 ID，在十六字节掩码中为超过该 ID 后仍保留的每个条目设置一位（`0x74ef18..0x74efb8`），当 `[window+0x54]` 置位时掩码为空。虚函数 13 `0x74efbc` 应用确认消息：解析 AckMessage（`0x742da0`），除非载荷为 `2 + 21 * count` 字节且条目的流字节等于窗口的 `+0x36`，否则丢弃；然后调用 `0x74f0ec(window, station, ack_id, mask)`，调用位置为 `0x74f09c`。发送条目为 0x5d0 字节，序列号位于 `+0x24`，各站点的待确认位图位于 `+0x2c`:

| 条目序列号 | 发送确认的站点对应的待确认位 |
| --- | --- |
| 小于 `ack_id` | 清除（`0x74f274`) |
| 等于 `ack_id` | 保留 |
| 大于 `ack_id` | 当掩码位 `seq - ack_id - 1` 置位时清除，支持不超过 0x7f 的偏移（`0x74f280..0x74f2a8`) |

| `ack_id` | 效果 |
| --- | --- |
| 0 | 无操作（`0x74f0fc`) |
| 小于窗口基准值 | 设置 `[window+0x4b8]`，返回（`0x74f17c`, `0x74f2d0`) |
| `base + count`（数量 `[window+0x32]`），即最后发送序列号的下一个值 | 释放所有条目 |
| 超过 `base + count` | 传入 `[vt+0x30]`，同时传入 `0x20000000` (`0x74f18c..0x74f1c0`），虚函数 6 为 `0x74f2e8`，在两个窗口类中都仅为 `ret`：忽略 |
| `0xffff` | 应用于整个窗口（`0x74f104..0x74f11c`) |

比较采用两个 16 位 ID 的 32 位差值：在同一条流上发送 65536 条消息后，超过窗口的 ID 会被判断为小于窗口。

ID 是累积确认值：确认 n+2 会释放 n，无论 n 是否已到达。主机确认的是连续序列末尾的下一个值，暂存条目通过掩码表示：四个小端序字（memcpy 位于 `0x742f00`，由 `0x74f2a0` 逐字读取），位 `seq - ack_id - 1` 就是该 128 位小端序整数的第 n 位（`pokeldn.ldn.reliable5.build_mask`）。零售版主机会在几十毫秒内确认主机端的 0x7c 数据（实测为 17 至 67 毫秒）。

接收端在读取标志之前，根据每条消息的最低待确认字段移动窗口基准值，确认消息也包括在内（`0x74c250` 将其存入 `[x0+0x20]`；基准值 `+0x18` 跳过空槽位，前进到首个已占用槽位，`0x74c2f0..0x74c2f8`；标志分派 `0x74c3ac`）；较低的值不会引发移动（`0x74c25c`）。若声明的最低待确认序列号超过某条尚未确认的消息，该消息重发时会落在基准值以下而被丢弃。零售版主机的确认消息所声明的最低待确认值小于确认 ID（确认 ID 为 8，最低待确认值为 6）。

`bin/pla_host.py` 和 `pokeldn.pla.joiner` 使用 `pokeldn.ldn.reliable5` (`SendWindow`, `ReceiveWindow`）：保留每条 0x7c 消息直至获得确认，0.4 秒后以相同序列 ID 和新的 nonce 重发；声明的最低待确认值不得超过自身最低未确认序列号（捕获中，作为主机端的主机端口 0 编号曾比加入端超前一位，若声明更大的值，会使其基准值越过加入端尚未发送的阶段 6）；确认连续序列末尾的下一个值并附带掩码，按序仅交付一次。加入端的 0x81 消息每 1 秒重发一次。主机在某端口上的首条 0x7c 消息序列号为 1（记录的 66 个端口全部如此）。

主机通过 `0x74c9c8` 重发 0x7c 和 0x81 数据（tick：0x81 为 `0x7419ec`，0x7c 为 `0x74a27c`/`0x74a2f8`）：处理基准值之后最多 127 个条目中，待确认位图 `+0x2c` 非零且截止时间已到的每个条目（`0x74cd10..0x74cd80`；0x81 经由 `0x742194`，仅发送给待确认站点），随后将截止时间设为当前时间 + 33 毫秒 + 最大往返时间的 1.4 倍（`0x74d06c`，浮点数 `0x3fb33333`；33 毫秒位于 `0x74a784`），对计数 `+0x14` 不设重试上限。待确认位仅在收到窗口范围内的确认（`0x74f1f4..0x74f204`）或站点离开时清除（事件 1，`0x7411cc` 至 `0x74b528`）；站点加入会将所有截止时间清零（`0x74b358`）。若对端仅用超过窗口的 ID 回应，主机会无限重发。

## 端口 1 上的通道表

0x7c 的端口 1 承载通道表：每个站点通告自己开放的处理器键，只有在对端通告某键已开放后，站点才会用该键发送。

分派器初始化函数 `0x2ca36f0` 构建一个 0x298 字节对象（虚表 `0x41997d8`），端口字节 `+0x70` = 1，保存在分派器的 `+0x20148`。每帧轮询函数 `0x2ca82d0` 从 0x7c 端口 1 接收到 `0x2ca9800`，并运行发送函数 `0x2ca83dc`。两个表均由 0x18 字节条目构成，每个条目在 `+0x00` 有一个八字节键，在 `+0x08`:

| 表 | 保存内容 |
| --- | --- |
| `+0xa0` | 站点自身的通道；条目偏移 `+0x10` 处的字节在通道存在时置位，位掩码标明已通知的站点 |
| `+0xd8` | 对端通告的通道；位掩码标明已通告该键开放的站点 |

每次轮询首先运行发送函数（`0x2ca8310`），条件是脏标志 `[obj+0x90]` 已置位（`0x2ca83fc`）；它按每个站点位遍历自身表：若通道存在且相应位未置位，则通告开放并置位；若通道已销毁但相应位仍置位（`0x2ca86c4`），则通告关闭并清除此位。通道析构函数携带该键调用接口槽位 1 `0x2caa12c`（`0x2ca3168..0x2ca3178`；表槽位 13 `0x2caa0d4` 是相同实现），清除 `+0x10` 并设置脏标志。

接收函数 `0x2ca9800` 由位于 `0x2ca83a8` 的轮询调用，每条待处理的端口 1 消息调用一次（`0x2ca8398..0x2ca83d4`）；它通过会话的 `[vt+0x38]` (`0x2ca9854`）解析发送端站点索引，若为 0xfd 则丢弃，若大于等于 2 则中止（`0x2ca9df0`）。对每个键的处理如下：

| 对端表 | 开放 | 关闭 |
| --- | --- | --- |
| 包含该键 | 将站点位按位或入掩码（`0x2ca9a6c`）；重复开放不改变任何内容 | 通过按位与清除该位（`0x2ca9ae4`）；若两个站点位均不再存在，则将尾部向前移动并执行 `[obj+0xe0] -= 0x18` (`0x2ca9b14`) |
| 不包含该键 | 追加一个包含该站点位的条目 | 追加一个掩码为零的条目 |

所有分支均不会调用游戏代码，也不会写入对端表以外的位置。清理函数 `0x2ca8f58`（每次轮询，`0x2ca8318`）删除零掩码条目（`0x2ca9060..0x2ca90c8`），当 `[obj+0x98]` 中没有任何位置位时清空表；站点离开路径 `0x2ca90e0`（来自 `0x2ca4a48`）清除 `[obj+0x98]` 及所有掩码中的该站点位。没有其他操作会清除对端条目。

创建通道（`0x2bcb8c8` -> `0x2ca5264` -> 构造函数 `0x2ca3024`，各函数都是下一函数的唯一调用者）会将表的接口（`[dispatcher+0x20148]` + 0x68，虚表 `0x41998c8`）存入通道的 `+0xb8` (`0x2ca30d0`，构建位置为 `0x2ca5acc`），并由位于 `+0xa8` 的弱引用间接持有（使用计数 `+0xc` 会在每次调用前检查），随后携带自身的键调用接口槽位 0 `0x2caa0cc` (`sub x0,x0,#0x68; b 0x2ca9dfc`，表槽位 12）：若 `+0x10` 未置位则置位（`0x2ca9e78`），已置位则返回（`0x2ca9e74`），缺失则追加为 `{key, 0, 1}` (`0x2ca9e90..0x2ca9ec0`）；第一和第三种情况会设置脏标志（`0x2caa034`). (`stp xzr,xzr,[x23,#0xb8]` 位于 `0x2ca3c6c` 将表自身的 `+0xb8` 清零。）对端表查询如下：

| 函数 | 槽位 | 回答的问题 |
| --- | --- | --- |
| `0x2ca9218` | 接口 2 | 自身表是否包含键 K |
| `0x2ca92e0` | 接口 3 | 执行槽位 10 的检查，站点由句柄指定并通过以下函数解析：`[vt+0x38]` |
| `0x2ca93d4` | 接口 4 | 执行槽位 10 的检查，按站点索引指定 |
| `0x2ca958c` | 接口 5 | `0x2ca9448` 作用于表对象 |
| `0x2ca9360` | 表的虚表 `0x41997d8`，槽位 10 | 对端表是否包含 K 且站点位 i 已置位 |
| `0x2ca9448` | 表槽位 11 | 除本站点外的所有站点是否都已通告 K |

每个通道发送函数都会通过 `+0xb8` 调用接口槽位 3，使用位于 `+0x6c` 的键，且仅在结果为是时发送：阶段发送函数通过 `0x2ca34e0` (`0x26d7e00`，位于 `0x26d7d8c`, `0x26d7ef8`，位于 `0x26d7e84`），交换盒子发送函数在 `0x26d9200`, `0x26d92f0`, `0x26d950c`, `0x26d9688`, `0x26d980c`（选择器 5）和 `0x26d9a1c` 以内联方式执行。对端表也控制端口 0 的发送，每个通道使用自身的键；当主机端在端口 1 上保持静默时，交换界面显示的等待正是由此造成。接口槽位 2、4 和 5 没有经由以下位置的调用点：`+0xb8`.

表指针位于 `[dispatcher+0x20148]`（最后一个字段；分配大小 `0x20150`, `0x2bcac00`），仅在分派器中使用：初始化 `0x2ca3d24`、析构函数 `0x2ca3f88`（位于 `0x2ca3f48`）、站点加入 `0x2ca4774` (`0x2ca4574`，来自 `0x2bcb2b8`：将该位按位或入 `[+0x98]`，设置脏标志）、站点离开 `0x2ca4a38` (`0x2ca90e0`）、每帧轮询 `0x2ca5020`、通道创建 `0x2ca5284`（表槽位 8 `0x2ca91cc`）。另一份副本位于各通道的 `+0xb8`（接口槽位 0、1、3）。未找到其他对端表读取器：虚表 `0x41997d8` 仅被 `0x2ca3c18` 引用，而 `0x2ca7f2c`, `0x41998c8` 无任何引用；通过 `+0x48/+0x50/+0x58` 发起、位于 `0x2ca3000..0x2cab000` 中的调用仅为 `0x2ca92c0`, `0x2ca9340`（槽位 10）、`0x2ca9490`（会话）；从外部调用 `0x2ca6000..0x2cab000` 只会到达 `0x2caa960..0x2caafec`；槽位 9 `0x2ca9264` 没有调用者。

消息使用游戏的带标签序列化格式：小于 0x80 的无符号整数直接编码为自身的单字节值；标签 0x80、0x81、0x82、0x83 分别作为小端序 1、2、4、8 字节值的前缀（`0x2661ec4`, `0x26619cc`, `0x2661f78` 分别写入 u32、u64、u16）。大小表 `0x397dfcc` 为 0x84 至 0x87 指定相同宽度，0x88 为四字节，0x89 为八字节，0xb5 至 0xbf 为一字节。0xb9 表示元组开始，后接字段数。

```
b9 01              a tuple of one field, the list
NN                 the number of entries
per entry:
  b9 02            a tuple of two fields, the key and its state
  b9 02 LO HI      the key as two u32, low word first
  01 | 00          1 open, 0 closed
```

主机在交换过程中发送三种消息：

| 消息 | 含义 | 时机 |
| --- | --- | --- |
| `b9 01 01 b9 02 b9 02 00 00 01` | 交换盒子键开放 | 端口 1 开放后，到达交换步骤时 |
| `b9 01 01 b9 02 b9 02 01 00 01` | 阶段键开放 | 确认之后，当 `0x26d7aa0` 创建阶段通道时 |
| `b9 01 01 b9 02 b9 02 01 00 00` | 阶段键关闭 | 交换写入完成后 |

`pokeldn.ldn.channel_table` 构建并解析这些消息。主机端对每个开放消息回应自身的开放消息，每个键一次；对关闭消息不回应：若返回关闭消息，会删除主机对端表中的阶段键条目（在本次交换中无害，因为没有操作轮询对端表），而保留该条目可供下一次交换使用（[同一会话中的第二次交换](#a-second-trade-in-one-session)).

## 交换盒子

两个通道均开放后，游戏消息在端口 0 上、零键之后传输。接收处理器 `0x26da310` 读取选择器和计数器，通过位于 `0x397e388` 的字节表分支，并丢弃大于 7 的值。

```
1   ready                0x26da3a4   sets [net+0x78], what step 0x20 waits on
2   showing a Pokemon    0x26da3f0   stored at [net+0x98] by 0x26da1d8, nothing else
3   showing no record    0x26da430   -> 0x26d93c8
4   offering a Pokemon   0x26da3b0   stored at [net+0xb0] by 0x26da23c, phase 0xbc := 3
5   confirmed            0x26da43c   counter check, -> 0x26da2c0
6   withdrawn            0x26da458   state 4|5 := 3, phase 0xbc := 2, counters moved
7                        0x26da49c   counter check, phase 0xbc := 5
```

除非第四个参数等于 `[net+0x88]`（即交换对象），否则处理器中止。端口 0 开放消息体 `01 00` 表示就绪（选择器 1，计数器 0），每个会话必须发送一次。

`0x26d9458`（唯一调用者为 `0x10fb200`，位于 `0x10fb198`，其自身仅在 `0x110a010` 被调用）在记录为空（`0x26d94a0`）或种类为 0 时（`0x2b5d3a4` -> `0x2b6849c` 作用于 `[pk+0x98]`，即 `0x3984e57` 最先写入的块的首个半字）发送无消息体的选择器 3；否则发送选择器 2，携带来自 `0x2b65514` (`0x26d9554..0x26d9570` 的 0x178 字节消息体）。该记录为 `0x11207f8(ui, box, slot)` (`0x1109fa0..0x1109fac`），即复制到 `[ui+0x1660]` 的槽位，复制函数为 `0x111da04` (`0x11208e4..0x1120910`, `0x111fc18..0x111fc4c` 的槽位）：光标停在空槽位时发送 `03 00`。收到 3 后，`0x26d93c8` 将 `[net+0x98]` 替换为新建的 0xb8 字节 `0x151dc70` 对象，而更新函数 `0x26d9094` 从不读取此对象。

选择器 6 撤回提议（状态 3：已发送自身的选择器 4，`0x26d95d4` 要求状态为 2，`0x26d9718` 写入 3）或撤回确认（状态 4：自身的选择器 5，`0x26d9788` 要求状态为 3，`0x26d9838` 写入 4）。其发送函数 `0x26d9898` 在状态 2 和 5 时拒绝发送（`0x26d98ac`: `cmp w8,#2; ccmp w8,#5,#4,ne`），发送计数器 `[net+0xf8] + 1` (`0x26d9918`），然后清除 `[net+0xc0]`，设置状态 2（`0x26d9a54`），置位 `[net+0xf8]` 和 `[net+0xfa]`，并将阶段 4 或 5 恢复为 3。接收分支 `0x26da458` 将计数器存入 `[net+0xfa]`，置位 `[net+0xf8]`，清除 `[net+0xc0]`，设置阶段 2，将状态 4 或 5 恢复为 3，且不发送任何消息：回送选择器 6 会撤销主机的确认。

选择器 2 和 4 携带相同的消息体：站点进入盒子时发送 2，玩家提出交换时发送 4。只有 4 会推进阶段。若主机端以展示消息回应交换提议，主机上的对方六边形会保持空白，且不显示错误；`pokeldn/pla/trade_box.py` 会原样回应选择器。

消息体由以下函数读取：`0x26dac6c`（选择器）、`0x26662fc`（计数器）和 `0x26dacbc`（记录）；0xbc 标记记录开始，由 `0x26da3b0` 手动检查。

```
0x00  1   the selector
0x01  1   the counter, 0 on both record-carrying selectors
0x02  1   0xbc
0x03  1   0x81
0x04  2   the record's length, 0x178
0x06  376 the record
```

九字节包头之后是 390 字节载荷，无目标位图，标志为 0x07（应用数据、消息开始、消息结束；无已初始化位，无 zlib 位），序列号为 2。

该消息仅取决于存档（不同主机端和会话密钥下完全相同）：捕获后可重放。

该记录是第八世代实体（`pokeldn.gen8` 头部、LCG、块置换及 16 位校验和），块大小为 0x58 字节：存储形式为 0x168，同行队伍形式为 0x178。`gen8.BLOCK_ORDER[(ec >> 13) & 31]` 在解密时按原样应用，加密时采用其逆置换。校验和无法区分这两种方向，但名称可以：直接读取时，昵称位于 0x60（第二块），训练家名位于 0x110（第四块）；按逆方向读取时，两者都会提前一块。0x0c 处的训练家 ID 和训练家名，就是数据交换中携带的玩家 ID 与姓名。

## 确认交换

选择“交换”会在零键上发送选择器 5 和计数器 `[net+0xf8]`。发送函数 `0x26d9770` 要求 `[net+0xb8] == 3`（自身提议已发送），并将其设为 4。消费函数 `0x26da2c0` 将阶段 `[net+0xbc]` 设为 4；当 `[net+0xb8]` 已为 4 时，清除 `[net+0xc8]` 并向其中分配对象：第二个确认的站点会继续推进。选择器 5 和 7 会丢弃计数器低于以下值的消息：`[net+0xfa]` (`0x26da440`, `0x26da4a0`).

确认后，主机在端口 1 通告阶段键开放（无已初始化标志），但在主机端也通告该键开放之前，不会在该键上发送任何消息；否则交换界面会停在阶段 5。

## 交换对象自身的状态机

`[net+0xb8]` 是步骤 0x20 检查的状态；更新函数 `0x26d9094` 推进它：

```
0     if [net+0x90] is set, 0x26d9170 -> state 1
1     once [net+0x78] is set, one 64-bit store of 0x200000002 puts the state at 2 and the
      phase [net+0xbc] at 2 in the same instruction
3, 4  while [net+0xc0] is set: read the stopwatch at [net+0xc8], and once [net+0xd0] is past
      1.5 seconds and the phase is 4 or 5, 0x26d9254 sends selector 7 and the state becomes 5
5     no case. The object is finished
```

状态 5（已提议且双方均已确认）不会修改存档；实际交换由下文的任务执行。

## 实际执行交换的任务

## 交换限制

交换限制是在存档块 `0x96993D83` 中保存的 u64 分钟计数，对应字段 `+0x70`，所属对象位于 `[game manager+0x2b8]`（管理器经由 `[0x4279560]`，访问器 `0x1048f94`；虚表 `0x40f2048`，构造函数 `0x102500c`）。其方法如下：

```
0x102518c  clear
0x1025194  set
0x102519c  decrement, stopping at 0
0x10251b0  read
0x10251b8  non-zero
```

注册函数 `0x1024d5c`（槽位 `0x40f2098`）将三个字段绑定到存档块，这些存档块通过 `0xff0ee8` 按 u32 键对 0x30 字节条目进行二分查找得到（`0xff0f3c..0xff0f70`):

| 字段 | 块 | 类型 |
| --- | --- | --- |
| `+0x68` | `0xAFA034A5`（键位于 `0x3978f78`) | 一个布尔值（`0xfddf30`) |
| `+0x70` | `0x96993D83`（键位于 `0x3978f7c`) | 一个 u64（`0xff0ee8`) |
| `+0x78` | `0x24E0D195`（构建于 `0x1024f30`），0x2F2 字节 | `0x1024ee4` |

PKHeX 的 `BlankBlocks8a.cs` 对这些大小的定义一致。在存档中，`0x96993D83` 为类型 11、值 0，`0xAFA034A5` 为值为假的布尔值，`0x24E0D195` 为一个零标志字节，后接最近交换收到的记录。

位于 `+0x78` 的字节标记已收到但尚未放置的记录。`0x10251c8` 将其置位（`0x102520c`），将记录复制到 `+0x79`；若提供了记录的交换后形态，还会将其复制到 `+0x1f1`（标志 `+0x369`）。它的唯一调用者是执行器虚函数 `+0x58`，位于任务状态 6（`0x26ddc64`）；若 `0x2b5be48` 对两者返回相同种类，就不传入交换后形态。`0x26dcc74` 读取该字节（`0x102527c` 位于 `0x26dccfc`）；若已置位，则放置记录（`0x10325a0`），将其登记到图鉴（`0x10342b0`），清除该字节（`0x1025268` 位于 `0x26dcdc8`），并以请求种类 3 保存。取消操作清除此字节（`0x26dd70c`）的前提是 `[executor+0xb0]` 已置位。`0x26dcc74` 在模式 5 步骤 10（`0x110accc`）、模式 9 步骤 0（`0x110bc88`），以及盒子代码中运行（`0xc17ce0`, `0xc17e8c`）。没有其他位置写入此字节。该计数的全部写入位置如下（基于整个 text 段的调用索引；没有指针槽位保存这些方法）：

| 位置 | 调用者 | 值 | 时机 |
| --- | --- | --- | --- |
| `0x26dd9a0` | 执行器虚函数 `+0x50` `0x26dd910`，任务状态 3 | 10 | 在对方的 `02 03` 之后，在任何一条记录移动之前 |

## 阶段协议，以及仅由主机端发送的消息

任务在键 `01 00 00 00 00 00 00 00` 上通告阶段，该键在创建任务时注册。通告对象保存三对字段，每对包含一个标志和一个半字：

```
[obj+0x94] / [obj+0x96]   the phase this station has announced, written by 0x26d7d8c
[obj+0x98] / [obj+0x9a]   the phase the peer has announced, on receiving selector 1
[obj+0x90] / [obj+0x92]   written by 0x26d7e84, and on receiving selector 2
```

两个发送函数的唯一区别是写入的选择器；接收处理器 `0x26d7f90` 与之对应：选择器 1 填充对端字段对，选择器 2 填充第三对，选择器 0 则中止。消息由选择器和阶段构成，阶段小于 0x80 时各占一字节。状态 2 分支中的 `0x26d7e5c(obj, 3)` 等待第三对字段中的值为 3。

选择器 2 只能由主机端发送。`0x26d7e84` 仅在 `[obj+0x78]` 通过后才可到达，该字段在创建任务时由 `0x26d7aa0` 写入一次，其值来自将本站点与会话主机端站点比较的判定。加入端从不发送选择器 2，因此它的任务只有收到主机端的选择器 2 才会离开状态 2。若主机端仅原样回应选择器 1，交换界面会一直等待，显示双方的宝可梦，且线上没有任何待处理消息。初始化有五个会使 `[obj+0x78]` 保持零的出口：参数为空、转换结果为空、`[vtable+0xd8]()` 未返回 2、位于 `+0x28` 的站点数不为 2、站点槽位为空。

站点在端口上发出的每条消息，包括镜像回应消息，都使用自身序列的下一个 ID。若回应时复用对端 ID，一旦双方计数出现差异便会发生冲突，消息会被确认但随后丢弃。

## 完成交换

主机依次通告 3、6、0xb 和 0xe；主机端对每个阶段以选择器 2 和相同阶段回应，从而推进任务：

```
<-  0x7c p0  01 03      ->  01 03   the mirror     ->  02 03   the host's
<-  0x7c p0  01 06      ->  02 06
<-  0x7c p0  01 0b      ->  02 0b
<-  0x7c p0  01 0e      ->  02 0e
```

首个 `02 03` 到达后，第三对字段读数为 1 和 3（实测 240 毫秒后）。动画结束后，盒子将主机端玩家显示为原交换对象。共有八个存档文件发生变化：`main`, `main2`, `backup` 在两个槽位中均变化，两个 ExtraData 文件也变化。

随后主机发送新的选择器 2（取决于当前光标所指内容），主机端以展示消息回应；主机还发送阶段键关闭消息 `b9 01 01 b9 02 b9 02 01 00 00`，主机端不对此回应。

## 同一会话中的第二次交换

一个会话可进行任意次数的交换：一次交换完成后，场景重置交换对象，在保持会话的同时返回盒子。

交换完成后，场景调用 `0x26d8fd0(net)`，调用位置为 `0x110aa04`（仅在 `[net+0xb8]` 为 6 时），并将步骤 `[scene+0xb4]` 设为 0xc。重置操作如下：

```

0x26d8ff4  [net+0xa8], [net+0xb0] released          shown and offered records
0x26d903c  0x200000002 to [net+0xb8]                state 2, phase 2
0x26d9044  [net+0xc0] cleared                       stopwatch flag
0x26d9050  [net+0xd8] released through 0x26dade4    the job
0x26d9064  32-bit zero to [net+0xf8]                both counters
```

`[net+0x78]`（对端就绪）和 `[net+0x88]`（交换对象）会保留：下一轮从状态 2 开始，不再发送新的选择器 1。场景更新函数 `0x1109a68`（指针位于 `0x3406990`, `0x40fc090`）先运行监视器，然后根据模式 `[scene+0xb0]` 经 `0x3979c5e` 进行分支（基址 `0x1109b60`):

| 模式 | 处理器 | 作用 |
| --- | --- | --- |
| 0 | `0x1109f00` | 盒子：光标、展示、选择“交换” |
| 1, 2 | `0x1109b6c` | 无操作 |
| 3, 4 | `0x110a65c`, `0x110a694` |  |
| 5 | `0x110a7f8` | 交换，按步骤处理（半字表 `0x3979c7c`，基址 `0x110a858`，步骤 0 至 13） |
| 6 | `0x110b330` | 对方已离开，无错误：显示消息，然后进入模式 1（`0x110b408`) |
| 7 | `0x110b468` | 会话错误，在步骤 9 取消任务：显示消息，然后进入模式 9（`0x110b508`) |
| 8 | `0x110b54c` | 步骤 9 发生会话错误，任务处于 6 至 10：显示消息，然后 `0x115e420(..., 1)` (`0x110b60c`) |

```

步骤 11 至 13 的被调函数都不会访问会话、通道表或发送消息：场景在保持会话的同时返回盒子。步骤 5 分支 `0x110ac9c` 共用通往以下函数的尾部：`0x110b9f0`. `0x10fb178` 清除盒子控制器的有效标志 `+0x164`, `+0x16c`, `+0x174`，并尾调用 `0x26d93c4`，后者将 `[net+0x98]` 替换为新建的 `0x151dc70` 对象，不发送任何消息。

模式 0 每帧读取光标（`0xc5294c` 为盒子，`0xc4bf2c` 为槽位，`0x11207f8` 为记录），并调用 `0x10fb198`，调用位置为 `0x110a010`；该函数通过 `0x26d9458` 发送展示消息，但仅在光标元组与缓存于 `+0x168/+0x170/+0x178` 的元组不同，或某个有效标志未置位时发送（`0x10fb1a8..0x10fb1f0`），发送后缓存该元组（`0x10fb208..0x10fb220`）；已清除的标志使交换后发送新的选择器 2。光标移动仅通过 `0x10fb198` 到达网络。提出交换（菜单结果 0x19，`0x110a098`）运行 `0x10fb25c`，通过 `0x26d95ac` (`0x110a24c` 发送选择器 4），成功后 `0x110a260 mov w8,#5; b 0x110a148` 从步骤 0 进入模式 5。

所有模式都从步骤 0 进入（`str x8,[x19,#0xb0]` 位于 `0x1109abc`, `0x1109ac8`, `0x1109bac`, `0x110a148`, `0x110a314`, `0x110ae14`, `0x110b408`, `0x110b508`, `0x110b9dc`, `0x110ba44`, `0x110bd98`, `0x110c9f0`; `stp w8,wzr`，在 `0x11094dc` 使用值 7），唯一例外是 `0x11094a8`：当盒子控制器的 `+0x160` 已置位时，从模式 5 步骤 1 进入（`0x10fb15c` 位于 `0x110948c`).

计数器 `[net+0xf8]` 仅在此处及 `0x26d8c04` 清零，仅在发送（`0x26d9a60`）或接收（`0x26da468`）选择器 6 时增加，并由所有发送函数通过 `0x26d81fc` 序列化（`0x26d91c8` 对应选择器 1，`0x26d92b8` 7, `0x26d94d4` 对应 2 和 3，`0x26d9640` 4, `0x26d97d4` 5).

下一个任务由 `0x26d9a90` 在场景步骤 7 构建（`0x110ad34`，条件是 `0x26d9354` 返回 4），并再次以键 1 创建其阶段通道（`bl 0x26d7aa0` 位于 `0x26dc398`）。其阶段值是 `0x26dc71c` 中的立即数：3 位于 `0x26dc978`，6 位于 `0x26dc7ec`，0xb 位于 `0x26dc848` 和 `0x26dc874`，0xe 位于 `0x26dc8ac`。没有撤回操作的第二次交换会逐字节重复 `05 00`, `07 00`、各阶段以及端口 1 阶段键开放消息；只有序列 ID 不同，因此若对端对每种不同消息体只回应一次，就不会回应第二次交换的任何消息。

若主机端曾回应主机的阶段键关闭消息，则第二次 `01 03` 会停在关卡中，直到主机端再次通告该键开放：任务处于状态 1，场景处于步骤 9，没有超时，也没有限制。

停在状态 1 或 2 的任务显示 `common/box` `msg_ui_box_p2ptrd_09`，即“正在通信，请稍候……”（法语提示含义相同），由“交换”回调 `0x110c3d8` 通过消息辅助函数显示（`[scene+0xc0]`, `bl 0x26bcc14` 位于 `0x110c424`，标签哈希位于 `0x110c408..0x110c418`），该辅助函数会设置步骤 6；其关闭函数 `0x26bcfc0` 仅在以下位置调用：`0x110a84c`, `0x110ac5c`, `0x110ace4`. `0x1128184(ui, 1)` 启用取消提示（`InputCancel`, `0x11281bc`），该提示仅在步骤 2 和 7 读取（`0x110ac00`, `0x110ad4c`).

## 交换会改写哪些内容

光标移到交换收到的记录时，该记录会作为展示消息返回。收到的记录与发送记录在以下字段上不同（一个等级 50、但附带等级 70 队伍尾部的记录有 23 字节变化）：

```
0x006  2   the checksum
0x092  1   the current HP, 235 sent, 192 stored
0x0b8  26  the handling trainer's name, filled in with the receiver's own
0x0d3  1   the handling trainer's language
0x0d4  1   the current handler, set to 1
0x0d8  1   the handling trainer's friendship
0x16a  12  the six party stats, recomputed
```

其他所有内容均按收到时的原样保存；高于当前等级的相遇等级也会保留。写入的亲密度取自种类个体数据条目中的基础亲密度（耿鬼和烈咬陆鲨为 50）。

各块起点相对于 `pokeldn.gen8` 的对应位置，每个前置块增加八字节：昵称 0x60（第八世代为 0x58）、当前训练家名 0xb8（0xa8）、原训练家名 0x110（0xf8）、队伍尾部 0x168（0x148）。块内偏移随所在块变化：第一块与第八世代相同，但招式除外（招式为 0x54，PP 为 0x5c，而第八世代位于第二块的 0x72 和 0x7a）；第二块为第八世代偏移加 8，第三块加 0x10，第四块加 0x18，且球种移至相遇日期之后。

`pokeldn/pla/trade_box.py` 和 `pokemon.py` 可复现主机生成的字节。

`bin/pla_host.py` 按顺序对每个 `(port, sequence id)` 仅处理一次，并重发尚未确认的回应。每次光标移动都会发来展示消息，取消的提议再次提出时表示为 `04 01`。第二次交换会重复消息体，因此按消息体去重会丢掉它的回应。

### 已精通招式

0x15d 处的八字节是游戏精通列表中 61 个招式的位图，顺序与列表一致；某种类只能精通其个体数据条目允许的招式（0xa8 处的 u64）。在牧场“更换招式”界面中，当招式的精通等级（`mastery_la`，按种类和形态区分，采用招式学习表格式）不高于当前等级，或对应位置位时，该招式会显示卷轴图标：对于等级 13 的小火焰猴，高速星星（20，索引 10）只有在对应位置位时才显示图标。

### 游戏计算的能力值

`pokeldn/pla/stats.py` 复现交换时覆盖尾部的能力值。每项能力值由奋斗项按 `(sqrt(base) * multiplier + level) / 2.5` 舍入后，加上基础项构成：`((level / 100 + 1) * base)` 截断后再加等级，得到 HP；其他能力值则对 `((level / 50 + 1) * base / 1.5)` 按性格乘以 110% 或 90% 后截断。乘数根据奋斗等级加个体值修正量（31 及以上加 3，26 时加 2，20 时加 1）查表取得，和的上限为

1.

0xac 和 0xb0 处的绝对身高、体重，以种类平均值乘以各标量对应的 `(scalar / 255) * 0.40000004 + 0.8` 计算；身高只使用身高因子，体重则将两者相乘，运算使用 32 位浮点数。标量 111 和 221 配合平均值 150 和 405，得到 146.11766052246094 和 452.38031005859375，正是主机耿鬼携带的浮点数。

种族值、性别比例、特性、经验曲线、平均体型、升级招式表及 PP，取自 PKHeX 保存的游戏表副本：`personal_la`（每条目 0xB0 字节；0x21 的位 6 标记游戏内存在的种类，共 264 种）、`lvlmove_la.pkl`（一个 16 位 BinLinker 归档，先存招式半字，再存等级字节）、`MoveInfo8a`, `Experience`.

## Clone Clock 与 Atomic 协议

这一区间将 Clone 家族拆分为独立协议，与 6.32 的克隆协议无关：Clone Clock 为 0x77，Clone Atomic 为 0x74。

Clone Clock 消息为 18 字节：种类、序列号、大端序 u64 发起 tick、大端序 u64 响应端毫秒时钟。种类 0 是请求（除非接收端为时钟主节点，否则忽略）；种类 1 是回复，会检查序列号、计算 NTP 式偏移，并推进 ClockProtocol 中位于 `+0x5c` 的状态（0 重置、1 正在请求、2 已同步、3 主节点、4 停驻）。加入的主机停在状态 4，发送少量请求后等待。主机端以种类 1 回复，回送序列号和发起 tick，并附带主机端毫秒时钟，即可使其同步并停止发送。

Clone Atomic 消息为 14 字节：种类（0 通告、1 提交、2 确认）、代次、大端序 u32 元素索引（小于 33）、大端序 u64 值。元素表有 33 个槽位，每个 0x18 字节：代次、状态（0 空、1 待处理、2 等待提交）、u64 值，以及位于 `+0x10` 的已确认站点位图；该位图仅由已知参与者发来的代次匹配的种类 2 消息写入（参与者表位于协议的 `+0x78`；站点 0 的主机端在加入完成后读数为 1）。只有交换场景会创建元素（本地通告 `0x6e1e48`）；种类 1 和 2 要求已有待处理元素，而主机端的种类 0 通告会引发种类 2 回显，但不会填充任何槽位。

## 读取和写入数据包

`pokeldn/ldn/pia6.py` 使用版本 11；消息成帧方式沿用 5.27 至 6.30，由 `pia5.parse_messages` 原样读取（标志 `0x01` 在 5.27 中表示目标位图）。

各层填充字节均为 0xFF。消息遍历会将值为 0x00 的存在标志字节视为单字节包头，并继承上一条消息的所有字段：零填充会导致游戏尝试解析第二条消息，解析失败后丢弃整个数据包（拒绝位置为 `0x74419c`）。主机在 `0x6f0af8`; `0x6e6cb0` 将加密缓冲区预填为 0xFF，并将分组大小设为 16。

`pokeldn/pla/` 保存口令（读取广播所需）、游戏密钥、本地通信 ID 和 `session_keys(ssid)`. `tests/test_pia6.py` 固定验证布局、与 `crypto.PiaCrypto` 对照的派生过程、两份捕获的广播，以及从以下文件读取的所有常量：`main`.

```

## 加入主机的网络

加入端必须向作为主机端的主机发送下列消息，顺序取自零售版加入端（Net 0x50 来自模拟主机端）；`pokeldn.pla.joiner` 负责发送这些消息。

| 主机端发送 | 加入端回应 |
| --- | --- |
| Net 0x11 | Net 0x12，回送序列 ID，消息标志 `0x11`，包头目标 0；首次还发送 Session 加入请求（类型 0），标志 `0x01`，包头目标 0 |
| Net 0x50 | Net 0x51，回送序列 ID，包头目标 0 |
| 指定加入端的 Session 类型 7 | 类型 8：先是类型 7 指定的目标位置 ID，再是主机端自身的位置 ID |
| Session 类型 5 | 类型 6：自身固定 ID、两个零字节、该更新的序列号 |
| 首个类型 5 | 端口 0 上的 0x81 流开启消息，`0f00000b 0001 0001 01 00000001 0000000000008000000000` |
| 它在端口 0 上的 0x81 记录 | 确认消息，以及自身在端口 1 上的记录（标志 `0x1f`，序列号 1，位图 `0x01`），然后是 0x7c 端口 1 上的零键开放消息，带已初始化标志 |
| 0x7c 端口 0 开放消息，`0000000000000000 0100` | 返回相同内容，使用自身端口 0 的序列号 1 |
| 展示或提议 | 自身的展示或提议，使用相同选择器和计数器 |
| 选择器 5 和 7 | 相同的两字节；7 之后在端口 1 开放阶段键 |
| 阶段键开放 | 依次发送阶段 3、6、11、14（选择器 1），每次等待主机端回应后再发下一个，最后关闭阶段键 |
| RTT 种类 0 | 种类 1，回送时间戳，最后两字节为请求端的可变 ID |

零售版加入端将 Net 0x12 发往包头目标 0（108 次全部如此）。若发往主机端的可变 ID，读取关卡会将其丢弃：模拟主机随后每 0.5 秒重发迁移用的 0x11，持续 4 秒，并在其类型 7 之后 4.1 秒发送首个 0x40。若目标为 0，0x11 仅发送一次，首个 0x40 在类型 7 后 0.10 秒出现（4 次占位全部如此）；若完全没有类型 8，则为 9.1 秒。

类型 7 来自 `LeaveMeshWithHostMigrationJob`，发生在主机的 WaitMember（3000 + rand%1000 毫秒，`0x2c491b8`）于加入请求被接受之前结束时，与朱中相同（[docs/sv.md](sv.md#what-decides-a-seat)); `bin/pla_join.py --join-delay 4.5` 会引出该消息。主机每秒重发一次，直到收到类型 8。它的类型 8 处理器 `0x739b08` 只接受长度为 25 字节且第二个位置 ID 为主机自身的消息；`0x73f0a8` 随后设置任务的完成标志 `+0xb0`，条件是第一个位置 ID 等于任务保存在以下位置的目标：`+0x68`:

```
08 | joiner location id (12) | host location id (12)
```

加入端在主机端回应后发送下一阶段，通常间隔零点几秒，交换动画期间则间隔数秒。

作为主机端的零售版主机会在加入端阶段到达前，用选择器 1 通告自身各阶段，再在收到加入端阶段后 0.02 至 0.04 秒用选择器 2 回应。只有选择器 2 才算阶段回应。若加入端在收到主机自身的 `01 0e` 时、在其 `02 0e` 之前关闭阶段键，就永远收不到 `02 0e`：交换不会完成，主机离开时显示错误 2-AW7KA-0007，并保留十分钟交换限制（[交换限制](#the-trade-restriction)). `bin/pla_join.py` 会在收到 `02 0e` 时关闭该键，并在交换后保持席位，直到主机玩家退出或 `--hold` 结束；`--hold-after-trade N` 在最后一次排队交换之后 N 秒离开。同一席位上的后续交换逐字节重复所有步骤，因此加入端在一次交换完成后会忘记已回应的步骤，并展示下一个 `--offer`。它约每秒在端口 0 和 1 重发 0x81 确认消息：

```
0000002c ffff 0002 01 00000001       header: size 0x2c, lowest pending 2, bitmap 1
00 02                                type 0 on the first, 1 on every later one; two entries
00 0002 0001 00*16                   the host's stream: one past its sequence, then its sequence
00 0001 0001 00*16                   its own stream
```

后续确认消息也会将序列号的下一个值写入首条目的第二字段。`tests/test_pla_joiner.py` 扮演脚本化主机端，与加入端通信；`tests/test_esp32.py` 在两块模拟板之间运行它。

| --- | --- |
| 本地通信 ID | `0x01001f5010dfa000` |
| LDN 协议 | 1：AES-CTR 广播，与剑相同 |
| 场景 ID | 1 |
| 广播帧版本 | 4（GBA 应用为 3，剑为 2） |
| 接受策略 | 全部 |
| 参与者 | 1 / 2 |
| SSID | 16 字节，用作会话密钥的输入 |
| 应用数据 | 112 字节 |

应用数据包含 0x5C 字节的系统属性块（`docs/ldn.md`，6.16 至 6.41：系统通信版本 21、应用通信版本 0、十六字节用户密码、已启用玩家数限制、一名玩家、名称大小 1、编码 1、名称为单个空格），随后是明文携带连接密码的 20 字节：

```
+0x00  16  the code as ASCII, NUL-padded
+0x10  4   its length, little-endian
```

密码 `0000 0000` 得到 `3030303030303030`，八个 NUL，长度为 8。

### 广播中的连接密码

用户密码就是同一连接密码，由 Pia 的密码设置函数 `0x6fc454` 加密。启用传输加密（会话 `+0x230`）且模式为 1（`+0x234`）时，该函数以 0xFE 填满十六字节缓冲区，将补 NUL 的连接密码复制覆盖到其中，再用 `0x6e68d0` 原地加密：采用 AES-128-GCM，密钥位于会话的 `+0x238`（即游戏密钥 `p1frXqxmeCZWFv0X`，通过 `0x6fc8a4` 设置），无附加数据，丢弃标签，使用取自密钥的四字节 IV，`key[1] key[8] key[7] key[2]` (`0x6fc4e4` 至 `0x6fc4fc`），此处为 `1emf`。单个 GCM 分组等同于与固定密钥流进行异或：

```
password = KEYSTREAM XOR (the code's ASCII, NUL-padded to 16)
KEYSTREAM = AES-128-GCM(key = p1frXqxmeCZWFv0X, iv = 1emf).encrypt(sixteen zero bytes)
          = e5ab19ed742b6d40885998bf968aa166
```

密钥流不随 SSID、信道、连接密码或游戏重启而改变。`pokeldn.pla` 包含 `link_code_keystream`, `user_password`, `link_code`，以及 `parse_advertise_data`（将声明的连接密码与解码后的用户密码核对）。设置函数属于 Pia，因此这一区间的每款游戏均采用相同方式加密（[无线通信层](ldn.md)).

## 零售版备注

零售版主机在两种角色下均运行与模拟主机相同的流程，无论是否使用连接密码。法语存档写入的当前训练家语言为 3，英语存档则为 2。`--fresh-pid` 使用新的 PID 和加密常数，重新发送存档中已有的记录。主机端会在每次提议之间重新读取提供记录的文件；若更改标志，则需要重启。若主机端在连接期间重启，主机下一次搜索时会显示错误 2318-0006；离开交换菜单后再次搜索即可清除。

## 离开

主机退出交换时运行 `nn::pia::session::LeaveMeshJob`：发送 Session 类型 3 离开请求，等待主机端类型 4 离开响应 500 毫秒，随后再次发送，最多发送四次，然后无论是否收到回应都离开网络。步骤依次为 SendLeaveRequest `0x73b898`（写入函数 `0x737ee8`，类型字节 3 位于 `0x737f40`，调用位置 `0x73b990`，0x1f4 毫秒期限位于 `0x73b9a8`）、WaitLeaveResponse `0x73bab8`（重试计数器 `[job+0x6c]`，超过 3 时在 `0x73bbf0` 放弃），以及 CompleteProcess `0x73ba54`.

```
03 | u32 random | location id (12) | address kind | IPv4 (4) | port big-endian (2)
04 | u32 random | location id (12)                          the response, 17 bytes
```

位置 ID 属于 `pia_connect._location_id`（站点固定 ID、零半字、大端序可变 ID），地址则为站点自身地址。每次发送的随机字都不同，重传也不例外。地址种类位于 `+0x11`，在所有捕获的离开消息中均为 0；若其值为 1，处理器随后读取 18 字节地址及端口，否则读取 6 字节（`0x7380f0`），接受 24 或 36 字节的请求（`0x738024`).

类型 3 处理器 `0x738000`（分派表 `0x3973f19`，基址 `0x735434`）仅在会话固定 ID（位于 `+0x50` (`0x7473ec`）等于站点自身固定 ID（位于 `+0x40` (`0x747388`）时执行。它根据位置 ID 找到离开者，向请求携带的地址回复 `04`、新的随机字，以及请求的第 5 至 16 字节（`0x7381c0..0x738248`，通过 `0x735fb0` 发送），随后移除该站点（`0x735b90`）。类型 4 处理器 `0x738280` 设置任务完成标志 `[job+0x69]`，但仅接受固定 ID 和可变 ID 都属于离开者自身的 17 字节消息，且仅在任务运行期间生效（`0x6e5f0c`）；若主机端不回应离开请求，每台退出的主机都要等待完整的四次发送。

| 主机端 | 从首个离开请求到解除认证 |
| --- | --- |
| `bin/pla_host.py` 在类型 4 响应之前（八次零售版离开） | 2.02 至 2.07 秒，四次请求间隔 0.49 至 0.55 秒 |
| `bin/pla_host.py` 以类型 4 回应（两次零售版离开） | 0.046 和 0.066 秒，一次请求 |

有类型 4 回应时，首个类型 3 在玩家确认退出后 0.15 秒内出现（以 BOOT 标记，两次离开），确认后 3.70 秒回到野外画面。

退出后，交换场景至少保持“正在通信，请稍候……”（`msg_ui_box_p2ptrd_09`）3.0 秒。玩家退出（`0x110bd50`，来自 `0x110b970` 处的是／否选择）、对方已离开的消息（`0x110c9bc`），以及会话错误（`0x110b504`）都会进入模式 9（`0x110b72c`，步骤 `[scene+0xb4]`，表 `0x3979c98`）。步骤 0 运行 `0x26dcc74`，仅在 `0x10457e4` 时保存（请求种类 3，`[[[0x4279560]+0x2b8]+0x78]`，即待放置的接收记录（[交换限制](#the-trade-restriction)）已置位。步骤 1 基于 `nn::os::GetSystemTick` 在 `[scene+0x278]` 启动秒表、启动离开过程（`0x26be890`），并取消交换任务（`0x26d9e90`）。步骤 2 等待经过 3.0 秒（`fmov d1,#3.0` 位于 `0x110b7d8`）、离开序列完成（`0x26bdc94`），以及任务消失（`0x26d9cf0`），然后关闭消息；步骤 3 在消息关闭后返回真。立即获得回应的离开（0.05 秒）和完全未获主机端回应的离开（2.0 秒）都在 3.0 秒内结束，因此主机端回应不会提前返回野外画面。一次收到类型 4 回应的零售版离开，从主机发出类型 3 到野外画面的实测时间为 3.77 秒。运行阿尔宙斯 1.1.1 的模拟主机自行主持搜索，在已有一个站点占位时退出，到达步骤 1（`0x110b78c`），并在 4.33 秒后通过步骤 2（`0x110b81c`），此时距其最后一个数据包为 0.43 秒：交给该站点的主机端迁移（类型 7）超过了 3.0 秒下限。步骤 3（`0x110b80c`）在 0.03 秒后执行，场景析构函数（`0x110bec0`）在步骤 2 后 0.33 秒执行。另一台运行阿尔宙斯 1.1.1 的模拟主机作为 `bin/pla_host.py` 的站点占位，从盒子退出时，在到达步骤 1 后 0.07 秒内发送类型 3（立即获得回应），在步骤 1 后 3.03 秒通过步骤 2，再过 0.03 秒执行步骤 3，析构函数在步骤 2 后 0.33 秒执行：当离开过程在最低等待时间内完成时，步骤 2 仅需等待满 3.0 秒。

Pia 内部没有任何位于首个类型 3 之前的定时器（[pia.md](pia.md)，离开会话）。`Session::LeaveAsync` 的唯一调用者是游戏的离开请求，其更新函数为 `0x2ca0a10`（虚表 `0x4198ef8`，状态 `[req+0x88]`，跳转表 `0x3985448`）：首次更新调用 `LeaveAsync` (`0x2ca0ac0`），除非已有 Session 任务在运行（`0x72a280`），后续更新则等待任务结果（`0x72a294`).

九次主机端离开中，从主机最后一条 0x7C 游戏消息到首个类型 3 的间隔为 1.91 至 83.4 秒，包含玩家输入时间。期间主机仅发送 RTT、Net 回应、周期性 0x81 记录，以及对主机端交换盒子消息的确认。线上离开请求之前没有固定延迟，也没有任何必须回应的前置消息。

`bin/pla_host.py` 对每个类型 3 请求都用类型 4 响应。`tests/test_pla_host_loss.py` 中的脚本化主机运行任务的计时，主机端回应则在 unicorn 下经过 `0x738280`。

收到离开消息不会改变主机画面；主机根据网络消失或对方持续静默采取行动。主机位于盒子界面且未提出交换时：

| 主机端 | 主机 |
| --- | --- |
| 网络关闭，无论是否发送离开消息 | 一秒内显示“错误代码 2318-0006” |
| 网络保持运行但静默，无论是否发送离开消息（`--leave-sends 0`) | “交换对象选择不再继续交换”（法语提示含义相同），随后显示“正在通信”，再进入 `DisconnectedByUser`，无错误代码（约 13 秒时显示消息，按 A 后“正在通信”持续约 3 秒） |

`--leave-after SECONDS` 会让 `bin/pla_host.py` 使用自身 ID 向每个已加入站点发送离开消息并结束运行；`--stay-after-leave` 则会让网络保持运行但静默，并在主机完成交换后离开时继续运行。离开消息格式已与捕获的四条主机离开消息核对固定。
