# 集友圈

集友圈是《朱／紫》中最多四名玩家共享野外场景的会话。代码中将其称为队伍圈（`TeamCircle`），蓝乐活（BBQ）则是一个 `bbmission`。pokeldn 以加入端身份加入主机的本地集友圈，报告蓝乐活任务完成情况，为主机端发放 BP 并解锁沙俪先生的传说的宝可梦，还能在主机端玩家周围生成野生宝可梦（[野外遭遇](#overworld-encounters)）。应用中的两个集友圈工具见“[应用指南](gui.md#union-circle).

下文的 Lua 均指《朱》4.0.0 的代码块 `be21e65463b9a98f`（`main.blua`，SHA-256 为 `c1a4f4e2625912cf0b739a642a79ba3357df0557a544b92da22a6cb139de2815`，也就是“[太晶团体战](sv_raid.md)”中的代码块），除非明确注明为 `main_dynamic`。一个 `0.N` 表示该代码块主函数的第 N 个原型，从 0 开始计数。原型编号与公开的 3.0.1 反编译结果（Martmists-GH/SV-Script-RE）相同。尖括号中的名称来自其哈希列表；其他名称仍以哈希表示。

## 获取 Lua

该代码块为 `script/lua/bin/release/main/main.blua`，位于 `arc/data.trpfs`，使用 Oodle 存储。4.0.0 更新的虚拟 RomFS 需要基础游戏的 RomFS：`arc/data.trpfd` 的一部分位于基础游戏中。

```
./.venv/bin/python tools/switch/nso_read.py main main.bin
./.venv/bin/python tools/switch/trpfs_read.py --update UPDATE.nsp --base BASE.nsp --keys prod.keys \
    --image main.bin --extract script/lua/bin/release/main/main.blua --out-dir OUT
```

`main` 是更新的 ExeFS 模块（`pokeldn.switch.container.exefs`），而 `--image` 会运行其中的 `OodleLZ_Decompress` (`0xcc8750`）。该代码块是标准 Lua 5.4 字节码，具有 30,829 个顶层原型。事件脚本位于另一个代码块中，即 `main_dynamic` (`script/lua/bin/release/main_dynamic/main_dynamic.blua`，具有 6,431 个顶层原型），提取方法相同。

## 蓝乐活

任务进度由原生代码处理，位于 Lua 模块 `c5137FC87` 中。Lua 游戏事件通过 `C00099C1DFBF96B11.S110BDDB84DEB4379` (`0.7064`）向它报告，将（任务类型、两个值、计数）传给 `c5137FC87.f4246D9CA`；例如，进化会报告类型 28，计数为 1。任务中与集友圈相关的部分位于另一个原生模块：`c4D400AC0`.

每个任务都有等级，即其 `mission_grade` 字段，所属行是社团数据中的 `MissionInfo` 行（`arc/worlddataclubMissionDifficultyWeightAdvanced.bin.trpak`）：0 普通、1 奖励、2 团体。沙俪先生将团体任务称为集友任务。完成事件中会携带任务等级。

资源包中的任务表是一个 FlatBuffer，包含 64 个 `MissionInfo` 结构体：类别（1 战斗、2 野外、3 相机）、`mission_type`, `mission_id`、目标、奖励 BP、刷新 BP（用于更换任务）、解锁类型、等级、难度（0 初级至 2 高级）和权重。所有消息中的任务 ID 都是对应行的 `mission_type`; `mission_id` 用于区分相同类型的不同行，这些行的等级、难度、目标或 BP 各不相同。蓝乐活列表通过以下二元组查找任务：（`0x29de0f4`）。第二张表 `MissionSettings` 按不同变体（宝可梦属性、生态区、口味）给出各类型的文本，位于 `club_bbmission`。任务表使用的类型如下：

创建蓝乐活管理器时（`0.7062`），它会将取值函数交给原生代码端。`c16FE4B25` 获取玩家自身所在的场地（`f61488ABA`，即存档的 `currentFieldId`）以及成员所在的场地（`f45B80F87`，即对应站点索引的 110 值）。`c5137FC87` 获取玩家是否身处野外（`f01FF34BD`）以及两个社团等级标志 `FSYS_CLUB_BBMISSION_LVUP_01` 和 `_02`.

每一帧，管理器的 `PreUpdate` (`0.7069`）都会取空三个原生队列：

| 队列 | 来源 | Lua 执行的操作 |
| --- | --- | --- |
| `c5137FC87.fB8D11637` / `f35493666` | 玩家自己完成的任务 | 将每个完成事件交给 `c4D400AC0.fAC449469`，条件是 `c4D400AC0.f5770F782` 成立。在集友圈中完成的奖励任务（`c4D400AC0.f48603105`）会交给 `c4D400AC0.f263D7D28` 和 `f07578A96`，在主机端上处理（`c4D400AC0.fE8E53DDE`），加入端不会因此记入任何奖励。其他完成事件都排队等待发放 BP |
| `c4D400AC0.fD7C6549F` / `f37737462` | 其他成员完成的任务 | 为每个事件显示通知；除奖励任务外，都排队等待发放 BP |
| `c4D400AC0.fD961BFD2` / `f541C4B17` | 集友圈发放的 BP | 将每次发放排队等待记入 BP |

`0.7075` 将排队事件合并到相同等级的事件中，并累加 BP（`fBCA6AEB8`). `0.7076` 将队列中的总额加到货币管理器中，而 `0.7077` 显示 BP 消息。管理器的增加函数（`0.15120`）将玩家的 BP 限制在 0 至 9,999,999（`0.15128`）。因此，虽然完成事件的 BP 是 s32，但单次完成最多只有 9,999,999 BP 会生效。

因此，Lua 不执行任何校验。主机端直接根据第二个队列，为成员完成的普通或团体任务发放奖励。奖励任务只能通过原生集友圈模块放入第三个队列的发放事件支付；在主机端，该模块也负责接收成员的完成事件。

## 原生模块

以下地址位于《朱》4.0.0 的 `main`.

原生模块名及其函数名都是纯字符串，位于 `main` 的只读数据中，例如 `c4D400AC0` 和 `f5770F782`；它们不是在运行时计算的。每个模块都有一个 `luaL_Reg` 风格的表，位于 `.data`：由 {名称, 函数} 指针对组成，通过 `R_AARCH64_RELATIVE` 重定位填充，以一对空指针结束。`c4D400AC0` 的表位于 `0x442e500`（22 个函数），而 `c5137FC87` 的表位于 `0x4420630`（45 个函数）。完成事件以 userdata 形式传入 Lua，其方法位于以下地址的表中：`0x441dc50`: `fBCA6AEB8` 返回 BP（以下地址的 s32：`+0x10`），而 `f0C278E84` 返回等级（以下地址的 s8：`+0xd`）。事件由以下函数构建：`0x29dd878`：任务 ID（以下地址的 u16：`+0x0`）、以下地址的 u32：`+0x4`、等级和 BP 均来自任务对应行。

`c4D400AC0` 的函数操作同一个集友圈对象，这是一个延迟构建的单例，位于 `0x4739410`:

| 函数 | 作用 |
| --- | --- |
| `f5770F782` | 集友圈是否准备就绪（`0xa0d038`) |
| `f48603105`, `fE8E53DDE` | 玩家是否处于集友圈中，以及是否为主机端（`0xa0e9ac`) |
| `fAC449469` | 将玩家的完成事件作为消息 3 发送（`0xa0db20`) |
| `f263D7D28` | 在主机端，将奖励任务的完成事件作为消息 5 发送（`0xa0dcf4`) |
| `f07578A96` | 在主机端，记入自身完成奖励任务的奖励（`0xa0df34`，然后推入发放事件：`0xa0e164`) |

集友圈通过自身的通道（对象的 `+0x70`）发送这些消息，而不通过 `TeamCircleNetReceiver`：使用 0x80 端口 0 上的游戏键 0x0048，消息类型放在 kind 字节中。随后，每条消息都包含以游戏的带标签格式编码的完成事件（`0xb9`，然后是 18 个字段，由以下函数读取：`0xa17694`），再接发送方的消息序号（对象的 `+0xb8`，每发送一次便递增）。消息 3 还携带发送方的蓝乐活状态记录（由以下函数写入：`0xa0f37c`，由以下函数读取：`0xa17170`），其中字节 `+0x185` 是发送方完成奖励任务的次数。

零售版主机端完成价值 20 BP 的普通任务时，成员收到的完成事件如下：

| 字段 | 值 |
| --- | --- |
| 0 | 任务 ID（29） |
| 1, 2 | 0, 0 |
| 3 | 任务的槽位（2，即第三个） |
| 4 | 等级（0，普通） |
| 5 | BP（20） |
| 6 | 包含发送方站点 ID 的元组（u64，标签 0x83） |
| 7 | 任务对应的 `MissionInfo` 行：类别（2，野外）、ID（29）、`mission_id`（0）、目标（1）、BP（20）、刷新 BP（10）、解锁类型、等级、难度（0，初级）、权重（8.0） |
| 8, 9, 10 | 0, 0, (0) |
| 11 | 再次给出槽位 |
| 12, 13 | 接替该槽位的任务：(id, 0.0, 0, 0) 及其对应行 |
| 14 至 17 | 空行 (0, 0, 0, 32767, 0, 0, 0, 0, 0, 0.0)、0、空行、0 |

其序号为 4。在它之前 0.1 秒，主机端发送了 kind 2：任务、-1、-1、其进度（1.0）、3，以及其状态记录。在带标签格式中，-64 至 127 的整数直接用自身的单字节表示，更大的整数放在有符号标签（0x84 至 0x86）之后，浮点数放在 0x88 之后。

### 蓝乐活状态记录

每名玩家的蓝乐活管理器将状态记录保存在其 `+0x40`；集友圈将它写入（`0xa0f37c`）消息 1、2 和 3。消息 1（kind 1）仅包含发送方的消息序号和记录。集友圈开始时，玩家先发送一条步骤 1 的消息，然后发送无消息体的 kind 4（`480004`），再发送步骤 2 的消息；主机端还会在每次成员完成任务后再发一条。记录是包含 11 项的元组：

| 元素 | 记录偏移 | 值 |
| --- | --- | --- |
| 0 | `+0x0` | 每条记录中均为 1：管理器位于以下地址的字节：`+0x40` |
| 1 至 3 | `+0x4`, `+0x50`, `+0x9c` | 玩家的三个任务槽位 |
| 4 | `+0xe8` | 长度为一个字节的字节串，每条记录中均为 1 |
| 5, 6 | `+0xec`, `+0x138` | 另外两个槽位，在所有已观察到的记录中均为空 |
| 7 | `+0x184` | 有符号字节，每条记录中均等于元素 9 |
| 8 | `+0x185` | 玩家为获得下一次发放奖励而累计完成的奖励任务次数 |
| 9 | `+0x188` | 单人总次数（管理器的 `+0x1c8`) |
| 10 | `+0x18c` | 团体总次数（管理器的 `+0x1cc`) |

一个槽位（`0xa0fa18`）占 0x4c 字节，记录只携带其中四项：任务 ID（u16，空槽位为 0）、进度（浮点数）、文本变体（`MissionSettings` 的变体：指定任务中的属性、生态区或口味，无此要求的任务为 0；某个零售版成员的生态区拍照任务中该值为 3，表示峡谷区），以及该行的 `mission_id`（蓝乐活列表通过 ID 和 `mission_id`, `0x29e17ec` 将槽位匹配到对应行）。成员收到主机端记录时，若主机端的第五个槽位（元素 6）指定的任务与自身不同，则将主机端的任务设为自己的任务（`0xa14290`，写入 `0x29e1ea0`).

`circle.bbq_record` 读取消息 1、2 或 3 末尾的记录。

在每次抓包中，零售版主机端的各槽位都存放对应任务类型的初级普通任务行（`mission_id` 为 0：20 BP；任务 1 的目标为打倒 10 只，其余目标为 1），在收到报告并完成前，进度一直为 0。它自身的完成事件会指定接替空出槽位的任务及其对应行。额外槽位始终为空，奖励任务计数始终为 0。pokeldn 每报告一次团体任务完成，其团体总次数便增加 1，符合“[沙俪先生](#snacksworth)”中所述。

### 成员推进主机端的任务

成员通过报告任务进度来完成主机端的任务，而不是发送完成事件。在一次双主机抓包中，零售版《紫》成员执行了《朱》主机端任务 9 的要求（从背后出其不意地袭击野生宝可梦），这并非《紫》自身的任务。《紫》只在 0x80 端口 0 发送消息 2（kind 2）：任务（9）、两个值（-1、-1）、计数（1.0）、其消息序号（3）和自身状态记录。0.1 秒后，主机端发送了任务 9 进度为 1 的记录，然后发送自身的消息 3：任务 9 的完成事件，将功劳归于《紫》的站点 ID（字段 6），奖励为 20 BP，槽位为 1，任务 23 接替该槽位。主机端的单人总次数从 5 变为 6。

消息 2 携带 Lua 进度报告（`c5137FC87.f4246D9CA`）传入的内容：任务、两个值和计数。主机端接收处理器将这四项连同成员标志和发送方，交给同一个原生进度分派器（`0x29dc838`），它自身的报告也会到达该分派器（`0x29dc6b0`）。因此，主机端将成员的进度计为自身进度，完成任务并自行生成完成事件；该完成事件会像自身完成的其他任务一样，计入其单人总次数。

`circle.progress_message` 构建消息 2。沙俪先生流程（[加入](#joining)）每次根据主机端最新记录，将报告发给其三个槽位中的下一个；计数为 500（普通任务行的最大目标），第一个值为槽位的变体，无变体则为 -1。零售版主机端完成了所有以这种方式报告的任务，每个任务都使其单人总次数增加 1。

## 主机端如何处理成员的完成事件

接收处理器（`0xa13b00`）通过位于以下地址的跳转表按类型分派：`0x3c5b7a4`。对于消息 3，主机端会：

1.
2.
3.
4.
5.

只有完成这些操作后，主机端才会比较消息序号和该成员上一次的序号，而且序号仅控制成员状态记录是否生效。

成员收到消息 5 后，通过同一个发放推入流程记入事件的奖励，除非其序号早于此前从主机端收到的最后一个序号。

因此，主机端会按成员消息指定的内容发放奖励：以下地址的 BP：`+0x10` 来自成员，此路径中没有任何操作会校验它，也不会检查任务是否存在。普通或团体任务的完成由 Lua 立即发放奖励。奖励任务的完成则经过发放推入流程，这是唯一施加顺序限制的环节。它暂存每个事件，只有满足以下条件才将其释放到发放队列（对象的 `+0x108`）：其 `+0x7c` 比上一个已释放事件的值大 1，或小 2，或两者均为 0。该值根据槽位构建，因此成员的下一次奖励任务完成事件必须报告比上一次多 1 的计数。

## 沙俪先生

蓝乐活管理器维护两个累计总次数，由 `c5137FC87.f6ED7C9B6` (`+0x1c8`）和以下函数读取：`fECB0EBF0` (`+0x1cc`):

| 总次数 | 增加条件 | 还由谁读取 |
| --- | --- | --- |
| 单人，`+0x1c8` | 玩家自身完成普通或奖励任务（`0x29dda40`) | 社团的蓝乐活升级事件，阈值为 15 和 45 |
| 团体，`+0x1cc` | 玩家自身完成团体任务，以及在主机端上收到的每个成员通过消息 3 报告的团体任务完成事件（`0xa14918`) |  |

沙俪先生对应事件 `s2_sub_012`，他的 25 只传说的宝可梦对应事件 `s2_sub_013` 至 `s2_sub_037`，各自的状态保存在 `WEVT_S2_SUB_0NN_STATE`。该事件在以下代码块中的类：`main_dynamic`（原型 `0.1995` 至 `0.2032`）读取单人总次数，使用 `0.2019`；读取团体总次数则使用 `0.2020`。玩家与他交谈时，`0.2002` 会在单人总次数扣除每只已通过单人路线解锁的宝可梦所消耗的 `missionReleaseCount` 后达到以下值时，解锁下一只单人路线的传说的宝可梦：`missionReleaseCount`; `0.2003` 对团体路线执行相同操作，使用团体总次数和 `teamMissionReleaseCount`。两个计数均来自事件配置表（`s2_sub_012.ReleaseConfigTable`，位于 `arc/worlddataeventcommandcommand_data_rootcommand_data_root.bin.trpak`）。资源包中唯一具有这种结构的表包含 10 和 1。

`s2_sub_012.ReleasePokeTable` 位于同一资源包中，将每只传说的宝可梦分配到四条路线中的两条：两条单人路线（`MissionA`, `MissionB`）和两条团体路线（`TeamMissionA`, `TeamMissionB`):

| 所属路线 | 传说的宝可梦 |
| --- | --- |
| 两条单人路线 | 急冻鸟、闪电鸟、火焰鸟、熊徒弟 |
| 两条团体路线 | 烈空坐、酋雷姆、奈克洛兹玛 |
| 各一条 | 其余 18 只 |

脚本询问 `CA4C5F9FA83D2AF80.SDF0C255E6E08D740` 玩家属于哪组路线，A 路线还是 B 路线。《朱》属于 A 路线：在《朱》中完成一次团体任务解锁了捷克罗姆，而它只出现在 `TeamMissionA` 中。每组都将 25 只传说的宝可梦划分为互不重叠的两部分：单人路线 13 只，团体路线 12 只。每次交谈最多解锁一份点心，优先尝试团体路线。每条路线都从尚未解锁的宝可梦中随机选取（`0.2007`）。路线的下一次解锁要求总次数达到“该路线的计数要求 ×（已解锁宝可梦数量 + 1）”。因此，解锁全部 25 只需要单人总次数达到 130，团体总次数达到 12，并交谈 25 次。

因此，没有任何消息会指定某份点心。主机端上的沙俪先生脚本将主机端自身的总次数与配置比较。每条携带团体任务完成事件的消息 3 都会让主机端的团体总次数增加 1；成员每完成一个主机端自身的任务（[成员推进主机端的任务](#a-members-progress-on-the-hosts-quests)），则让其单人总次数增加 1。主机端不检查该任务是否为自身持有的团体任务，序号也不会阻止重复事件。在 `teamMissionReleaseCount` 为 1 时，每次事件都相当于一份团体路线点心，通过与沙俪先生交谈领取。这覆盖了主机端团体路线的 12 只；单人路线的 13 只需要单人任务完成次数，成员可通过完成主机端的任务来为其增加这些次数。

## 加入

`bin/sv_join.py --union-circle` 加入主机主持的集友圈，方式与团体战加入端加入团体战相同（`pokeldn.sv.circle`）。它入席、发送自身身份记录、在 0x7C 端口 1 上镜像主机端的通道表，并持续占用席位 `--hold`，默认持续整个 `--seconds`。它不发送大厅消息，也不会在主机离开时接任主机端角色。主机端的场地就绪后，它会将自身玩家放入其中（`circle.Member`, [场地](#the-field)）。它会打印用户需要关注的内容；`--verbose-circle` 还会输出其发送的每条集友圈消息和区域搜索的每个步骤，而无论是否启用此选项，`--capture` 文件都会保留这些信息。

```
./.venv/bin/python bin/sv_join.py --union-circle --code 3707 --hold 540 --capture circle.jsonl
```

零售版《朱》4.0.0 在使用连接密码主持集友圈时，会广播场景 5、最多四名参与者，以及与交换相同格式的应用数据：密码字段和游戏字节中均含有连接密码，其长度位于 +0x24。游戏字节还包含 `aa 08 3e`，位于 +0x21，而搜索中的主机会将该值保留为零。

它为加入端安排席位的方式与连接交换或太晶团体战主机端相同：加入响应、站点列表、通道表（键 0x007B、0x0132、0x0232 和 0x0332）、两个流的打开、时钟应答和自身身份记录。加入端随后等待主机端玩家启动集友圈。

## 启动集友圈

启动时，主机端发送 Net 0x50，其广播信息中包含成员计数；在 0x80 端口 2 发送类型 7 公告（以及接受每个成员的类型 9）；并在 0x80 端口 0 发送集友圈消息。

集友圈消息就是 Lua 的网络消息。每条都是游戏消息（处理器键、kind、step，然后是序列化器头部；见“[太晶团体战](sv_raid.md#the-lobby)”），使用键 0x0132，kind 为 Lua 消息 ID。团体战的“加载中”和“已加载”（0x0132，kind 为 0x6E 和 0x73）是同一接收器的消息 110 和 115。部分载荷为 FlatBuffer 表，其余为固定结构；104 和 106 使用 LZ4 压缩（序列化器压缩值为 2）。

| 消息 | 来源 | 载荷 | 由以下部分处理：`TeamCircleUI` |
| --- | --- | --- | --- |
| 100 | 主机端，启动时 | 包含一个 u32 的表，始终为 12345678 | 开始音效；加入端的开始标志 |
| 101 | 每个站点；主机端紧接自身的 100 之后发送，成员在收到主机端的 100 时发送 | 32 字节：站点所在位置（场地 ID、三个宝可梦中心标志） | 按站点保存 |
| 103 | 每个站点 | 包含一个 u32 的表，值为同步点 ID | 1 和 2 交给界面（开始演出已加载、已结束），其他 ID 均交给同步对象 |
| 111 | 主机端 | 5916 字节：四个零字节，然后是包含两个表向量的 FlatBuffer（分别为 30 项和 10 项） | 仅设置标志；内容由原生代码读取 |
| 104 | 主机端 | 一个表：游戏时间、现实时间及各自已经过的秒数（浮点数）、天气种子（u64）、抽选序列长度，以及当前和下一次天气的 {类型, 持续时间} 对 | 时钟和天气，交给游戏时间管理器和 `WeatherManager.Sync` |

主机端在启动后的两秒内按表中顺序发送这些消息，并在自身的 101 之后发送三条键为 0x0048 的消息。

每个站点都运行相同的启动例程：到达同步点 2215，等待所有站点的 101，发送自身的 106，然后等待所有其他站点的 106（`IsGemInfo`）。场地就绪后播放开始演出，它以同样方式等待 ID 为 1 和 2 的 103。当每个成员都发送了对应 ID 的 103 时，即视为到达同步点（`CEEE8D2836ABEDE23`）。如果某个成员尚未发送 101 和 103，主机端在发送自身针对 2215 的 103 后便不再发送任何内容。

零售版主机会将超过 1395 字节的消息分片，并且未确认一条未分片、长度为 1818 字节的 106（300 个槽位，未压缩）。106 应像主机端自身的消息一样，使用 LZ4 压缩发送。

收到所有 106 后，主机端传送到自身 102 指定的飞翔地点，并发送 115 (1, 0)。

## 野外遭遇

集友圈中的每台主机都会根据自身游戏版本，在自身玩家周围生成野生宝可梦，并将每只宝可梦广播给其他主机。位于第零区的《朱》主机端和《紫》成员各自生成了对应版本的悖谬宝可梦：主机端生成《朱》独有的种类（开发 ID 982），成员生成《紫》独有的种类（992）。成员能捕捉另一版本的限定宝可梦，是因为另一台主机生成并共享了它们。双方不会交换版本信息，主机端在这里也没有特殊作用。

共享宝可梦通过 0x80 端口 0 和不可靠协议传输，由拥有者广播；只有请求某只宝可梦及其拒绝应答，才通过 0x7c 端口 0 发给单个站点：

| 键 | 消息 | 内容 |
| --- | --- | --- |
| 0x0026 | kind 1，其 96 字节记录以字节串形式发送 | 拥有者生成了实体 (station, n) |
| 0x0026 | kind 2，(station, n) | 实体已消失 |
| 0x0026 | kind 5，((station, n), (station, n)) | 主机向拥有者请求该实体，以发起战斗，并指定请求方自己的 ID；通过 0x7c 端口 0 仅发给拥有者 |
| 0x0026 | kind 6，相同的 ID 对 | 拥有者拒绝；返回给请求方 |
| 0x0026 | kind 7，相同的 ID 对 | 实体现在属于第二个 ID 的站点，并由该站点与其战斗；曾有一条此类消息在该实体的 kind 2 之前 15 秒到达 |
| 0x0126 | kind 3，(station, n)，(一个浮点数, 0.0, 0.0, 0, 0 或 1) | 实体状态，每 0.2 秒（成员）至 0.5 秒（主机端）发送；最后一个元素是其状态 |
| 0x011E | 0x68 上的 kind 4，按对象 ID 标识 | 实体变换，与玩家相同 |

实体的对象 ID 为 station + 4n，即记录开头的 u16：主机端的 (0, 37) 为 0x94，成员的 (1, 159) 为 0x27D。移除消息成批到达，每台主机都随玩家移动不断生成新实体。主机只与玩家靠近自身玩家的成员共享实体：在 pokeldn 加入端玩家开始跟随主机端之前，主机端没有向它发送任何实体。每个 ID 都是一对无符号整数：分派器（`0x1dbd4b0`，跳转表 `0x3c5b9a0`）不读取任何有符号标签。

主机将其他主机的实体登记为未稳定（状态 1），并拒绝与其战斗（`BattleStartWait`），直到收到指定状态 0 的状态消息。玩家走入已稳定实体时，会显示“！”，并向拥有者发出请求（`0x1972664`）：为实体分配自身的新 ID，保存 ID 对和回调，然后其管理器更新函数（`0x1593884`）向发送实体记录的站点发送 kind 5。遭遇流程（`GameEventEncount`，NetInitWait）随后等待拥有者的应答，要求指定相同的 ID 对（`0x1dbdd70`），且没有超时。若实体属于拥有者自身且没有其他主机占用，拥有者会将其移交（`0x1dbdc20`，然后由更新函数在以下位置广播：`0x15934c8`），否则拒绝（`0x1593914`）。移交时，每台主机都将实体重命名为请求方的 ID（`0x1595a1c`），并将其标记为已进入交战；请求方将其登记为自身实体并开始战斗。主机与自身实体战斗时，会广播 kind 7，其中 ID 对的两个 ID 相同。

| 偏移 | 位 | 字段 |
| --- | --- | --- |
| 0x00 | u16 | 对象 ID |
| 0x04 | u64 的位 0–10 | 开发用种类编号 |
|  | 11-22 | 携带道具 |
|  | 23-30 | 体型缩放 |
|  | 31 | 性别（1 为雌性） |
|  | 32 | 异色；置位时生成异色宝可梦 |
|  | 33-37 | 形态 |

|  | 53-57 | 性格 |
|  | 58-62 | 太晶属性 |
| 0x0C | u32 的位 0–3 | 霜奶仙糖饰 |
|  | 8-27 | HP、攻击、防御、速度个体值，各占 5 位 |

`UpdateNetworkSpawn` 仅根据记录构建宝可梦：种类、形态、携带道具、体型缩放、性别、性格、等级、六项个体值和特性槽位写入 `InitialSpec`；异色位在置位时将其稀有度字段（`+0x18`）设为 `0x2ffffffff`，清零时则设为 `0x1ffffffff`，因此无论是否异色，都由拥有者提供的位决定；随后为创建的宝可梦设置证章（非 0 时）、太晶属性和霜奶仙的糖饰（`c113335A8.f7AC1FE6B`）。记录不包含招式、PID 或加密常量。捕捉后，会像捕捉其他野生宝可梦一样，添加捕捉者的训练家信息、精灵球、地点、日期和等级。

| 字段 | PKHeX 接受的条件 |
| --- | --- |
| 种类、形态、等级 | 捕捉地点存在《朱／紫》的野生遭遇槽位，种类和形态相符，且等级落在其等级范围内；锁定异色或只能通过固定遭遇获得的种类（如烈空坐）始终不被接受 |
| 太晶属性 | 该种类自身属性之一，除非当地的活动大量出现涵盖该种类 |
| 性别 | 符合该种类的性别比例 |
| 证章 | 不能是最强之证或宝主之证；最大之证要求体型缩放为 255，最小之证要求为 0；天气证章仅能用于遭遇槽位指定了对应天气的地点 |
| 异色、性格、个体值、特性槽位（包括隐藏特性）、体型缩放、携带道具 | 任意值 |

PKHeX 将《朱／紫》的所有野生遭遇槽位都列在两个版本下，因此通过集友圈捕获另一版本的限定宝可梦也是合法的。存储后的宝可梦不保留捕捉时刻，所以遭遇槽位的昼夜条件不会限制它。记录中的种类是内部索引（`gen9.national` 给出全国图鉴编号）。所有抓包中主机端生成的宝可梦，其种类、形态和等级范围均符合某个槽位，粉蝶虫的随机花纹则符合 PKHeX 的随机形态规则。

键 0x0025 是成员定期向主机端发送的查询。kind 1 列出 ID，kind 3 为每个 ID `((id,), flag)` 回答 0 或 1，kind 2 则列出成员放弃的 ID，几乎都是主机端此前回答为 1 的 ID。这些 ID 不在遭遇文件或点位文件中。其最高五位表示类别，成员大约每九秒遍历相同的类别（1、2、3、4、5、9、10、13、16），每次询问几个至 250 个 ID。场地刚打开时，主机端对每个 ID 都回答 1；之后约有一半回答 0。主机端从不询问成员。

## 构造的遭遇

`sv_join --spawn SPECIES:LEVEL` 以成员身份加入集友圈，并在主机端玩家周围维持三只由用户定制的宝可梦；启用 `--follow-host` 后，加入端玩家会跟随主机端。`--spawn-*` 标志设置记录携带的内容：形态、异色、太晶属性、性格、性别、特性槽位、大小、携带道具和个体值。未指定的字段会按主机端自身野生宝可梦的方式抽选：大小、性格和每项个体值随机，特性槽位为 0 或 1，不携带道具。每只宝可梦生成在距主机端玩家 15 至 25 米的位置。若主机端与其战斗（发送请求并完成移交）、移除它（发送指定它的 kind 2），或走到距其超过 50 米的位置，则放弃该宝可梦，并在主机端附近生成另一只。抓包中，主机端从未为成员生成的宝可梦发送 kind 2，只发送过与其战斗的请求。

启用 `--spawn-legal` 后，由 PKHeX 决定。其《朱／紫》野生遭遇槽位指定了在对应地点捕捉时记录的地点；PKHeX 辅助程序的 `wild_areas` 命令按地点列出这些槽位，将槽位随机抽选的形态（粉蝶虫花纹）视为任意形态。`wild_legal` 命令会按各地点的槽位种类、形态和等级，构建定制宝可梦从该槽位被捕获的结果，每种太晶属性各构建一次，并对每个结果运行 PKHeX 合法性分析。记录中的单个性别位仅对具有两种性别的种类有效；其他种类采用其固有性别。如果某只生成的宝可梦在任何地点都不被 PKHeX 接受，运行便会停止。某种类在帕底亚的槽位可能只允许自身属性，但 PKHeX 在其他地点可能接受任意太晶属性（例如北上乡的皮卡丘，因当地的活动大量出现），因此决定太晶属性的是分析结果，而非种类本身。

随后，生成流程等待确定主机端所在区域（`wild.Locator`）。主机端主机共享的每只野生宝可梦（键 0x0026、kind 1，在加入端玩家靠近后发送），都会将候选地点缩小为具有符合其种类、形态和等级槽位的地点。当剩下的每个地点都能让 PKHeX 接受定制宝可梦时，便视为区域已找到，不必只剩一个地点。随后生成宝可梦；主机端走到距找到区域时的位置超过 50 米处时，它们全部消失，并重新开始查找。在此之前，主机端距某只已用于判断的宝可梦超过 100 米时，也会重新查找；遇到不属于任何剩余地点的宝可梦时，同样会重新查找。不属于任何野生槽位的宝可梦（来自团体战或活动）会被排除。

在第零区内（以及飞往其入口的途中），主机端主机不发送玩家变换数据：最后读到的变换为 (0, 0, -2)。它仍会共享在玩家周围生成的野生宝可梦；在外部测量时，这些宝可梦距玩家 8 至 46 米。若连续 2 秒没有变换数据，则将主机端位置设为过去 30 秒内最新六只生成宝可梦的中心；在外部，十次此类估计中有九次落在主机端玩家的 50 米范围内。宝可梦会在该估计位置周围生成并维持。如果这段时间内没有生成宝可梦，则主机端位置未知，在出现新的宝可梦前不再生成新宝可梦。距原点 10 米以内的变换（骑乘时或落地时）从不用于定位主机端。

运行期间，它会将查找情况打印为状态卡片（一个 `[panel]` 行，ID 为 `zone`，发生变化时打印），由应用显示在工具选项上方：仍可能的区域、其中多少允许该宝可梦，以及用于判断的野生宝可梦数量。当所有剩余区域都不允许该宝可梦时，卡片会列出应前往的区域；主机端走得过远后，会说明重新查找的原因；找到后，会显示主机端距找到区域时位置的距离。它也会说明主机端位置是根据生成的宝可梦估计的，还是未知。在找到区域之前，如果当前位置允许野餐，它会建议进行野餐：收拾野餐后会重新生成玩家周围的野生宝可梦，从而更快缩小候选区域。
